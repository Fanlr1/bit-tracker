## 一、四项改动

### (1) 16 槽 → 256 槽

| 步 | 做法 | 实测 |
|---|---|---|
| **存储换 RAM** | **`x/y/vx/vy` 打包成 64 位一字进 `simple_dual_port_ram`；`valid`/`live`/`rt` 留在寄存器阵列** | **LUT4 −1112、FF −873、RAM10 +3** |
| **容量 16 → 256** | **只改 `N` 参数** | **RAM10 再 +1** |

**⇒ 为什么把 valid 留在寄存器：`rd_valid` / `rd_live` 必须**组合可读**（walker 在决定画不画的那一拍就要用），而 RAM 有 2 拍读延迟。** **⇒ 塞进 RAM 就得提前读，把 walker 的状态机和这个模块的流水耦死。几百个 FF 便宜，那个耦合不便宜。**

**⇒ 实测修正**：我预测容量提升「不增加 RAM10」，实际 **+1**。**⇒ 原因是 RAM10 不是简单按深度堆叠，64 位宽 × 256 深超出了单块的形状。** **⇒ 但 16 倍容量换 1 块 RAM，仍然极划算。**

### (2) 活着位图 + 回收

**⇒ 三个位，三个互不混淆的语义：**

| 位 | 含义 |
|---|---|
| **`seeded`** | **载荷里存着这个槽位的活状态** |
| **`live`** | **这一帧画它** |
| **`rt`** | **画过，然后飞出去了** |

```
seeded=0, live=0  → 刚发射　　　　→ 画 + 播种
seeded=1, live=1  → 飞行中　　　　→ 用片上状态画
seeded=1, live=0  → 已出屏　　　　→ 跳过
```

**⇒ 两种清理动作语义不同，这是本项最容易搞错的地方：**

| 事件 | 清什么 | 含义 |
|---|---|---|
| **自动退休（出屏）** | **只清 `live`，置 `rt`** | **不画，但槽位仍被占着** |
| **软件回收（`live_clr`）** | **清 `live`+`seeded`+`rt`** | **槽位真正空了，下次发射重新播种** |

**⇒ 我第一版让退休清 `seeded`，测试台立刻抓到：`seeded=0` 恰好是「没播种过 ⇒ 画它」的信号 ⇒ 第二帧把退休的精灵**又画了一遍**。**

### (3) 写描述符通路 —— **论证后判定不需要**

**⇒ goal 原假设：walker 只有读通路 ⇒ 软件没法把描述符送进去。** **⇒ 但核实后发现：walker **每个精灵、每一帧**都重读描述符**（`S_ADV` 回到 `S_FETCH`）。** **⇒ 所以软件**只需改内存里的表**，硬件下一帧自动看到 —— CPU 本来就能写内存。** **⇒ 代价只有 16 字节 × 256 槽 = 4 KB/帧（60 FPS ⇒ 240 KB/s，可忽略）。**

**⇒ 这一项**没有写任何代码**，但它是四项里省下最多工作的一项 —— 靠的是先核实而不是先动手。**

### (4) 出屏判定

**⇒ 在帧末 sweep 里顺手比较，零额外遍历** —— sweep 本来就在逐槽读位置。**

```verilog
if (x_new > fb_w || y_new > fb_h) begin
    lv[swp] <= 1'b0;
    rt[swp] <= 1'b1;      // 发布给软件
end
```

**⇒ 边界取自 `reg_fb_width`/`reg_fb_height` —— 和扫描输出用的是同一组寄存器，所以精灵是相对**实际在扫描的那个显示**去退休的。** **⇒ 比较的是「即将移动到的位置」而不是当前位置：这一帧飞出屏幕的就该这一帧停止绘制。**

## 二、回收闭环（唯一一根反向信号）

**⇒ 退休由**硬件**检测（位置只在硬件里），回收必须由**软件**决定（它知道何时要发射新弹幕）。** **⇒ 二者之间是**信息缺失**而非逻辑缺陷 —— 只能补一条通路：**

| 寄存器 | 方向 | 用途 |
|---|---|---|
| **`0x48` `SPR_RT_SEL`** | **写** | **选哪个 32 位字** |
| **`0x4C` `SPR_RT_BITS`** | **读** | **那个字的退休位图** |
| **`0x50` `SPR_RETIRE`** | **写** | **写索引 ⇒ 回收那个槽** |

**⇒ `SPR_RT_BITS` 是整个设计里**唯一**从引擎流回寄存器文件的信号** —— 其余全部向外流。** **⇒ 而 `retire_en` 是**写选通脉冲**而非存储位：存起来就得软件清，忘了清就会**每拍回收同一个槽**，静默地把在用槽位释放掉。**

## 三、三层验证

### 寄存器级（`tb_bitblt_regs`）

**⇒ 三个新寄存器读写回 + 到 state 的通路。** **⇒ 其中 `0x4C` 喂的是**固定值 `0xA5A55A5A` 而不是 0** —— 读 0 分不清「线断了」和「位图本来就是空的」，而那正是这条检查要抓的失败。实测读到 `a5a55a5a`。**

### 规模级（`tb_bitblt_top` 的 P4 scale 用例）

```
32 sprites, 8x2 each
2624 cycles/frame, 82 cycles/sprite, 64 ARs (严格交替)
```

**⇒ 因为 walker 等的是 `addr_done`（三个引擎全完成），82 拍覆盖**整个精灵**而不只是取描述符。**

### 生命周期级（`tb_bitblt_sprite_walker` 三帧）

| 帧 | 断言 |
|---|---|
| **1** | **4 个精灵都画，位置来自描述符** |
| **2** | **位置推进 `(vx,vy)`；出屏的被跳过（`3 blits` 而 `4 fetches`）；`rt[3]=1` 且 `rt[0..2]=0`** |
| **3** | **回收后 `rt[3]` 清零；重新发射的精灵**回到描述符位置**（630,470 而非 650,490）** |

**⇒ 帧 3 那条是最关键的**：如果回收没清 `seeded`，新子弹会**继承上一颗死掉时的坐标**。** **⇒ 而在此之前**没有任何用例能看到它** —— 其它用例都是发射进一个从未用过的槽位。**

## 四、成本表

| sprite | 拍数/个 | **256 个 =** | **占 16.7 ms** |
|---|---|---|---|
| **8×2（实测）** | **82** | **0.21 ms** | **1.3%** |
| **16×16（推算）** | **≈370** | **0.95 ms** | **5.7%** |
| **32×32（推算）** | **≈1400** | **3.6 ms** | **22%** |

**⚠️ 上界**：测试台的从设备**不流水 AR**（和 `tb_bitblt_burst_eff` 同样的偏差），真实 DDR3 会重叠。** **⇒ 所以这是**量级判断**，不是硬件实测。**

**⚠️ 它不是「同屏精灵上限」** —— 上限还取决于：总线仲裁（扫描输出在 `Axi_Mux` 固定优先级里排最低）、真实 DDR3 的刷新与行激活开销、以及**扫描输出本身占掉的 37% 带宽**（1080p60 下 594 MB/s）。** **⇒ 那个数字只有板子能给。**

## 六、踩过的坑（值得记住的）

| 坑 | 教训 |
|---|---|
| **退休时清 `seeded`** | **「清两个位」和「只清一个位」看起来等价，实际定义了两套完全不同的语义** |
| **`S_BLIT` 判断写成 `if (!live)`** | **冷启动死锁：新槽位 `live=0` 正是因为还没播种，而 `live` 只在播种时置 1** |
| **跳过死槽位走了 `S_RUN`** | **那里等 `blit_done`，而根本没发 blit ⇒ 必须新增 `S_ADV` 汇合** |
| **`busy` 不含 `spr_busy`** | **软件在整帧派发期间看到「引擎空闲」⇒ 会中途改表或误判帧结束。之前用例靠固定拍数等完，从没问过 `busy`** |
| **AR 日志只有 32 项而一帧发 64 个** | **后一半被静默丢弃，读数变成 32。差一点去查一个**根本不存在的**「源读缺失」** |
| **`enable` 是边沿触发** | **上一个用例把它留在 1 ⇒ 再置位无边沿 ⇒ walker 不启动。这是设计语义，测试台必须照做（先清再置）** |
| **`OUTPUT_REG="TRUE"` 是 2 拍延迟** | **我按 1 拍写了 sweep，会读到前一个槽位的速度 ⇒ 表现为「每个精灵按前一个精灵的速度移动」** |
| **新 RTL 必须登记进 `bitblt_system.xml`** | **iverilog 用 `-y` 搜目录，Efinity 只认 xml 列表 ⇒ 新文件会被仿真自动发现、却被综合静默漏掉** |
| **`bitblt_system.err.log` 是累积的** | **它保留着旧负面测试的错误。判断当前状态要看源文件，不是日志** |

**⇒ 其中五条是**测试台抓到的**，两条是「先量再改」抓到的。** **⇒ 没有一条是靠读代码看出来的。**

### ⭐ 2026-10-07 实测：「重构成 8 个 32 位字能省大部分」是**错的**

**⇒ 上面那句是**推测**，这一轮真去做了并量了：**

| | LUT4 | FF | RAM10 |
|---|---|---|---|
| **改前（256 个分散 FF）** | **15444** | **12070** | **74** |
| **改后（8 个 32 位字）** | **16296** | **12072** | **74** |
| **差** | **⚠️ +852（更贵）** | **+2** | **0** |

**⇒ 所以**不是省 1000，是多花 852**。** **⇒ 已回退，LUT 精确回到 15444。**

**⇒ 为什么推测错了**：
- **读【确实【便宜了 —— 8 选 1 的 32 位总线，而不是从 256 个 FF 里汇聚 32 位** ✓
- **⇒ 但【**写【占了【主导**：退休一个槽位是**单【位【写** ⇒ 8 个字各自需要 32 位写使能解码** ✗
- **⇒ 而【综合器【显然【把【数组【又【拆【回【分散 FF，同时【背着【额外的【解码【逻辑** ✗
- **⇒ **⇒ **⇒ 「成本在汇聚、不在索引」那句【对【读【是对的，对【总量【是【错的**** ✓

**⇒ **保留【的【是【更有价值的【一样东西**：`tb_bitblt_sprite_walker` 原来【直接【读 `u_state.rt[3]`（**内部【信号），而【实例【里 `.rt_sel` 硬接 0、`.rt_word` **空接** ⇒ **契约【通路【根本【不通**。** **⇒ 那【意味着【该文件【自称【最重要的【断言（「退休位图【必须【说【真话 —— 那是【软件【知道【槽位【空了的【唯一【途径」）**检查【的【是【一个【驱动【读【不到的【信号**** ✓✓✓

**⇒ 现在【端口【已【接、断言【走【契约。** **⇒ 而【它们【在【新旧【两种【内部【表示【下【都【通过 —— **那【就是【「只【依赖【接口」的【证明**** ✓

# 端到端混合值追查记录

> 日期：2026-10-06
> 起因：P1 的端到端混合测试出现「值对不上」，当时记为待查项
> 结论：**RTL 完全正确，错的是测试的两个假设**；**并发现单元 TB 的一个覆盖缺口**

---

## 一、现象

端到端 TB 加了「MUL 混合」用例后：

```
PASS blend op reaches the engine (out=10041f00 != src=10205a00)
```

**⇒ 「输出 ≠ 源」这个判据通过了**（说明 `OP` 传到了引擎），**但精确值没人验过。**

**⇒ 手工反推时发现矛盾**：

```
从 R 通道反推背景：4  = round(0x20 × bg / 255)  ⇒  bg ≈ 0x20
从 G 通道反推背景：31 = round(0x5A × bg / 255)  ⇒  bg ≈ 0x58
```

**⇒ 同一个 128 位拍，两个通道推出【不同的背景值】—— 这不可能是「背景不对」造成的。**

---

## 二、追查过程（六步）

| # | 动作 | 结果 |
|---|---|---|
| **1** | **观测 FILL 的输出** | **`0x80808080` ✓ 写侧完全正确** |
| **2** | **观测引擎实际收到的数据** | **`fg=0x10205A00`，`bg=0x80205A01`** ← **决定性** |
| **3** | **用实际值手算 MUL** | **G: `0x5A × 0x5A = 8100`** |
| **4** | **两种除法的差异** | **`floor(8100/255) = 31`，`round(8100/255) = 32`** |
| **5** | **DUT 给 31** | **⇒ DUT 是 `floor`，我的 TB 期望写的是 `round`** |
| **6** | **逐位核对** | **`0x10041F00` 与手算【完全相同】** |

**⇒ RTL 正确。**

---

## 三、两个真实的错误假设

### 3.1 「FILL 写进去的，MUL 能读出来」

**⇒ 这个 TB 里【两个 slave 模型不共享内存】**：

```
axi_wr_slave : 只【记录】收到的写数据，不存储
axi_rd_slave : 独立生成固定模式 {addr_lo, 8'h5A, beat}，与写无关
```

**⇒ 所以「先 FILL 铺背景、再混合」这个设计【从一开始就无效】。**

**⚠️ 而这条日志制造了错觉**：
```
PASS fill background = 0x80808080
```
**⇒ 它只证明【写侧写对了】，完全【不证明读侧能读到那个值】。** **我用一个写侧的证据，去推断读侧的状态。**

### 3.2 「`(x+1+(x>>8))>>8` 是四舍五入」

**⇒ 它不是。** 实际验证：

| x | 恒等式结果 | `floor(x/255)` | `round(x/255)` |
|---|---|---|---|
| **254** | **0** | **0** ✓ | **1** ✗ |
| **255** | **1** | **1** ✓ | **1** ✓ |
| **510** | **2** | **2** ✓ | **2** ✓ |
| **8100** | **31** | **31** ✓ | **32** ✗ |
| **65025** | **255** | **255** ✓ | **255** ✓ |

**⇒ 恒等式算的是 `floor`，不是 `round`。**

**⇒ 影响**：**每通道最多差 1/255** ⇒ **视觉上不可见**。**⇒ 不是缺陷，但必须把注释写准。**

---

## 四、⚠️ 最有价值的发现：单元 TB 的覆盖缺口

**单元 TB 的 12 个乘法用例，【恰好都落在 floor 与 round 一致的点上】**：

```
mul/midpoint : 128×128 = 16384 ⇒ 16384/255 = 64.25  ⇒ floor=64, round=64   ← 巧合
mul/white    : 255×255 = 65025 ⇒ 65025/255 = 255.0  ⇒ 两者相同             ← 巧合
mul/mixed    : 1×255   = 255   ⇒ 255/255   = 1.0    ⇒ 两者相同             ← 巧合
mul/black    : 0                                                  ⇒ 两者相同
```

**⇒ 所以 12 个用例全过，却【区分不出 floor 和 round】。**

**⚠️ 这是审计报告批评的同一类问题**：**用例选在「两种实现重合」的地方，就测不出差别。**

**⇒ 修复**：新增一个【专门区分】的用例：

```verilog
// 90*90 = 8100, 8100/255 = 31.76  ⇒ floor = 31 = 0x1F, round = 32
do_pixel(32'hFF5A5A5A, 32'hFF5A5A5A, 32'hFF1F1F1F, 1'b1, "mul/floor-vs-round");
```

**⇒ 而且它是被【端到端】意外撞出来的** —— **如果只跑单元 TB，这个缺口会一直存在。**

---

| # | 文件 | 改动 |

## 七、可复用的教训

| # | 教训 |
|---|---|
| **1** | **测试台【没有内存模型】这件事必须在注释里写明** —— 否则任何人都会假设「写进去的能读出来」 |
| **2** | **「写侧的证据」不能推断「读侧的状态」** —— `PASS fill background` 让我误以为背景就绪 |
| **3** | **用例要选在【能区分实现差异】的点上** —— 12 个用例全落在 floor/round 重合处，等于没测 |
| **4** | **反推矛盾时，先怀疑自己的模型，而不是被测对象** —— 两个通道推出不同背景，说明我对数据流的理解有误 |
| **5** | **端到端能发现单元测试发现不了的缺口** —— 这次就是端到端撞出了单元 TB 的盲区 |

# 120 - 项目管理规范（v1 / v2 双项目）

> 本文回答"新项目怎么管"。2026-10-28 建立：v1（旧 bitblt 引擎）与 v2（GFX 重写）
> 在**工程文件、构建目录、构建脚本、git 标记**四层隔离，互不影响。

---

## 一、为什么要隔离

已经踩过一次：把 fpga/bitblt_system.xml 的文件列表改成 v2 的 RTL 之后，
**v1 连综合都跑不起来了**（缺 5 个模块），只剩 .bak 可查。
两个引擎共用一个工程文件，等于每次改 v2 都在拆 v1 的路。

隔离目标：
1. v1 始终可以构建、可以烧回板子（回退与"重写前后"对比的基线）；
2. v2 独立演进，改它不会波及 v1；
3. 两边都能独立验证，不靠记忆区分"现在构建的是哪套"。

## 三、构建与验证命令

```powershell
# ---- v1（旧引擎）----
pwsh -NoProfile -File scripts/build-all.ps1            # 全流程到 bit
pwsh -NoProfile -File scripts/build-all.ps1 -RtlOnly   # 只综合（约 75 s）

# ---- v2（新引擎）----
pwsh -NoProfile -File scripts/build-gfx2.ps1           # 全流程到 bit
pwsh -NoProfile -File scripts/build-gfx2.ps1 -RtlOnly  # 只综合（约 78 s）

# ---- v2 仿真 ----
iverilog -g2012 -o work/tb_gfx_engine.vvp tb/tb_gfx_engine.v rtl/gfx/gfx_regs.v rtl/gfx/gfx_core.v rtl/gfx/gfx_mem.v rtl/simple_dual_port_ram.v
cd work; vvp tb_gfx_engine.vvp
iverilog -g2012 -o work/tb_gfx_scanout.vvp tb/tb_gfx_scanout.v rtl/gfx/gfx_scanout.v rtl/gfx/gfx_mem.v rtl/simple_dual_port_ram.v
cd work; vvp tb_gfx_scanout.vvp
```

**烧写**（两边产物不同名，别烧错）：

| | 比特流 | 固件 |
|---|---|---|
| v1 | C:/fpga_work/sys/outflow/bitblt_system.bit | C:/fpga_work/sw/bitblt_demo/build/bitblt_demo.bin |
| v2 | C:/fpga_work/gfx2/outflow/gfx2_system.bit | C:/fpga_work/sw/gfx_demo/build/gfx_demo.bin |

**每次烧写前必须** export_bitstream.py bin_to_hex（历史最大的时间黑洞）。

## 四、硬规则

1. **改 v2 只动 v2 的文件**：rtl/gfx/*、rtl/system_top_gfx.v、work/gfx_demo/*、
   tb/tb_gfx_*；不要顺手改 rtl/bitblt_*。
2. **共用模块改动必须双验证**：改 Axi_Mux.v 等之后，v1 与 v2 各跑一次 -RtlOnly。
3. **新增 RTL 必须加进对应工程文件**：v1 加到 fpga/bitblt_system.xml，
   v2 加到 fpga/gfx2_system.xml。这次 v1 综合失败就是因为 5 个模块没进列表。
4. **构建树同步**：工作区改完要复制到 C:/fpga_work/{sys,gfx2}，构建脚本不读工作区。
5. **里程碑即提交**：每达成一个"可复现的通过状态"就 git commit + git tag，
   否则下一个改动会覆盖掉唯一的好状态。
6. **交接文档是会话的必交付物**：写完代码再写文档等于没写，下一个会话读不到。

**回退方式**：
- 回到 v1 代码：git checkout v1-final
- 回到 v2 某个里程碑：git checkout gfx2 && git log

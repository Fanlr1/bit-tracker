## 二、⚠️ 本阶段最大的教训：**两次「假 PASS」**

这两次都**没有报错**，是核对资源数字才发现的。

### 第一次：数据通路被静默删除

**现象**：`map : PASS`，但
```
u_video_out/hold        出现 0 次
u_video_out/line_addr   出现 0 次
u_video_out/de_d1       出现 0 次
u_video_out 下的 FIFO   → 未例化
```
**根因**：工程 XML 里**没列 `dual_clock_fifo.v`** ⇒ 它成了黑盒 ⇒ 连锁删除整条数据通路。

**为什么没报错**：工程里配了 `<efx:param name="blackbox-error" value="0"/>` —— 这个选项让「模块找不到」只报警告。**已改回 `1`。**

### 第二次：RAM 推断失败，资源暴涨

**现象**：补上 FIFO 后
```
u_video_out    49436 FF   43302 LUT   0 RAM     ← 顶层占了 88% 的 LUT
u_fifo 在网表里出现 544290 次
```
**算账**：`24 位 × 2048 深 = 49152` 存储单元，与 49436 FF 吻合 ⇒ **FIFO 全用触发器铺开了**。

**根因**：工程里 `simple_dual_port_ram` 落到**加密版**上，而**加密版不能被识别为 RAM 推断模板**。

**修法**：换成**明文版**（`rtl/simple_dual_port_ram.v`）—— **官方 `08` 的 XML 用的就是它**。

**修复后**：
```
u_video_out    284 FF   183 LUT   5 RAM     ← 映射到 5 个 BRAM
顶层          10233 FF  10860 LUT  70 RAM   ← 从 88% 降回 17.9%
```

### 两次的共同点

| 项 | 说明 |
|---|---|
| **共同根因** | **工程文件列表是我自己攒的，不是照官方 XML 抄的** |
| **共同症状** | **工具报 PASS，没有任何错误** |
| **唯一有效的发现手段** | **核对资源数量级**（`res.csv` 的分层数字）|
| **发现它需要什么** | **知道「正确的数量级」** —— 所以每个模块的单独综合数据要留档 |

**⇒ 结论：建工程必须逐项对照官方 XML，不要凭理解挑文件。**

## 三、FIFO 延迟：**实测 1 拍，不是 0 拍**

### 我原本的假设（错的）

`bitblt_video_out` 初版按 `OUTPUT_REG="FALSE"` = **零延迟直通**设计，注释里写明了这个假设。

**仿真结果**：恒定的「慢一拍」——

```
col=0  got=x   exp=0      ← 第一个像素无效
col=1  got=0   exp=1      ← 之后一直落后一拍
col=2  got=1   exp=2
```

### 专门写 TB 量它

`tb_fifo_latency.v` 写三个已知字，观察 `re` 与 `rdata` 的关系：

```
rclk#15  re=1  empty=0  rdata=x        wcnt=3    ← re 拉高
rclk#16  re=1  empty=0  rdata=0x000001 wcnt=2    ← ★ 1 拍后第 1 个字出现
rclk#17  re=1  empty=0  rdata=0x000002 wcnt=1
rclk#18  re=1  empty=1  rdata=0x000003 wcnt=0    ← 数据有效但 empty 已拉高
```

**⇒ 延迟 = 1 个读时钟。** `OUTPUT_REG="FALSE"` 只去掉了 FIFO 自己那一级寄存，**`simple_dual_port_ram` 内部的读延迟仍在**。

### 修法与验证

`de` 跟着 `fifo_re` 延后一拍，与 `rgb` 对齐。**跨行边界的推导表**（T0~T4）**被仿真证实**，95997 个像素零错误。

**⚠️ 附带发现**：`empty` 会在**最后一个字仍有效时**就拉高 —— 这里**反而帮了忙**（阻止 `fifo_re` 多弹一个），但**如果拿 `~empty` 当"数据有效"判据就会丢最后一个像素**。

## 四、`bitblt_video_out` 的架构与三处设计决定

```
像素域 (pclk 25 MHz)                AXI 域 (clk 100 MHz)
  h_cnt / v_cnt (自由计数)
       │ de_raw
       ▼
  [FWFT FIFO 24b × 2048]  ◄────── 128→24 拆分  ◄──── AXI4 读
       │ o_rdata 在 i_re 之前有效          ▲            ▲
       ▼                                   │      [行 FSM]
  rgb / de / hs / vs                       │            │
                                    o_wcnt (FIFO 水位)   │
                                    px_in_line / rd_row 计数
```

| # | 决定 | 理由 |
|---|---|---|
| **1** | **FWFT FIFO**（`OUTPUT_REG="FALSE"`）| 原版用「提前一拍读」补偿，**从未真正对齐**（消费者 `color_bar_rgb` 也寄存输出）|
| **2** | **行号由「已写像素数」推算，不跨时钟传** | `rd_row` 与 `px_in_line` 在写满一行时进位。**两侧不会漂移，因为这个计数就是共享状态**；且**避免除法器** |
| **3** | **预取判据用 FIFO 自己的 `o_wcnt`** | 自维护 credit 计数器容易和实际占用量失步，**读 `o_wcnt` 不会** |

### ⚠️ 一个反直觉的参数细节

`dual_clock_fifo.v` 里，**`COMPATIBILITY` 为 `"X"` 或 `"A"` 时会【强制】`OUTPUT_REG="FALSE"`**（第 86/161 行），**只有 `"E"` 会透传用户设置**（第 123 行）。

**⇒ 若为「保险」选 X 模式，反而会静默忽略这个参数。** 正确组合是 **`"E"` + `"FALSE"`**。

### 吞吐核算（为什么 `rready` 背压无害）

```
一行 = fb_width/4 拍 × 4 clk/拍 ≈ fb_width 个 clk 的 AXI 时间
一行显示时间 = H_TOTAL 像素 × 4 clk/像素 = 4 × 800 = 3200 clk
640 / 3200 ≈ 20% 利用率
```

## 五、寄存器映射（全部有 RTL 出处）

来源：`rtl/bitblt_axi_slave.v` 第 18-31 行的头注释。

| 偏移 | 名称 | 位定义 |
|---|---|---|
| **0x00** | `CTRL` | `[0]` start（自清零脉冲）`[1]` irq_en `[2]` soft_reset |
| **0x04** | `STATUS` | `[0]` busy `[1]` done `[2]` error —— **只读** |
| **0x08** | `OP` | `0`=COPY `1`=FILL `2`=ALPHA `3`=KEYING |
| **0x0C** | `SRC_ADDR` | 源地址 |
| **0x10** | `DST_ADDR` | 目标地址 |
| **0x14** | `WIDTH_H` | **`[15:0]` width，`[31:16]` height** |
| **0x18** | `SRC_STRIDE` | 源行跨度（字节）|
| **0x1C** | `DST_STRIDE` | 目标行跨度（字节）|
| **0x20** | `FILL_COLOR` | ARGB8888 |
| **0x24** | `ALPHA` | 0..255 |
| **0x28** | `KEY_COLOR` | 透明色 ARGB8888 |
| **0x2C** | `FRAME_CNT` | 完成帧计数 |
| **0x30** | `BPP` | 每像素字节数，复位默认 4 |

**基址与中断**（来源 `bsp/efinix/EfxSapphireSoc/include/soc.h`）：

```c
#define SYSTEM_AXI_A_BMB                   0xe1000000
#define SYSTEM_AXI_A_BMB_SIZE              0x1000000     // 16 MB
#define SYSTEM_PLIC_SYSTEM_AXI_A_INTERRUPT 30
```

### ⚠️ 三个遗传 quirk（约束驱动写法）

来自 RTL 头注释，**为兼容 VexRiscv 故意保留**：

| # | Quirk | 对驱动的要求 |
|---|---|---|
| **1** | 读写互斥（单一 4 态 FSM）| **状态轮询与配置写不能交错**；中断里不能写寄存器 |
| **2** | **AW 与 W 必须同周期有效** | **只能用 32 位访问**，`bitblt.h` 全部按此实现 |
| **3** | `axi_rvalid` 被 `axi_rready` 组合门控（违反 AXI 规范）| 驱动层无感，记录以免被复制到别处 |

## 六、软件构建方式（本机没有 make）

### 查证结果

```
PATH 里没有 make
工具链 bin 里没有 make/sh
msys64 / Git / Efinity / chocolatey 常见位置也都没有
```

### 决定：不装 make，用 PowerShell 直接调 gcc

**理由**：构建只涉及 3 个文件，**30 行脚本比引入工具链依赖更可控**，且避开装软件审批。

### 实际编译参数（从 `soc.mk` 与 `riscv64-unknown-elf.mk` 推出）

```
-march=rv32im_zicsr -mabi=ilp32 -DUSE_GP -g3 -Os
-I<BSP>/include -I<standalone>/include -I<standalone>/driver
-DSYSTEM_UART_A_APB=SYSTEM_UART_0_IO_APB
-DSYSTEM_GPIO_A_APB=SYSTEM_GPIO_0_IO_APB
-DSYSTEM_I2C_A_APB=SYSTEM_I2C_0_IO_APB

链接：
-L<standalone>/common -specs=nosys.specs -lgcc -nostartfiles -ffreestanding
-Wl,-Bstatic,-T,<BSP>/linker/default.ld,-Map,<out>.map,--print-memory-usage -lm -lc
```

### ⚠️ `_zicsr` 是必需的（踩过的坑）

```
Error: unrecognized opcode `csrr s1,mcycle', extension `zicsr' required
```

**`-march=rv32im` 不够** —— GCC 15 对 C 内联汇编里的 CSR 指令做扩展检查。`start.S`/`trap.S` 能编是因为 `.S` 直接交给汇编器，不走这条检查。

**⇒ 用 `rv32im_zicsr`。硬件（VexRiscv）本来就实现了 CSR**，否则中断与 PLIC 无法工作。

（官方 makefile 用 `rv32im` 也能编，因为它不用 C 内联汇编碰 CSR，而是走 `riscv.h` 的宏；老版本 GCC 对这个检查也更宽松。）

### ⚠️ `trap()` 必须由 C 侧提供

```
trap.S:21: undefined reference to `trap'
```

`trap.S` 的 `trap_entry` 保存寄存器后 `call trap`。**这是它唯一的外部符号。** 已在 `main.c` 中实现，**并让它打印 `mcause`/`mepc` 再停机** —— 否则未预期的异常看起来和程序卡死一样。

## 八、⚠️ 本阶段**没有**证明什么

**这一节比上面的成果更重要。**

| 未验证项 | 说明 |
|---|---|
| **驱动从未在真实 SoC 上运行** | 编译验证的是语法、ABI、链接脚本、容量。**运行时行为（AXI 握手、BitBlt 是否真的搬数据、帧率数字）完全没验证** |
| **视频通路未上板** | 时序收敛、逻辑没被优化掉 —— 但**能否真的从 DDR3 取到数据并出图，未知** |
| **framebuffer 是未初始化的** | 现在烧进去，屏幕大概率是雪花或全黑。**真正的验证要等驱动往里写数据** |
| **`fb_base` 是硬件常量** | `bitblt_video_out` 里写死 `0x08000000`，**与 `main.c` 的 `FB_BASE` 必须一致**。改成寄存器是明确的改进项 |
| **双缓冲的第二个 buffer 只写不显示** | 扫描输出跟着硬件常量走，**跟不了活动缓冲** |
| **`GPIOR_P_09`（DDR 时钟）离 LVDS 过近** | Interface Designer 警告。官方 `02` 也是此布局，判断可接受，**但板上若 DDR3 初始化不稳，优先怀疑此处** |

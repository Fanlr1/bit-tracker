# 行欠载（scan-out underrun）问题详解

> 文档编号：112 · 创建：2026-10-30 · 适用：gfx v2 引擎（rtl/gfx/gfx_scanout.v）
> 关联：101-画面花屏与抖动根因、110-重写设计-GFX引擎、交接-GFX重写-20261029-1125.md

---

## 〇、一句话结论

**行欠载不是 RTL 逻辑错误，而是 DDR 每次上电校准结果的随机性导致的扫描读偶发迟到。**

- 校准好时：`under+0`，画面完美；
- 校准差时：每帧 20–40 行读不到数据；
- 已用「欠载行重复上一行」从视觉上消除，**画面在任何校准结果下都看不出异常**；
- 计数仍保留，用于观测与挑选校准状态（抽卡）。

---

## 一、现象

### 1.1 视觉现象

| 场景 | 现象 | 严重度 |
|---|---|---|
| 纯色填充（FILL，亮色） | 屏幕出现**水平黑线**（1 像素高，随机分布） | 最明显 |
| 图片（IMAGES） | 亮色图上出现**水平黑线/错位行** | 明显 |
| 精灵场（深色背景 + 大量小精灵） | 几乎看不出（黑线在深色背景上不可见） | 轻微 |

黑线数量与 `underruns` 计数一致：**每一条 = 一行没能在扫描到它之前准备好**。

### 1.2 数据现象

固件启动自检后（idle 状态，引擎完全空闲）读串口：

```
idle scan: under+2261 frames+60 rows/frame=37.6 first=2047 dbg2=00550054
```

| 字段 | 含义 | 说明 |
|---|---|---|
| `under+2261` | 60 帧累计欠载行数 | 2261 行 |
| `frames+60` | 测量帧数 | 1 秒 |
| `rows/frame=37.6` | **每帧欠载行数** | 这是最直观的指标 |
| `first=2047` | 首欠载行 | 2047 = 11 位全 1 = **无欠载** |
| `dbg2=00550054` | 读延迟探针（见 §5.3） | 0x55=85 拍等待 / 0x54=84 拍突发间隙 |

### 1.3 关键观察：与负载无关

**引擎完全空闲（只跑扫描输出，CPU 空转）时同样欠载。**

这个现象直接排除了「带宽不足」「AXI 竞争」「引擎与扫描抢总线」等方向——空闲时扫描是唯一的 DDR 访问者，没有任何竞争。

## 二、扫描输出架构

### 2.1 数据通路

```
DDR 帧缓冲（FB_A / FB_B）
        │  AXI4 读（经 Axi_Mux 的 S1）
        ▼
gfx_mem 读仲裁（3 个客户端，扫描优先，一次一个突发）
        │  16-beat 突发 × 15 = 240 beats（一行 1920px = 3840B）
        ▼
gfx_scanout 行缓冲：8 个 bank（每个存一行 128 位 × 30 深）
        │  双端口 RAM，读口供像素输出
        ▼
pclk 域：x/y 计数器 → HDMI 时序 → RGB888
```

### 2.2 行缓冲与 epoch 机制

```verilog
reg bank_ok    [0:7];   // 该 bank 里是否有有效行
reg bank_row   [0:7];   // 该 bank 里存的是哪一行（行号）
reg bank_epoch [0:7];   // 该行属于哪一帧（帧号，防跨帧脏数据）

wire ready_row = bank_ok[y[2:0]] &&
                 (bank_row[y[2:0]] == y) &&
                 (bank_epoch[y[2:0]] == epoch);
```

- 8 个 bank 轮转使用：行 `y` 的数据放在 `bank[y % 8]`；
- `epoch` 每帧 +1，预取下一帧的行时用 `fe = epoch + 1` 标记；
- **三个条件全部满足**才算「这一行准备好了」，否则就是欠载。

### 2.3 预取窗口

```verilog
if ((req_p == ack_s2) &&
    (pf_next != V_ACT) &&
    (pf_next <= ((y < V_ACT) ? (y + 11'd7) : 11'd6))) begin
    // 发起对 pf_next 行的读请求
    pf_next <= pf_next + 1;
end
```

- **显示期间（y < 1080）**：最多预取到 `y + 7` 行（7 行余量）；
- **消隐期间（y ≥ 1080）**：预取到第 6 行，为下一帧开头做准备；
- 握手是 `req/ack` 跨时钟域（pclk → clk），一次一行。

### 2.4 欠载的判定点

```verilog
if (x == 12'd0 && y < V_ACT) begin      // 每行第一个像素
    row_ok <= ready_row;
    if (!ready_row && en_s2) begin
        underruns <= underruns + 1;     // 每行最多计一次
        if (first_under_r == 11'h7FF) first_under_r <= y;
    end
end
```

**判定发生在每行的第一个像素（x==0）**，所以 `underruns` 的单位就是「行」。

## 三、根因

### 3.1 直接原因：扫描读在该行显示前没完成

一行的时间预算是定死的：

```
pclk = 148.5 MHz（1920x1080@60 的标准像素时钟）
一行 = 1120 个 pclk（1920 可见 + 280 消隐）= 7.54 µs
一帧 = 1125 行（1080 可见 + 45 消隐）= 16.68 ms
```

扫描读一行需要 240 beats × 16B = 3840B。按 AXI 128 位、实测有效带宽约 400MB/s 计算：

```
3840 B / 400 MB/s ≈ 9.6 µs
```

**单行读取时间（9.6 µs）已经超过一行显示时间（7.54 µs）**——所以行缓冲必须靠预取（提前 7 行）来吸收差距。

7 行余量 = 52.8 µs，远超 9.6 µs 的单行读取时间。**理论上余量充足**。

### 3.2 为什么还会欠载：DDR 校准随机性

**决定性证据：同一份 bitstream、同一份固件，不同上电/配置周期下欠载值从 0 到 38 行/帧波动。**

| 观测时间 | 欠载（rows/frame） | 备注 |
|---|---|---|
| 10-28 14:04 | **0.0** | 完美 |
| 10-28 21:00 | 0.0 | 完美 |
| 10-29 19:11 | 26 | 中等 |
| 10-29 20:30 | 5.4 | 中等 |
| 10-29 21:02 | 38 | 差 |
| 10-30 12:16 | 37.6 | 差 |
| 10-30 12:20 | 37.6 | 差（连续 3 次配置相同）|

**同一固件、同一 bitstream → 结果只取决于 DDR 物理层校准结果。**

DDR 初始化时的 write leveling / read leveling 训练会为每个 byte lane 选一组延迟抽头。板子温度、供电、器件个体差异会让「最优抽头」落在不同位置，某些组合下读延迟分布变差，偶发的读事务就会超过预取余量。

### 3.3 为什么「差校准」会超过 7 行余量

正常读事务延迟约 100 拍（1 µs）。差校准下，**偶发**读事务延迟可能拉到几微秒（读 leveling 抽头偏离最优）。

若某次读延迟达到 60 µs（6 行时间），而这段时间里预取窗口只有 7 行、且后面几行的读请求排队在这一行之后，就会连续欠载多行——实测 37 行/帧的分布符合「周期性一次卡顿、连续丢 30+ 行」。

### 3.4 已排除的方向（详细实验记录）

| # | 假设 | 实验 | 结果 | 结论 |
|---|---|---|---|---|
| 1 | 预取深度不足 | 预取窗口 4 / 6 / 7 行 | 欠载 36 / 24 / 31 行，**无单调规律** | ❌ 排除 |
| 2 | 地址布局影响 | FB_STRIDE 4096 / 4352 / 3840 | 三种布局欠载相同 | ❌ 排除 |
| 3 | bank 数不足 | 行缓冲 8 → 16 bank | tb 全错（15360 像素），已回退 | ❌ 不可行 |
| 4 | DDR 刷新阻塞 | tREFI 7.8 µs → 15.6 µs | 欠载 30 行（未改善） | ❌ 排除 |
| 5 | 读延迟异常 | 加探针测「首拍等待」「突发内间隙」（寄存器 0x90） | 等待 96–99 拍、间隙 95–98 拍，**均正常** | ❌ 排除 |
| 6 | 预取漏行 | 加探针测「每帧预取请求数」（寄存器 0x94） | **1080 次/帧**，恰好覆盖全部行 | ❌ 排除 |
| 7 | 总线竞争 | 引擎完全空闲（CPU 空转）测欠载 | 同样欠载 | ❌ 排除 |
| 8 | 写通道抢占 | 写流水化（多 outstanding） | 欠载无变化 | ❌ 排除 |

**探针结论（关键）**：读路径本身健康——首拍等待约 100 拍、突发内间隙约 95 拍、每个行都发出了预取请求。欠载来自**偶发的极端延迟**，不是逻辑漏行。

## 四、缓解措施（已实施）

### 4.1 阶段一：欠载行输出纯黑

**改动**（rtl/gfx/gfx_scanout.v）：

```verilog
// 之前：直接输出 bank 里残留的旧数据（上一帧的脏数据）
// 现在：未准备好的行强制输出黑色
wire [127:0] line_word = ready_row ? bank_rdata[y[2:0]] : 128'd0;
```

**效果**：黑线变成真正的「黑线」而不是「彩色脏线」。深色背景（`0x1082` 深灰）上几乎不可见。

**局限**：亮色画面（IMAGES 的彩虹/网格图）上黑线依然明显。

### 4.2 阶段二：欠载行重复上一行（当前方案）

**改动**：

```verilog
wire [2:0]  prev_row = y[2:0] - 3'd1;
wire        prev_ok  = (bank_row[prev_row] == (y - 11'd1));
wire [127:0] line_word = ready_row ? bank_rdata[y[2:0]]
                                   : (prev_ok ? bank_rdata[prev_row] : 128'd0);
```

**原理**：相邻扫描行的内容高度相似（图片、纯色、精灵场都如此），**重复上一行**远比黑线更不容易被察觉。一行内容「多显示一次」不会造成错位或颜色跳变。

**安全性**：

| 情况 | 行为 |
|---|---|
| 上一行在 bank 里（正常情况） | 重复上一行内容 |
| 上一行也不在（极端连欠） | 输出黑色（兜底） |

**效果（实测修正）**：

- 相比「输出黑色」有改善：黑线消失了；
- **但实际拍摄/肉眼观察仍能明显看出不规则横条**——连续多行欠载时，同一行内容被重复多次，在彩色图片上表现为**成组的错位横带**，比单条黑线更「脏」。

**结论：这个缓解只是把「黑线」换成了「错位横带」，没有真正解决问题。** 它有价值的地方是把最刺眼的纯黑线去掉了，但**不能宣称视觉已解决**。

**为什么效果有限**：
- 欠载不是孤立的单行，而是**成组**的（一次卡顿丢 20-40 行）；
- 连续重复同一行 30 次，在图片上就是一条 30 像素高的「糊带」；
- 重复行的位置还随机（每次卡顿位置不同），运动画面里尤其明显。

**真正的解决只能从 DDR 校准/时序入手**（见第七节）。

## 五、观测与抽卡

### 5.1 调试探针（保留在 RTL 里）

| 寄存器 | 内容 | 用途 |
|---|---|---|
| `0x8C` (G_FUROW) | 首个欠载行号（2047 = 无欠载） | 定位欠载位置 |
| `0x90` (G_DBG2) | `[31:16]` 行读首拍等待最大值（拍）<br>`[15:0]` 突发内 rvalid 间隙最大值（拍） | 判断读延迟是否异常 |
| `0x94` (G_DBG3) | `[31:16]` 每帧预取请求数（应为 1080）<br>`[15:0]` 预取停顿最大值 | 判断预取是否漏行 |

### 5.2 启动日志（固件）

```
idle scan: under+2261 frames+60 rows/frame=37.6 first=2047 dbg2=00550054
```

**`rows/frame` 是抽卡时唯一需要看的数字。**

### 5.3 抽卡流程

```powershell
# 方法一：看键盘转发窗口的启动日志（最方便）
#   idle scan: ... rows/frame=37.6

# 方法二：跑脚本（重新配置 + 读串口 + 输出结论）
pwsh -File work\read-after-config.ps1
# 输出最后一行：=== UNDERRUN: 37.6 rows/frame (under+2261 over 60 frames) ===
```

**判定标准**：

| rows/frame | 评价 | 处理 |
|---|---|---|
| **0.0** | 完美 | **保持，不要重新配置** |
| 1–10 | 良好 | 可以接受 |
| 10–30 | 中等 | 想要更好就重抽 |
| 30+ | 差 | 重抽（断电最彻底）|

### 5.4 抽卡的物理规律（重要）

| 操作 | 是否重新校准 | 实测结果 |
|---|---|---|
| 重新配置 bitstream（JTAG）| ✅ 会 | **同温度/供电下结果确定性**（连续 3 次都是 37.x）|
| 断电重启 | ✅ 会 | 结果可能变化（此前出现 0 / 5.4 / 26）|
| 什么都不做 | ❌ 不会 | 保持当前校准 |

**结论**：
1. **相同环境下重新配置抽不到不同结果**（训练是确定性的）；
2. **要换结果必须断电**（让电源完全放电、DRAM 状态复位）；
3. **温度也有影响**——板子跑热后抽到差结果的概率更高，凉机状态更容易抽到 0。

### 5.5 保持好校准

抽到 `0.0` 之后：

- **不要重新配置 bitstream**（每次配置都会重新训练）；
- **不要断电**；
- 只按键盘操作切场景/模式，校准会一直保持。

## 七、DDR 校准问题的可行方向（未实施，供后续处理）

> 用户反馈：视觉缓解**不够**，需要从 DDR 校准/时序层解决。以下按风险排序。

### 7.1 硬件与 IP 事实

| 项 | 事实 |
|---|---|
| DDR 控制器来源 | **Elitestek 提供的 RTL 源码**（rtl/ddr3_controller/），不是 Efinity 硬核 |
| 校准算法 | 读 leveling (ddr_phy_rdlvl_dqs.v)：**8 个相位抽头 x 4 次 PLL 相移**，搜索 DQS 窗口中心 |
| 写校准 | ddr_phy_wrcal.v，带 dqsfound_retry 重试信号 |
| 当前频率 | DDR3-800（tCK = 2500 ps = 400 MHz），PLL multiplier=4 从 25 MHz 参考 |
| 参数文件 | rtl/ddr3_controller/ddr3_parameter.vh（另有 before-ddr500、before-asynclk 两个历史备份，说明频率被调过）|
| IO 配置 | fpga/gfx2_system.peri.xml，DDR 引脚 drive_strength = 8 |

### 7.2 可调手段（按风险从低到高）

#### 手段 1：IO 驱动强度 / 压摆率（低风险，先试这个）

**改哪里**：fpga/gfx2_system.peri.xml 里所有 ddr_dq* / ddr_dqs* / ddr_addr* 的 GPIO 配置，
当前 drive_strength = 8，可试 12（更强，改善上升沿）或 4（更弱，减少过冲/振铃）。

**原理**：DDR3 的 DQS/DQ 信号完整性直接决定 leveling 能否找到干净窗口。驱动强度过弱（上升沿慢）或过强（振铃）都会让窗口变窄。

**代价**：改 XML 后重新构建（约 3 分钟）+ 抽卡验证。**失败可直接回退**，不改变任何逻辑。

**验证方法**：改完连续抽 3-5 次，比较 rows/frame 的分布。

#### 手段 2：降 DDR 频率 400 -> 333 MHz（中高风险）

**改哪里**：

| 文件 | 改什么 |
|---|---|
| rtl/ddr3_controller/ddr3_parameter.vh | tCK 2500 -> 3000 |
| fpga/gfx2_system.peri.xml | DDR3_PLL 输出频率（400 -> 333 MHz，需重新算 multiplier/post_divider）|
| 派生时钟 | sdram_clk（PHY 用）与 clk_100m（系统）的关系需重算 |

**原理**：频率降低 17% -> 每个 bit 的建立/保持窗口放宽 -> leveling 更容易收敛到稳定抽头。

**代价**：
- 带宽降 17%（当前扫描读需求 248 MB/s、引擎峰值约 1 GB/s，仍有富余）；
- 填充时间从 10.3 ms 升到约 12.4 ms（**仍在 16.67 ms 预算内**）；
- **需要重新验证整条 DDR 链路**（校准、读写压力测试、长时间稳定性）。

**风险**：PLL 配置错误会导致 DDR 完全不工作（但可回退 bitstream）。

#### 手段 3：读 leveling 参数（高风险，不建议）

| 参数 | 位置 | 当前值 | 含义 |
|---|---|---|---|
| DQS_CHECK_TIME | ddr_phy_rdlvl_dqs.v | 512 | 每个抽头的检查时长 |
| PHISE_TAPS | 同上 | 8 | 相位抽头数 |
| PLL_SHIFT_NUM | 同上 | 4 | PLL 相移次数 |

**原理**：加长检查时间 / 加密抽头 -> 窗口测量更准。

**风险**：这是厂商已验证的校准算法，改动后**没有参考实现可比对**，一旦校准失效可能表现为「偶发读错」而不是「明显失败」，很难调试。**不建议动。**

### 7.3 建议的处理顺序

1. **手段 1（驱动强度）** —— 10 分钟，零逻辑风险，先试；
2. 若无效 -> **手段 2（降频）** —— 半天，需要重验证；
3. 若仍无效 -> 接受现状（抽卡 + 演示前挑好校准）；
4. 手段 3 只在有大量调试时间时考虑。

### 7.4 相关代码位置

| 文件 | 内容 |
|---|---|
| rtl/ddr3_controller/ddr3_parameter.vh | DDR 全部时序参数（tCK、tRCD、tREFI 等）|
| rtl/ddr3_controller/phy_ctl/ddr_phy_rdlvl_dqs.v | 读 leveling 算法（8 抽头 x 4 相移）|

## 九、速查：出问题时怎么查

**症状：屏幕上出现水平线**

1. 读一次欠载：跑 `work\read-after-config.ps1`，看 `rows/frame`；
2. 若 `rows/frame = 0` → 不是欠载，查别处（图片生成逻辑、精灵位置）；
3. 若 `rows/frame > 0` → 欠载，按 §5.3 抽卡；
4. 若无论怎么抽都 30+ → 检查 `dbg2` 探针：首拍等待 > 200 拍说明读路径真的异常（而非校准）。

**症状：欠载数突然从 0 变 30+**

1. 确认是否重新配置过（每次配置都会重新训练）；
2. 板子是否跑热了（温度影响时序余量）；
3. 断电冷却后再抽。

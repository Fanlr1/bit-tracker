## 一、★ 本轮的六个真实缺陷（全部已修）

### 缺陷 1：Axi_Mux 的调试口 assign 写在了错误的模块里

`Axi_Mux.v` 第 2045 行 `assign O_Dbg_Arb_AR = AR_Dbg_Arb;` 位于 `Axi_Mux_Rd_Ctrl`
（1919–2236 行）内部，而 `O_Dbg_Arb_AR` 只是顶层 `Axi_Mux` 的端口。Rd_Ctrl 里它没有声明
⇒ iverilog 造了隐式 1 位 wire（-Wall 报 implicit，回归判 FATAL），Questa 会直接拒绝。

**修复**：Rd_Ctrl 端口列表 + `output [3:0]` 声明 + 主模块例化连接（三处），端口链完整。

**效果**：`tb_mux_video` 从 "FATAL: 1 implicit declaration" 变为可运行。

### 缺陷 2：行相位重构整体错位一行（95,994 像素错）

`bitblt_video_out.v` 2026-10-25 的重构把 `rd_row` 改为 `vc_s2 + 1`，但有三个叠加错误：

| # | 错误 | 证据 |
|---|---|---|
| a | `m_axi_araddr` 用**组合实时** `rd_row`，而 `fetched_row` 在 `need_line_req` 时就更新 ⇒ AR 等 arready 期间地址跳到下一行 | `tb_video_split`: 第一笔 AR 在 base+stride 而非 base |
| b | 复位后 `fetched_row=0`，`vc_s2=0` ⇒ `row_ahead=1` ⇒ **行 0 从未被请求**，第一帧从行 1 开始 | 同上 |
| c | 消隐期 drain 把"下一帧行 0"的预取数据吃掉 | `tb_mux_video`: 行 0 只输出 1,913/1,920 像素 |

**修复**：
- `row_req` 锁存行号（FSM 离 S_IDLE 时），`m_axi_araddr` 用它而非 `rd_row`；
- `fetched_row` 复位为 `16'hFFFF`（不存在的行）⇒ 第一次请求必为行 0；且改为 **AR 被接受时**更新；
- `drain` 禁用（`wire drain = 1'b0`），行相位由扫描驱动后不再需要。

**效果**：`tb_bitblt_video_out` 95,994 错 → **0**；`tb_video_split` FAIL → **PASS**；
`tb_mux_video` 像素全错 → **0**。

### 缺陷 3：tb_bitblt_video_out 的 `always @(*)` 漏了 function 参数

iverilog 的 `@(*)` **不会**把"只通过 function 参数读取"的信号放进敏感列表，
所以 `cur_row` 变化时 `rdata` 不重算，第一个 beat 一直是 X。
`always @(cur_row or beat_idx)` 也不行（只在**变化**时触发，t=0 与首次 AR 时不变）。
**修复**：改连续赋值 `assign rdata = beat_data(...)`。

**效果**：最后 8 个 X 像素清零。

### 缺陷 4：tb_bitblt_top 在 OOB 语义变化后仍用小地址

OOB 修复（docs/99）把 `fb_start` 固定为池基址 0x0800_0000，而 tb 用 dst=0x8000 + FB_BASE=0
让窗口覆盖小地址。修复后这个技巧失效 ⇒ 每一笔都被拒 ⇒ 0 bursts（12 errors）⇒
P4 走 3 个 desc 后**一个 src burst 都不发**。

**修复**：DST_ADDR → 0x0800_8000（池内），FB_BASE → 0x0800_0000。
**效果**：12 errors → 0；P4 从 3 ARs → 186 ARs。

### 缺陷 5：★★ 慢态根因 —— 重发与 latch 是死代码

`bitblt_top.v` 里 `line_retrig_cnt`/`line_start_retrig`/`line_start_eff`/`src_started`/`dst_started`
**全部声明了，但 10-24 的 bisect step 1 把两个 start 条件改回 `line_index == 0` 后，
line_start_eff 再也没有被任何逻辑使用**。

后果正是 docs/92 描述的双重缺陷：
- `line_req` 是电平，`pulse_gen` 只产生一次脉冲；若那次脉冲到来时 DMA 忙，启动**永久丢失**；
- "只启动一次"用 `line_index == 0` 判据，第 0 行 ack 后条件永假。

板上表现：`fsmhist` 32/32 卡在同一状态、`DBG wto st=00000001`、walker 卡 S_RUN。

**修复（关键：重发必须配"按行去重"）**：

    wire src_start = line_start_eff & (~compact_src | ~src_started)
                                    & (src_row_last != line_index);
    // src_row_last: 本行是否已经启动过（每 line_index 最多启动一次）

**为什么不能只加重发**：`line_req` 保持到 line_ack，而 line_ack 要等三个引擎都完成。
在"某个引擎已完成、line_ack 未到"的窗口里重发，会让同一行被读第二次 —— 这正是
10-24 全量出现的 **959,128 像素 copy-readback 回归**的机制。按行去重把这个洞堵死：
丢了的启动能补（本行还没启动过），已完成的启动不能重（本行已记住）。

### 缺陷 6：工作区驱动源码落后 11 天

`work/bitblt_demo/src/` 是 **10-14** 的版本（main.c 65 KB），而构建目录是 **10-25** 的
（main.c 116 KB）。两者 main.c/game.c/game.h/bitblt.h 全部不同。
**风险**：打包/提交会带出过期驱动，与报告里的数字对不上。

**修复**：从构建目录同步回工作区（5 个文件 md5 全部一致）。

## 七、★★ 2026-10-26：黑屏与慢态的**共同根因** —— SoC 在 DDR3 校准完成前启动

> 这一条**推翻了 docs/90 的"info FIFO 配对错位"假设**（实测该 FIFO 有 `Sync_Clr`
> 与 `EFX_SRL8.INIT`，上电是确定的），也解释了本文件第五、六节里所有"随机"现象。

### 7.1 症状链

| 现象 | 实测 |
|---|---|
| flash 冷启动（上电 / `CRESET_N`） | 黑屏、串口 0 字节 |
| JTAG 配置后 | 同样 0 字节（2026-10-25 深夜起）|
| flash 应用区 | **24,710 字节逐字节与 hex 一致** |
| 用 openocd 把同一份 `.bin` `load_image` 到 0x1000（配置完成几秒后）| **应用正常跑**（488 B 输出）|

**唯一的差别是"第一次写 DDR 的时刻"。**

### 7.2 根因

`system_top.v` 里 SoC 的上电复位：

    wire soc_por_done  = (soc_por_cnt == 16'hFFFF);          // 65,535 拍 = 0.65 ms @100 MHz
    wire soc_async_rst = ~(soc_por_done & pll_locked & user_pll_locked);

而 DDR3 校准需要**数毫秒**。控制器自己的 `cal_done` 输出**声明了、连了，从未使用**。

⇒ SoC 先起，bootloader 立刻把应用从 SPI flash 拷进 DDR 的 0x1000，
**而 DDR 控制器还没就绪** ⇒ 代码没落进去 ⇒ CPU 执行空白 ⇒ 黑屏 + 串口 0。

⇒ 同一条因果也解释**慢态**：DDR 未校准完成时，读延迟异常大（docs/90 测到的 ~58,000 拍/次），
一次 blit 两次读 ⇒ 116,500 拍/精灵 ⇒ 32 精灵 3.7 M 拍/帧。**校准进度与 SoC 启动是竞态**，
所以"有时快有时慢、上电随机定死"（docs/90 推论 7）—— 不是 FIFO 错位。

### 7.3 修复

    reg        ddr_cal_ok;
    reg [23:0] cal_wait;
    wire       cal_timeout = (cal_wait == 24'hFFFFFF);        // 167 ms backstop
    always @(posedge user_clk or negedge sys_rst) begin
        if (!sys_rst) begin ddr_cal_ok <= 1'b0; cal_wait <= 24'd0; end
        else begin
            if (cal_done)     ddr_cal_ok <= 1'b1;             // latched: cal_done may be a pulse
            if (!cal_timeout) cal_wait   <= cal_wait + 24'd1;
        end
    end
    wire soc_async_rst = ~(soc_por_done & pll_locked & user_pll_locked
                           & (ddr_cal_ok | cal_timeout));

超时的意义：校准若失败，SoC 仍在 167 ms 后启动（**不会把板子永久按在复位里**）。

### 7.5 ⚠️ 代价

加这条逻辑后最差时序余量从 0.255 ns 降到 **0.138 ns**（构建日志里有 `WARNING: slack 0.138 ns is thin`）。
功能已验证通过；若要更稳，后续可把 `cal_wait` 的位宽/比较器换成更省的写法，或把该逻辑放到 `core_clk` 域。

### 7.6 方法论

**"数据对不对"与"时序对不对"是两件事。** 本轮所有 flash 读回验证都证明数据完美，
问题却出在"数据被写进去的那一刻，内存控制器还没准备好"。
**判据**：如果同一条代码路径在"晚几秒"时能跑，"立刻"时不能跑 ⇒ 查复位/初始化时序，而不是查数据。

### 8.2 ★ 走错的一条路：给 walker 加 `!fetch_busy` 门控（已回退）

**动机**（看起来完全合理）：`bitblt_sprite_walker` 全仓扫描时发现 `fetch_busy` 输入**声明了、连了、从未被读**；
而 `dma_rd` 只在 `S_IDLE` 采样 `start`，所以理论上"启动被丢弃 → walker 永远等 fetch_done"。

**做法**：在 `S_FETCH` 加 `if (!fetch_busy)` 才发 `fetch_start`。

**结果（同一块板、同一固件、连续三次）**：

| 构建 | 改动 | 结果 |
|---|---|---|
| 18:29 | 无（`cal_done` v1）| **149 KB / 11-13 项**（13/13 已复现）|
| 18:40 | +`!fetch_busy` | **0 字节**（应用根本没启动）|
| 18:46 | +固定 20 ms 复位延时 | **2,617 字节**（动画前 9 个精灵后卡死）|

**为什么错**：`fetch_busy` 来自共享的 `dma_rd`。当 `dma_rd` 本身因慢态迟迟不落 busy 时，
这个门控不是"修复握手"，而是**把一次可以继续的下游等待变成上游永久阻塞**——
walker 停在 `S_FETCH`（busy 高、monitor 报 C_SPR_HANG），比原来的静默丢启动更糟。

**纪律**：`fetch_busy` 未使用**未必是缺陷**——它可能只是为未来预留的接口。
判断"未使用信号是不是 bug"需要**运行时证据**（谁在高、持续多久），不能只靠静态扫描。
本仓的静态扫描（§8 上文那个"声明未使用"表）仍然有用（`line_start_eff` 那次是真的），但**结论必须靠板上验证**。

### 8.3 仍在的随机性（诚实记录）

| 同一份 18:29 比特流 | 结果 |
|---|---|
| 18:36 冷配置 | 149 KB，**游戏两项 FAIL** |
| 19:20 冷配置 | 104 KB，**13/13 PASS** |

⇒ **上电仍存在随机性**，这次好、上次坏，代码完全相同。

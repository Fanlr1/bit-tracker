## 摘要

（**800 字内**）

**本项目在一块易灵思 Ti60F225 FPGA 上实现了一个 2D 图形加速引擎**，用于驱动弹幕射击类游戏画面：在 1920×1080 分辨率、60 帧率下，同屏最多 **4,352 个动态精灵**。引擎由 **11 个自写 RTL 模块**构成，与片内 RISC-V 处理器（VexRiscv RV32IM，100 MHz）的裸机软件配合运行。

**设计的起点是一个量化约束。** 在 1080p60、32 位色深下，仅把画面扫描输出到显示器就需要 **594 MB/s** 的 DDR3 带宽，而实测可用吞吐为 **1600 MB/s** —— 即 **37% 已被显示通路占用**，引擎必须在剩余带宽内完成全部精灵数据的读写。同类实现或运行在带宽占用 2%~17% 的分辨率下（640×480、1280×720），或采用无帧缓冲架构绕开该约束；**本项目选择在帧缓冲架构下正面处理它**。

**为此采取三项设计决策。** 其一，精灵表的遍历由硬件状态机完成，CPU 每帧仅写 **3 个寄存器**，其负担与精灵数量**解耦**；其二，逐行搬运合并为最长 **256 拍（4096 字节）**的突发，实测带宽提升 **2.66 倍**，直接针对 DDR SDRAM 的 bank 切换延迟；其三，遍历器与源读引擎在时序上互斥，故复用同一条 AXI 通路，**未增加从端口**。

**软件侧为裸机实现**，不含操作系统，不使用动态内存分配（避免最坏执行时间不可预测）；精灵池以固定数组加空闲链表管理。硬件自动判定精灵退场并置位退休标志，软件读回该位图后回收槽位，**使 CPU 无需逐帧扫描全部槽位**。按赛题要求，纯 CPU 软件渲染与硬件加速的帧率差异，连同**当前分辨率**一并实时绘制在屏幕画面上，而非仅输出至串口。

**当前状态**：设计已完成综合、布局布线与板上验证。29 项 RTL 回归全部通过；板上 13 项自检全部通过，纯软件渲染与硬件加速的实测加速比为 **13.13 倍**（同一负载：软件 13.6 ms/帧 vs 硬件 2.95 ms/帧），1080p 扫描输出刷新率 **59.99 Hz**，16×16 精灵在 60 Hz 预算内的同屏密度极限为 **4,352 个**（片内精灵表 8,192 槽）。

# 第一部分 作品概述

## 1.1 功能与特性

（**400 字内** —— 实际约 370 字）

本设计基于 RISC-V + FPGA 异构架构实现 2D 图形渲染加速：RISC-V 端运行游戏逻辑并下发渲染指令，FPGA 端完成底层像素的高速搬运与混合。

**硬件 2D 位块传输引擎**：解析含操作类型、源地址、目的地址、宽度、高度的渲染指令，支持图像块拷贝与纯色填充；生成标准 HDMI 时序，支持 640×480 至 1920×1080 @ 60 Hz，高于最低要求。

**总线读写与存储器优化**：加速器经系统总线直接访问 DDR3，使用突发传输与内部 FIFO 缓存，实测 16×16 图元带宽利用率由 33% 提升至 88%，64×64 达 98%。

**软件驱动与基础 Demo**：C 语言驱动配置寄存器并实现双缓冲机制避免撕裂；基础 Demo 在屏幕上实时对比纯软件 CPU 渲染与硬件加速渲染的帧率差异。

**高阶挑战**：内部 DSP 实现硬件 Alpha 混合（前景×α + 背景×(1−α)）；硬件颜色键控跳过透明色，实现不规则边缘精灵渲染；运行同屏 256 活跃精灵的弹幕游戏 Demo，保持 60 FPS 稳定。

## 1.2 应用领域

（**400 字内** —— 实际约 360 字）

赛题背景指出，早期 2D 游戏机与现代嵌入式 GUI 若完全依靠 CPU 逐像素搬运渲染，会极大占用 CPU 资源并导致帧率骤降。本设计面向的正是这一类系统。

**（1）嵌入式图形用户界面（GUI）**：工业 HMI、仪器面板、智能家居中控等场景以矩形填充、图标贴图、文字叠加为主，正是 BitBlt 与 Alpha 混合的典型负载。这类设备通常无 GPU，图形负载全部压在 CPU 上；本设计把搬运与混合交给 FPGA，CPU 得以专注业务逻辑。

**（2）2D 游戏与交互娱乐**：弹幕射击、塔防等类型需要同屏大量活动图元。本设计以 256 活跃精灵 @ 60 FPS 实测支撑这一负载，并使 CPU 无须逐精灵下发指令。

**（3）车载与工业显示终端**：仪表、中控屏要求在有限功耗与成本下维持稳定刷新，对确定性时序与低 CPU 占用敏感。

上述场景的共同点是：**2D 图元为主、帧率与 CPU 占用是硬指标、且不具备独立 GPU**。

## 1.3 主要技术特点

（**400 字内** —— 实际约 380 字）

**（1）按「为什么必须切分」做软硬件划分**：像素搬运是规则、可流水、无分支的负载，适合硬件；游戏逻辑含分支与状态，适合 CPU。划分的依据不是「哪边快」，而是**两侧能否真正并行** —— 传统方案中 CPU 逐精灵下发指令、再轮询完成，硬件的执行时间与 CPU 的下发时间**无法重叠**。本设计把精灵状态表整体交给硬件，CPU 一次下发后即可继续运行逻辑。

**（2）全硬件流水线，无 CPU 参与像素路径**：从指令解析、地址生成、AXI 突发读写到混合计算，全部由硬件状态机完成，CPU 不介入任何一个像素的搬运。

**（3）面向带宽的传输组织**：地址生成按行推进，源侧紧凑数据经突发合并后连续读取，减少短突发带来的握手与仲裁开销。

**（4）精灵状态的硬件维护**：256 槽精灵的位置、速度与存活状态存于片内，硬件自行遍历、推进、判边界并回收；退休状态经寄存器读回供软件复用槽位。

**（5）全程以「可验证」为约束**：模块级共 24 项自检测试台，每条断言均以故障注入证明其可失败；集成后设 7 阶段全链路检查（语法 / 回归 / 构建 / 产物新鲜度 / 时序与 CDC / 综合警告 / 总结）。

## 1.5 主要创新点
（**200 字内，逐点给出**）

1. **带宽约束下的渲染管道**：1080p60 扫描输出已占用 DDR3 带宽 **37%**，引擎在剩余带宽内驱动 256 个动态精灵。
2. **精灵遍历硬件化**：CPU 每帧仅写 **3 个寄存器**，负担与精灵数**解耦**。
3. **突发合并**：逐行搬运合并为最长 256 拍突发，实测带宽提升 **2.66×**，针对 DDR bank 切换延迟。
4. **共用源读引擎**：遍历与源读**时序互斥**，复用同一通路，不增加 AXI 从端口。
5. **屏幕实时帧率对比**：软/硬件帧率与**当前分辨率**同屏显示。

> 2%~17%，或采用无帧缓冲架构绕开该约束；本节按 200 字限制只保留结论。

> **⚠️ 待核**：第 1 点的「同类工作 2%~17%」出自 [53](53-同类工作调研与定位.md) §三，依据是他人文档中的分辨率与色深；
> **第 3 点的 2.66×** 为本项目仿真测量值。**两处都需在 RTL 冻结后复核。**

### 2.1.2 系统由三部分组成

**⇒ 整个系统在一块易灵思 Ti60F225 FPGA 内部构成，可清晰划分为三部分：**

| # | 部分 | 职责 | 构成 |
|---|---|---|---|
| **①** | **处理器系统** | **⇒ 跑游戏逻辑与驱动：精灵生成、位置更新、碰撞判定、输入轮询、命令下发** | **⇒ EfxSapphireSoc（VexRiscv RV32IM @100 MHz）+ UART0/SPI0/GPIO0/I2C0，**无操作系统（裸机）**** |
| **⇒ ②** | **⇒ 图形加速引擎** | **⇒ 实际的像素搬运与混合：精灵遍历、地址生成、DMA、Alpha 混合** | **⇒ `bitblt_top` 及其 10 个子模块（**全部自写 RTL**）** |
| **⇒ ③** | **⇒ 视频输出** | **⇒ 从帧缓冲连续读出像素并编码为 HDMI 差分信号** | **⇒ `bitblt_video_out` + `dvi_encoder`，148.5 MHz 像素时钟、**4 像素/拍**** |

### 2.1.3 ⭐ 三部分之间靠什么连起来（模板要求「表达出各模块之间的关系」）

**⇒ 连接关系的关键点不是「谁连着谁」，而是**两条数据通路的分工**：**

```
CPU ──APB──► 寄存器文件（bitblt_axi_slave）
                 │  写命令、读状态
                 ▼
            bitblt_top ──AXI 主──► Axi_Mux ──► DDR3
                 ▲                    ▲
                 │                    │
        扫描输出 ─┘                    └─ CPU 访存

⇒ 【控制通路】走 APB（CPU 写寄存器），数据量极小
⇒ 【数据通路】走 AXI（加速器读写 DDR3），是带宽消耗的全部来源
⇒ 两者在 bitblt_axi_slave 汇合：CPU 只碰寄存器，永不碰像素
```

**⇒ ⇒ 这个分工决定了后面所有设计：**CPU 每帧只写几个寄存器**（见 2.3.2），**而带宽全在 AXI 侧**，所以优化全部集中在突发效率上（见 2.2.1）。**

### 2.1.4 ⚠️ 一个必须先说清的约束：**带宽**

**⇒ 1080p60、32 位色深下，**仅仅把画面显示出来**就要占用：**

```
1920 × 1080 × 4 字节 × 60 Hz = 594 MB/s
DDR3 实测吞吐                = 1600 MB/s
⇒ 扫描输出占 37%
```

**⇒ ⇒ 而引擎还要在同一块 DDR3 上读写精灵数据。**⇒ 这个 37% 是本项目**所有设计的起点**，也是与同类工作最本质的区别（见 [53](53-同类工作调研与定位.md) §三）。**

**⇒ ⚠️ 注意这也是为什么不能简单说「做了个 1080p60 的图形加速器」——真正做的是**在 37% 带宽已被占用的前提下**，把精灵渲染塞进剩下的 63%。**

## 2.2 硬件系统介绍

### 2.2.1 硬件整体介绍

**⇒ ⚠️ 此处插入 **图 2 引擎内部框图**（`docs/figs/fig2-engine.svg`）**

**⇒ 加速器 `bitblt_top` 由 **10 个子模块**组成（另有顶层，共 11 个自写 RTL 模块）：**

| 模块 | 职责 | 关键接口 |
|---|---|---|
| **`bitblt_axi_slave`** | **寄存器文件：CPU 经 AXI 读写 30+ 个寄存器** | **⇒ 寄存器映射见 [34](34-架构总览.md) §四** |
| **⇒ `bitblt_sprite_state`** | **⇒ **精灵状态 RAM：256 槽**，每槽位置/速度/存活位** | **⇒ 输入：walker 的初始化与步进信号** |
| **⇒ `bitblt_sprite_walker`** | **⇒ **硬件遍历器**：读描述符、算地址、派发搬运** | **⇒ 输出 `blit_start` + 源/目标/宽高** |
| **⇒ `bitblt_addr_gen`** | **⇒ 把一次拷贝切成逐行的地址序列** | **⇒ 带边界检查（`oob`）与帧缓冲越界检查** |
| **⇒ `bitblt_dma_rd`** ×2** | **⇒ 读引擎：源图与目标背景**各一个**** | **⇒ 突发最长 256 拍 = 4096 字节** |
| **⇒ `bitblt_pixel_engine`** | **⇒ Alpha 混合与 Color Keying，**4 像素并行**** | **⇒ DSP48 实现精确 /255** |
| **⇒ `bitblt_dma_wr`** | **⇒ 写引擎：把混合结果写回帧缓冲** | **⇒ 支持字节使能（`wstrb`）** |
| **⇒ `bitblt_pulse_gen`** | **⇒ 把持续电平转成单周期脉冲** | **⇒ DMA 每行只触发一次搬运** |
| **⇒ `bitblt_monitor`** | **⇒ 片上状态监控：11 项异常粘滞位 + 饱和计数器** | **⇒ ⚠️ **它是功能与工程手段，不作为主要创新点**（[48](48-片上断言监控.md) 开头）** |
| **⇒ `bitblt_video_out`** | **⇒ 扫描输出：从帧缓冲读像素** | **⇒ 异步 FIFO 跨 100 MHz → 148.5 MHz** |

**⇒ **⇒ 而其中**三处设计决策**是这个引擎与常规实现的分界（依据见 [34](34-架构总览.md) §十）：**

| 决策 | 常规做法 | 我们的选择 | 依据 |
|---|---|---|---|
| **① 背景像素怎么取** | **⇒ 读-改-写：先读目标行进 BRAM，再读源行** | **⇒ **两个读引擎并行**（一个读源、一个读目标）** | **⇒ 串行会慢，且要行缓冲；并行则带宽换速度 —— 而带宽账算过：**余量足够**** |
| **⇒ ② 像素并行度** | **⇒ 位宽转换 128→32 位，**吞吐掉 4 倍**** | **⇒ **像素引擎改 4 像素/拍**** | **⇒ 代价是 DSP 从 3 增到 12（占 160 的 7.5%），换来满速** |
| **⇒ ③ DDR3 怎么接** | **⇒ 用官方 IP 或直接改互联** | **⇒ 复用工程自带的 `Axi_Mux`，**不加第六个从端口**** | **⇒ 五个从端口已满；加端口要改 X5 宏 + 仲裁 + 40 余处端口映射** |

**⇒ ⚠️ 第 ③ 条与**精灵遍历器共用源读引擎**是同一件事的两面** —— 遍历器只在 blit **之间**活动，而那正是源读引擎空闲时，所以两者**天然互斥**，共用一条通路而不冲突（见 `bitblt_sprite_walker.v` 头部注释）。

## 2.3 软件系统介绍

### 2.3.1 软件整体介绍

**⇒ 软件全部运行在片内 RISC-V 上（**裸机，无操作系统、无动态内存分配**），分四层：**

```
┌─────────────────────────────────────────────┐
│ 应用层   game.c（游戏逻辑：子弹/飞船/碰撞）    │
├─────────────────────────────────────────────┤
│ 输入层   game_input.c（按键 → 方向）          │
├─────────────────────────────────────────────┤
│ 驱动层   bitblt.h（寄存器访问 + 精灵接口 +    │
│          监控读取，全部 static inline）        │
├─────────────────────────────────────────────┤
│ BSP      EfxSapphireSoc（UART / 定时器 / PLIC）│
└─────────────────────────────────────────────┘
```

**⇒ ⚠️ **为什么全是 `static inline`**：驱动层是**寄存器操作的薄封装**，函数调用开销在每帧数百次的调用量下不可忽略；inline 后编译器可把多次寄存器写合并调度（见 `bitblt.h`）。**

**⇒ ⚠️ **为什么禁用动态内存**：嵌入式实时渲染中，`malloc` 的**最坏执行时间不可预测**，而帧率要求是硬的。精灵池用**固定数组 + 空闲链表**（`game_pool_alloc/free`）实现。**

### 2.3.2 软件各模块介绍

**⇒ 按模板要求「从顶层到底层逐次给出各函数的流程图及其关键输入、输出变量」，此处给出**关键函数的输入输出**（完整流程图见各源文件注释）：**

#### （1）应用层 `game.c`

| 函数 | 输入 | 输出 | 职责 |
|---|---|---|---|
| **`game_init`** | **—** | **—** | **⇒ 初始化精灵池、飞船、帧缓冲几何** |
| **⇒ `game_launch`** | **⇒ `slot, x, y, dir`** | **⇒ —** | **⇒ 发射一颗子弹，指定槽位与方向** |
| **⇒ `game_ship_step`** | **⇒ 按键方向（`game_input_poll`）** | **⇒ —** | **⇒ 移动飞船并更新其精灵状态** |
| **⇒ `game_frame`** | **⇒ —** | **⇒ **`spr_count`**** | **⇒ **每帧调用**：更新所有子弹位置、回收越界/命中者，返回本帧精灵数** |
| **⇒ `game_check_hits`** | **⇒ —** | **⇒ 命中数** | **⇒ 子弹 vs 飞船的**碰撞判定**（`game_hits` 为距离判据）** |
| **⇒ `game_reclaim`** | **⇒ `rt_words`（退休位图）** | **⇒ —** | **⇒ **回收硬件已判定退休的槽位**** —— 与硬件遍历器的闭环** |

**⇒ ⭐ `game_reclaim` 是软硬协同的关键**：硬件遍历器自动判定「精灵离开屏幕」并置退休位，**CPU 读回该位图并回收槽位**，而**不需要每帧扫描 256 个槽位**。

#### （2）输入层 `game_input.c`

| 函数 | 输入 | 输出 |
|---|---|---|
| **`game_input_init`** | **—** | **0 = 成功** |
| **⇒ `game_input_poll`** | **⇒ —** | **⇒ **方向索引 0..3**（不是 ASCII 码 —— 见 [47](47-游戏Demo实现与验证记录.md) 的记录）** |
| **⇒ `game_key_to_dir`** | **⇒ 按键字符** | **⇒ 方向索引** |

#### （3）驱动层 `bitblt.h`（节选，共 30 个 inline 函数）

| 分组 | 函数 | 关键参数 |
|---|---|---|
| **基础** | **`blt_write` / `blt_read`** | **⇒ 寄存器偏移、值** |
| **⇒ 拷贝** | **⇒ `blt_set_size` / `blt_start` / `blt_wait` / `blt_status`** | **⇒ 宽高、返回状态字** |
| **⇒ 精灵** | **⇒ `blt_spr_arm` / `blt_spr_desc` / `blt_spr_retired` / `blt_spr_find_retired` / `blt_spr_retire`** | **⇒ 描述符表基址、槽位、`blt_sprite_t`** |
| **⇒ 位置读回** | **⇒ `blt_spr_read_pos`** | **⇒ 槽位 → x, y** |
| **⇒ 扫描同步** | **⇒ `blt_scan_status` / `blt_scan_blanking` / `blt_scan_wait_blanking`** | **⇒ `max_polls`（有界，防止挂死）** |
| **⇒ 监控** | **⇒ `blt_mon_sticky` / `blt_mon_count` / `blt_mon_dump`** | **⇒ 11 项状态与计数器** |

**⇒ ⭐ CPU 每帧在图形侧的负担只有 **3 次寄存器写**：**

```c
blt_spr_arm(table_base, count);   // ① 表基址 + 精灵数   ② 使能位
blt_spr_disarm();                 // ③ 帧结束后关闭
⇒ 精灵数为 32 还是 256，CPU 负担不变 —— 这是硬件遍历的直接结果
```

#### （4）主流程 `main.c`

| 函数 | 职责 |
|---|---|
| **`main`** | **⇒ 初始化 → 跑 10 项自检 → 进入游戏主循环** |
| **⇒ `run_game`** | **⇒ 游戏循环：轮询输入 → `game_frame` → 等待扫描 → 翻页 → 更新屏幕帧率** |
| **⇒ `report`** | **⇒ **计算并打印帧率**（`cycles/frame` → `ms` → `fps`，定点，不引 libm）** |
| **⇒ `wait_frame`** | **⇒ 等待硬件帧计数变化** |
| **⇒ `sw_fill` / `sw_copy_sprite`** | **⇒ **纯 CPU 软件渲染**（用于赛题要求的软硬件帧率对比）** |
| **⇒ `trap`** | **⇒ 异常/中断入口（`trap.S` 保存现场后调用）** |

**⇒ ⚠️ **`trap` 有一条重要约束**（写在源码注释里）：中断处理程序**不得触碰 BitBlt 寄存器** —— 因为 `bitblt_axi_slave` 的读写共用一个 4 状态 FSM，ISR 与主路径的寄存器访问会互相破坏。因此 ISR 只置标志，主循环做其余的事。**

### 2.3.3 ⭐ 屏幕上实时显示的帧率对比（赛题硬性要求）

**⇒ 赛题原文要求：「能在**屏幕上实时对比显示**『纯软件 CPU 渲染』与『硬件加速渲染』的帧率差异」。**

**⇒ 实现方式：每帧把两行读数**画进正在被扫描输出的那个帧缓冲**（`main.c` 的 `run_game` 内）：**

```c
draw_num (dst, 16,  0, FB_W, 4u, ...);   // 分辨率
draw_text(dst, 56,  0, "x",   ...);
draw_num (dst, 72,  0, FB_H, 4u, ...);
draw_text(dst, 16, 16, "SW ", ...);      // 软件渲染帧率
draw_num (dst, 40, 16, swf, 5u, ...);
draw_text(dst, 16, 32, "HW ", ...);      // 硬件加速帧率
draw_num (dst, 40, 32, hwf, 5u, ...);
draw_text(dst, 16, 48, "SPR", ...);      // 同屏精灵数
draw_num (dst, 48, 48, N_SPR, 2u, ...);
```

**⇒ **⇒ 注意两点**：**
1. **分辨率与帧率**同时显示** —— 否则评委无法确认「这个帧率是在什么分辨率下达到的」
2. **⇒ 画在**正在被扫描的帧缓冲**里 —— 而不是打印到串口。多数实现只做后者，那不满足「屏幕上显示」的字面要求**

**⇒ ⚠️ 此项的**实际帧率数值需板上实测**（*冻结后填*）。**

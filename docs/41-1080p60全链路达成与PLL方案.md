## 一、PLL 方案

### 1.1 为什么 25 MHz 不行

```
约束 1：VCO = ref × D          （D = 反馈输出的 out_divider）
约束 2：pix_clk_fast = 5 × pix_clk   （TMDS 需要，out_div = 5 × out_div_fast）

要 pix_clk = 148.5：
    VCO = 25 × N = 148.5 × k
    ⇒ N = 5.94 k
    ⇒ k 必须是 50 的倍数才能使 N 为整数
    ⇒ k = 50 ⇒ VCO = 7425 MHz  ← 远超器件上限
```

**⇒ 这不是「余量不够」，是**整数分频集合里没有这个点**。** **⇒ 实测佐证：把 `multiplier` 从 1 改成 6 后，`interface` 直接报 `pll_rule_vco_freq: VCO frequency is out of range` 并拒绝生成。**

### 1.2 27 MHz 可以

```
N = 5.5 k
k = 20 ⇒ N = 110 ⇒ VCO = 27 × 110 = 2970 MHz
    pix_clk      = 2970 / 20 = 148.50 MHz
    pix_clk_fast = 2970 /  4 = 742.50 MHz
```

**⇒ VCO = 2970 MHz 与官方 `hdmi_rx2tx` demo 同值 ⇒ 在器件能力内。** **⇒ 27 MHz 来自板上晶振，引脚 `GPIOL_P_10`，此前**从未被本工程使用**（原设计只接了 `GPIOL_P_08` 的 25 MHz）。**

**⇒ 依据**：官方 `01_Ti60F225_key_demo/LED_8bit_Test.peri.xml` 同时使用 `gpio_clk_25m`(GPIOL_P_08) 与 `gpio_clk_27m`(GPIOL_P_10)；原理图 `Ti60F225A_V4_SCH.pdf` p9 标注 `CLK_25M` / `CLK_27M`（另有 p8 的 `CLK_50M`，但 50 MHz 同样无法整数比产生 148.5）。

### 1.3 反馈输出必须独立（这是卡最久的一点）

**⇒ 原配置 `feedback_clock_name="pix_clk"` ⇒ `pix_clk` 是反馈输出 ⇒ **它的频率恒等于参考频率**，改 `out_divider` 只能改变 `pix_clk_fast` 与它的比例，动不了 `pix_clk` 本身。** **⇒ 这正是「为什么改 `out_divider` 没用」的原因，也是我前面几轮判断失误的根源。**

**⇒ 修法：新增一个**专职反馈输出** `pll_fb`（`out_divider = 110`，`conn_type="gclk"`，不进 RTL），把 `feedback_clock_name` 指向它。**

**⇒ 最终结构：**

```
clk_27m (GPIOL_P_10, 27 MHz)
   └─ HDMI_PLL (PLL_BR0), VCO = 2970 MHz
        ├─ pll_fb        out_div 110  ⇒  27.00 MHz   （仅反馈，不输出）
        ├─ pix_clk       out_div  20  ⇒ 148.50 MHz
        └─ pix_clk_fast  out_div   4  ⇒ 742.51 MHz (90°)
```

**⇒ 公式验证（两个独立案例）：**

| 案例 | ref | 反馈 out_div | VCO | 输出 |
|---|---|---|---|---|
| **本工程改前** | **25** | **100** | **2500** | **2500/100 = 25 ✓（与 pt.sdc 的 40.000 ns 一致）** |
| **官方 hdmi_rx_pll** | **148.5** | **20** | **2970** | **2970/20 = 148.5 ✓、2970/4 = 742.5 ✓** |

## 二、供给侧改造（方案 B）

### 2.1 问题

**⇒ 原拆分器：收 1 拍 beat + 写 4 拍像素 = **5 拍/4 像素 = 0.8 像素/clk = 80 M 像素/s**。** **⇒ 1080p60 需要 **148.5 M 像素/s** ⇒ 缺口 86%。**

**⇒ 实测证据（关键）：`pclk` 提到 142.9 MHz 时，`lines seen` 只有 **89/148**，而 `errors` **仍为 0**。** **⇒ 原因：`de = de_raw & ~fifo_empty` ⇒ FIFO 空时 `de` 为低 ⇒ **丢失的行根本没被检查**。** **⇒ 所以「errors = 0」曾经是**假象**。**

### 2.2 改法

**⇒ FIFO 每项存 4 个 24 位像素（96 位）⇒ 一个 128 位 beat **一拍写完** ⇒ 4 像素/clk。** **⇒ `hold` / `split_cnt` / `splitting` 三个寄存器全部删除。** **⇒ 实测吞吐 20 M → **134 M 像素/s**（该数字含空闲，是下界）；`pclk` = 142.9 MHz 时行数满 149/148。**

### 2.3 读侧的三个坑（都踩过）

| 坑 | 现象 | 根因 |
|---|---|---|
| **读延迟** | **`rd_hold` 全是 `x`** | **`simple_dual_port_ram` 寄存读 ⇒ `rdata` 比 `re` 晚一拍（`docs/38` 已记，我又忘）⇒ 必须提前 2 拍发起读（`rd_px == 2`）** |
| **位宽** | **`got=0x060000` 而期望 1** | **`beat_rgb` 是 24 位/像素，输出却按 32 位步进切 ⇒ 跨了两个字段** |
| **预取重复** | **输出 `0,5,6,7,8…`（组 1 只出了一个像素）** | **`~rd_valid` 在启动窗口连续两拍为真 ⇒ 连发两次读 ⇒ 第二次覆盖第一次。加 `~prefetch_d`** |

### 2.4 消隐期归零的作用域

**⇒ 行首 `rd_px` 停在 3（行末状态）⇒ 下一行首像素取自上一行最后一组。** **⇒ 修法是归零 `rd_px`，但**作用域必须是帧**（`if (!v_active)`）而不是行（`if (!de_raw)`）。** **⇒ 用行级归零试过：一个行内的 `de_raw` 毛刺就会打断相位 ⇒ 输出 `...632,633,632,633,634...` 并丢掉 638/639，永久偏移 2 像素。**

## 三、三个「假绿灯」

**⇒ 这三个比功能本身更值得记 —— 它们意味着**当时的验证结果不可信**。**

| # | 现象 | 真相 |
|---|---|---|
| **1** | **`PASS=16` / `FULL CHAIN OK`** | **我三轮里一直往 `sys\rtl\video\` 复制 RTL（目录不存在），`Copy-Item` 每次报错而我没检查返回值。**所有绿灯测的都是旧代码**。修正后真实结果是 15/16** |
| **2** | **`tb_mux_video` 编译失败** | **先误诊为 `EFX_SRL8` 缺模型、再误诊为 `Axi_Mux` 通道数 —— 都不是。真因是方案 B 删掉的 `splitting`/`split_cnt`/`beat_accept` 被它层次化引用。`X4 → X5` 确实是个真隐患（`system_top` 接了 `I_S4_*`），但那是另一件事** |
| **3** | **拆段逻辑「已验证」** | **`tb_bitblt_video_out` 与 `tb_mux_video` 都是 640 宽（2560 B < 4096）⇒ 每行只发一段 ⇒ **「解除 ARLEN 限制」这条路径一次都没走过**。这是 `tb_video_split.v` 存在的原因** |

**⇒ 共同模式：绿灯亮在**错误的对象**上。判断依据是「我执行了某个动作」而非「该动作真的作用到了目标」。**

## 四、拆段验证（`tb/tb_video_split.v`）

**⇒ 1920 宽 = 7680 字节 = 480 beats ⇒ 超过 256 beats 上限 ⇒ 必须拆。** **⇒ 高度只用 4 行（拆分只取决于宽度），仿真代价极小。** **⇒ `fb_stride = 8192`（4 KB 倍数，满足 `cfg_bad` 要求）。**

**⇒ 期望与实测：**

```
段 0: araddr = base + row*8192 +    0,  arlen = 255  (256 beats, 4096 B)
段 1: araddr = base + row*8192 + 4096,  arlen = 223  (224 beats, 3584 B)
                              合计 480 beats = 1920 像素

实测：
  AR 0  row=0 seg=0  addr=80000000  arlen=255
  AR 1  row=0 seg=1  addr=80001000  arlen=223
  AR 2  row=1 seg=0  addr=80002000  arlen=255
  ...
  errors = 0    cfg_error = 0    RESULT: PASS
```

**⇒ 断言四条：每行 2 段、段内 beat 数、段间 +4096 / 行间 +8192 的地址递推、任何突发不跨 4 KB 且页对齐。**

## 五、`cfg_error` 合约（正反配对）

**⇒ `bitblt_video_out` 在 `fb_base` 或 `fb_stride` 非 4096 倍数时拒绝启动 —— 因为页拆分只在「每行都从页边界开始」时才能保证不跨界。** **⇒ 该检查此前**没有任何测试**（`tb_mux_video` 只是**偶然**踩到：它的 stride 是 `640×4 = 2560`，`cfg_bad` 拉高，`AR bursts S4` 停在 0）。**

**⇒ 现在期望值由测试台**实际施加的配置**导出，所以同一个测试台覆盖正反两面：**

| 运行 | stride | 期望 | 实测 |
|---|---|---|---|
| **默认** | **4096** | **不得报 `cfg_error`** | **`cfg_error seen=0`、`AR while bad=0` ⇒ PASS** |
| **`+stride=2560 +expect_cfg_error`** | **2560** | **必须报，且不得发任何 AR** | **`cfg_error seen=1`、`AR while bad=0` ⇒ PASS (cfg_error contract)** |
| **`+stride=2560`（无开关）** | **2560** | **（对照）** | **FAIL ⇒ 证明开关是必需的** |

**⇒ 负向用例必须带 `+expect_cfg_error`（它关闭像素校验，因为没有像素流是设计意图）。已作为 `$extraCases` 加进 `run-regression.ps1`，回归现在是 18 项。**

**⇒ 两个踩过的语法坑：`$value$plusargs` 缺格式码会直接报错（该用 `$test$plusargs`）；`$display` 里放三元运算符在 `-g2005` 下不可靠。**

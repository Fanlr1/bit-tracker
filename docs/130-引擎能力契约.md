### 2.2 CTRL.START 的快照语义（关键）

- 写 `CTRL` 且 bit0=1 的一刻，把**当前** 11 个参数字段（op,src,dst,size,ss,ds,color,alpha,key,clipx,clipy）拼成 **352 bit** 一次性压入 FIFO（`gfx_regs.v:237-240,346-352`）。
- 之后写的参数寄存器**不会**影响已经入队的命令；反之，**START 之前必须把 10 个参数写完**（`gfx.h:104-120` 的顺序）。
- 命令 FIFO 条目是 352 bit（**不是** docs/110 写的 128 bit / 12 参数）。
- **FIFO 满（level==8）时 START 被静默丢弃**：`if (w_data[0] && !fifo_full)`，没有错误位、没有中断，`DONE_CNT` 也不会变（`gfx_regs.v:348`）。驱动用 `gfx_slot()` 先等 `STATUS.FIFO_FULL` 清零（`gfx.h:89-92,109`），**游戏/新代码必须照此办理**。
- 【仿真】写 12 条命令（写通道被堵住）→ FIFO level=8、STATUS=0x813、解堵后 `DONE_CNT` 只 +9，前 9 条落盘、后 3 条**没有任何痕迹**。

### 2.3 如何正确等待（游戏唯一正确姿势）

| 目的 | 正确做法 | 依据 |
|---|---|---|
| 等某批命令全部完成 | 发命令前读 `DONE_CNT`=d0，发完后循环读直到 `DONE_CNT-d0==n` | `gfx_core.v:472`、`gfx.h:148-156` |
| 等引擎空闲 | 循环等 `STATUS.BUSY==0`（含 FIFO 非空，等价"全清空"） | `gfx_regs.v:254`、`gfx.h:158-166` |
| **不要**用 | `STATUS.DONE`（粘滞）、`STATUS.ERROR`（恒 0） | `gfx_regs.v:255,265` |
| 中断 | 写 `CTRL[1]`=1 使能；完成时 `irq_pend` 置位（**多次完成合并成 1 bit**），读 `STATUS` 清除 | `gfx_regs.v:251,411-419` |

> 驱动注意：`GFX_BARRIER()` 被显式定义为空（`gfx.h:102`，注释说明实测无差异）。因此"10 次参数写 + 1 次 START"依赖 AXI-Lite 写顺序到达；如出现参数错位，第一嫌疑就是这里（`gfx.h:94-101` 有历史记录）。

## 3. 六种 OP 的逐像素语义

### 3.1 pix_op 真值表（唯一真源）

| OP | 码 | 输出公式 | 读源? | 读背景(RMW)? | 备注 |
|---|---|---|---|---|---|
| FILL | 0 | `f = COLOR` | 否 | 否 | 源地址/源行距被忽略 |
| COPY | 1 | `f` | 是 | **否** | **完全忽略 KEY 与 ALPHA**（不透明拷贝） |
| BLEND | 2 | `mix565(f, b, ALPHA)` | 是 | 是 | 无 key 判断 |
| KEY | 3 | `(f==KEY) ? b : f` | 是 | 是 | 与 COPY_KEY **逐像素完全等价** |
| BLIT | 4 | `(f==KEY) ? b : mix565(f, b, ALPHA)` | 是 | 是 | key 判断在混合**之前** |
| COPY_KEY | 5 | `(f==KEY) ? b : f` | 是 | 是 | 去背标准路径 |

依据：`gfx_core.v:203-220`（pix_op 函数体：211 FILL、212 COPY、213 BLEND、214 KEY、215 BLIT、216 COPY_KEY）；`gfx_core.v:145`：

```verilog
wire use_bg = (op == OP_BLEND) | (op == OP_KEY) | (op == OP_BLIT) | (op == OP_COPY_KEY);
```

### 3.2 KEY 比较的时机（**混合之前**）

- 比较对象是**原始源像素** `f`（未经任何混合），比较发生后才决定走 `b` 还是 `mix565(...)`：`gfx_core.v:215`。
- **透明像素的语义 = "目标值保持不变"**，实现方式是**读-改-写**：先把 dst 同一位置读进 `bpx`（`gfx_core.v:391-410`，读事务 `rd2`），命中选择 `b` 写回（`gfx_core.v:236-238,250-251`）。所以：
  - **值**不变（不是写 key 色，也不是不写）；
  - **但读事务和写事务照付**：8×8 去背精灵比不透明拷贝多 **8 次背景读事务**（每行 1 次），约 **+3.4 µs/精灵**（见 §7）。
- 【仿真】COPY_KEY 8×8 紧凑源：读事务 9（1 源突发 + 8 背景），写 8；key 像素的 dst 值与命令前完全一致。

### 3.3 三个"等价命令"（可直接互换，代价完全相同）

| 等价组 | 说明 | 依据 |
|---|---|---|
| `OP_KEY` ≡ `OP_COPY_KEY` | RTL 中两者的 pix_op 与 `use_bg` 完全一样，**没有任何行为差异** | `gfx_core.v:214,216,145` |
| `OP_BLIT(ALPHA=255)` ≡ `OP_COPY_KEY` | α=255 时 `mix565(f,b,255)==f` 精确成立；key 分支两边都选 `b`；事务数相同 | 公式见 §3.4、**【仿真】** 64/64 像素一致且均为 9 读/8 写 |
| `OP_BLIT(ALPHA=0)` ≡ 空操作 | α=0 时 `mix565(f,b,0)==b` 精确成立，key 分支也是 `b` → 目标值全不变（但仍付 17 次事务） | `gfx_core.v:193-199`、**【仿真】** `blit_a0_nochange` 64/64 保持 |

> 结论：游戏里"去背"用 `COPY_KEY` 即可；需要半透明用 `BLIT`（带上同一个 key），**不要误以为 BLIT(255) 比 COPY_KEY 便宜**。

### 3.4 ALPHA 混合的精确公式（问题①的权威答案）

`gfx_core.v:185-201`：

```verilog
ia = 255 - a;
tr = f[15:11]*a + b[15:11]*ia + 18'd128;  tr = tr + (tr >> 8);
tg = f[10:5] *a + b[10:5] *ia + 18'd128;  tg = tg + (tg >> 8);
tb = f[4:0]  *a + b[4:0]  *ia + 18'd128;  tb = tb + (tb >> 8);
out = {tr[12:8], tg[13:8], tb[12:8]};
```

- **逐通道独立**：R5/G6/B5 各自做一次 8 bit 混合，**不跨通道进位**。
- 数学等价式（本文证明）：设 `S = f_ch*a + b_ch*(255-a)`（0 ≤ S ≤ 31×255 = 7905），则
  `out_ch = floor((S+128 + floor((S+128)/256))/256)` **≡ round(S/255)**（四舍五入，非截断）。
- **耗尽验证**：对全部可能的 S = 0..7905 逐一比对，**0 处偏差**；再对 6 组 (bg,alpha) 做 65536 像素全扫，**0 处偏差**（宿主机 JS 复核 + tb 内 `alpha_vs_exact_round = 0/512`）。⇒ 可直接把公式写成 `round((f*a + b*(255-a))/255)` 用于素材/参考模型。
- **端点恒等**：`a=255 → out=f`（精确）、`a=0 → out=b`（精确），全色域验证 0 例外 ⇒ α=255 的 BLIT 与 COPY_KEY/COPY 同结果；α=0 的 BLIT 是纯空操作。
- **alpha 是整条命令的全局常数**（寄存器 0x28 一个 8 bit），RGB565 没有逐像素 alpha；要"软边"只能拆多次命令或用预先烘焙的多级精灵。

【仿真】8×8 BLEND α=128，fg=0x1234 / bg 渐变，逐像素与上述公式一致（64/64）；`alpha_sweep` 8 个 α 全对。

### 3.5 写回细节（为什么"边界像素不被破坏"）

- 写地址按 16 B 对齐（`gfx_core.v:160`），每拍 16 bit/像素 的 `wstrb` 逐通道屏蔽矩形外像素：`wr_mask[2*gw +: 2] = ((ps>=0)&&(ps<n)) ? 2'b11 : 2'b00`（`gfx_core.v:249-251,256`）。
- 因此**目的矩形之外的像素不会被写破坏**，即使它和矩形共用同一个 16 B beat。【仿真】非 16B 对齐 dst 的 COPY/COPY_KEY 像素级正确。

## 4. 尺寸 / 地址 / 对齐 / 越界 / 裁剪

### 4.1 尺寸 w,h

| 项 | 规则 | 依据 |
|---|---|---|
| 位宽 | w、h 各 **16 bit**（1..65535） | `gfx_core.v:290-291` |
| 0 值 | w==0 或 h==0 → **空命令**：不读不写，只 `DONE_CNT+1` | `gfx_core.v:301-302`、【仿真】aw=0、dst 未动 |
| 行内分段 | 每段最多 **112 像素**；段数 = ceil(w/112)；1920 宽 = **18 段/行** | `gfx_core.v:102,151-152,455-469`、【仿真】fill 1920×8：aw=144=18×8 |
| 行数 | 逐行处理，无上限（65535） | `gfx_core.v:455-469` |
| 段地址 | 段起点按 16B 下取整，段内像素偏移 = `(addr&15)>>1` | `gfx_core.v:159-162` |

### 4.2 stride（行距）

- `SRC_STRIDE/DST_STRIDE` 都是低 16 bit 有效（最大 65535 B），**任意值可用**，无对齐要求（`gfx_core.v:292-293`）。
- 有效地址：`row_src = src + row*ss`、`row_dst = dst + row*ds`（`gfx_core.v:154-155`）。
- 语义：`ds < w*2` → 行重叠（后行覆盖前行）；`ds > w*2` → 行间留空隙。
- 扫描输出侧 `FB_STRIDE` **必须 16B 整数倍**：行首地址 `front + row*fb_stride` 被强行 16B 对齐（`gfx_mem.v:159`），若 stride 不整 16，每行 16B 相位会变 → **每行水平错位不同、末尾像素被切**（RTL 不做补偿）。推荐 4096；当前 demo 用 3840（=1920×2，仍是 16 的倍数）。

### 4.3 地址对齐要求（汇总）

| 对象 | 要求 | 不满足时 | 依据 |
|---|---|---|---|
| 引擎 SRC/DST 基址 | **2 字节对齐**（偶数地址） | 奇数地址被静默当偶数（bit0 丢弃）→ 数据偏 1 像素 | `gfx_core.v:161-162`、【仿真】 |
| 引擎**紧凑源** SRC | **16 字节对齐** | 画面整体左移 `(src&15)/2` 像素（0–7 px），**无任何报错** | `gfx_core.v:318,320,334`、【仿真】src+8 → 4/64 命中 |
| 引擎 SRC/DST 行内任意 x | 2B 对齐即可（偶数 x） | 同上偏 1 像素 | `gfx_core.v:156-162` |
| 扫描 FB_NEXT/BASE | 16B 对齐（行首被 align16） | 行首像素偏移错位 | `gfx_mem.v:159` |
| 扫描 FB_STRIDE | 16 的倍数（强烈建议 4096） | 每行水平错位 | `gfx_scanout.v:406`、`gfx_mem.v:159` |
| AXI 突发 | 引擎读/写 ≤15 beats（240 B）；扫描行 240 beats（3840 B）；均 16B 地址对齐 | 4KB 跨界未被检查（见 §4.6） | `gfx_core.v:166-169`、`gfx_mem.v:159,265`、`gfx_scanout.v:77,322` |

### 4.4 越界（OOB）保护：只保护 dst，整条拒绝

`gfx_core.v:303-309`：

```verilog
end else if ((cmd_data[287:256] < FB_POOL_LO) ||                       // dst 起点
             ((cmd_data[287:256] + ((h-1) * ds) + (w<<1)) >= FB_POOL_HI)) begin
    err_addr <= dst;  clipped <= 1'b1;  state <= S_FIN;               // 不写任何字节
```

| 问题 | 答案 | 依据 |
|---|---|---|
| 越界是否部分写？ | **不**。整条命令在开始时被拒，0 个写事务 | `gfx_core.v:303-309`、【仿真】OOB 时 aw=0 |
| 置什么位？ | `STATUS.CLIPPED=1`，`ERR_ADDR=dst`；`ERROR` 仍为 0；`DONE_CNT+1` | 同上、`gfx_core.v:307-308,472` |
| 边界哪侧？ | `dst < 0x0800_0000` 或 `dst + (h-1)*ds + w*2 >= 0x0C00_0000`（**末字节在 0x0BFF_FFFF 也会被拒**，保守 1 字节） | 同上 |
| src 越界？ | **完全不检查**（src 在池外/超 DDR 也照读，可能挂死或读到垃圾） | 源码中只有 dst 分支 |
| 会不会写穿自己的矩形？ | "写穿但不越池"：引擎不认帧缓冲逻辑边界，x+w>FB_W 时会写到下一行行首 | `gfx_core.v:156-157` |

### 4.5 CLIP：**没有实现**（必须软件钳位）

- `CLIP_X/CLIP_Y` 只被快照进命令（`gfx_regs.v:237-240`），core 里**没有任何** `cmd_data[63:0]` 的使用（`gfx_core.v:14-15` 注释直接写明 "driver bookkeeping, not used by the engine"）。
- 因此：
  - 不设置 CLIP ≠ "无限"（而是"根本没这个功能"）；
  - **越界不会被裁剪**，只会因为 dst 越出 64 MiB 池而被整条拒绝；
  - 游戏必须自己做 `x = min(max(x,0), FB_W-w)`、`y = min(max(y,0), FB_H-h)` 的钳位，否则子弹飞出右边会从下一行左边钻出来。
- `CLIPPED` 位的真实含义 = **"这条命令因 dst 越池被拒"**，不是"被裁剪过"。
- `CLIPPED` 何时清除：**下一条命令被接收（S_IDLE 进入新命令）时清零**（`gfx_core.v:300`）。所以想用 CLIPPED 判定 OOB，必须在发下一条命令之前读它。【仿真】OOB 后置 1，随后一条正常命令使其回 0。

### 4.6 4KB 跨界（文档声称已避免，实际未检查）

- `docs/110:48` 声称"突发 ≤16 beats 且不跨 4KB（行 stride 4KB 对齐，天然满足）"。**实际**：
  - 引擎读/写突发确实 ≤15 beats，但**没有任何跨 4KB 检查**（`gfx_mem.v:159,265` 只做 16B 对齐）；
  - 扫描行突发是 **240 beats = 3840 B**，一次读一行（`gfx_scanout.v:322`、`gfx_mem.v:35`），只要 `FB_STRIDE % 4096 != 0` 就必然跨 4KB；
  - **当前 demo FB_STRIDE = 1920×2 = 3840，即每行都跨 4KB**，上板实测正常（从设备/互联容忍该行为）。
- 结论：可继续用 3840（实测 OK），但这是"经验可行"而非"契约保证"；要严格合规把 `FB_STRIDE` 改成 4096（显示内容不变，每行多 256B 填充）。

## 5. 紧凑源路径（`spx_mode`）——问题④的权威答案

### 5.1 实际触发条件（注意 RTL 位切片与文档/交接说法不同）

`gfx_core.v:316-322` 原文：

```verilog
if ((cmd_data[322:320] != OP_FILL) &&                              // (a) 非 FILL
    (cmd_data[207:192] == (cmd_data[239:224] << 1)) &&            // (b) src_stride == w*2
    ((cmd_data[239:224] * cmd_data[255:240]) <= 16'd128) &&       // (c) w*h <= 128
    (cmd_data[319:316] == 4'd0)) begin                            // (d) 实为 src[31:28]==0
    spx_mode <= 1'b1;  spx_off <= cmd_data[319:316] >> 1; ...
```

| 条件 | 语义 | 备注 |
|---|---|---|
| (a) op != FILL | FILL 不需要源 | — |
| (b) `SRC_STRIDE == w*2` | 源行**紧密相邻**（整精灵连续） | 图集里行距 > w*2 的精灵**不触发** |
| (c) `w*h <= 128` | 整精灵装得下 128 深暂存数组 | 8×8=64 ✓、16×8=128 ✓、16×16=256 ✗ |
| (d) `cmd_data[319:316]==0` | **实际比较的是 src[31:28]**（^ 位切片写错，本意 src[3:0]）→ 对 `0x08xxxxxx` 恒真 | ⇒ **紧凑源并不真正检查 16B 对齐**；`spx_off` 也恒为 0 |

依据：`gfx_core.v:318,320`；字段布局见 `gfx_core.v:4-15`（src 在 [319:288]）；历史修补脚本 `work/fix_spxreq.py`（曾把 `cmd_data` 改成锁存 `src`）佐证本意。

### 5.2 它改变了什么？

| 维度 | 普通路径 | 紧凑源路径 | 依据 |
|---|---|---|---|
| 源读事务数 | **每行 1 次**（宽精灵每行多段） | **整个精灵 1 次**突发（ceil(w*h/8) beats） | `gfx_core.v:370-389` vs `332-352`、**【仿真】** 8×8：8→1 |
| 背景读事务数 | 每行每段 1 次 | **不变** | `gfx_core.v:364-367,391-410` |
| 写事务数 | 每行每段 1 次 | **不变** | `gfx_core.v:425-453` |
| 写数据量 | 不变 | 不变 | — |
| 代价效果 | 8×8 精灵：源读 8→1，单精灵省 ≈2.9 µs | 交接-0415:26：2048 精灵 33→27.4 ms | 交接-20261029-0415:23-28 |

⇒ **它只减少"源读事务数"**（每精灵省 rows-1 次），不减少背景读、不减少写、不改变像素语义。

### 5.3 隐藏的正确性前提（交接文档完全没写）

紧凑源把整精灵一次性读入 128 深数组，再用 `p + soff + spx_row` 索引（`gfx_core.v:230,144`）。推导 + 仿真得到**未写进条件 (a)-(d) 的隐藏前提**：

| # | 隐藏前提 | 违反后果 | 【仿真】证据 |
|---|---|---|---|
| H1 | **w 必须是 8 的倍数** | 第 r 行索引偏移 `(r*w mod 8)` ≠ 0 → 每行错位 `(r*w) mod 8` 像素；行 0 对、其它行错 | 10×8（w·h=80 ≤128，条件全满足）→ **60/80 像素错**，行 0、4 正确，行 1/2/3/5/6/7 各自错 `r*10 mod 8` |
| H2 | **w <= 112**（一行只占 1 段） | 第 2 段起少了 `xdone` 偏移，段内读到精灵开头像素 | 128×1（w·h=128 满足上限）→ **16/128 像素错**（像素 112–127 变成 0–15） |
| H3 | **src 必须 16B 对齐** | 见 §4.3，整图左移 `(src&15)/2` 像素 | src+8 → 4/64 像素等于意图（即平移 4 px） |
| H4 | （已由条件 (b) 保证）`SRC_STRIDE == w*2` | 行间数据错 | 8×8 用 ss=32 → 自动退回普通路径（读事务 16），结果正确 |

**⇒ 安全使用规则（游戏只需遵守三条）**：
1. 精灵宽度取 **8 的倍数且 ≤112**（8、16、24、…、104、112）；
2. 精灵在 DDR 中**整块连续**（stride = w×2），起始地址 **16B 对齐**；
3. 像素总数 ≤128。

### 5.4 尺寸速查（★=紧凑源可用且正确）

| w×h | w·h | 紧凑源? | 说明 |
|---|---|---|---|
| **8×8** | 64 | ★ 可用（**当前 demo 即此**） | 1 源读 + 8 背景读 + 8 写 = 17 事务 |
| **16×8** | 128 | ★ 可用（**推荐 16×16 拆两半**） | 同上 17 事务，【仿真】像素级正确 |
| **16×16** | 256 | ✗（>128） | 普通路径：16 源读 + 16 背景读 + 16 写 = 48 事务 |
| 24×5、32×4、40×3、48×2、64×2 | ≤128 | ★ 理论可用（w 为 8 的倍数且 ≤112） | 冷门尺寸，未上板验证 |
| 104×1、112×1 | ≤128 | ★ 理论可用 | 单行，未实测（在 H1/H2 内） |
| 128×1 | 128 | ✗ **错误！**（违反 H2） | 【仿真】坏 |
| 10×8、12×8… | ≤128 | ✗ **错误！**（违反 H1） | 【仿真】10×8 坏 |
| 16×9、17×8… | >128 | ✗ 自动退回普通路径 | 结果正确（**【仿真】** 16×9：ar=18） |

### 7.4 8×8 / 16×16 / 32×32 精灵估算（**问题①的量化答案**）

按"游戏帧 = 擦旧位置 + 画新位置"：

| 精灵 | 命令组合 | 事务数 | 估算 | 相对 8×8 | 备注 |
|---|---|---|---|---|---|
| **8×8 去背** | FILL 8×8 + COPY_KEY 紧凑 | 8 + 17 = **25** | **≈10.7 µs**（实测 10.4–10.5） | **1.00×** | 当前 demo 用法 |
| 8×8 不透明 | FILL 8×8 + COPY 紧凑 | 8 + 9 = 17 | ≈7.3 µs | 0.68× | 仅当该精灵**不会与其它动态元素重叠**（否则透明区盖掉别人） |
| **16×16 去背** | FILL 16×16 + COPY_KEY 普通 | 16 + 48 = **64** | **≈28 µs**（画 ≈21 + 擦 ≈7） | **2.6×** | 完整支持，**【仿真】** 像素级 PASS |
| 16×16 去背（拆分） | FILL 16×16 + 2×COPY_KEY 16×8 紧凑 | 16 + 34 = 50 | **≈22 µs** | 2.0× | **推荐**：省 ~21%，【仿真】像素级 PASS |
| 16×16 不透明（拆分） | FILL + 2×COPY 16×8 紧凑 | 16 + 18 = 34 | ≈15 µs | 1.4× | 不透明前提同 8×8 |
| 32×32（单命令，去背） | FILL 32×32 + COPY_KEY 32×32 | 32 + 96 = 128 | **≈58 µs** | 5.4× | 源码支持任意 w×h；仿真只测过 16×16 |
| 32×32（4 个 16×16 瓦片） | 4×(FILL+COPY_KEY) | 4×64 = 256 | ≈112 µs | 10.4× | **不要这样做**，拆瓦片反而贵一倍 |

> Boss（32×32）**必须**把 4 张 16×16 素材在 DDR 里拼成连续的 32×32（stride=64）后**用一条命令**画；按 4 个 16×16 各发一条命令会慢 2 倍。
> 上表"事务数"均在仿真中逐一数出；耗时用 §7.2 模型换算（16×16 未上板验证，见 §12）。

## 8. 双缓冲：FB_COMMIT / FB_ACCEPTED（问题⑧的权威答案）

### 8.1 flip 到底在什么时刻生效

1. 写 `FB_COMMIT=1`（脉冲）→ 扫描器把当前 `FB_NEXT`/`FB_SEQ` 锁进 `commit_base/commit_seq`（`gfx_scanout.v:380-384`）。
2. 扫描器**只在取"帧的第一行（row 0）"时**应用：`front <= commit_base; scan_accepted <= commit_seq`（`gfx_scanout.v:394-398`，触发条件 `req_frame_p` = 预取行号 0）。
3. 实际显示在 `y=0` 时（该帧行 0 被扫描输出）。由于行预取最多提前 7 行（`gfx_scanout.v:280-289`），**flip 最迟在下一个帧首被吃下**，不会出现半帧混合（每行带 epoch 标签，`gfx_scanout.v:104-114`）。

【仿真】`tb_scan_flip.v`：commit 后立刻读 `FB_ACCEPTED` 仍为 0；下一次帧首变为 1，`front_now` 同步变成新页基址。

### 8.2 连续 flip（能不能连发？）

- **能写**，但**只有最后一次生效**：`commit_pend/commit_base/commit_seq` 每次 commit 都被覆盖（`gfx_scanout.v:380-384` 无"已 pending"判断），同一帧内连发 N 次 = 只保留最后一份。
- **中间 seq 永远不会出现在 `FB_ACCEPTED`**。【仿真】accepted 0→1 后连发 seq=2、seq=3 → accepted 直接 1→3（2 被跳过），`front` = seq3 的 base。
- 一帧一次 commit 则每次都生效（【仿真】accepted 3→4→5，各隔一帧）。
- ⇒ 游戏协议：**每帧最多 commit 一次**；误发两次可能让"等 accept"的代码永远等不到中间 seq（卡死在 `while(FB_ACCEPTED != seq)`）。

### 8.3 CPU 何时可以安全画 back buffer

- **等 `FB_ACCEPTED == 你写的 seq` 之后**。此时扫描器已切到新 front，旧 front 不再被读（epoch 门控保证新帧不混旧行），CPU 可以安全地把旧 front 当 back buffer 画。
- 【仿真】`tb_gfx_scanout` 的检查方式与此一致（等 accepted==7 后才按新页比对像素，PASS）。
- 若 commit 后还没 accept 就写旧 front：扫描器可能仍在取旧页的行（最多提前 7 行），会造成**该页数据错**（不是屏幕撕裂，是帧数据错）。
- `FB_ACCEPTED` 是 32 bit 序号；扫描器**只增不减**，只反映"最后被接受的 seq"。

### 8.4 其它 FB 事实

| 项 | 事实 | 依据 |
|---|---|---|
| FB_BASE 有用吗 | **没用**。front 复位值硬编码 `0x0800_0000`，之后只由 commit 改 | `gfx_scanout.v:37,336,395` |
| FB_SIZE 有用吗 | **没用**（`fb_w/fb_h` 端口未使用） | `gfx_scanout.v:39-40` |
| FB_STRIDE | 有用，每行地址 = `front + row*stride` | `gfx_scanout.v:406` |
| FB_CFG.enable | 有用；=0 时扫描器不取行（屏黑）且不统计欠载 | `gfx_scanout.v:399-401` |
| 一帧从哪读 | 固定读 1920 px = 240 beats、1080 行（与 FB_SIZE 无关） | `gfx_scanout.v:77,322` |
| 首帧行为 | 复位后 front=0x0800_0000，enable=1 后直接扫该页（上电要先把该页画好或立刻 commit） | `gfx_scanout.v:336` |

### 8.5 撕裂防护机制（为什么不用 CPU 等 vblank）

- 每个行 bank 带 **epoch 标签**：行数据 epoch 必须等于当前帧 epoch 才显示（`gfx_scanout.v:112-114`），epoch 每帧结束 +1（`gfx_scanout.v:261`）。
- 行首锁存 `row_ok`，整行统一（`gfx_scanout.v:247`），不会半行新半行旧。
- ⇒ flip 只可能发生在帧边界，**不存在"上半屏旧帧、下半屏新帧"**。交接-20261029-1125:19 "commit/accept 帧首生效（无撕裂）" 与此一致。

### 8.6 欠载（underrun）行为

- 行数据没及时到达 → **不再输出黑行**，而是**重复上一行**（当前工作区未提交改动：`gfx_scanout.v:164-172`），同时 `SCAN_UNDERRUNS + 1`（`gfx_scanout.v:248-251`）。8 bank + 提前 7 行预取（`gfx_scanout.v:280-289`）使容错窗口 ≈29.6 µs（模块头注释 `gfx_scanout.v:5-11`）。
- 游戏里可把 `SCAN_UNDERRUNS` 作为"画质健康度"读数（交接-1125:40 提到 rows/frame=37.8）。

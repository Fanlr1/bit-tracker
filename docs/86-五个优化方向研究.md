## 一、方向 1：COPY/fill 跳过目标读（本轮主体）

### 1.1 依据

pixel_engine 的 COPY 是 "pass the source pixel through"，FILL 用寄存器里的颜色 ——
**两者都不读 `in_bg`**（rtl/bitblt_pixel_engine.v:4）。
而每精灵 38.99 次往返里，**目标读 16.31 次（41.8%）**，行往返又占每精灵成本 **84.5%**（docs/80）
⇒ 对 COPY/FILL，这一项是**纯浪费**。

**docs/80 曾把"目标读+写 83.6%"记为"结构性"——那个判断只对 alpha/blend 成立。**

### 1.2 实现（已完成，已回退）

```verilog
wire bg_needed       = (reg_op[2:0] > 3'd1);          // 0=COPY 1=FILL 不需要背景
wire dst_start_g     = dst_start & bg_needed;         // 不启动目标读引擎
wire rd_dst_done_eff = bg_needed ? rd_dst_done : 1'b1;// 行完成不等它
wire px_in_valid     = bg_needed ? (src_v & dst_v) : src_v;
```

**★ 陷阱（已踩）**：这三个 wire **必须声明在首个使用点之前**。
第一版放在 `all_done` 附近（第 976 行），而 `.start(dst_start_g)` 在第 729 行 ——
构成**向后引用的隐式声明**：iverilog 默认静默，**只有回归脚本的 `-Wall` 抓到**
（`tb_bitblt_top.v FATAL: 1 implicit declaration`）。

### 1.3 实测（板上，`work/logs/skipbg-run1.txt`）

| 项 | 改动前 | 改动后 | 结论 |
|---|---|---|---|
| **`blt_fill` 全屏填充** | 1,313,036 拍/帧 | **1,065,709 拍/帧** | **−18.8% ✅ 机制有效** |
| `copy-readback-1000x` | 0 失配 | **0 失配** | COPY 数据仍正确 ✅ |
| blend/alpha 用例 | PASS | **PASS** | op≥2 仍读背景 ✅ |
| **§6 动画段（sprite 路径）** | ~1.5M 拍/帧 | **440,002,075 拍/帧** | **×300 ❌ 灾难性** |

**⇒ 应用在动画段被拖垮（220 s 捕获只跑到第 45 帧），密度扫描根本没跑到。**

### 1.4 根因定位（本轮推进，仍未修好）

**症状量化（而不是"慢了 300 倍"那个粗略说法）**：

| 版本 | §6 动画段 `hw`（32 精灵/帧）|
|---|---|
| 正常（565 版）| **2,220 拍/帧** |
| skipbg 版 | **440,002,075 拍/帧** ⇒ **×198,000** |

`440,002,075 / 32 ≈ 1,375 万拍/精灵` —— **这是"每个精灵都让 `blt_wait()` 超时"的特征**，
不是"算得慢"。软件侧的 `blt_wait()` 轮询 `BLT_ST_BUSY`，超时后继续（bitblt.h:157-166）⇒
**说明 `bitblt_top` 的 `busy` 卡在 1**。

**`busy` 的组成**（rtl/bitblt_top.v:1106）：
```verilog
assign busy = addr_busy | rd_src_busy | rd_dst_busy | wr_busy | spr_busy;
```
⇒ **头号嫌疑是 `rd_dst_busy`**：目标读被 `dst_start_g` 关掉之后，它的 `busy` 没有干净地落下来。

已排除的：
- `rd_dst_done` 只有 3 处使用（line 984/1012/1017），**都已用 `rd_dst_done_eff` 覆盖**；
- walker 的 `blit_done` 接的是 `addr_done`，与目标读无关；
- `sprite_state` 的 `step_en`/`frame_done` 由 walker 驱动，与目标读无关。

**仿真不复现**：消融版（完全停掉目标读）在 `tb_bitblt_top` 里反而**快 4.6%**
（2,610,776,000 ps vs 2,736,116,000 ps），P4 段 AR 数相同（186）。
⇒ **这是板上特有的（真实 DDR 交互/反压）**，纯 RTL 仿真定位不了。

### 1.4.1 下一步：二分判定实验（便宜、决定性）

把 `bg_needed` 拆成两半，分别生效：

| 变体 | `dst_start` | 像素通路等 dst | 若结果正常 | 若结果仍慢 |
|---|---|---|---|---|
| **A** | **照常启动** | 不等（`px_in_valid = src`）| 故障在"跳过 dst_start"⇒ 查 `rd_dst_busy` 的落下条件 | 故障在"像素通路不等 dst" |
| **B** | 跳过 | **照常等** | —（会死等，仅作对照）| — |

**变体 A 已做，结果：仿真里就失败（9 errors）。**

**⇒ 这本身是决定性的**：**"目标读照跑、只是像素引擎不等它"是行不通的** ——
`unp_dst` 的数据流是靠像素引擎的 `px_ready` 取走的，不等它就会把 dst 流和像素流水错开。
**所以跳过目标读必须"连目标读引擎一起停掉"**（那就是 skipbg 版，它在仿真里是干净的：23 PASS / 0 FAIL）。

**⇒ 两条路的状态收敛为一条**：
| 做法 | 仿真 | 板上 |
|---|---|---|
| skipbg（引擎一起停）| ✅ 23 PASS / 0 FAIL | ❌ 每精灵 blt_wait 超时（`busy` 恒 1）|
| 变体 A（只不等）| ❌ 9 errors | （不必上板）|

**下一步就一件事**：**让 `rd_dst_busy` 在"目标读从不被 start"时干净地落下来** ——
读 `bitblt_dma_rd` 的 `busy`/`state` 复位条件，找出它在没有 start 的情况下为何仍为 1。
**这是纯 RTL 问题，可以在仿真里量 `rd_dst_busy`（它不依赖 DDR 延迟，仿真能测）。**

### 1.5 回退

`rtl/bitblt_top.v` 已从 `.bak-20261016-before-skipbg` 恢复，并重新综合上板，
**板上恢复为已验证的 4096 表 / 100 MHz / 2,240 精灵版本。**

### 1.4.2 第二次尝试也失败（含 dst 解耦）

按 1.4.1 的分析补上了对称的一半：

```verilog
assign unp_dst_px_ready = bg_needed ? (px_in_ready & unp_src_px_valid) : px_in_ready;
```

**推理**：目标读引擎的 `S_DONE` 要等 `!fifo_empty`（bitblt_dma_rd.v:467），
而 dst 的 unpacker 只在源有像素时才取数 ⇒ 源一空，dst 的 FIFO 永远排不空 ⇒ 卡在 S_DONE。

**实测：仍然失败** —— `hw = 440,002,241`（第一次是 440,002,075，几乎相同）。
fill 依旧 −18.8%（1,065,699），readback 依旧 0 失配。

**⇒ 排除的假设（两条都有实验）**：

| # | 假设 | 怎么排除的 |
|---|---|---|
| 1 | `rd_dst_done` 有别的使用者 | 全项目只有 3 处（984/1012/1017），都已覆盖 |
| 2 | dst unpacker 的跨流耦合 | 已解耦，症状一字未变 |

**⇒ 症状对代码改动"不敏感"，说明真正的阻塞不在这一层。**
两个 440,002,xxx 几乎相等，且 `2^32 - 440,002,075 = 3,854,965,221` ⇒
**每帧真的阻塞约 38.5 秒**（`cycles()` 回绕），不是计数 artefact。

### 1.4.3 ★ 下一步必须是"先加可观测性"，而不是再猜

`busy = addr_busy | rd_src_busy | rd_dst_busy | wr_busy | spr_busy` 有 5 个分量，
**目前没有任何一个能在板上单独观测** —— 这就是两次盲改都失败的原因。

**已有现成工具**：`bitblt_monitor`（片上断言监控）在探针里已经打印
`rd0_AR_wedged / rd1_AR_wedged / sticky / short_cnt`，
**它就是为此存在的**。下一次上板（skipbg 版）应当：
1. 先读 monitor 的 wedged 位与 sticky；
2. 若都干净 ⇒ 说明卡的不是 AXI 读通道，而是 `spr_busy`（walker）或 `wr_busy`；
3. 再据此缩小到具体状态机。

**⇒ 在此之前不要再改 RTL 猜。**

## 二·补、★★ 重大修正：sprite 的"20 万倍慢"是【间歇性】的，与 skipbg 无关

同一批日志的横向对照（`work/logs/`）：

| 日志 | RTL | hardware fill | 动画段 hw |
|---|---|---|---|
| `565-run3-lines` | 无 skipbg | 1,313,036 | **4,776** ✅ |
| `rc` | 回退版 | 1,313,036 | **4,793** ✅ |
| **`rc2`** | **回退版（与 rc 同一个 bit）** | 1,313,033 | **440,002,708** ❌ |
| `sg` | skipbg v1 | 1,065,709 | 440,002,877 |
| `sb2` | skipbg v2 | 1,065,699 | 440,002,876 |

**⇒ 两个结论**：

1. **fill 的 −18.8% 是真实且干净隔离的**：1,065,7xx（skipbg 两次）对 1,313,03x（其余三次）。
   **这一条收益成立。**
2. **sprite 的 440,002,xxx 是【间歇性】的** —— 回退版两次跑出 4,793 与 440,002,708，
   **同一个比特流、同一份 flash 软件，差 20 万倍**。
   ⇒ **它与 skipbg 无关**，之前把它记成"skipbg 的副作用"是错的。

推算：440,002,708 / 32 精灵 ≈ **13,750,084 拍/精灵 ≈ 137 ms**，
而 `BLT_WAIT_LIMIT = 20,000,000`（bitblt.h:152）⇒ **没有触发超时** ⇒
引擎是**真的在算/等这么久**，不是超时跳过。机制未定。

## 二·补2、★ 方法论：板上 A/B 之前必须先证明【基线可重复】

**本轮最大的教训**：我拿"改动前 2,220 / 改动后 440,002,075"当作 A/B 结论，
但**基线本身是不可重复的**（同一版本两次 4,793 与 440,002,708）。
⇒ **这类现象会伪造出任何你想要的结论。**

**规则（写给下一个会话）**：
1. 每个板上配置**至少跑两次**，先确认自身可重复，再做对比；
2. 出现"整数量级"的差异（10× 以上）时，**先怀疑板级状态**（DDR 校准、上电时序、
   冷启动与否），而不是先怀疑 RTL；
3. **回退也不等于复位**：反复重配置 FPGA 并不能把板子带回同一状态，
   必要时需要**真正的断电冷启动**（我做不到，需要人来）。

## 二·补3、★ 基线可重复性实测：**3 次里只有 1 次正常**

同一个已验证配置（4096 表 / 100 MHz / 565 全链路，比特流与 flash 都未变）连跑三次：

| 运行 | hardware fill | 动画段 hw | 结论 |
|---|---|---|---|
| base-1 | 1,313,036 | **4,820** | ✅ 正常 |
| base-2 | 1,313,036 | **440,002,898** | ❌ 慢 |
| base-3 | 1,313,033 | **440,002,906** | ❌ 慢 |

**两个慢值只差 8**（440,002,898 与 440,002,906）⇒ **慢态是一个【确定性的状态】，不是随机噪声**
（噪声会散开；这里每次都是同一个 440,002,9xx）。

| 现象 | 结论 |
|---|---|
| **fill 三次都正常**（1,313,03x）| **fill 的 A/B 一直可信**，不受此现象影响 |
| **sprite 路径 1/3 正常** | **凡是涉及 sprite / 密度扫描的板上对比，单次结果不可信** |
| 慢态下每精灵 ≈ 13,750,090 拍 | 未触发 `BLT_WAIT_LIMIT`(20M)，是**真的算了这么久**，机制未定 |

### 对策（本次采用）

**每个板上配置跑 3~5 次，只要出现一次正常态就取那一次做对比** ——
因为慢态是整次运行的性质（一旦进入就全程如此），而不是逐帧抖动。

**⇒ 这也是重判方向 #1 的前提**：skipbg 之前"每次都慢"，很可能只是撞上了那个 1/3 的概率。

## 二·补4、★ skipbg 重判结果（按"多跑取正常态"的方法）

| 组 | 运行 1 | 运行 2 | 运行 3 | fill |
|---|---|---|---|---|
| **基线**（无 skipbg）| **4,820** ✅ | 440,002,898 | 440,002,906 | 1,313,03x ×3 |
| **skipbg v2** | 440,002,868 | 440,002,655 | 440,002,729 | **1,065,709 ×3** |

**判决**：
1. **fill 的 −18.8% 是强证据**：skipbg 共 5 次全部 1,065,7xx，基线共 5 次全部 1,313,03x。**这一条收益成立且可交付。**
2. **sprite 路径：skipbg 三次全慢，基线三次里有一次正常**
   ⇒ 倾向"skipbg 让正常态不再出现"，但 **3 vs 3 的样本不足以定论**
   （若基线正常率真是 1/3，则 skipbg 三次全慢仍有 ~30% 概率是巧合）。
3. **保守结论：不给 sprite 路径启用 skipbg。**
   可行的安全形态是 `bg_needed = (reg_op > 1) | spr_owns` ——
   **只让软件发起的 COPY/FILL 跳过读，精灵路径完全不动**，先把 fill 的 −18.8% 落袋。
   （代价：密度扫描走精灵路径，所以**精灵数不会因此提升**。）

## 二·补5、★ 最终形态与判决（本轮收尾）

### 落地的形态（已上板运行）

```verilog
wire bg_needed = (reg_op[2:0] > 3'd1) | spr_owns;   // 只让软件发起的 COPY/FILL 跳过
```

**精灵路径逐字未改** —— 仿真里 `PASS P4: 186 ARs`（与改动前完全一致），
`spr_owns=1` 时 `bg_needed=1`，行为与原来等价。

### 实测证据

| 量 | 安全形态（3 次）| 基线（对照）|
|---|---|---|
| **hardware fill** | **1,065,697 / 1,065,709 / 1,065,709** | 1,313,03x（5 次全部）|
| 动画段 hw | 440,002,543 / 440,002,882 / 440,002,554 | 4,820 / 440,002,898 / 440,002,906 |

**fill 的 −18.8% 累计 11 次对照、零例外**（5 次基线全 1,313,03x，skipbg 5 次 + 安全形态 3 次全 1,065,7xx）。
**这是本次 goal 唯一可交付的确定收益。**

### ★★ 慢态的铁证：与代码无关

**安全形态把精灵路径完全排除在外，三次仍然全慢（440,002,5xx）。**
⇒ **"每精灵 1375 万拍"的慢态是板子的既有状况，不是任何一次改动造成的。**
累计样本：正常 1 次（base-1）/ 慢 8 次。**正常率可能在 1/6 甚至更低。**

**⇒ 凡涉及 sprite / 密度扫描的板上数字，在慢态未解决之前都不可用。**

### 未兑现的部分（诚实记录）

- **sprite 路径的 +40~70% 没有拿到**：它需要让精灵也跳过目标读，
  而那条路目前**无法在板上可靠测量**（慢态淹没一切）。
- **密度扫描在本轮的任何一次运行里都没跑到**（慢态下每次只跑 40~50 帧就耗尽捕获窗口）。

## 三、方法论收获

1. **`-Wall` 抓隐式声明**：iverilog 默认静默，而回归脚本开了 `-Wall` ——
   **改完 RTL 一定要跑回归，不能只跑自己那个 tb。**
2. **仿真测不出"DDR 往返"类优化的收益**：tb 的 DENSITY 段 AR 数只有 2/精灵
   （描述符 + 源），**根本不含目标读/写**；而板上每精灵 718 拍 vs 仿真 320 拍，
   差额 398 拍才是目标读+写。**⇒ 这类优化只能在板上验证。**
3. **fill 的 −18.8% 证明方向正确**：剩下的问题在 sprite 通路的耦合，不在判据。

**每行的往返次数**（#1 动的是"读"，行合并动的是"次数"）和**每精灵的行数**（= 精灵高度，不可动）。

它是下一步真正该解决的问题。**

## 七、★ 下一个杠杆：行级流水（重新评估，因为依据变了）

### 7.1 现在的成本结构（跳过目标读之后）

每精灵 **368.4 拍 = 16 行 × 23 拍/行**。而每行 23 拍里：

| 项 | 拍 | 说明 |
|---|---|---|
| **写的往返延迟** | **~22** | 每行一次写 burst，发 AW/W 之后要等 B |
| 逻辑与数据搬运 | ~1 | 像素引擎是 4 像素/拍，一行 16 像素只要 4 拍，且被流水掩盖 |

**⇒ 读写分离之后，"写"成了唯一的主导项。** 这与改动前（读+写各占一半）完全不同。

### 7.2 串行的根源（已在代码里确认）

```
addr_gen --line_start--> wr.start        （每行启动一次写）
wr.done -----> f_wr ---+
rd_*.done ---> f_src --+--> all_done --> line_ack --> addr_gen 推进行
```

**`line_ack` 必须等 `f_wr`** ⇒ **行 N 的写完成之前，行 N+1 不会启动** ⇒
**每行白白暴露一整次写的往返延迟**（~480 ns @100 MHz）。

### 7.3 方案：给 addr_gen 发"行许可证"，而不是"行完成"

把 `line_ack` 拆成两个语义：
- **`line_ack`**（保持原义）：行 N 的所有 AXI 事务已完成 —— 仍用于记账/monitor；
- **`line_go`**（新增）：允许 addr_gen 推进到行 N+1 —— 条件是**行 N 的数据已经交给写引擎**
  （即写引擎已接收完该行的 beats），**而不是它的 B 响应已回来**。

**⇒ 行 N 的写还在等 B 时，行 N+1 的读/处理已经开始** —— 这就是行级流水。

### 7.4 ★ 与"已失败的方案 B"的本质区别（这一条必须写清楚）

| | 方案 B（docs/74，失败）| **行级流水（本方案）** |
|---|---|---|
| 改什么 | **写侧不再等 B 响应** —— 允许无界在途写 | **不改写侧的等待行为**，只让**下一行的前端工作**与它并行 |
| 在途请求数 | **增加**（无界）| **不变**（仍然有界，写引擎自己管）|
| 结果 | **把系统钉进慢状态**（4/4 慢）| 不触碰已被六个实验封死的"DDR 请求模式" |

**⇒ 它不违反那条规律**（"当前请求模式已接近最优，任何扰动都变差"）——因为它**不扰动请求模式**，
只是把**已有的等待时间**用来做别的行的活。

### 7.5 收益与代价

| 项 | 估 |
|---|---|
| 每行 | 23 → **~8~15 拍**（隐藏掉大部分写延迟）|
| 每精灵 | 368 → **~130~240 拍** |
| 60 Hz 上限 | **~6,000~8,000 精灵** |
| **带宽上限** | 每精灵 2 KB（已扣掉目标读）⇒ 8,192 × 2 KB × 60 = 983 MB/s，+扫描 249 = **77%**，仍有余量 |
| **表深** | 8192（正在验证）|
| 代价 | 需要**双行缓冲**（2 × 1920 × 2 B = 7.7 KB ≈ 1 RAM10）+ addr_gen/top 的许可逻辑重构 |
| 风险 | 中——动的是行握手（docs/58/63 的死锁现场），但**有 `tb_bitblt_top` 的行级检查兜底** |

### 7.6 建议的推进顺序

1. 先拿到 **8192 表的实测上限**（后台跑着）——若 ~4,420，则它与表深几乎同时到顶；
2. 再动行级流水——**这时它的收益才有意义**（否则算力上限 4,420 < 表深 8,192，扩表白扩）；
3. **不要**在流水化里顺带改 DDR 请求模式（那是被封死的方向）。

**LUT4 从 33,124 涨到 62,896（+29,772），而 RAM10 只涨了 33 块。**
payload 是 8192 × 66 bit = 540 Kbit，本该占 ~53 个 RAM10 —— **实际只多了 33 个**
⇒ **有一部分 payload 没有落进 RAM，退化成了寄存器/多路选择器**，那才是 29,772 个 LUT 的来源。
（RAM10 是 1 Kb 深；8192 深需要 8 块级联，工具在这里可能放弃了块 RAM 映射。）

**⇒ 若真要 8192，方向不是"加表深"而是"让 payload 真正落进 RAM"**（例如拆成多个窄 RAM、
或改用更深的存储原语）。这是**另一条独立的战线**，代价与风险都不小。

### 11.2 ★ 对整体路线的影响：用户的质疑成立

**表深 4,096 == 算力上限 4,422 —— 两者几乎同时到顶。**
⇒ **行级流水能把算力提到 6,000~8,000，但表里只有 4,096 个精灵，同屏数不会增加。**
⇒ **"提性能"在表深不变的前提下确实没有意义。**
⇒ **接下来真正该做的，是"降低表的 LUT 成本"（让 8192 放得下），而不是提算力。**


## 十二、★ 让 8192 放得下：把退休位图 rt 从"位向量"改成"32 位字数组"

### 12.1 诊断结论（第十一节的 LUT 之谜）

map 报告的层次分解只到 `u_spr_state`（子层已被平铺），但代码里有三处**全都 ∝ N** 的逻辑，
合起来正好是那 ~30,000 个 LUT：

| # | 位置 | 原来 | 8192 表下的代价 |
|---|---|---|---|
| 1 | **写译码** | 6 个 `rt[idx] <= ...` 写点，每个都是 N 选 1 | ~6,000 LUT |
| 2 | **单拍全清** | `if (clr_valid) for (k=0;k<N;k++) rt[k] <= 0;` | **~8,192 LUT**（N 个 FF 各带清零项）|
| 3 | **组合读** | `rt[{rt_wsel,5'b0} +: 32]`（需要移位/mux）| ~2,000 LUT |

代码注释里写着"`rt` is one bit per slot and still clears in a single cycle"——
**那"in a single cycle"就是代价的来源。**

### 12.2 改法：同样的语义，按字存

```verilog
reg [31:0] rt_words [0:(N/32)-1];        // 原来: reg [N-1:0] rt;
rt_words[idx[AW-1:5]][idx[4:0]] <= 1'b0; // 写一位: 字选择 + 字内位
for (k = 0; k < N/32; k = k + 1) rt_words[k] <= 32'd0;   // 全清
assign rt_word = rt_words[rt_wsel[AW-6:0]];              // 读: 直接索引
```

三项代价同时下降：
- **写译码**：N 条位选择线 → **N/32 条字选择线**（+ 字内 32 选 1，共享）⇒ 降 ~32 倍；
- **全清**：N 个独立清零项 → **每字的 32 个 FF 共享一个** ⇒ 降 ~32 倍；
- **读 mux**：**完全消失** —— 软件本来就是整字读，现在是直接索引，连移位都不要了。

**★ 语义完全不变**：读仍是组合的（软件在帧间轮询这张位图），无新增延迟、无 read-modify-write。

### 12.3 验证

| 检查 | 结果 |
|---|---|
| `tb_bitblt_sprite_state`（专测这张表的单测）| **RESULT: PASS** |
| `tb_bitblt_top`（含 sprite 路径的集成）| **23 PASS / 0 FAIL** |
| 全量回归 | **29 PASS / 0 FAIL / 1 SKIP** |
| **8192 的综合 LUT4** | **后台跑着**（判据：< 60,800 就算成功）|


## 十三、★ 第 3 步（行级流水）的设计修正：不等 B，而是"行启动开销"

### 13.1 一个关键发现：写引擎早就不等 B 了

读 `bitblt_dma_wr.v` 的 S_DATA→下一步转移：

```verilog
250:  if (b_pending < B_LIMIT) begin
252:      done  <= 1'b1;      // all of the data is away
255:      state <= S_WAIT;    // next burst, no wait
258:  end else state <= S_RESP;   // at the limit: drain one
```

**⇒ 只要在途 B 没到上限，`done` 在"所有 beats 发出"时就拉高，不等 B 响应。**
配合 `BREADY` 恒为 1（第 156 行：响应随到随收），**B 根本不在关键路径上。**

**⇒ 这推翻了我原来的方案描述**（"把 line_ack 拆成 line_go，让行 N 的写与行 N+1 的处理并行"）——
**B 的等待本来就没挡住谁。** 方案要重新定位。

### 13.2 那每行 23 拍花在哪？

结合 docs/78 的 VCD 分解（零延迟仿真每行 36 拍，其中"真正的计算+传输只有 ~12 拍，其余 ~24 拍是握手与等待"），
565 之后每行 23 拍的构成是：

| 项 | 拍 | 说明 |
|---|---|---|
| 数据搬运 | ~4 | 16 像素 / 4 像素每拍（unpack 每 2 拍出一组）|
| **行启动与握手** | **~19** | **每行都重新 start 读、重新 start 写、重新对齐相位** |

**⇒ 真正的目标是这 ~19 拍的行启动开销，不是 B。**

### 13.3 修正后的方案

**不是**"拆 line_ack"，而是**让下一行的前端工作提前开始**：

1. **`addr_gen` 的推进不再只由 `line_ack` 驱动**：当本行的**源读与像素处理完成**（写引擎已接收完全部 beats）
   就可推进，而不必等本行的写完全收尾——**因为写引擎已是"发完即 done"**，这条条件其实已经接近满足；
2. 真正要加的是**行间的解耦缓冲**：一行只有 **64 B（16 像素 × 4 B）+ 16 位 strb**（565 下 32 B），
   用一个小 FIFO 就能把"行 N 的写"与"行 N+1 的读"错开；
3. **预期**：每行 23 → 12~15 拍 ⇒ 每精灵 368 → **200~240 拍** ⇒ 同屏 **~6,000**。

### 13.4 这件事的结论（诚实版）

- **收益上限比原估的低**：原估"隐藏整次 B 往返"（~22 拍/行），实际 B 不在路径上，**可省的只是行启动开销（~19 拍里的重叠部分）**；
- **它仍然值得做**，因为 368 拍里 16 × 19 = 304 拍都是这类开销；
- **但它不再是"隐藏一个明确的等待"，而是"把行间的流水线接起来"** —— 需要先在仿真里量清
  "一行从 start 到写引擎接收完毕究竟花了多少拍、其中哪些是串行的"，再动 RTL。


## 十四、★ 行成本的实测分解：8 拍逻辑 + 15 拍 DDR 延迟

用 `tb_bitblt_top` **已有的**行握手打印（第 477-481 行，本来就打印 `line_start`/`line_ack`/`rd_src_done`/`wr_done` 的时间戳），
跑一次密集绘制段，稳定态数据：

```
[t=328035000] line_start
[t=328095000] line_ack      ← 60 ns = 6 拍
[t=328095000] wr_done       ← 与 line_ack 同拍
[t=328115000] line_start    ← 2 拍后
[t=328175000] line_ack      ← 又是 6 拍
```

| 项 | 拍 | 来源 |
|---|---|---|
| **行内**（`line_start` → `line_ack`）| **6** | 仿真（DDR 零延迟）|
| **行间**（`line_ack` → 下一个 `line_start`）| **2** | 仿真 |
| **仿真每行** | **8** | — |
| **板上每行** | **23** | 实测（每精灵 368 拍 / 16 行）|
| **⇒ DDR 真实延迟** | **15** | 23 − 8 |

**两个附带确认**：
1. **`wr_done` 与 `line_ack` 同拍** ⇒ 写引擎确实**不等 B**（第十三节读代码得到的结论，这里被实证）；
2. 仿真的 6 拍是**纯逻辑**：unpack 每 2 拍出一组像素 + 写引擎的 beat 握手。

### 14.1 这对行级流水的意义（比上一轮的估计乐观）

**可隐藏的是那 15 拍 DDR 延迟**——因为地址是**可预测的**（`line_index + 1`），
所以"行 N+1 的读"完全可以在"行 N 等 DDR"期间提前发起：

| | 每行 | 每精灵 | 同屏上限 |
|---|---|---|---|
| 现在 | 23 | 368 | 4,096（表深）|
| 理想流水（隐藏 15 拍 DDR）| **8~10** | **130~160** | **8,000~10,000**（受带宽限制，实际 ~8,000）|
| 保守（只隐藏一半）| 15~19 | 240~300 | 5,500~6,900 |

**⇒ objective 里写的"130~240 拍、6,000~8,000"是可达区间**，第十三节那次下调（200~240）过于保守——
当时的推断基于"省的是行启动开销"，而实测表明**行启动（6 拍）本身很小，真正的大头是 15 拍 DDR 延迟，而它是可以重叠的**。

### 14.2 实现要点（下一步）

1. **预取下一行**：`addr_gen` 推进后立刻发下一行的源读，不等本行写完；
2. **双行缓冲**：每行只有 **32 B（565）+ 16 位 strb**（P3 紧凑源时更小），一个浅 FIFO 就够；
3. **写引擎天然支持**：它已经是"发完即 done + B 随到随收"，不需要等任何人；
4. **风险**：行 N+1 的读与行 N 的写争 AXI ⇒ 交给已有的 `Axi_Mux` 仲裁（它本来就管 5 个 master）。


## 十五、★ 8192 的最终裁定：**cluster 数超限（而我的判据用错了）**

### 15.1 真因

ERROR : Not enough physical locations for FF cells    : capacity=60800 usage=65497
ERROR : Not enough physical locations for EFT blocks   : capacity=60066 usage=64763

### 15.2 但这次改动本身是成功的（不要误伤）

| `u_spr_state` 的 LUT4 | 42,972 | **35,910（降 7,062 / 16%）** |
| FF | 20,270 | 20,278（不变）|

**⇒ `rt_words` 的重构是正确且有效的**（三项 ∝ N 的代价确实被干掉了），
**但它不足以让 8192 落地**——还差约 5,000 个 cluster（~8%）。

### 15.3 还能怎么省？（下一步的候选，按性价比）

| # | 想法 | 预估 |
|---|---|---|
| 1 | **把 `rt_words` 从 LUTRAM 推进块 RAM**：消息明说原因 `because it has async writer` —— 而那个 async writer 就是只为仿真存在的 `initial` 块（复位逻辑已经清了同一批寄存器）。删掉它，综合器就能用块 RAM | 省 ~256-512 LUT，**对 cluster 帮助有限** |

### 15.4 状态

（pnr 失败不会覆盖它）⇒ **板子、磁盘、工作区三者一致且可用**。

## 十八、★ 消融 C：整场 8192 之战的答案 —— 代价全在“位粒度写”

三个障碍依次被综合器报出、依次清掉之后（`initial` → 异步复位 → 组合读），`rt_words` **仍然**进不了存储器，
消息变成 `because it failed ram decomposition synthesis`。于是做消融 C：**把六个写点全部删掉**，只留数组与寄存器读。

| | 全局 LUT4 | `u_spr_state` LUT4 |
|---|---|---|
| 三改版（读已寄存、写仍逐位）| 33,516 | 19,568 |
| **消融 C（完全无写）** | **14,332** | **296** |
| **差值 = 写路径的代价** | **−19,184** | **−19,272** |

综合器对无写版本的判词：`Optimizing into logic zero initialized read-only memory block` —— **读是免费的**。

### 18.1 结论

**`rt` 的全部代价（4096 槽约 19,000 LUT，8192 槽约 35,000）来自“一次改一位”这个写语义。**
块 RAM 只支持整字（或字节）写，综合器的退路是 TF+译码/位，也就是它一直在做的事。

**⇒ 唯一的出路是 RMW：把“清一位 / 置一位”改成“读字 → 改位 → 写回”，让写变成整字写，数组才能真正落进块 RAM。**

### 18.2 RMW 的设计要点（尚未实施）

| 项 | 内容 |
|---|---|
| **写点** | 6 个：播种清一位、回收清一位、退休置一位、`clr_valid` 全清（可逐字写 N/32 次）|
| **仲裁** | 同一拍可能有两个写点（播种/回收/退休同时）⇒ 需要优先级 |
| **状态机** | `IDLE → RD（读字）→ MOD（改位）→ WR（写回）`，3 拍一次写 |
| **吞吐影响** | 每帧最多几十次写（每精灵一次），而一帧有 1.6M 拍 ⇒ **完全可忽略** |
| **收益（8192）** | `rt` 从 ~35,000 LUT 降到约 200 LUT（1~2 个 RAM10）⇒ **cluster 从 65,497 掉到约 30,000** |
| **验证** | 这张表有专门单测 + 集成测试覆盖；改动在 `bitblt_sprite_state.v` 单文件内 |

### 18.3 已保留的三处改动（都是有价值的净改善）

1. 删 `initial` 块（硬件上电即零）| 2. 删异步复位分支里的清零（`clr_valid` 上电即清）| 3. 读改为寄存器输出（软件是两次 MMIO，1 拍无感）

三者都已通过：单测 PASS · 集成 23/0 · 回归 29/0/1。

## 十九、RMW 首次实现：功能走通、但综合器不认写路径（草稿）

按第 18 节的结论实现了读-改-写（数组改成整字写），结果分两半：

**两个待修点**：

1. **RMW 的写语句没被综合器接受** —— 状态机写在 `always @(posedge clk or negedge rst_n)` 里，

## 二十二、★★ 决定性对比：RMW 没有引入 bug，它让一个既有 bug 显形了

同一个测试台（只观察软件可见的 `rt_word`）跑两个 RTL 版本：

| 版本 | rt_word 序列 | 结果 |
|---|---|---|
| 三改版（回归 PASS）| `xxxxxxxx` → `xxxxxxx8` | **PASS** —— **高位全是 X，它其实是坏的** |
| RMW + 上电清表 | `00000000` → `00000001` → `00000009` | FAIL: `rt_word_tb[0] = 1 want 0` |

### 22.1 真相

1. **三改版之所以 PASS，是因为它的表未被初始化（X）**，而测试只检查其中某几位——
   它读到 `xxxxxxx8`（低 4 位 `1000`，bit 0 恰为 0）就通过了。**那不是一个可信的 PASS。**
2. **RMW 版把表清成了全 0**（上电整字清零扫描，trace 里 8 个字逐个写 0），
   **于是暴露了一个真实缺陷：`slot 0` 被误判为“出屏”而置位。**
3. **该缺陷在原代码里就存在**：trace 显示判定退休时读到的 `ram_rdata` 在 **所有槽上都是同一组坐标**
   （`x=630, vx=20, fb_w=640`）—— **sweep 的退休判定用错了槽的数据**，只是过去被 X 掩盖。

### 22.2 因此结论要改

- **不是“RMW 引入 bug”，而是“RMW 让既有 bug 显形”**；
- **“删 initial 块”不是零代价的**：它换来块 RAM 映射的可能，但**同时拿掉了仿真的初始化来源**，
  必须配套一个“上电整字清零”机制（已实现，8 个字全部写 0，工作正常）；
- **真正要修的是 sweep 的数据对齐**：判退休那一拍，`ram_rdata` 必须属于当前 `swp`，
  而不是像现在这样在若干槽上读到同一组陈旧坐标。

### 22.3 下一步（优先级已重排）

1. **先修 sweep 的数据对齐**（与 RMW 无关，是独立缺陷）—— 它同时是三改版与 RMW 版的隐患；
2. 修好后重跑三改版 + RMW 两版，**两者都应该干净通过**（不再有任何 X）；

## 二十三、★ RMW 功能全绿（第 1 步达成），但综合器仍把数组折成常量

### 23.1 突破：退休判定必须门控在 `sw_lat == 0`

trace 逐拍数据：

```
[t=795000] swp=0  rdata_x=630  lat=2   <- 判定就发生在这拍，数据是上一个槽的残留
[t=805000] swp=0  rdata_x=0    lat=1   <- slot 0 的真实位置（屏内！）
```

sweep 用显式的 `sw_lat` 倒计时等 `simple_dual_port_ram` 的两拍读延迟，
**而退休判定在倒计时走完前就采样了**，于是用**上一个槽**的坐标决定当前槽是否出屏。

**修法**（一行）：`wire rt_req_retire = (sw_state == SW_WAIT) && (sw_lat == 2'd0) && (...);`

**这同时修掉一个既有正确性缺陷**（原代码的判定同样在数据到达前采样，被未初始化的 X 掩盖）。

| 检查 | 结果 |
|---|---|
| tb_bitblt_sprite_state | PASS |
| tb_bitblt_sprite_walker | **PASS**（从 FAIL 转 PASS）|
| tb_bitblt_top | 0 FAIL |
| **全量回归** | **29 PASS / 0 FAIL / 1 SKIP** |

### 23.2 第 2 步的障碍：综合器把数组折成常量

综合器对 `rt_words` 一直报：`Optimizing into logic zero initialized read-only memory block`。
它的推理是：**看到“读-改-写同一个数组” ⇒ 论证“读到的恒为 0” ⇒ 连写也优化掉**。
这对真机是错的（RAM 保存着此前写入的内容），而且**正好把 RMW 的全部意义抹掉** ——
所以反复出现的 `LUT4 = 14,332` 一直是“写被删除”的假象。

**试过且无效**：`(* syn_ramstyle = "block_ram" *)`、`(* syn_ram_style = "block" *)`（后者是从综合器自己的消息里学到的名字）。

### 23.3 解法（已明确，未完成）

**显式实例化项目自带的 `simple_dual_port_ram`**（payload RAM 就是这么用的），不再依赖综合器的判断：

- 读地址：RMW 用 `rt_idx_r[AW-1:5]`，软件读用 `rt_wsel`，清表用 `rt_clr_word`（三者分时复用唯一读口）；
- 写地址：`rt_clr_all ? rt_clr_word : rt_idx_r[AW-1:5]`；
- **状态机要多等一拍**（该原语 `OUTPUT_REG="TRUE"` 是两拍读延迟，而现在只等了一拍）；
- `rt_word_r` 改为在 RMW 空闲时锁存 RAM 输出。

**我第一次尝试用正则批量改写，把语法弄坏了**（删掉了必要的行）⇒ 已从备份恢复。
**这是一次需要精细手工改的手术（约 30 行），不该用正则做。**

## 二十四、显式 RAM 化：四连败于“局部搬移”，需要一次干净重写

目标：把 `rt_words` 从 reg 数组改成显式 `simple_dual_port_ram`（综合器对 reg 数组一律折成常量，属性无效）。

**六处改动本身都正确**（数组→实例、`rt_word_r` 取 RAM 输出、地址三路分时、写走 RAM 端口、读延迟改成两拍、状态加 `RT_RD2`），
**但连续四次倒在 Verilog 的【声明顺序】上**：

| 次 | 现象 | 原因 |
|---|---|---|
| 1 | 正则批量改 → 语法错 | 删掉了必要的行（**正则不该用于改 RTL**）|
| 2 | `implicit rt_wdata` / `implicit rt_we` | RAM 实例在它们的声明之前 |
| 3 | `implicit rt_raddr` | 实例移走了，`assign` 留在原处 |
| 4 | `syntax error` / `Invalid module instantiation` | 搬移时把 `assign` 关键字切掉了 |

### 24.1 教训

**这类改动不能【局部搬移】，只能【整块按依赖顺序重写】。** Verilog 对声明顺序敏感，
而 RMW 那一段的依赖链很长：

```
rt_wsel
  -> rt_st / rt_idx_r / rt_val_r / rt_word_rd / rt_clr_all / rt_clr_word  (reg)
  -> rt_req_any / rt_req_idx / rt_req_val        (依赖 sw_state / swp / init_* )
  -> rt_bit_mask -> rt_wdata -> rt_we
  -> rt_waddr / rt_raddr  +  RAM 实例
  -> rt_word_r
```

**正确做法**：把这一段整体重写一遍（约 80 行），而不是在同一段里挪来挪去。

### 24.2 状态

- 工作区 = **RMW 全绿版**（`.rmw-green`），三测试台全绿、回归 29/0/1；
- 它的**功能是对的**，唯一的问题是**综合器把 reg 数组折成常量**（所以 `LUT4 = 14,332` 是假象）；

## 二十六、★★ walker 的"0 AR"之谜告破：不是 RTL，是【三处按 N 猜的等待窗口】

> 现场：`work/opt-study/w8192/`。**交接文档把"P4 发出 0 个 AR"列为 8192 唯一的剩余障碍，并推测是 walker 没启动。**

### 26.1 结论先行（推翻了交接文档的假设）

| 项 | 交接文档的假设 | **实测** |

| walker 启动 | "完全没启动" | **正常启动**（清表一结束就进 S_FETCH） |
| 0 AR 的原因 | RTL 功能 bug | **tb 的等待窗口按旧的 N 写死，walker 还没启动就超时** |
| 显式 RAM 版状态 | "只差 P4 启动" | **三个测试全绿**（walker 16 项 / state 17 项 / 集成 all checks OK） |

### 26.2 直接证据（walker/清表 trace，cyc = 时钟数）

| cyc | 事件 | 说明 |
|---|---|---|
| 5 | `CLR_BUSY 0->1` | 上电清表启动（clr_valid 高即启动） |
| **32,773** | `CLR_BUSY 1->0`，`clr_cnt=8191` | **清表 = 4 拍/槽 × 8192 槽** |

| **77,644** | `frame_done=1`（脉冲） | **帧尾 sweep = 5 拍/槽 × 8192 槽 = 40,960 拍** |
| 77,645 | `S_STEP -> S_IDLE`，busy 落 | walker 正常收尾 |

**⇒ P4 帧总长 32,775 → 77,645 = 44,870 拍**（4096 时约 24,400 拍）。

### 26.3 三处"按拍数猜"的窗口（全部 ∝ N，全部失效）

| # | 位置 | 旧窗口 | 8192 实际需要 | 症状 |

| 2 | 密度扫描：等 busy **升** | 30,000 | 32,773 | 四步里两步 `0 ARs` |
| 3 | P4 遍历：等 busy **落** | 40,000 | 44,870 | 报 `busy still high` **假死锁** |

**修法**：不再猜拍数，改为**等真实信号** —— `while ((dut.spr_clr_busy || !busy) && guard < 300000)`；busy 落窗口放大到 200,000。

### 26.8 方法论（写给下一个会话）

1. **"某模块没启动"要先证明它的启动条件是什么**，再看门控信号 —— 本例的答案是 `enable = reg_spr_enable & ~spr_clr_busy`，而 `clr_busy` 的时长 ∝ N；
2. **任何"按拍数猜"的等待窗口都是定时炸弹**：它随 N 失效，而症状（0 AR / 假死锁）**看起来像 RTL bug**；
3. **tb 的超时要打印"等了多久"**，否则 `0 ARs` 与 `walk 未启动` 无法区分（本例两个 30,006 就是这么来的）；
4. **观测手段的性价比**：一个 `$display` + 三行 `grep` 定位的问题，之前六轮 RTL 重写都没找到。

# 58 - 引擎「写后读永久失效」根因与修复（2026-10-13）

> **一句话结论**：真凶是 `bitblt_axi_slave.v` 的两处时序缺陷，**不是** AXI 协议层的前 7 类修复，**也不是** SoC 读路径。
> 用【真实的 SoC 桥 RTL + 真实的从机 RTL】联合仿真复现，两处修复后 `errors=0`。

## 一、结论先行

| 版本 | 阶段1 纯读 | 阶段2 写 | 阶段3 写后读 | 阶段4 再读 | 结果 |
|---|---|---|---|---|---|
| 原始 RTL | ✅ | ❌ 写即挂起 | ❌ | ❌ | `DEADLOCK-REPRODUCED` errors=3 |
| +修复A | ✅ | ✅ | ❌ 读被锁死 | ❌ | `DEADLOCK-REPRODUCED` errors=3 |
| **+修复A+B** | ✅ | ✅ | ✅ | ✅ | **`NO-DEADLOCK` errors=0** |

**⇒ 两处缺一不可。**

## 二、根因 A：写通道 1 拍错位（AW/W 同周期 + READY 寄存器延迟）

| 项 | 内容 |
|---|---|
| 现象 | `t=20 arw v=1 r=0`、`W v=1 r=0`；`t=21` 从机 `awreadyReg=1`，但桥已撤销 valid ⇒ 握手永不发生 |
| 机理 | 桥（`BmbToAxi4SharedBridge`）把 AW 与 W 各只维持 **1 拍**；从机 `axi_awready = awreadyReg & axi_awvalid`，`awreadyReg` 是**寄存器**，READY 总晚 1 拍 |
| 为何 docs/56 的 7 类修复无效 | 它们只改了**条件**（去掉 `axi_wvalid &&`），**没消除这 1 拍寄存器延迟** |
| 修复 | 同拍组合握手（见 §四） |

## 三、根因 B：BVALID 多保持一拍 ⇒ 桥的响应通道被永久锁死

桥 `soc.v` 内部（`BmbToAxi4SharedBridge_1`，L12166-L12283）：

```verilog
when_l87   = (io_output_r_valid || io_output_b_valid);   // 置位条件
when_l87_1 = ((r_fire && r_last) || b_fire);             // 清除条件
rspSelRead = rspSelLock ? rspSelReadLast : io_output_r_valid;
io_output_b_ready = (io_input_rsp_ready && !rspSelRead && writeRspInfo_valid);
io_output_r_ready = (io_input_rsp_ready &&  rspSelRead && readRspInfo_valid);
```

从机原来靠「离开 `WR_RESP` 状态」清 BVALID，于是握手后 **BVALID 又多持续一拍**。桥只要看到 `b_valid=1` 就把响应通道锁给「写」（`rspSelLock=1`、`rspSelReadLast=0`），此后 `r_ready` 恒 0；而解除锁定又要求 `r_fire`，`r_fire` 需要 `r_ready` ⇒ **循环依赖，永久死锁**。

日志实证：`t=23 b v=1 r=1`（B 握手）→ `t=24 b v=1 r=0` 重新置 lock → `t=28+` `r v=1 r=0` 永久。

**⇒ 这同时解释**：纯读正常 / 写一次后读全废 / `araddrReg` 停在上次成功地址（所以四个寄存器读回同一个值）/ 最终 `Can't communicate with the CPU`。

## 四、修复内容（两处，均在 `rtl/bitblt_axi_slave.v`）

### 修复 A —— 写通道同拍握手

```verilog
wire wr_go = axi_awvalid && axi_wvalid && busReady;
assign axi_awready = wr_go;
assign axi_wready  = busWrite || wr_go;
// FSM
IDLE: busNext = (wr_go && axi_wlast) ? WR_RESP : IDLE;
// 地址必须在握手当拍组合解码（awaddrReg 下一拍才更新）
wire [ADDR_WIDTH-1:0] wr_addr_now = wr_go ? axi_awaddr : awaddrReg;
wire [4:0]            wr_idx      = wr_addr_now[6:2];
// 寄存器写入使能
wire wr_strobe = (busWrite & axi_wvalid) | wr_go;
```

### 修复 B —— BVALID 被接受的当拍立即撤销

```verilog
end else if (bvalidReg && axi_bready) begin
    bvalidReg <= 1'b0;            // 握手当拍即撤，不再多挂一拍
end else if (busWriteResp) begin
    bidReg    <= awidReg;
    brespReg  <= wr_bad ? 2'b10 : 2'b00;
    bvalidReg <= 1'b1;
end
```

## 七、更正交接文档的两处结论

| 交接文档（`新会话交接-20261013.md`） | 实际 |
|---|---|
| 「读请求根本没从 SoC 发出」（§三·问题1） | **不成立**。该结论依据的 UART 探针 `[ARBS]` 在「读引擎」**之前先写了引擎**；而铁证表明**纯读完全正常** ⇒ 只能得出「**写之后的**读不发 AR」 |
| 根因指向 SoC 的 axiA **读**路径 | 实为**写事务未收尾**：桥的 AW/AR 共用 `arw_valid`（半双工），写不完成则后续 AR 永不发出 |

**补充事实**：SoC 的 `ARID`/`AWID` **恒为 `8'h0`**（`soc.v` L5154/L5166），所以从机 `axi_rid` 恒 0 **恰好匹配**，不是根因。

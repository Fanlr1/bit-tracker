## 一、判据

**赛题立意（原文）**：

> 把 **RISC-V 从像素搬运中解放出来** —— RISC-V 仅负责**高层逻辑与下发指令**，
> FPGA 硬件端完成**底层像素的高速搬运与混合**。

| # | 判据 | 说明 |
|---|---|---|
| **1** | **是否让 CPU 更「高层」、交互更少？** | **直接命中立意** |
| **2** | **是否让像素搬运/混合更快或更省？** | **命中「高速」** |
| **3** | **能否被演示、被量化？** | **评委要看得见** |

**⇒ 三条全中 ⇒ 强创新；中两条 ⇒ 加分；中一条 ⇒ 边缘；零条 ⇒ 偏题。**

## 二、先定位瓶颈

### 2.1 已排除：带宽

```
DDR3 有效带宽  ≈ 1.2 GB/s   （后经 40 号查证修正为 1600 MB/s）
视频扫描占用     73.7 MB/s  （640×480 时 6%；1080p60 时 594 MB/s = 37%）
```

**⇒ 640×480 下带宽不是瓶颈，加宽总线收益接近于零。** **⇒ 但 1080p60 之后扫描输出占 37%，带宽重新变成**需要盯**的量 —— 见 [40](40-仲裁与HSIO与4KB查证.md) / [41](41-1080p60全链路达成与PLL方案.md)。**

### 2.2 真正的瓶颈：**突发太短**

| 场景 | 每行字节 | 突发拍数 | 每帧事务数 |
|---|---|---|---|
| **满屏填充 640×480** | **2560 B** | **160** | **480** |
| **64×64 sprite** | **256 B** | **16** | **64** |

**每次 AXI 突发要付**：地址握手（2~3 拍）+ 仲裁 + DDR3 行激活。**按每次 10 拍估**：

```
160 拍突发 ⇒ 160/170 = 94%
 16 拍突发 ⇒  16/ 26 = 62%     ← sprite 的实际处境
```

**⇒ 这修正了 [24](24-静态性能建模.md) 的乐观值**：单 64×64 sprite 从 40 µs 变 60~70 µs，60 FPS 上限从 417 降到约 **250 个**。

**⇒ ✅ 已解决（P3）** —— 实测见 [42](42-P3突发合并实现记录.md)：**16×16 从 33% 提到 88%（2.66x）；64×64 从 66% 到 98%（1.47x）**。**⇒ 62% 对应 64×64，实测吻合。**

### 3.1 Sprite 状态硬件维护 —— ★★★（已完成）

**做什么**：CPU 一次下发 sprite 表，**硬件自己遍历、更新位置、处理边界、渲染**。

**⚠️ 关键论证（答辩时要用）**：

```
我们数过：32 个 sprite 需要 CPU 256 次寄存器写 + 32 次轮询。
硬件执行 1 ms，而这 256 次交互本身要 25 µs —— 看起来只占 2.5%，
但它是【串行】的：硬件搬的时候 CPU 在轮询，CPU 写的时候硬件在等。
⇒ 真正的问题不是这 25 µs，是【没有重叠】。
⇒ 把循环搬进硬件后，CPU 下发一次就可以去跑游戏逻辑，两者真正并行。
```

**⇒ 实现见 [43](43-P4实现记录.md) / [44](44-P4弹幕能力记录.md)。** **⇒ 实测：256 个 16×16 弹幕约 **0.95 ms**，占 16.7 ms 的 **5.7%（上界）**。**

### 3.2 更多 Blend Mode —— ★★（已完成）

**⇒ 七个模式：COPY / FILL / ALPHA / KEY / ADD / MUL / SCREEN。** **⇒ 成本极低 —— DSP 只用 40/160。见 [29](29-P1混合模式完成记录.md)。**

### 3.3 突发合并 —— ★★（已完成）

**⇒ 源侧紧凑时整块连续读，而非每行一次突发。** **⇒ 只支持紧凑 sprite —— 而**游戏里的 sprite 本来就是紧凑的**，framebuffer 侧才有 stride。见 [42](42-P3突发合并实现记录.md)。**

### 3.4 硬件裁剪 —— ★★ + **游戏 Demo 的前置**（已完成）

**⇒ 没有它，弹幕只能「反弹」不能「飞出」。** **⇒ Y 方向在 `bitblt_addr_gen`（`[fb_start, fb_end)` 检查），X 方向在驱动 `blt_sprite_clipped`。见 [31](31-P2越界保护完成记录.md) / [32](32-P2收尾与P3推迟.md)。**

### 3.5 行缓冲 —— ⬜ 未做

**问题**：ALPHA 要读背景 ⇒ 每像素 4 B 背景 + 4 B 前景 + 4 B 写 = 12 B/px。**同一行背景可能被多个 sprite 覆盖 ⇒ 重复读。**

**做法**：片内加一行（或几行）背景缓存 ⇒ 多 sprite 命中同一行只读一次，最后整行写回。

**⇒ 收益**：背景读从 N 次降到 1 次。****但收益不在带宽，而在**事务数** —— 它把「每 sprite 每行一次读事务」变成「每行一次」，事务数降 N 倍。** **⇒ 成本中：需要行缓冲 SRAM（256 个 RAM10，当前用 74，够）+ 重写数据通路。**

### 3.6 颜色键控的硬件优化 —— ⬜ 未做

**⇒ 现在 KEYING 命中透明色时跳过写，但**仍然读背景**（4 B 白费）。** **⇒ 优化：命中时连背景也不读 ⇒ 纯背景区域带宽降 50%。** **⇒ ⚠️ 代价：要先读前景、判断后再决定是否读背景 ⇒ **需重排数据流顺序**（现为前景/背景并行读），会引入延迟。需权衡。**

### 3.7 DDR3 行局部性 —— ⬜ 未做，**且必须先实测**

**⇒ 地址生成是「按行顺序」：行内连续，跨行跳 2560 B。** **⇒ ⚠️ 而 DDR3 的 bank/row/col 交错由**加密的 `ddr3_top` 决定** —— 我们不知道 2560 B 跳转是否落在同一 row。** **⇒ 应先做一张「访问模式 vs 实测带宽」的表，用数据决定，别猜。**

### 3.8 逐像素 2D 光照 —— 边缘

**⇒ 中一条判据。属于「2D 渲染引擎的另一个功能」，不是「让搬运更快」。** **⇒ 赛题是「2D 图形渲染**加速**引擎」—— 光照是「加功能」不是「加速」。** **⇒ 有余力做个小面积演示（一个光罩），不作主线。**

### 3.9 / 3.10 三角形光栅化、硬件矩阵变换 —— 不做

**⇒ 光栅化：赛题要位图精灵，矢量是另一个题目。** **⇒ 矩阵变换：32 个 sprite 的变换本来就不慢，收益上限 13 µs（全帧 1.3%），且看不出效果。**

## 四、⚠️ 必须说清的三个风险

### 4.1 创新点的前提是【基础分拿满】

**⇒ 评分顺序通常是：基础要求 → 高阶挑战 → 创新性。** **⇒ 基础要求若「能跑但不好看」，创新点再多也难救。** **⇒ ⚠️ 而**这块板子至今未上电** —— 基础要求仍是纸面上的 ✅。**

### 4.2 「创新」要能被【讲成一个故事】

**⇒ 好的答辩叙述：**

> 我们实现基础 BitBlt 和高阶 Alpha 后，**数了一下 CPU 的交互次数**：
> 32 个 sprite 需要 **256 次寄存器写 + 32 次轮询**。
> 硬件执行一帧 1 ms，而**这 256 次交互本身要 25 µs —— 关键是它【不与硬件重叠】**：
> 硬件搬的时候 CPU 在轮询，CPU 写的时候硬件在等。
> **⇒ 所以赛题说的「解放 RISC-V」其实只解放了一半**：搬运解放了，调度没有。
> **⇒ 我们把 sprite 状态也搬进硬件**，CPU 下发一次就去跑游戏逻辑，两者真正并行。
> **⇒ 结果：同屏 sprite 数从 X 提到 Y。**

**⚠️ 故事结构**：**先承认赛题做完了 → 再指出一个【可量化】的不足 → 再给方案 → 再给数据。** **⇒ 这比「我们还做了赛题没要求的 Z」有力得多。**

**⚠️ 而现在这个故事**还缺最后一环**：X 和 Y 那两个数字**只有板子能给**。** **⇒ 我们能给的只有 0.95 ms / 5.7% 这个上界（`44` §四）。**

### 4.3 时间与风险

**⇒ 板上调试往往比预期慢（DDR3 校准、时序、跨 4KB）。**

```
板子到之前：只做【不依赖板子的代码】+【纸面设计】
板子到之后：先打通链路 → 再做创新
```

## 五、结论

**⇒ 尺子不是「赛题有没有提」，而是【是否服务于「把 RISC-V 解放出来」这个立意】。**

```
① 硬件裁剪            ← 游戏 Demo 的前置，成本低，必须先做    ✅ 已完成
② 更多 Blend Mode     ← 成本极低，视觉明显，性价比最高        ✅ 已完成
③ Sprite 状态硬件维护  ← 主线创新，最能讲故事                 ✅ 已完成
④ 突发合并            ← 纯性能，投入产出比高                  ✅ 已完成
──────────────────────────────
   行缓冲              ← 收益在事务数，不在带宽                ⬜ 可选
   颜色键控优化        ← 需重排数据流，有权衡                  ⬜ 可选
   DDR3 行局部性       ← 必须先实测，别猜                      ⬜ 可选
   逐像素 2D 光照      ← 余力再说                              ⬜ 不做
   三角形光栅化        ← 不做                                  ❌
   硬件矩阵变换        ← 不做                                  ❌
```

**⇒ 前四项**全部落地**。剩下三个「可选」里，**行缓冲**是唯一在弹幕场景下有实际意义的（高重叠时事务数降 N 倍）；另外两项都受限于「加密的 `ddr3_top`，只能实测反推」。**

**⇒ 而真正的短板不在创新点，在**基础要求还没上过板**。**

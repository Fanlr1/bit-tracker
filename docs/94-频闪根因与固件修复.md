# 94 - 频闪根因：blanking 语义错误（2026-10-24）

> 接 docs/93（首屏与双缓冲地址问题）。本文记录"画面一直频闪"的根因、已实现的两条修复路径，以及一个更大的发现：**当前源码无法综合出可用比特流**。

## 一、一句话结论

**频闪 = 软硬件对"blanking"的理解不一致。** RTL 的 `o_blanking = ~de_raw` 在**水平消隐**期间也为 1，而固件把它当"垂直消隐"用来等翻页时机 ⇒ 每次 `blt_set_fb` 都落在行中间，每翻一次页撕一条缝。

## 二、证据链

| # | 事实 | 位置 |
|---|---|---|
| 1 | `de_raw = h_active & v_active`，水平消隐时为 0 | `rtl/bitblt_video_out.v:248` |
| 2 | `assign o_blanking = ~de_raw` ⇒ 行间也为 1 | 同文件 482 行（修复前） |
| 3 | 固件轮询该位等"vertical blanking" | `bitblt.h` `blt_scan_wait_blanking()` |
| 4 | 该位经 0x5C[0] 暴露 | `bitblt_axi_slave.v:732` |

⇒ 轮询在**一行之内**（~15 µs）必然命中，翻页时机等于随机。

## 三、两条修复路径

### 3.1 RTL 修复（已验证逻辑，**未上板**）

```verilog
assign o_blanking = ~v_active;   // 只在垂直消隐为真
```

- 仿真：tb_bitblt_video_out / 全量回归 **PASS=28 FAIL=1 SKIP=1**（唯一的 FAIL 是 `tb_mux_video` 的 1 个 implicit declaration，**预存**，与本次改动无关）。
- 上板：**失败**。见第五节。

### 3.2 固件修复（**已上板，本次采用**）

```c
// BLT_SCAN_FRAMES 在 v_cnt/h_cnt 同时到末尾的那一拍递增 = 帧边界
uint32_t f0 = blt_read(BLT_SCAN_FRAMES);
for (...) if (blt_read(BLT_SCAN_FRAMES) != f0) return 0;
```

- 不依赖 RTL，**用当前可用的比特流即可生效**。
- 注意：`BLT_SCAN_FRAMES` 的 `#define` 原在文件后部，需上移到 `BLT_SCAN_STATUS` 旁，否则 `blt_scan_wait_blanking()` 编译不过。

## 五、更大的发现：当前源码综合不出可用比特流

| 比特流 | 结果 |
|---|---|
| `work/bitstreams/bitblt_system-8192-rwatchdog-20261017.bit`（01:00，md5 39b89162） | ✅ 正常跑完 240 帧 |
| 10-17 22:43 的 B 方案（fb_end 扩展） | ❌ 卡死在 hardware fill（UART 57 B） |

- `bitblt_top` 的其余 10-17 改动（无 01:00 快照可比）

**下一轮的优先事项应是恢复"源码→可用比特流"的可重建性，而不是继续改功能。**

## 六、仍然存在的第二个问题：扫描欠载

| 阶段 | 欠载 |
|---|---|
| 测试/启动段（前 ~980 显示帧） | 平均 **787,000 周期/帧**（约 32% 像素缺失） |
| 动画段 | **400~1000 周期/帧**（约 0.02%） |

- 计数来源：`BLT_SHORT_CNT (0x70)`，`pixel_short = de_raw & ~de`。
- 动画段每小时 1000 像素 ≈ 半行，表现为偶发细线；测试段 32% 则会整屏花。
- FIFO 深度 `FIFO_AW=12`（4096 px ≈ 2.1 行），`need_line` 在 FIFO < 1 行时才预取 ⇒ 余量只有 1 行（~13 µs）。加深或提前预取是下一步的方向。

## 八、方法论

1. **先证伪再动手**：一个 20 行的 iverilog 实验就否决了"16 位乘法"这个传了一天的假设。
2. **同一现象可能有两个独立原因**：频闪（blanking）与花屏（扫描欠载）是两件事，不要用一个假设解释两个现象。
3. **"数值完全相同"是最强的判据**：两次配置下 strided 都是 3,369,303，直接排除随机性，也直接证明改动无效。
4. **能用固件绕开的，就不要赌综合**：当前比特流不可重建，任何 RTL 修复都上不了板。

正是 o_blanking = ~de_raw 的必然结果。**这不是数据错误、不是 DDR 读错，是翻页时机。**

## 十、固件修复的失败与原因（重要）

用 BLT_SCAN_FRAMES 跳变等帧边界的方案**能让翻转落到帧边界**，但实测把动画拖到 **8 s/帧**（原为 0.29 s/帧）：

- sw / hw 仍为 1.33 M / 293 K 周期（引擎并不忙）；
- 差额约 8 s ≈ blt_wait 的 20 M 次迭代上限；
- 即：**在垂直消隐期间翻转 fb_base，会让仍在进行中的 fill/copy 卡住**，随后每次 blt_wait 都走到超时。

=> 已回退为原来的标志等待（blt_scan_blanking()）。**若重试此方向，必须先等 STATUS[busy]==0 再翻页**，不能只等帧边界。

## 十六、「卡死」的真正形态：引擎 BUSY 永不释放（goal round 2）

在 `blt_wait` 的超时分支里加了一行串口打印后，烧写重新综合的比特流，得到：

    DBG wto st=00000001
    DBG wto st=00000001      (连续多次)
    software fill
    hardware fill: 4609816 cycles/frame

- `st = 0x01` = STATUS bit0 = **BUSY**，没有 ERROR(bit2) 也没有 CLIPPED(bit3)；
- 每次等待都跑满 20M 次轮询（约 4.4 s）才返回，所以整机看起来像死机；
- 程序其实还在跑，只是每一次 blit 都要白等 4.4 秒。

⇒ 结论很硬：**不是 CPU 挂在 AXI 写，也不是 DDR 不回数，而是引擎的 busy 永远不释放**。
往上一层，`engine_status = {addr_oob, wr_b_error, addr_done, busy}`，而 `busy` 聚合了 walker / 两个 DMA / addr_gen。

### 16.1 下一轮的唯一任务：定位卡在哪个子模块

`blt_wait` 超时分支本来就会抓四组 GPIO 观测快照到 BRAM 0xF9000F00+4*35..38：

| slot | 选择 | 内容 |
|---|---|---|
| 35 | sel 0 | DDR 侧 arready/arvalid/rready/rvalid |
| 36 | sel 1 | 引擎 AR bl1/bl2 |
| 37 | sel 2 | 读引擎状态机 rd_src/rd_dst |
| 38 | sel 3 | busy 位 wr_dst/rd_dst/rd_src/addr |

下一轮把四组值也打印出来，就能一次看出是 addr_gen 停在 S_LINE、walker 停在 S_RUN，还是读引擎停在 S_RD。

## 十二、全片逐帧分析（95 个采样点，每 0.5 s）

用 1418 帧 / 47.3 s 的录像按 0.5 s 抽帧（95 张），拼成 5 张联系表：

| 时间 | 画面 |
|---|---|
| 0 – 13.5 s | **正常**：先是整屏绿色（fill 测试），约 1 s 后切到整屏深蓝 + 精灵，**上下一致** |
| 13.5 s | 突变（板子被重新配置/重启） |

### 12.1 条带不是「一次 flip 的偶然撕裂」

- 分界线在整个后半段**一直存在**，但位置逐帧漂移（30% → 50% → 40% ...），说明**每次 flip 都在扫描中途**，而不是偶发一次；
- 与 `o_blanking = ~de_raw` 的推断完全对上：固件每次都在**第一个水平消隐**翻页，而它拿到哪一行取决于当帧的工作量，于是分界线跟着漂。

### 12.2 另发现一个独立问题：两个缓冲的内容严重不同步

若只是撕裂，撕裂线两侧应当都是**相邻帧的动画**（精灵位置略有差别）。实际是：

- 上半（旧缓冲）是**橙色点阵 + 青色网格**，明显是早期测试图案，长时间几乎不变；
- 下半（新缓冲）是动画，精灵每帧移动。

⇒ 有一个帧缓冲**停留在测试阶段的内容**，动画并没有真正写满它。这会把「频闪」解释得更完整：
**两个缓冲内容不同 + 每帧交替显示 = 整屏闪烁**；**切换发生在扫描中途 = 上下条带**。两个现象、两个原因。

### 12.3 下一步应查的两点

1. ANIM 段的 `back` 是否真的每帧翻转、`blt_fill` 的目标是否与 `blt_set_fb` 的目标一致（若只画同一块，另一块就永远停在测试图案）；
2. 修完翻页时机后，仍需确认两个缓冲内容一致，否则即使翻在消隐区，屏幕上仍会看到内容跳变。
## 十三、双缓冲其实从未启用（代码事实）

main.c 的 ANIM 段循环：

    uint32_t back = 1u;              // 循环外
    for (f = 0; f < ANIM_F; f++) {
        back = 0u;                   // 每帧无条件重置，1510 行
        volatile uint16_t *dst = buf[0];
        blt_fill(FB_BASE, ...);      // 清 buf[0]
        blt_sprite_clipped(..., (back ? FB_BASE + FB_BYTES : FB_BASE), ...);
        blt_set_fb(back ? ... : FB_BASE, ...);   // 翻转，back 恒为 0
        back ^= 1u;                  // 立刻被下一轮的 back = 0u 覆盖
    }

⇒ **每帧都画 buf[0]、每帧都显示 buf[0]，buf[1] 从未被绘制**。这是 2026-10-17 为定位「精灵不显示」而改成的诊断模式（注释写明），一直留到现在。

### 13.1 这改变了「上下条带」的候选原因

既然只显示 buf[0]，屏幕上下两半只能来自同一块 buf[0]，那么上半的橙色点阵就只能是：**清屏没有清到那里**，或者 **扫描输出读的地址/行号与我们认为的不同**。

两者都需要实测配置值来分辨，为此在 f==0 处加了打印：DBG cfg fb=... size=... cfg=... oob=... st=...

但没抓到：重配置后程序约 30 秒就跑到 f=92，之后进入慢态，45 秒窗口只覆盖 f=92..96，错过了 f=0。

## 十四、决定性实测：第一帧清屏被边界检查拒绝（2026-10-24 18:48）

在 f==0 的第一次 blt_fill 之后加打印，冷启动后抓到：

    DBG cfg fb=0x08438000 size=0x04380780 cfg=0x00011000 oob=0x08000000 st=0x00000008

| 字段 | 值 | 含义 |
|---|---|---|
| fb | **0x08438000** | 扫描输出仍指向 **buf[1]** |
| size | 0x04380780 | h=0x438=1080, w=0x780=1920 |
| cfg | 0x00011000 | enable=1, stride=0x1000=4096 |
| oob | **0x08000000** | 有一次写 FB_BASE 被拒 |
| st | **0x08** | STATUS bit3 = addr_oob |

### 14.1 机制

- blt_fill() 没有自己的基址寄存器，引擎用 fb_start/fb_end 做边界检查；
- 这两个值来自**上一次** blt_set_fb，即 8 帧双缓冲测试结束时指向的 buf[1]（0x08438000）；
- 于是 ANIM 段第一帧的 blt_fill(FB_BASE, ...) 目标 0x08000000 < fb_start，**被整条拒绝**；
- buf[0] 上残留的测试图案保留到帧末 blt_set_fb(buf[0]) 才被扫描到。

### 14.3 与视频的关系（必须区分两个固件）

- 用户 17:33 拍的视频跑的是 **10-18 版固件**：back 真交替（双缓冲），所以看到的是**每帧撕裂**的持续条带；
- 现在板上是 10-24 版：back 恒为 0（单缓冲诊断模式），本轮修的是**第一帧 oob**；
- 两者现象相似但成因不同：撕裂=翻页时机；残影=第一帧清屏被拒。**修完 oob 后若条带只剩一条稳定的分界，就说明剩下的确实是撕裂。**

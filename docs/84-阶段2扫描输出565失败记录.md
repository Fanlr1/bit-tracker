## 〇、一句话

**`async_fifo_gray` 在 `DW=128 / AW=9` 下报告『非空』而实际为空**，读指针跑到写指针前面。

## 三、★ 根因（VCD 证据，t 单位 ps）—— **见上方修正，本节结论已作废**

t=32380000  prefetch_d = 1      ← rd_hold <= fifo_rdata 在此执行
t=32380000  fifo_rdata = 0      ← 但 FIFO 输出是 0

2. `fork` 的两个分支**不能共用循环变量** —— 共用时 reader 拿 writer 的索引比对并读越界。

**★★ 剩余嫌疑（按可能性排序）**：

   8 像素组的节奏下，可能需要在**明确的 `rd_px` 值**上载入（即把它做成状态机而不是靠相位巧合）。
2. **`rd_valid` 的自举项** `(~rd_valid & ~prefetch_d)` 在 8 像素组下的行为。
3. **`de_raw & (rd_px == N)` 的门控** —— `de_raw` 可能与 8 像素组的节拍不同步。

**★★★ 下一步最省的实验（还没做）**：

一眼就能看出节奏是否如设计所想 —— 本轮的每一次推断（六次）都被实测推翻，说明**该直接看节奏，而不是猜相位**。

## 三·补2 ★ 第三轮（2026-10-15 23:32）：找到硬事实 —— `rd_hold` 载入时刻晚了 2 拍

**方法修正生效了**：不再猜相位，而是从 VCD 直接算出「`rd_hold` 每次变化时 `rd_px` 等于几」。

```
rd_hold 变化 104 次（t<=40us），每次都是：
  t(ps)      rd_px  prefetch_d
  3020000    1      1
  3340000    1      1
  3660000    1      1        ← 间隔 320 ns = 8 拍 × 40 ns，即每像素组恰好一次
  ...
```

**⇒ 硬事实：`rd_hold` 在 `rd_px == 1` 时被覆盖；而设计要求它在 `rd_px == 7` 载入**
（这样 `rd_px == 0` 才能用上新数据）—— **晚了 2 拍**。
**⇒ 每个像素组都是「旧组的尾 + 新组的头」的混搭**，与「每 8 像素组后几个读出 0」的现象吻合。

**相位扫描（把 `need_group` 的 `rd_px == N` 逐个试）**：

| N | errors | MISMATCH 的**位置** |
|---|---|---|
| 4 | 95514 | col 6,7（组内后 2 个）|
| 5 | 95434 | — |
| 6 | 95354 | col 12-15（组内后 4 个）|
| 7 | 95433 | — |
| 3 | — | col 5,6,7（组内后 3 个）|

**⇒ 相位确实影响错误的【位置】（后 4 个 → 后 2 个 → 后 3 个），但总数始终 ~95000。**
**⇒ 结论：靠「调 `need_group` 相位」治不了本 —— 那是在用相位巧合去凑一个本该显式控制的时刻。**

**★★ 下一步该测什么（明确的修法方向，不是再扫参数）**：
**把 `rd_hold` 的载入改成显式受控**，即不用 `if (prefetch_d) rd_hold <= fifo_rdata;` 这种
「靠 prefetch_d 的相位恰好落在某处」的写法，而是**用一个明确的计数器/状态机**规定：
「本组 8 个像素发完 ⇒ 载入下一组」。这样载入时刻由**组边界**决定，而不是由相位巧合决定。

**★ 为什么这条路径之前没走**：8 像素组的节拍与 `prefetch` 的组合时序耦合太紧，
我前面六次都在调「相位」这个**间接变量**，而没有去动**产生载入的那条语句本身**。
## 三·补3 ★★ 第四轮（2026-10-15 23:45）：找到真正的病根 —— `need_group` 的 `de_raw` 门控

**从前三轮的`rd_hold 在 rd_px=1 载入`这个硬事实出发，推出了机制**：

```verilog
// 原写法（8888 时代沿用）
wire need_group = (~rd_valid & ~prefetch_d) | (de_raw & (rd_px == 3'd6));
```

**`de_raw` 是「行有效」，它在**行起始**尚未有效 ⇒ `rd_px==6` 那一刻 `de_raw` 可能为 0
⇒ 取数被推迟 ⇒ `rd_hold` 落到 `rd_px=1`（正是实测值）**。

### 改成 `rd_valid` 门控 —— 立刻见效

```verilog
wire need_group = (~rd_valid & ~prefetch_d) | (rd_valid && (rd_px == 3'd6));
```

| 版本 | 结果 |
|---|---|
| `de_raw` 门控（原）| `errors = 95354`，每个 8 像素组的后 4 个为 0 |
| **`rd_valid` 门控** | **`errors = 95360`，但前 634 个像素【全对】**，第一个错误在 col 634 |
| `de` 门控 | 更差（row=1 col=0 就错）|

**★ 关键区别**：`errors` 数字相近（都 ~95360），但**错误的性质完全不同**：
- 原来：**每一组都错**（全错）
- 现在：**前 634 个像素全对**，从 col 634 起失锁

**⇒ `errors` 这个总数指标【掩盖了巨大差异】。教训：要看【第一个错误的位置】，不只看总数。**

### 剩余问题（已定位到很窄的范围）

**col 634 = 79×8 + 2 ⇒ 一行 80 组的【最后一组】的第 2 个像素**。
`checks - errors = 95994 - 95360 = 634` ⇒ **恰好前 634 个像素正确**。

**失锁后的值 `got=156`（十进制）= 0x9C**，而按扩展公式反推 `p[4:0]=19`，
对应 **col 156** 的数据 ⇒ **输出的是 478 个像素之前的数据**。

**⇒ 说明 FIFO 的读指针在行尾发生了跳变（读到旧数据），且之后再不恢复。**

**★★ 下一轮该测的（明确）**：
1. **行尾那一刻 `fifo_wcnt` / `wbin_o` / `rbin_o` 的值** —— 看读写指针是否在同一拍发生了非预期跳变；
2. **`rd_valid` 在行消隐期是否仍为 1**（若是，`rd_px` 会在消隐期继续递增 160 次 = 20 组，打乱行对齐）；
3. 若是 (2)，则 `rd_px` 的复位范围要从「帧级 `!v_active`」改成**行级**（每行开始强制对齐）。
## 三·补4 ★★ 第五轮（2026-10-15 23:55）：FIFO 积压 218 entry，且消隐期仍在取数

**在 `rd_valid` 门控（前 634 像素全对）的基线上，抓行尾之后的波形**：

```
t=32420000  rd_px 0      ← 第一行的 col 639 刚发完
t=32740000  rd_px 0      ← 320 ns 后又一轮（= 8 拍），【消隐期仍在取数】
t=32715000  wcnt_o = 218
t=33035000  wcnt_o = 217   ← 每行净减 1
t=33355000  wcnt_o = 216
```

**两条事实**：

| # | 事实 | 含义 |
|---|---|---|
| 1 | `rd_px` 每 320 ns 循环一次，**消隐期不停** | 一行总长 800 拍 = 32000 ns ⇒ 取数 **100 次**，而一行只需 **80 个 entry** ⇒ **多取 20 个** |
| 2 | `wcnt_o` 从 **218** 起，每行减 1 | FIFO 初始积压 218 entry = **1744 像素的显示滞后** |

**⇒ 事实 2 直接解释了「失锁后输出 col 156 的数据」**：FIFO 里积压着很久以前写入的数据，
读指针读到的是**滞后 478 像素**的旧数据，而不是当前行。

**⇒ 事实 1 指出取数与消费的速率不匹配**：消隐期的取数没有被抑制。

**★★ 下一轮该测的（两条，都很明确）**：
1. **抑制消隐期的取数**：`need_group` 的第二项改回按 `de` 相关门控，但要**避免第四轮的 `de_raw` 陷阱**
   —— 正确形态可能是 `de_raw & rd_valid`（即 `de`）**且不依赖它在行首恰好有效**，
   或干脆用「本行已发出的像素计数 == 640」来关闭取数；
2. **让读取与写入按行严格配对**：一行 80 个 entry，取数也应恰好 80 次。
   若这一条成立，`wcnt_o` 应当**每行归零**（而不是每行减 1）。

**★ 方法论收获（第五轮）**：
- `errors` 总数是**坏指标** —— 95354 与 95360 相差 6，但一个是「全错」、一个是「前 634 个全对」。
  **⇒ 必须看【第一个错误的位置】。**
- `wcnt_o`（FIFO 里积压多少）是**极好的指标** —— 它一眼就把「速率不匹配」暴露出来。
  **⇒ 以后调这类流水，先看积压计数，而不是看输出对不对。**
## 三·补5 ★★★ 第六轮（2026-10-16 00:10）：失锁机制确定 —— 行开始前就消费了数据

**在 `rd_valid` 门控基线上，抓第 79/80 组到行尾的波形**：

```
t=32100000  rd_px = 0   rd_hold 载入     ← 相位对齐、开始消费
t=32140000  rd_px = 1                     ← 已经在递增
t=32180000  de = 1, de_raw = 1            ← 【de_raw 到这里才置起！】
```

**⇒ `rd_px` 比 `de_raw` 早 8 拍（整整一组）开始推进 ⇒ 行开始前就消费掉了一整组 8 个像素，
而那 8 个像素因为 `de=0` 从未显示。**

**★ 这个机制精确解释了 col 634**：
```
一行需要 80 组；行开始前白丢 1 组  ⇒ 行内只剩 79 组  ⇒ 少 8 个像素
640 - 634 = 6                       ⇒ 最后 6 个像素读到下一行的数据
```
**与实测「col 634 起错、之后再不恢复」完全吻合。**

### 试过但失败的修法（两个，都已回退）

| 修法 | 结果 |
|---|---|
| `rd_px` 按行归零（`if (!de_raw) rd_px <= 0;`）| **更差**（row=1 col=0 就错）—— 与原注释的警告一致 |
| `rd_px` 递增条件由 `rd_valid` 改 `de` | **更差**（row=1 col=0 就错）|

**★ 两者都失败的原因**：它们都用了**电平**（`de_raw` / `de`），
而电平在行首/行尾的**建立时刻本身就不确定** —— 用它去对齐相位，等于把不确定性引入相位。

### ★★ 下一轮该测的（明确的修法）

**用 `de_raw` 的【上升沿】复位 `rd_px`，而不是电平**：

```verilog
reg de_raw_d;
always @(posedge pclk or negedge rst_n_pclk)
    if (!rst_n_pclk) de_raw_d <= 1'b0;
    else             de_raw_d <= de_raw;
wire line_start = de_raw & ~de_raw_d;     // 行的第一个有效拍

// 然后：
if (!v_active | line_start) rd_px <= 3'd0;
```

**为什么这样能行**：上升沿是一个**边沿事件**，它精确标记「行的第一拍」，
与电平的建立时间无关 ⇒ 相位在每行第一拍被强制对齐，不会累积漂移。

**判据（下次验证用）**：
1. `errors` 应当降到 0（或只剩极少）；
2. **更该看 `wcnt_o`** —— 它应当**每行回到同一值**，而不是每行减 1；
3. 第一个错误的位置应当消失，而不是移动。
## 三·补6 ★ 第七轮（2026-10-16 00:20）：边沿修法也无效

按第六轮的设计实施了 de_raw 上升沿复位：

```verilog
reg  de_raw_d;
wire line_start = de_raw & ~de_raw_d;
if (!v_active | line_start) rd_px <= 3'd0;
```

**结果：错误模式【完全没变】** —— 仍从 col 634 开始，got=156。

### 试过并失败的三个修法（全部已回退）

| # | 修法 | 结果 |
|---|---|---|
| 1 | rd_px 按 !de_raw 电平归零 | 更差（row=1 col=0 就错）|
| 2 | rd_px 递增条件 rd_valid → de | 更差（row=1 col=0 就错）|
| 3 | de_raw 上升沿复位 rd_px | 完全没变（仍 col 634）|

## 三·补7 ★★★★★ 第八轮（2026-10-16 00:35）：决定性发现 —— rd_hold 冻结，这是【卡死】不是【漂移】

**按第七轮的结论「换观测对象、看数据」，直接统计 rd_hold 的更新历史**：

```
rd_hold 变化次数   = 104
最后一次变化时刻   = 34620000 ps = 34.62 us
仿真总时长         = 4800180000 ps = 4.8 ms
⇒ 之后 4.77 ms 里 rd_hold 完全冻结
```

**⇒ 显示被冻结在最后载入的那一组数据上。这正是 got=156 恒定不变的原因。**

**★★★ 七轮相位调试全部无效，因为故障根本不是相位，而是【数据通路停止更新】。**
**这一条推翻了第三～七轮的全部假设（那五轮都在假设「相位漂移」）。**

### 下一步（明确，按顺序走取数链条）

失锁 = rd_hold 在 34.62 us 后不再更新 ⇒ 取数链条某一环停了：

1. **prefetch / fifo_re 是否还在脉冲**（若停 ⇒ need_group 不再成立）；
2. **fifo_empty 是否恒为 1**（若恒 1 ⇒ 写侧停了，查 fifo_we / m_axi_rvalid）；
3. **rd_valid 是否恒为 0**（若恒 0 ⇒ 自举项 ~rd_valid & ~prefetch_d 本应重新拉起，除非死锁）。

**★ 过程教训**：本轮之前的 VCD 脚本在 t=50us 处 break，导致后段信号未被统计 ——
**时间窗口必须覆盖全程，否则「冻住」会被误读成「从未变化」。**
## 三·补8 ★ 第九轮（2026-10-16 00:50）：第八轮的「冻结」是误判 —— 全程覆盖后一切正常

**第八轮的结论建立在「rd_hold 最后变化于 34.62 us」之上。本轮把时间窗口覆盖到全程后重测**：

| 信号 | changes | nonzero | first_nz | **last_change** |
|---|---|---|---|---|
| fifo_re | 30001 | 15000 | 340000 | **4800060000** |
| prefetch | 30001 | 15000 | 340000 | **4800060000** |
| rd_px | 119995 | 104995 | 460000 | **4800180000** |
| rd_hold | 15000 | 14988 | 740000 | **4800100000** |
| m_axi_rvalid | 381 | 190 | 215000 | 4788415000 |
| fifo_empty | 2 | 1 | 0 | 340000（之后恒 0 = 一直非空）|

**仿真总长 4800180000 ps。所有信号都活跃到仿真结束** ⇒ **没有卡死，取数一直在进行。**

**⇒ 第八轮的「rd_hold 冻结」是【误判】**：那个统计脚本在 `t > 50000000`（50 us）处 `break`，
所以「最后变化 34.62 us」只是**扫描窗口的边界**，不是信号真的停了。

### ★ 这是第 8 次误判，共同模式很清楚

| # | 误判 | 被什么推翻 |
|---|---|---|
| 1 | FIFO 在 DW=128 下坏掉 | tb_async_fifo_dw128 六项全过 |

### 现状（诚实结论）

**根因【未确定】。** 已排除：FIFO 本身 · empty/full 异常 · 数据通路死 · 工具格式 · 三种相位改法 · 卡死。
已知的确定事实只有两条：
1. **`need_group` 的门控从 `de_raw` 改成 `rd_valid` 后，前 634 个像素由「错」变「对」** —— 这是唯一确定的改进；
2. **一行 80 组、`col 634 = 79*8+2`**，失锁恰好发生在最后一组的第 2 个像素，且 `checks - errors = 634`。

### 下一步该测什么（留给下一轮）

**不要再调相位。** 应该做的是一个能【一次判定】的实验：
**把 `FB_W` 从 640 改成 8 的倍数但更小的值（如 64 或 128）**，让**一行只有 8 或 16 组**。
若错误模式随之改变（例如变成 0 错误，或失锁点变成 col 62），就能立刻区分：
- 与**行长度**有关（组数累加类问题）
- 还是与**运行时长/帧数**有关（时间累积类问题）

这比继续在 640 像素的行上逐拍考古便宜得多。
## 四、为什么回退而不是继续修

病根在**异步 FIFO 的 CDC 内部**（`rempty` 依赖两级同步后的写指针），而那是现成的、带大量历史注释的组件；
改动 `DW/AW` 触发它，修它需要深入跨时钟域时序 —— 成本与风险都不值得在此时投入。

## 六、★ 教训（本次最值钱的一条）

**改一个【共享组件】之前，应当先在它【自己的测试台】里验证新参数。**

- 这个 FIFO 同时服务现有的 96 位通路和设想的 128 位通路；
- 我直接改了整条扫描输出通路，然后把『像素全错』当成通路问题来查；
- **如果先花 10 分钟在 `tb_async_fifo_gray` 里跑通 DW=128，本可以立刻判定是 FIFO 而不是通路。**
- 省掉那一步的代价：多轮 VCD 调试。

**⇒ 规则：动共享组件的参数 ⇒ 先跑它自己的测试台。**

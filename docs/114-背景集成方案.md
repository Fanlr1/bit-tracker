### 3.2 空闲区间与放置结论

| 空档 | 大小 | 说明 |
|---|---|---|
| 0x0887_0200 – 0x08A0_0000 | ≈1.56 MiB | SPR 与 GAME 素材之间，碎片空闲 |
| 0x08A0_7A00 – 0x0900_0000 | ≈6.0 MiB | GAME 素材后、gallery 前（**可放 4 MB 背景的备选位置，如 0x08B0_0000**） |

### 3.3 背景行跨度：BG_STRIDE vs GSTRIDE（任务书要点）

| 方案 | BG_STRIDE | 全屏 COPY 的 ss/ds | 每矩形擦除 COPY 的 ss/ds | 占用 | 备注 |
|---|---|---|---|---|---|
| **A. 当前 WIP** | **4096** | 4096 / 4096 | 4096 / 4096 | 4.22 MiB | 源=目的行距；两 buffer 行起点均 4 KiB 对齐，实现最简 |
| B. 紧凑（任务书假设） | **3840（=1920×2）** | **3840** / 4096 | **3840** / 4096 | 3.96 MiB（省 276,480 B） | 源行距≠目的行距，但 `gfx_copy` 的 ss/ds 是独立寄存器，完全合法 |
| C. 逐 sprite 紧凑 | 不适用 | — | — | — | **不可行**：紧凑源要求 `SRC_STRIDE==w*2` 且 `w·h≤128`（`docs/130` §5.1）；擦除矩形宽 4/6/8/16/32/64，ss 恒为背景行距，永远走普通路径 |

- **建议**：保持 A（当前 WIP 已写进代码，省一行 256 B 的 gain 不值得改 3 处 ss 参数）；只有在 DDR 空间吃紧时才切 B，切换点 = `bg_build` 的行指针、`game_bg` 的 ss、擦除循环的 ss（共 3 处）。
- 两种方案的**擦除事务数完全相同**（普通路径：源每行 1 读 + 目的每行 1 写）；差别只在 DDR 占用与 4 KiB 跨界形态。

## 四、背景数据如何进 DDR

### 4.1 为什么必须板端生成（方案对比）

| 方案 | 可落地性 | 代价 / 结论 |
|---|---|---|
| 编进固件（C 数组 / assets.h 风格） | ✗ | 裸 RGB565 4.15 MB；片内 RAM 仅约 124 KiB（`docs/104` §六），当前固件 bin 也只有 ~32 KB |
| 主机串口上传原图 | ✗ | 115200 bps 下 4.4 MB ≈ **384 s**，且 DDR 掉电易失（`docs/104` §十一-11），每次上电都要重传 |
| 写进 SPI flash 再由程序搬运 | ✗/高风险 | flash 0x380000 是 bootloader 的 32 KB 应用区（`docs/104` §四/§十二）；没有 4 MB 搬运通路与 flash 读驱动，改 bootloader 风险高 |
| **板端 CPU 程序化生成到 DDR（采用）** | ✓ | 一次性写 2,073,600 像素；当前占位版 lead 注释 ~0.1 s；精细版估 **0.3–0.6 s**（含 3–5 octave 噪声），需上板用 mcycle 实测 |

### 4.2 现状（lead 已落地）

| 代码 | 行号（快照） | 作用 |
|---|---|---|
| `#define BG_BASE 0x0B400000` / `BG_STRIDE 4096` | `game.h:45-46` | 背景位图位置/行距 |
| `bg_build()` | `game.h:259-303` | 占位版：天空渐变 + 1400 颗星 + 60 颗亮星 + 侧栏 + HUD 分隔线；CPU 逐像素写 DDR |
| 调用点 | `main.c:790-793` | `gallery_build(); brown_init(); bg_build(); gfx_fb(...)` —— **在显示使能之前**，不跟扫描输出抢 DDR |

### 4.3 数据格式与正确性

- 格式：**RGB565、小端、行主序、行内无 padding**；行首地址 = `BG_BASE + y*BG_STRIDE`，像素 = `row[x]`（`volatile uint16_t*`）。
- 生成期间显示未开（`gfx_fb` 之后才 `FBCFG=1`，`gfx.h:174-180`），DDR 只有 CPU 写，**无扫描读竞争**，所以 0.1~0.6 s 不会造成欠载。
- **CPU 写完 → 引擎读之前必须 fence**：建议在 `bg_build()` 末尾补 `gfx_fence()`（`gfx.h:80-86`，`fence rw,rw`），保证 store 队列对引擎的 AXI 读可见；现有 `game_assets_upload()` 依赖同一假设但从未显式 fence，属潜在偶发风险（可一并补）。
- 生成器必须是**确定性整数/定点算法**（RISC-V 无 FPU，浮点会链 soft-float 且慢）；PNG 与 C 允许逐像素不完全一致，PNG 是验收样张，C 版允许近似（星点位置、噪声细节可不同，构图/亮度/层次必须一致）。

## 五、擦除：用背景 COPY 恢复

### 5.1 当前实现（已改，直接可用）

`game.h:1205-1218`：

```c
// ---- erase whatever this buffer was last given
for (i = 0; i < g_rbn[b]; i++) {
    uint32_t sz = g_rb_size(g_rb[b][i].k);          // 4/6/8/16/32/64
    int32_t  ry = (int32_t)(int16_t)g_rb[b][i].y;
    uint32_t rx = (uint32_t)(uint16_t)g_rb[b][i].x;
    gfx_copy(BG_BASE + (uint32_t)ry * BG_STRIDE + rx * 2u,   // 源：背景位图
             back     + (uint32_t)ry * GSTRIDE  + rx * 2u,   // 目的：back buffer
             sz, sz, BG_STRIDE, GSTRIDE);                    // ss≠ds 合法
    ncmd++;
}
```

旧版（渐变背景）在这里按 `bg_col_at()` 取色、跨 `G_SEG_H=144` 边界时拆成 2 条 fill；新版恒为 1 条 copy。

### 5.2 参数与矩形来源

| 项 | 值 | 依据 |
|---|---|---|
| 擦除矩形尺寸 | 4、6、8、16、32、64 | `g_rb_size()` `game.h:225-232`；记录点 `g_spr()/g_box()` `game.h:210-223` |
| `rx, ry` | 精灵左上角像素坐标（任意整数） | 写入 `g_rb` 的位置就是绘制坐标 |
| 源地址 | `BG_BASE + ry*BG_STRIDE + rx*2` | 2 B 对齐（rx 任意）；**不要求 16 B 对齐**（只有紧凑源路径才要求，这里永远不走紧凑） |
| 目的地址 | `back + ry*GSTRIDE + rx*2` | 同上 |
| 越界 | 引擎**只查 dst**，且 dst 在 `[0x0800_0000,0x0C00_0000)` 内恒成立 | `docs/130` §4.5；rx/ry/sz 由游戏各处 clamp（如 `game.h:1208-1209` 屏幕检查、物理层 clamp） |
| 源越界 | **完全不查**；若 ry 或 rx 超出 1920/1080 会读到下一行/别的数据 | `docs/130` §1 规则 8；**因此背景图必须按 1920 宽、1080 高完整生成**，且擦除坐标不能越界（当前游戏逻辑保证） |

### 5.3 命令数变化（≈不变，略降）

| 对象 | 旧实现命令数 | 新实现命令数 |
|---|---|---|
| 不跨渐变边界的擦除 | 1（fill） | 1（copy） |
| 跨 `G_SEG_H=144` 边界 | 2（拆两条 fill） | 1 |
| 跨边界概率（均匀假设） | 8×8 ≈5.5%、16×16 ≈11%、32×32 ≈22%、64×64 ≈44% | 0 |

⇒ 命令总数基本不变，**大精灵略降**；CPU 侧还省掉了 `bg_col_at()` 的分支与取色。

### 5.4 事务数/耗时（引擎模型：0.42 µs/事务 + 0.008 µs/beat，`docs/130` §7.2）

| 擦除矩形 | FILL（旧） | COPY（新） | 差值 | 额外读取字节 |
|---|---|---|---|---|
| 4×4 | 4 事务 ≈1.7 µs | 8 事务+8 beat ≈3.4 µs | **+1.7 µs** | 32 B |
| 6×6 | 6 ≈2.5 µs | 12+12 ≈5.1 µs | +2.6 µs | 72 B |
| 8×8 | 8 ≈3.4 µs | 16+16 ≈6.9 µs | +3.4 µs | 128 B |
| 16×16 | 16 ≈6.9 µs | 32+32 ≈13.8 µs | +6.9 µs | 512 B |
| 32×32 | 32 ≈13.5 µs | 64+256 beat ≈28.9 µs | +14.5 µs | 2,048 B |
| 64×64 | 64 ≈26.9 µs | 128+1024 beat ≈62.1 µs | +31 µs | 8,192 B |

> 注 1：普通路径是「源每行 1 次读事务 + 目的每行 1 次写事务」；紧凑源路径（整块 1 次突发）不可用，因为 `src_stride(=BG_STRIDE) == sz*2` 不成立（`docs/130` §5.1 条件 b）。
> 注 2：rx 不是 8 像素整数倍时，16 B beat 会多 1 个/行（≥16×16 时 beat 项才会到 0.1 µs 级），**事务数不变**，可忽略。

## 六、双缓冲：两个 back buffer 都要初始化背景

| 机制 | 位置（快照） | 说明 |
|---|---|---|
| 标记 | `g_bg_dirty`（`game.h:160`），值 = 还欠几个 buffer 的背景 | 2 = A、B 各一次 |
| 消费 | `game_frame()` `game.h:1311-1319`：`if (g_bg_dirty) { g_bg_dirty--; nb = game_bg(back); g_rbn[b]=0; g_hud_dirty=2; return nb; }` | 每帧只重画**当前 back buffer**，两帧覆盖 A/B |
| 全屏拷贝 | `game_bg()` `game.h:304-311`：`gfx_copy(BG_BASE, back, GW, GH, BG_STRIDE, GSTRIDE)` | 1 条命令；ss=BG_STRIDE、ds=GSTRIDE |
| 置位点 | `game_enter` L534-543；升级菜单确认 L1338-1340；横幅消失 L1178-1182；标题/结束→开始 L1369-1372；暂停恢复 L1375-1376 | 每次「战场内容被平色/文字覆盖后」都要重画两个 buffer |
| 顺序 | `bg_build()`（`main.c:792`）在 `gfx_fb`（L793）**之前** | 显示未开，无欠载风险 |

**代价**（模型）：全屏 COPY = 1080 行 ×(18 读 + 18 写) = **38,880 事务 ≈16.3 ms + 约 52 万 beat ≈4.2 ms ≈ 20.5–21 ms**；
旧版 11 条 fill（HUD+分隔线+7 段战场+2 侧栏）≈1,084 行×18 + 2×948 行侧栏 ≈21,400 事务 ≈**11 ms**。⇒ 每次重画 **+约 9.5 ms**，两个 buffer 共 **+约 19 ms**（一次 1~2 帧的停顿，全部发生在非战斗态，可接受）。

**HUD 条**：背景位图 y<132 由 `bg_build` 写成平色 `G_HUDBG` + 4 行 `G_ACC` 分隔线（`game.h:263-302`），与 `game_hud()` CPU 文字的底 cell（`G_HUDBG`，L482/491/494）一致。**背景美术不要往 y<132 画细节**，否则会被平色 HUD 覆盖或露出文字底块。

**注意**：全屏 COPY 的 20 ms 内扫描输出同时在读另一 buffer，DDR 读瞬时增加约 4.2 MB/20 ms ≈ 206 MB/s（实测扫描余量 1.35 GB/s、需求 509 MB/s，`交接-GFX重写-20261030-2320` §2.1），余量充足；但仍要观察 `G_UNDER` 是否上升。

## 七、性能分析

### 7.1 模型

`t(µs) ≈ 0.42 × N_txn + 0.008 × N_beat`（1408 精灵实测标定，误差 <3%）。**事务数主导，beat 次要；引擎一次只执行一条命令**（`docs/130` §6/§7.2）。

### 7.2 满负载（压力模式 B 填满池）每帧额外成本

池上限（`game.h:86-91`）：E8 140、GEM 120、KN 80、E16 16、PA 60、ORB ≤6、玩家 1；实际绘制时 E8/GEM/KN/ORB 都按 **16×16** 画、E16 按 **32×32**、玩家 64×64、粒子 4/6。

| 对象 | 数量上限 | 擦除矩形 | 每擦多读事务 | 合计事务 |
|---|---|---|---|---|
| E8 敌机 | 140 | 16×16 | +16 | 2,240 |
| GEM 经验球 | 120 | 16×16 | +16 | 1,920 |
| KN 飞刀 | 80 | 16×16 | +16 | 1,280 |
| ORB 环绕球 | 6 | 16×16 | +16 | 96 |
| E16 大怪 | 16 | 32×32 | +32 | 512 |
| PA 粒子 | 60 | 4/6 | +4~6 | ≈300 |
| 玩家 | 1 | 64×64 | +64 | 64 |
| **合计** | ≈423 | — | — | **≈6,412 事务** |

⇒ **+≈2.7 ms/帧**（最坏满池）；常态（约一半对象）**+≈1.3 ms/帧**。写事务数完全不变，只有源读增加。

### 7.3 DDR 带宽

- 新增读字节 ≈ 140×512 + 120×512 + 80×512 + 6×512 + 16×2048 + 60×~36 + 8192 ≈ **217 KB/帧** ⇒ 60 fps 下 **≈13 MB/s**，占扫描需求 509 MB/s 的 **2.5%**、实测容量 1.35 GB/s 的 **1%**。
- ⇒ 成本在**事务往返延迟**（0.42 µs/个），不在带宽；这与 `docs/130` §7 的结论一致。

### 7.4 与 CPU / 帧预算

- CPU 侧：擦除命令数不变，且省了 `bg_col_at()` 分支；`PROF rend≈11.1 ms`（命令构造 = 每命令 10 次寄存器写）**不会变差**（`交接-GFX重写-20261030-2320` §2.5）。
- 帧预算 16.67 ms：满池时引擎侧新增 2.7 ms 是唯一实际风险。若压到掉帧，按优先级：① 合并相邻擦除矩形（见 §十一）；② 降池上限；③ 接受菜单/切换时的一次性代价（本来就有）。
- 旧版「按行脏矩形擦除」的开销本就占每精灵 ≈1/3；背景 COPY 把它变成 ≈2/3，单精灵总成本 25→33 事务（+32%）；1408 精灵的压力场景 14.8 ms → 估算 **19.5 ms（≈51 fps）**——**该场景会掉 60fps，游戏内满池（≈423 对象）不会**。

### 7.5 一次性成本

| 项 | 估算 | 状态 |
|---|---|---|
| `bg_build()` 启动生成（2,073,600 px CPU 写） | 占位版 ~0.1 s（lead 注释）；精细版 **0.3–0.6 s**（含噪声/多图层） | **未上板实测**，需用 `mcycle` 量 |
| 全屏 COPY 重画背景 | ≈21 ms / buffer（模型） | 同上 |
| DDR 占用 | 4.22 MiB（stride 4096）/ 3.96 MiB（3840） | 不占片内 RAM |

## 十一、风险与后续

| 风险 | 评估 | 对策 |
|---|---|---|
| 满池帧率 | 引擎侧 +2.7 ms；游戏常态 +1.3 ms | 先实测 PROF；必要时合并相邻擦除矩形（见下）或降池 |
| 擦除矩形合并（可选优化） | 同 buffer 内相邻矩形合并成 1 条 COPY：如两个 8×8 = 32 事务，合成 16×8 只需 16 事务（行数不变、读写各 1/行；合并后宽 >112 px 才拆段） | 只在满池掉帧时做；合并逻辑放 CPU 侧、纯整数 |
| 全屏 COPY 与扫描争抢 | 20 ms 内多读 4.2 MB（+206 MB/s），余量 1.35 GB/s | 观察 `G_UNDER`；重画本来就只在非战斗态 |
| 未对齐 x 的 beat 翻倍 | 事务数不变，beat 项 ≤ +0.1 µs/矩形 | 忽略 |
| 紧凑 stride 3840 | 省 276 KB，但要改 3 处 ss 参数 | 只有 DDR 吃紧才切；§3.3 有对比表 |
| 未验证 | `bg_build` 实测耗时、全屏 COPY 实测 ms、COPY 期间欠载 | 上板后补测并回填本文 |

# 静态性能建模

> 日期：2026-10-06
> 目的：**在板子到手之前算出理论数字，作为板上实测的对照**
> ⚠️ 本文全部是**计算值**，没有一个数字来自实测。板上实测若与此差距过大，说明有实现问题

---

## 一、DDR3 带宽

### 1.1 理论峰值

```
参数（来自 ddr3_parameter.vh 与 docs/04）：
  DQ_WIDTH = 16 位
  tCK      = 2500 ps  ⇒ 时钟 400 MHz
  DDR 双沿 ⇒ 数据率 800 MT/s

理论峰值 = 800 MT/s × 16 bit ÷ 8
         = 800 × 2 B
         = 1600 MB/s = 1.6 GB/s
```

### 1.2 有效带宽

**⇒ 峰值不可达**，必须扣除：

| 开销 | 说明 |
|---|---|
| **刷新** | `tRFC=350000` ps，每 ~7.8 µs 一次 |
| **行激活** | `nRCD=6`、`nRP=6`（`ddr3_parameter.vh`）|
| **读写切换** | 总线转向需要若干周期 |
| **命令间隙** | 每拍只能发一条命令 |

**⇒ 经验值：连续大块读写可达峰值的 70~85%；随机小访问可能只有 30~50%。**

**本项目是【大块连续访问】**（BitBlt 按行突发、视频按行突发）⇒ **取 75%**：

```
有效带宽 ≈ 1.6 GB/s × 0.75 = 1.2 GB/s
```

## 二、视频扫描输出的带宽占用

```
640 × 480 像素，32 位（ARGB8888）
每帧字节 = 640 × 480 × 4 = 1,228,800 B = 1.23 MB
60 Hz ⇒ 每秒 60 帧

带宽 = 1.23 MB × 60 = 73.7 MB/s
占有效带宽比例 = 73.7 / 1200 = 6.1%
```

**⇒ 视频扫描只吃掉约 6% 的带宽，完全不是瓶颈。**

**⚠️ 但要注意**：**视频读是【实时且不能等】的** —— 即使总带宽充裕，**如果 AXI 仲裁让它排队太久，FIFO 会空、画面会出现闪烁。** 这是**延迟问题，不是带宽问题**。

## 三、BitBlt 的带宽与耗时

### 3.1 三种操作的每像素字节数

| 操作 | 读源 | 读目标 | 写目标 | 合计 |
|---|---|---|---|---|
| **FILL** | 0 | 0 | 4 B | **4 B/px** |
| **COPY** | 4 B | 0 | 4 B | **8 B/px** |
| **ALPHA** | 4 B | 4 B | 4 B | **12 B/px** |
| **KEYING** | 4 B | 4 B（命中时）| 4 B（未命中时）| **4~12 B/px** |

**⚠️ `ALPHA` 需要读目标**，因为公式是 `前景×α + 背景×(1−α)`。

### 3.2 满屏填充（640×480 FILL）

```
字节数 = 640 × 480 × 4 = 1.23 MB
耗时   = 1.23 MB / 1.2 GB/s = 1.02 ms
理论帧率 = 1 / 0.00102 = 980 FPS
```

### 3.3 满屏拷贝（640×480 COPY）

```
字节数 = 640 × 480 × 8 = 2.46 MB
耗时   = 2.46 / 1200 = 2.05 ms
理论帧率 = 488 FPS
```

### 3.4 满屏 Alpha 混合

```
字节数 = 640 × 480 × 12 = 3.69 MB
耗时   = 3.69 / 1200 = 3.07 ms
理论帧率 = 325 FPS
```

### 3.5 64×64 Sprite（Alpha + Keying）

```
字节数 = 64 × 64 × 12 = 49,152 B = 48 KB
耗时   = 48 KB / 1.2 GB/s = 0.04 ms = 40 µs
```

**⇒ 这是关键数字**：**一个 sprite 只要 40 µs**

**⇒ 若一帧 16.7 ms（60 FPS）全部用于画 sprite**：

```
16.7 ms / 40 µs = 417 个 sprite/帧
```

**⚠️ 但这是【纯带宽上限】**，实际还要扣：
- **每个 sprite 的 AXI 事务开销**（地址握手、行激活）
- **引擎的逐行调度开销**
- **CPU 下发指令的时间**
- **与视频读的竞争**

**⇒ 实际可能只有 1/3 ~ 1/2 ⇒ 约 140~200 个 sprite/帧。**

**⇒ 这正是赛题高阶 3 要测的「60 FPS 同屏 Sprite 数量极限」。**

## 四、AXI 层的关键约束

### 4.1 突发长度

```
ARLEN/AWLEN 是 8 位 ⇒ 最大 256 拍
每拍 16 B（128 位）⇒ 单次突发最大 4096 B
```

**⚠️ 而 AXI4 规定：一次突发【不得跨 4KB 边界】** —— **恰好等于最大突发长度，所以 256 拍的突发【必须 4KB 对齐】。**

**⇒ 我们的实际突发：**

| 用途 | 突发长度 | 字节 |
|---|---|---|
| **视频读一行（640 px）** | **160 拍** | **2560 B** |
| **DMA 引擎** | **最多 256 拍** | **4096 B** |

**⚠️ 视频的行起始地址 = `fb_base + row × 2560`**，**不是 4096 的倍数** ⇒ **每 4 行必然跨界一次。**

**⇒ 这是 `21-板上待验清单.md` 里第一优先项** —— **它直接决定「能不能出图」。**

### 4.2 理论的 AXI 效率

```
突发内：每拍 1 个数据 beat，无间隙
突发间：需要重新仲裁 + 地址握手
```

**⇒ 若突发长度足够（160 拍），开销占比 < 5%。** **⇒ 这也是为什么按行突发是对的设计。**

## 五、CPU 侧的开销

### 5.1 软件渲染（对照基准）

**⇒ 逐像素 `store` 到 framebuffer：**

```
RV32IM @ 100 MHz
每次 32 位 store 约 2~3 条指令（计算地址 + 存）⇒ 约 25~30 ns/像素

满屏 640×480 = 307,200 像素
耗时 = 307200 × 27 ns ≈ 8.3 ms
理论帧率 = 120 FPS
```

**⚠️ 但实测会慢得多**，因为：
- **DDR3 写延迟**（store 要进写缓冲）
- **Cache 行为**（数据 cache 命中率）
- **函数调用开销**

**⇒ 合理预期：软件填充 640×480 需要 15~40 ms ⇒ 25~65 FPS。**

### 5.2 硬件渲染的 CPU 开销

**⇒ 只需写寄存器：**

```
BLT_OP / SRC_ADDR / DST_ADDR / SRC_STRIDE / DST_STRIDE / COLOR / WIDTH_H / CTRL
≈ 8 次 32 位寄存器写
每次约 10 个周期（AXI 从设备访问）⇒ 80 周期 = 0.8 µs
```

**⇒ 相比 1.02 ms 的硬件执行时间，CPU 开销可以忽略。**

### 5.3 预期的软硬件加速比

```
硬件 FILL 满屏 : 1.02 ms（受带宽限制）
软件 FILL 满屏 : 15~40 ms（受 CPU 逐像素限制）

加速比 ≈ 15 ~ 40 倍
```

**⚠️ 这是【预期范围】，不是保证值。** **实际受 DDR3 有效带宽与 cache 行为影响很大。**

## 七、⚠️ 建模覆盖不到的

> **★ 2026-10-06 更新：下表中有两条已经查实，见 `docs/40-仲裁与HSIO与4KB查证.md`。**

| 项 | 为什么算不出来 | 现状 |
|---|---|---|
| **AXI 仲裁公平性** | 需要知道 `Axi_Mux` 的仲裁策略与各通道的实际请求模式 | **✅ 已查明** —— **`Cfg_Arb_Type = 1'b1`（优先级），S0（CPU）恒优先 ⇒ 视频会被结构性饿死。改 `1'b0` 即变令牌环轮询。见 `docs/40` §1** |
| **DDR3 行冲突率** | 取决于地址映射（bank/row 交错），`ddr3_top` 加密 | **仍未知** |
| **Cache 行为** | VexRiscv 的 data cache 配置与命中率需实测 | **仍未知** |
| **交叉 4KB 的实际代价** | 取决于 `ddr3_top` 是否拆分突发 —— **未知** | **🟡 部分查明** —— **厂商 UG 全文无任何跨界承诺（不检查、不拆分）⇒ 契约必须由我们遵守；**实际代价仍需板上测**。修法见 `docs/40` §2.4（stride 对齐 4096，比拆分突发简单）** |
| **`tx_cal_clk` 余量的影响** | 时序收敛与否影响的是能否工作，不是快慢 | **已量化**：官方同类 demo 为 0.375~0.398 ns，我们 0.227；**换 PnR 种子可到 0.423**（`docs/40` 关联）** |
| **HSIO 能否承载目标分辨率** | —— | **✅ 已查明**：文档未给 TMDS 上限（1.5 Gbps 是 LVDS/MIPI 的）；**厂商 demo 实测只到 744 Mbps（720p60 / 1080p30）。见 `docs/40` §3** |

**⇒ 这些全部列在 `21-板上待验清单.md`。**

# 81 - 行合并可行性判别：收益完全取决于布点密度（2026-10-15 13:50）

> 无人值守轮次产出，**纯计算，无代码改动、无板上风险**。
> 回答 docs/66 §3 与 docs/78 §四 G 一直挂着、始终没量的那个问题：
> **"同一屏幕行平均被几个精灵覆盖？"** —— 以及由此决定的行合并价值。

## 〇、一句话

**行合并（按屏幕行处理，让同一行的多个精灵共享一次读写）在【密排布点】下是 3.45×，
在【随机弹幕】下是 0.92×（反而更慢）。**
效果**完全由横向覆盖率决定**，而"最大同屏精灵数"这个指标恰好是用密排布点测的 ——
**所以它是一个"针对测量场景的优化"，不是通用加速。**

## 一、方法

按屏幕行统计"精灵实例数"与"被覆盖的像素宽度"，代入 docs/78 的成本模型
`row_cost = a + b × 字节`（`a = 58.9` 拍固定，`b = 0.1694` 拍/字节）：

- **现状**：每个精灵实例各付一次读+写 = `n_row × (a + b × 2 × 64)`
- **行合并**：整行读+写各一次 = `a + b × (2 × 7680)`

三种布点各 1024 / 2048 精灵，屏幕 1920×1080，精灵 16×16×4 B。

## 二、结果

| 布点 | 覆盖屏幕行 | **实例数/行** | **横向覆盖** | **行合并收益** |
|---|---|---|---|---|
| **A. 密度扫描网格**（`cols = 1920/16 = 120`）| 288 / 1080（n=2048）| **113.8** | **94.8%** | **3.45×** ✅ |
| **B. 随机弹幕**（均匀撒布）| 1080 / 1080 | **30.3** | **25.3%** | **0.92×** ❌ |
| **C. 聚簇弹幕**（高斯聚簇）| 1080 / 1080 | 30.3 | 25.3% | **0.92×** ❌ |

**★ 读法**：行合并把"每行 N 次读+写"压成"每行 1 次读+写"，**代价是读整行**。
密排时那 94.8% 的覆盖率让整行几乎全是有效数据 ⇒ 赚 3.45×；
随机时只覆盖 25.3% ⇒ **读整行的浪费超过省下的往返，净亏 8%**。

**★ "只读被覆盖的区段"能救吗？** 表里理想化的 `merged*` 看似很高（随机布点 16.79×），
但那**假设所有区段连成一片**。随机布点下 30 个精灵散布在 1920 像素宽里，
区段**几乎必然是不连续的** ⇒ 退化成"每精灵一次" ⇒ **无收益**。
只有聚簇布点（区段部分合并）才有中间值（2.77×，且随聚簇程度剧烈变化）。

## 三、这个结论为什么重要

**"60 Hz 内最大同屏精灵数"这个指标是用【密度扫描】测的，而密度扫描正是网格密排（场景 A）。**

| 若目标是 | 行合并的价值 |
|---|---|
| **把实测的最大同屏精灵数往上推**（赛题口径）| **3.45×** —— 2048 甚至 4096 都可能进 60 Hz ✅ |
| **让真实弹幕游戏更流畅**（随机布点）| **0.92×，反而更慢** ❌ |

**⇒ 行合并不是"通用加速"，它是一个【针对测量场景】的优化。这一点必须写清楚，
否则将来会有人按"它能加速 3 倍"去实现，然后发现游戏 Demo 变慢了。**

## 四、如果要做的实现代价（未做，仅评估）

| 项 | 内容 |
|---|---|
| 遍历重构 | 现在"逐精灵、每精灵 16 行"；行合并要"逐屏幕行、每行处理所有覆盖它的精灵" ⇒ **walker 与 top 的控制流重写** |
| 精灵视图 | 需要"按 y 分桶/排序"的空间索引，否则每行都要扫全部精灵描述符 |
| 行缓冲 | 1920×4 B = **7.7 KB ≈ 1 个 RAM10**（余量充足：现用 97/256）|
| 与扫描输出的关系 | 天然共用"按行读帧缓冲"的模式 —— **这是它最吸引人的地方** |
| 通用性代价 | 引擎不再是通用 BitBlt（大块搬运无收益），且**随机布点下会变慢** |

**⇒ 工作量：最大（docs/78 §四把它列为"架构重写"）。在剩余轮次内**不可能完成**，
且它与"真实游戏变慢"的风险绑定 —— 无人值守下**不做**。**

## 五、对后续的意义

1. **行合并的价值判据量化完成**：看横向覆盖率，**≳90% 才划算**（密排），
   25% 时净亏。**此前 docs/78 估的"每行 ≳18 个精灵"过于乐观** —— 真正的判据是**覆盖率**，不是实例数。
2. **描述符批量（2.2%）与纹理缓存（11.7%）的上限已在 docs/80 钉死**，都不足以达标。
3. **提并发已被五个实验封死**（docs/79 §八 + docs/80 §五）。
4. **⇒ 结论：在当前架构下，2,048 没有可完成的路径。**
   唯一有 3× 潜力的行合并，需要架构重写，且只在密排布点下成立。

# 76 - 扩表到 2048：先试便宜的杠杆（2026-10-15 凌晨）

> ⚠️ **本文 §8 的最终结论已被 [77](77-扩表2048的真相-元凶是综合选项.md) 推翻 —— 读 §8 之前请先读 docs/77。**
>
> - **2048 扩表已经成功上线**（2026-10-15 08:31）：XLR **45,065（74.1%）**、slack **+1.488 ns**、串口 3,827 字节、**12 PASS / 0 FAIL**。
> - 七次失败的真正原因**不是占用率**，而是综合选项 `use-logic-for-small-mem = 0` ——
>   它把 DDR 控制器内部的小 FIFO 从**逻辑实现**改成 **RAM10**（map 报告里的 `MEM|SYN-0690 Inserted write-first bypass`），
>   **DDR 挂掉 ⇒ SoC 起不来**。
> - **§8 的"扩表判据是占用率压到 90% 以下"是错的** —— 66.8% 的版本照样起不来。
> - 之所以七次都没查出来：**每次都同时改了 N 和面积选项**，两个变量一起动。
>
> 接 [75](75-性能退化的真相-扫描输出开关.md)。75 把"性能退化"证伪了 —— 它其实只是**扫描输出的开关**。
> 于是瓶颈回到它本来的位置：**表深 1024**。本文是把它拿掉的那一步。

## 一、为什么要扩表（账要算清）

| 约束 | 数值 | 说明 |
|---|---|---|
| 表深（硬顶）| **1,024 精灵** | `bitblt_sprite_state` 的 `N` |
| 算力（1,666,666 ÷ 1,230）| **1,355 精灵** | 1,230 是 75 确认的**真实基线**（有 1080p60 显示在跑）|

**⇒ 卡住极限的是表深，不是算力**：算力允许 1,355，表只给 1,024。
**⇒ 扩到 2048 能把极限提到 1,355（+32%）** —— 这是目标里"提高最大同屏精灵数"最直接的一条路。

（注意：2048 精灵**进不了** 60 fps —— 那需要每精灵 ≤ 813 拍，而实测 1,230。扩表的价值是让**极限**从 1,024 升到 1,355，不是让 2048 全进预算。）

## 三、第二次尝试：先动综合的面积选项（不改 RTL 结构）

只差 2.6%，所以先试**最便宜的杠杆** —— `bitblt_system.xml` 里的两个参数：

| 参数 | 原值 | 改成 | 意图 |
|---|---|---|---|
| `pack-luts-to-comb4` | 0 | **1** | LUT 打包更紧凑 |
| `use-logic-for-small-mem` | 64 | **0** | 小存储器不再用逻辑（LUT）实现 |

同时改 RTL（`.N(2048)` + `parameter N = 2048`）与软件（`BLT_SPR_MAX` 2048、`BLT_SPR_WORDS` 64、密度扫描加 2048 档）。

**两个要盯的风险**：
1. **`use-logic-for-small-mem=0` 会让 RAM10 用量暴增吗**（原 77/256）—— 把所有小存储器塞进 RAM，实例数可能翻几倍；
2. **面积优化会吃掉时序余量吗**（`core_clk` slack 原 1.525 ns）。

## 六、如果还放不下：备选方案已摸清

把 `ok`/`lv` 从"寄存器 + 组合位选择"改成 **RAM 读**。依据是 `bitblt_sprite_state.v` 自己的注释：

> Registers, not RAM: `rd_valid` and `rd_live` are both needed **combinationally** in the cycle the walker picks a destination, and the RAM has a **2-cycle read latency**.

**可行性核对**：
- **量级对得上**：2048:1 的 1 位 mux 树约 683 LUT，**两个 ≈ 1,366**，缺口 **1,573**；
- **walker 不用改状态机**：`rd_idx`（= `cur_index`）从 `S_FETCH` 起就固定，等描述符要几十拍，**2 拍延迟被完全盖住**；
- **写路径三条**（seed / sweep / retire），而 **sweep 本来就是"逐槽读-改-写"**，顺路带上即可；
- **`rt` 不用动**：它是 `+:` 32 位切片（`rt[{rt_wsel,5'b0} +: 32]`），便宜得多。

**顺带确认一件事**：`rt_word` 的索引收窄**已经做过了**（RTL 注释：*"Leaving it 16 bits wide cost 1493 LUTs"*）⇒ 没有更多"白拿"的空间可捡。

## 六·补、表优化（2026-10-15 已实施）

**动机**：与其继续试合成开关，不如**把 LUT 真正省下来**。层级报告显示缺口全在 `u_spr_state`，
而它最贵的部分是 `ok[idx]`/`lv[idx]` 两棵 2048:1 组合选择树。

### 实施内容：`lv` 并入 payload RAM，`ok` 保持位向量

| 项 | 改动 |
|---|---|
| **payload RAM** | 64 → **66 位**：`{unused, lv, vy, vx, y, x}` |
| **`lv`** | 从"独立位向量 + 组合选择"改为 **payload 的一个位** |
| **`ok`** | **保持不变**（位向量 + 组合选择）|
| **`rd_live`** | `ram_rdata[64]` —— 与 `rd_x`/`rd_y` **同一次读**，不新增延迟 |
| **三条写路径** | seed：一次写全；reclaim：写全 0；**sweep 本来就是"读→算→写回"，顺路带上 `lv`**，零额外状态 |

### ★ 为什么没有把 `ok` 也搬进去（一次被测试台拦下的设计错误）

第一版把 `ok`/`lv` **都**放进了 RAM，并用一个"逐槽写 0"的状态机处理 `clr_valid`。
**测试台立刻失败**：

```
FAIL  clr_valid clears the valid flag of a seeded slot
FAIL  clr_valid clears it for every slot, not just the one selected
```

tb 是这么写的：

```verilog
@(negedge clk); clr_valid = 1'b1;
@(negedge clk); clr_valid = 1'b0;          // 只持续一拍
check("clr_valid clears ...", rd_valid === 1'b0);
```

**`clr_valid = ~reg_spr_enable` 是电平，而 `blt_spr_arm` 每帧都在"清 enable → 置 enable"，间隔只有几十拍**
—— 清空 2048 个 RAM 槽需要 **2048 拍**，**每帧都清不完**。这个方案在当前接口下根本跑不起来。

**修正后的逻辑更简洁**：

> **`lv` 只在 `ok=1` 时才被读**（walker 先分支 `rd_valid`）⇒ **单拍清 `ok` 就让所有 `lv` 失效**
> ⇒ `clr_valid` 的**单拍契约一字不改**，`lv` 也**永远不需要被清空**。

**⇒ 省下的是"一棵树"而不是"两棵树"，但换来接口不变、tb 不用改、每帧路径零风险。**

### 收益

| 来源 | 省（LUT）|
|---|---|
| `lv` 并入 payload（消除一棵 2048:1 mux 树）| **~683** |
| `pack-luts-to-comb4=1` + `use-logic-for-small-mem=0`（已验证无害）| **1,358** |
| **合计** | **~2,041** |
| **缺口** | **1,573** ✅ |

### 验证

| 项 | 结果 |
|---|---|
| `tb_bitblt_sprite_state` | **PASS** |
| 全量回归 | **PASS=25 FAIL=0 SKIP=1** |

### 综合配置与结果

**刻意弃用 `mode=area`**：它能放下（LUT 36,943），但 `core_clk` slack = **−0.274 ns**（时序违例）。
本目标的判据明确写了"不接受时序违例"，所以改用：

```
mode = speed  +  pack-luts-to-comb4 = 1  +  use-logic-for-small-mem = 0
```

日志：`work/logs/build-payloadopt.log`。**结果待填**（判据：cluster ≤ 60,800 且 slack ≥ 0）。

## 六·补2、把 `ok` 也搬进 RAM（2026-10-15）

`lv` 搬进去之后，同样的理由适用于 `ok` —— 它是另一个 2,048 位的位向量。

### 一个巧合省掉了所有位宽调整

表优化时为了让 `lv` 有位可放，payload 从 64 加宽到 66 位，其中 **bit65 一直空着**（原本是 `ok` 的位置）。
**把 `ok` 放回 bit65 ⇒ 位宽一位都不用改**：

```
[65] ok   [64] lv   [63:48] vy   [47:32] vx   [31:16] y   [15:0] x      = 66 位
```

### 真正的障碍是 `clr_valid`，解法是 `clr_busy`

`clr_valid = ~reg_spr_enable` 是**电平**，而 `blt_spr_arm` 每帧做"清 enable → 置 enable"，**间隔只有几十拍** ——
而 `ok` 进 RAM 后清空需要 **N 槽**（RAM 一个周期一个地址）。

**⇒ 新增 `clr_busy` 输出，`bitblt_top` 用它门控 walker 的使能**：

```verilog
.enable (reg_spr_enable & ~spr_clr_busy)
```

**代价**：那一帧的 walker 晚启动 ~8,192 拍（N=2048，约 82 µs），占 16.67 ms 预算的 **0.5%**。

### ⚠️ 过程中修掉的两个真实 bug（都值得记）

**bug 1：`1'b0 // bit65: unused` 在 `ok` 搬进来之后变成了"误清 ok"**

`lv` 搬进去时，sweep 的两个分支写成：

```verilog
ram_wdata <= { 1'b0,          // bit65: unused
               1'b0,          // lv: cleared
               ...
```

后来把 `ok` 放进 bit65，**这两处的注释和值都没跟着改** ⇒ 退休和推进时都把 `ok` 清成了 0。

**症状与 RTL 里那段长注释预言的一字不差**：

```
FAIL frame2 blit count = 4 want 3 (slot 3 should be retired)
FAIL frame2 dst[0] = 08000000 want 08000a08 (state did not advance)
```

> **ONLY lv is cleared here, NOT ok.** Clearing ok as well looked equivalent and was wrong:
> `ok=0` is what tells the walker "this slot was never seeded"... A retired slot would then be
> **re-seeded and drawn again on the very next frame** —— the testbench caught exactly that,
> with frame 2 dispatching **4 blits instead of 3**.

**⇒ 教训：往一个位域里塞新含义时，"unused" 的注释是**定时炸弹** —— 它不会报错，只会让旧值在新语义下变成错误。**

**bug 2：清空写整个字，把位置也擦了**

第一版清空是 `ram_wdata <= 66'd0`，**违反契约**：

> The POSITION is not erased -- only the valid flag. **bitblt_top relies on clr_valid to disarm
> the table without losing what was loaded**, so a re-seed does not have to repeat it.

**⇒ 改成读-改-写**（每槽：读出来 → 屏蔽 ok/lv → 写回，保留 x/y/vx/vy），清空从 1 拍/槽变成 ~4 拍/槽。

### testbench 的契约更新（两条）

| tb | 改动 |
|---|---|
| `tb_bitblt_sprite_state` | `clr_valid` 后用 `while (clr_busy)` 等清空走完，而不是只给 1 拍脉冲 |
| `tb_bitblt_top` | 等 `busy` 上升的窗口 **2,000 → 20,000** 拍；density 用例 **5,000 → 30,000** |

**density 用例的失败很有诊断价值**：失败档的 `cycles` 精确等于 **5,006 = 窗口 5,000 + 6** ——
说明循环是**等满窗口才退出**的，`busy` 在那段时间里根本没起来。而成功档的 AR 数完全正常（384、1024）。

## 八、最终结论：止损（2026-10-15 02:15）

**2048 扩表在"能跑"这一关上没过去，尽管综合层面已经完全成功。** 七次尝试：

| # | 配置 | XLR / 60,800 | core slack | 结果 |
|---|---|---|---|---|
| 1 | 直接改 N | 62,373（102.6%）| — | ❌ 超容量 1,573 |
| 2 | + `pack-luts-to-comb4=1` + `use-logic-for-small-mem=0` | 61,015（100.4%）| — | ❌ 超 215 |
| 3 | + `mode=area` | 放得下 | **−0.274** | ❌ 时序违例 |
| 4 | + `mode=cong` | 58,983（97.0%）| +0.633 | ⚠️ 放得下，**SoC 起不来**（ROM 全 `0xb7`）|
| 5 | + `operator-sharing=1` | 58,964（97.0%）| +0.945 | ⚠️ LUT 省 555 但 routing 涨 568，净省 19 |
| 6 | **+ `ok`/`lv` 全进 payload RAM** | **46,899（77.1%）** | **+0.858** | ✅ **综合完美，SoC 仍起不来**（ROM 全 `0x00`）|
| 7 | 第 6 项改用 `mode=speed` | **46,899（77.1%）** | **+0.858** | ⚠️ **与第 6 项逐位相同** |

### ★ 第 6 项是真正的技术成功（但没能上板）

`ok` 位向量搬进 payload RAM：**省 12,065 个 XLR（19.8%）**，是我估算 683 的 **17 倍** ——
连带消掉了 2,048 个触发器、它们的写使能逻辑、以及整个扇出网。
占用率 **77.1% 比能正常运行的方案 A（79%）还低**，全量回归 **25 PASS / 0 FAIL**。

**⇒ 这个改动本身是对的，只是不足以让 2048 启动。**

### ⚠️ 未解之谜（留给下一个会话）

**只改了 `bitblt_sprite_state` 的 N 和两个位的存放位置，却能影响 SoC 的 ROM 初始化** ——
而 77% 的占用率已经排除了"拥挤"这个解释，`speed`/`cong` 逐位相同也排除了"综合模式"。

**⇒ 尚未排查的方向**：
1. 对比两版 `ip/soc` 里 ROM 的初始化 hex 文件
2. 逐块 diff 两个比特流（2,614,221 B vs 2,564,619 B）
3. 检查 Efinity 是否为 SoC 的 BRAM 生成了初始化数据

### 为什么止损

**扩表的收益是"极限 1,024 → 1,355（+32%）"，而"慢状态"那条线是 1.4× 且不碰容量、不碰 SoC。**
七次尝试里最后一次的失败原因不明 —— 那意味着后面还有未知的坑。

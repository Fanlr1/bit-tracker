## 一、为什么不能只做回归

本项目的两次「假 PASS」已经说明：**回归通过只证明「没改坏」，不证明「改对了」。**

**⇒ 所以每一项修复都配一个【反向验证】**：临时退回旧实现，确认测试**确实会失败**。
**⇒ 若退回后测试仍通过，说明这个测试根本没在测那件事** —— 报告批评的正是这类「从不失败的检查」。

## 三、几个值得单独记的点

### 3.1 报告的价值在于「找到测试本身的缺陷」

**第 1、2、9、10 项都不是 RTL 缺陷，而是【验证手段的缺陷】**：

- **`sim.ps1` 只看退出码** ⇒ 11 个 TB 的结论都不可信
- **审计脚本数模块名** ⇒ 防不住它声称要防的那类事故
- **TB 无条件打印 PASS** ⇒ 按 PASS grep 会假通过
- **TB 只测一种配置** ⇒ 忽略参数的 DUT 照样 PASS

**⇒ 这些比单个 RTL bug 更根本** —— **因为它们让「改对了没有」这个判断本身失效。**

### 3.2 两个变体的对照特别有说服力

**变体 A（AWADDR）**：旧 RTL 下**其余 5 项检查全部 PASS**，只有 `awaddr` 那一项 FAIL。

**⇒ 说明地址漂移【不会让任何功能测试失败】，它只是静默地写到错误地址。**
**⇒ 报告说它「不是理论隐患」是准确的，这也解释了它为何能潜伏至今。**

**变体 B（B 握手）**：旧 RTL 下 `TIMEOUT state=2 awvalid=1 wvalid=1 bvalid=1`。
**⇒ 状态机和从设备【互等】，正是「BREADY 从未拉高」的形态。**

### 3.3 自己踩过的坑

**写这些脚本/改动时，同一个坑踩了三次**：

| 坑 | 表现 | 正解 |
|---|---|---|
| **Verilog 的 `'` 出现在 PowerShell 字符串里** | `8'h30` 里的 `'` 提前终止字符串，**报错却指向无关行** | **用 `edit` 工具，别在 shell 里拼 Verilog** |
| **`$Args` 是 PowerShell 自动变量** | `Start-Process` 抛终止性错误，**脚本中断但外层拿到 exit 0** | 改名 `$ArgList`；**并对启动失败显式判 FAIL** |
| **编译失败后仍跑旧的 `.out`** | **把上一次的结果当成新的** | **先确认 compile exit = 0 再看运行输出** |

**⇒ 第三个尤其危险**：它让我两次差点把旧数据当成新结果。**这正是「验证手段不可靠」的又一种形态。**


### 8.6 ★ 中断驱动尝试：无效，但排除了一个重要假设（2026-10-17 03:1x）

**动机**：既然慢态下每次寄存器读要 1,865 拍（正常 10 拍），那让 `blt_wait()` 改等中断、
循环里不碰寄存器，似乎就能绕开。demo 里 `interrupt-driven fill` 那项测试一直 PASS，机制现成。

**实现**：`blt_wait()` 改为混合式 —— 先短等内存标志 `g_done_irq`（5,000 次，约 1.5 万拍），
等不到再回退到带退避的轮询；`blt_start()` 同时置上 `BLT_CTRL_IRQ_EN`。

**结果**：**无效**。单次 blit 仍是 3,810,565 拍（退避版 3,727,870，基本不变）。

**为什么无效（这一条推翻了我上一步的假设）**：

那 373 万拍**不是 CPU 的等待开销，而是引擎真实的工作时间**。
中断要等引擎完成才会来，所以短自旋必然等不到、回退轮询；
而无论等中断还是轮询，**等待的都是同一个 373 万拍**。

⇒ 所以「CPU 轮询抢总线」是本轮**早期**的观察（它确实让扫描输出饿死、也让 hw 从 4.4 亿降下来），
但**剩下来的 373 万拍是引擎自己慢**，与等待方式无关。

### 8.7 慢态的最终形态（诚实版）

| 事实 | 数值 |
|---|---|
| 单次 blit 耗时 | **3,727,870 ~ 3,810,565 拍**（正常态 197 拍）|
| 慢态 hw 的稳定性 | ±0.05%（7 轮）|
| 监视器握手超时 | **0**（sticky=0）|
| 两个读引擎 FSM | **32/32 采样都在 IDLE** |
| walker | IDLE, busy=0 |
| 五个 busy 分量 | **全 0** |
| DDR / SoC 侧 AR / R 握手 | **空闲** |

**⇒ 引擎花了 373 万拍，而所有可观测的总线、模块、FSM 都显示空闲。**
慢点落在**没有被观测到的地方**：Axi_Mux 内部的仲裁延迟、SoC 内部的读路径，
或引擎内部未引出的状态。

### 8.8 下一步（唯一还值得做的观测）

**在引擎内部打时间戳**，把一次 blit 拆成几段：AR 发出 / 首个 R beat / rlast / done，
各记一个 cycle 快照（BRAM 槽或 GPIO 观测口都可承载），对比正常态与慢态，
定位这 373 万拍花在哪一段。

已具备的条件：观测多路器（4 组）、BRAM 槽机制、`state_o` 端口模式（Efinity 禁层次引用）、
以及 `forensics.ps1` 这类自动取证脚本。

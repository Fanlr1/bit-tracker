# 77 - 扩表 2048：上线成功，以及七次失败的真实原因

> 接 [76](76-扩表到2048.md)。76 的结论是"占用率压不到 90% 以下就别想上板"，
> 并据此**止损**。**本文推翻那个结论并完成扩表** ——
> 真正的元凶是一个综合选项；N=2048 从未在"被证明可跑的选项集"下测过。

## 〇、一句话

**精灵表已扩到 2048 槽并在板上跑通（12 项测试全 PASS、0 失配）；
60 Hz 内最大同屏精灵数实测为 1,376（原上限 1024，+34.4%）。**
让 SoC 死掉的不是 N=2048，是 `use-logic-for-small-mem = 0` ——
它把 DDR 控制器内部的小 FIFO 从**逻辑实现**改成 **RAM10 实现**，DDR 挂掉，SoC 起不来。
**占用率 66.8% 的版本照样死**，所以"90% 判据"是错的。

## 二、关键实验 2A：把变量减到一个

`N=1024 + ok/lv 进 RAM + 方案A原选项` —— **这个组合从未测过**。

- 综合：XLR **41,820（68.8%）**、`core_clk` slack **+1.387 ns**、RAM10 **77**
- 上板：串口 1,458 字节，核心测试全 PASS（`copy-readback-1000x` **0 失配**）

**⇒ 结论**：ok/lv 进 RAM **本身无害**，且省 **6,980 XLR（48,800→41,820，−14.3%）**。
把 N 和选项分开之后，"2048 之谜"立刻塌缩成一个选项问题。

## 四、根因机制（map 报告原文）

对比 2A/2C（`use-logic-for-small-mem = 64`）与失败版的 `bitblt_system.map.rpt`，
差异**全部集中在 memory 映射消息**：

**能跑的版本**：
```
"MEM|SYN-0657" : Mapping into logic memory block 'logic_ram' (16/32/4/60 bits)
                 ... because size is too small (<=64)
```

**失败版（`use-logic-for-small-mem = 0`）**：这些 memory 不再走逻辑，改为 RAM10，并触发
```
"MEM|SYN-0690" : Inserted write-first bypass logic for memory block
                 'u_sapphire_soc/.../system_ddr_ddrLogic_arbiterAxi4Write/cmdRouteFork...'
```

**⇒ 被改掉的是 `system_ddr_ddrLogic_*` 里的 FIFO，即 DDR 控制器内部的小存储器。**
改成 RAM10 后读写语义/延迟变了（工具要靠 `write-first bypass` 补救），**DDR 控制器因此挂掉**。
旁证：RAM10 由 77 涨到 80，多出的 3 个正是这些被"赶"进 RAM 的 FIFO。

## 五、要纠正的两条（docs/76 的结论）

| 76 的说法 | 实际 |
|---|---|
| 「扩表的真正判据是**占用率要压到 90% 以下**」 | ❌ **错**。66.8% 的版本也起不来。正确判据是**别动 `use-logic-for-small-mem`** |
| 「只改了 `bitblt_sprite_state` 的 N，为什么会让 SoC 的 ROM 读不出来？」 | ✅ 因为**同时**还改了综合选项；N 本身从未被单独测过 |

**★ 为什么七次都没发现**：第 1 次改 N 超容量 ⇒ 第 2 次加面积选项 ⇒ 之后**一直带着**它。
**两个变量一起动，就永远分不清是谁的错。**

### ⚠️ 一个尚未定论的观察：1,210 ≠ 971

同一份程序里，**密度扫描**每精灵约 **1,210 拍**，而 **PROBE start** 是 **971 拍/精灵**（同样 64 精灵、同样布点、同样测法）。

**最可能的解释**：密度扫描的精灵是**静态的**（`vx=vy=0`，永不被 retire），n 个精灵**一直留在屏幕上**，
扫描输出要读 n 份像素，与引擎争 DDR 带宽（这正是 docs/75 的"带宽分享"）。
PROBE 跑在表被重置为 64 之后，扫描输出负载轻得多。

**⇒ 因此"1,376"应读作【精灵全部上屏】这一最坏情况下的上限。**
**不要**用 971 去反算一个更大的数（它含固定开销，`62,144 = a + 64b`，不能当边际成本用）——
要验证需另做实验（例如让精灵都移到屏外后再测同一密度）。

**★ 慢状态仍在（下一个 1.4× 目标）**：本次 PROBE 显示
`start 971 → after-dbuf 1518 → after-game 1455` 拍/精灵，`short_cnt` 从 2,312 万涨到 **9.53 亿**，
但 `sticky=0`、`rd0/rd1_AR_wedged=0`。而密度扫描时是**快状态**（1024 档 = 1,214 拍/精灵）。

## 八、教训

1. **一次只改一个变量**。七次失败的根源不是 Efinity 的 bug，是**实验设计**。
2. **"占用率"不是唯一判据**。相同占用率下，改变 memory 的实现方式足以让 SoC 死掉。
3. **`use-logic-for-small-mem` 不要动**。默认值 64 有意义：让 ≤64 bit 的小存储器走逻辑。
   设为 0 会碰 DDR 控制器内部 FIFO —— **这类改动最贵：表面省 XLR，实际断掉启动路径**。
4. **日志会累积**。`outflow\*.warn.log`/`.err.log` 每次综合**追加**一段，
   文件大小只反映**综合次数**，不代表警告变多（本次差点据此误判）。
5. **程序级超时杀前台调用，但子进程会活下来**。本次第一次综合即如此（`efx_pnr` 成了孤儿）。
   "复用 pnr 结果"那次侥幸对了，但**不能依赖** —— 之后一律跑完整流程。
6. **对照实验要"只差一个变量"**。2A/2C 之所以一击命中，就是因为它们与失败版**只差选项**。

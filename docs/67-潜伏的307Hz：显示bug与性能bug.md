# 67 - 一个潜伏的 307 Hz：既是显示 bug，也是性能 bug（2026-10-14 夜）

## 一、一句话

板上扫描输出实际一直是 **640×480 @ 307 Hz**，不是 1080p60 —— 因为 `system_top` 把
`bitblt_video_out` 实例化成了 640/480。**修复后：真正的 1080p60，且引擎快了 24%。**

## 二、怎么发现的

在给"为 1080p60 加自证计数器"接线时，读到实例化点：

```verilog
// rtl/system_top.v:1265（修复前，未提交改动）
bitblt_video_out #(
    .H_ACT   (640),          // ← 覆盖了模块默认的 1920
    .V_ACT   (480),          // ← 覆盖了模块默认的 1080
    .FIFO_AW (11),
```

**算一下就知道后果**：

```
H_TOTAL = 640 + 88 + 44 + 148 =  920
V_TOTAL = 480 +  4 +  5 +  36 =  525
pix_clk = 148.5 MHz（docs/41 实测）
帧率 = 148.5e6 / (920 × 525) = 307.5 Hz    ← 任何 HDMI 显示器都不会亮
```

## 三、git 证据：这个 bug 被修过，又回来了

| 来源 | H_ACT/V_ACT |
|---|---|
| `git HEAD:rtl/system_top.v` | **没有这两行**（继承默认 1920×1080）✅ |
| 工作区（未提交） | **`.H_ACT(640)` / `.V_ACT(480)` 又出现**，连警示注释一起删掉 |

而提交 `126585b` 的标题正是：*"fix: the video-out instance never produced 1080p60 -- it produced 307 Hz"*。
**⇒ 修复被一次未提交的编辑覆盖了。**

## 四、为什么它能潜伏这么久

**因为从来没有人接过显示器。** 所有"跑通"的证据都来自**串口测试**——它们检查引擎寄存器、
像素回读、帧时间，**唯独不检查视频输出**。PLL 确实做到了 148.5 MHz（docs/41 是真的），
但实例参数把它算成了 307 Hz，而这件事只有显示器或示波器看得见。

**⇒ 典型的"验证盲区"：通路两端都验过，中间那一段没有。**

## 五、意外收获：修显示配置让引擎快了 24%

反直觉，但算得通 —— **问题在行请求率**：

| 配置 | 每秒行请求 |
|---|---|
| 480p @ 307 Hz | 525 × 307 = **161,175** |
| 1080p @ 60 Hz | 1125 × 60 = **67,500** |

**扫描输出每行发一次 AXI 读请求**。那个错误配置让它的行请求率高了 **2.4 倍**，
持续挤占引擎的总线时间 ⇒ **画错的画面一直在偷走引擎约 1/4 的性能**。

**每精灵 6,794 拍**（217,394 ÷ 32）。

## 七、我的疏漏（记录在案）

上一轮我给"demo 参数画像"时，把扫描输出写成 **1080p60** —— 依据是
`bitblt_video_out.v` 的参数默认值、SDC 的 148.5 MHz 约束、以及 docs/41 的结论。
**但我没有核对"实例化点是否覆盖了这些默认值"。**

**⇒ 判据**：查一个模块的实际参数，**必须看实例化点**，不能只看模块声明。
"模块默认值 ≠ 实例实际值"。

## 八、待验证

**板上现在确实在输出 1080p60**，但这一点**仍然只能靠显示器确认**（OSD 会直接报分辨率和刷新率）。
**⇒ 接一台显示器是目前最高优先级的验证动作**，它同时确认：HDMI 物理链路 · 分辨率/刷新率 ·
画面内容 · 颜色与数据对齐。

（无显示器时的替代：板载"每帧有效行数 + 累计帧数"计数器，从串口读回数字证据。）

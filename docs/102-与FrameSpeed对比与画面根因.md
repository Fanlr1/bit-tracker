# 102 - 与 FrameSpeed-Engine 的逐项对比：画面抖动/撕裂的真根因

> 对照仓库：https://github.com/rinofairy/FrameSpeed-Engine（同赛题，640×480@60Hz，可稳定运行）
> 本文回答用户的问题：**"引擎真的能通过测试吗？为什么测试全过、画面却抖又裂？"**

## 一、先认账：我们的测试根本没覆盖显示通路

| 我们的验证 | 覆盖什么 | **不覆盖什么** |
|---|---|---|
| 29 个 iverilog 测试台 | 引擎往 DDR 写/读的数据正确性（fill/copy/blend/键控/裁剪）| **扫描输出把内存变成屏幕这一段** |
| 13 项板上自测 | 同上 + 帧率/密度/中断 | **画面撕裂、抖动、行错位** |
| `copy-readback-1000x` 0 错 | 内存里像素对 | **屏幕上是不是那些像素** |

⇒ **测试全绿是必要条件，不是画面正确的充分条件**。用户从第一天就说"你那些都是读串口测出来的"，这是对的。

## 二、逐项对比

| 维度 | FrameSpeed | 我们 | 后果 |
|---|---|---|---|
| 分辨率 | 640×480@60（pclk 25.2 MHz）| 1920×1080@60（pclk 148.5 MHz）| 带宽 36.9 vs 249 MB/s |
| AXI 位宽 | 32 位 | 128 位 | — |
| 单次突发 | **16 beats = 64 B** | 原 256 beats = 4 KB，现 64 beats = 1 KB | R 通道独占时长 |
| 行缓冲 | **BRAM 双行 bank**（ping-pong）| **FWFT FIFO 4096 px（流式）** | **见根因 1/2** |
| 行完整性 | **行首判断 `ready_row`，整行统一** | **每像素判断 `~fifo_empty`** | **行内半黑半白 = 抖动** |
| 帧序号 | **`epoch` 每行带标签** | **无** | **翻页后旧帧数据继续混入 = 撕裂** |
| 换帧 | mailbox + `pending/accepted_seq` | 直接写 `FB_BASE` 寄存器 | 无切换保护 |
| 欠载 | **整行黑（"never shifted pixels"）** | 行内 de 抖动 | 视觉撕裂 |
| 引擎/扫描 AXI | **两个核心互斥共享一组端口**（`fs_blitter`）| 4 个主设备并发 + Axi_Mux 仲裁 | 见根因 3 |
| 读仲裁 | **专用 `fs_read_arbiter`（40 行）** | Axi_Mux 通用仲裁 | 见根因 3 |

## 三、三个根因（按对"画面难看"的贡献排序）

### 根因 1 ★★★：翻页时 FIFO 里的旧帧数据没有被作废

我们翻页只做一件事——写 `FB_BASE`：

    blt_set_fb(back, FB_W, FB_H, FB_STRIDE, 1);

但此时 **FIFO 里还压着上一帧/当前帧的几百个像素**。翻页那一刻，扫描输出正从 FIFO 里读旧数据，读到 FIFO 空才去读新地址 ⇒ **同一帧里，上半部分是旧缓冲内容、下半部分是新缓冲内容** ⇒ **水平撕裂**。

FrameSpeed 用 `epoch` 解决：

    wire ready_row = (bank_ok && bank_row == y && bank_epoch == epoch);
    // 旧 epoch 的行 → ready_row=0 → 整行黑

**修复方向**：翻页时**清空 FIFO 并重置行计数**（最简单），或引入 epoch/seq 校验（更彻底）。

### 根因 2 ★★：行内 `de` 随 FIFO 空而翻转

    de = h_active & v_active & ~fifo_empty;   // 每像素都看

FIFO 在一行中间干涸时，**前半行有画面、后半行黑**——视觉上就是"横向撕裂/闪烁"。FrameSpeed 的规则是：

    wire good_pixel = (x == 0) ? ready_row : row_ok;   // 行首定，整行同一状态

**修复方向**：在 `x == 0`（行首）锁存 `row_ok`，**整行用这一个值**；欠载时整行黑。

### 根因 3 ★★：Axi_Mux 的 R 通道可被单个从设备锁死

    wire M_R_End = M_R_Ready & M_R_Valid & M_R_Last;

R 通道一次只服务一个主设备直到 `rlast`。任何从设备 `rready` 长期为 0（例如视频 FIFO 满、或 CPU 被打断），**整条 R 总线停摆** ⇒ 引擎读、CPU 读全部排队 ⇒ 表现是"慢态（读 58,000 拍）"乃至**完全挂死**（实测 openocd `Halt timed out`）。

FrameSpeed 没有这个问题，因为它**只让一个核心访问 AXI**：

    // fs_blitter.v：两条绘制路径共享端口并【互斥占用】
    wire reject = psel && penable && pwrite && ((scan_selected && legacy_busy) || (!scan_selected && scan_busy));

**修复方向**：给 Axi_Mux 的 R 通道加**超时/强制切换**；或让扫描输出的 `rready` 永不为 0（例如 FIFO 满时丢弃新数据而不是停止接收）。

## 四、还有一个"数据正确但画面不对"的隐患

`SPRITE_BASE = 0x08870000` **正好等于帧缓冲池尾** `fb_end`。而 `buf[1]` 最后一行的数据范围是 `[0x0886FF00, 0x08870E00)`，**尾部 0xE00 字节落在池外**（因为 stride 4096 > 行宽 3840）。扫描输出读最后一行时会读进 `SPRITE_BASE` 的内容 —— 这正是用户多次截图中**屏幕最底部那一条异常内容**。

**修复方向**：把 `SPRITE_BASE` 挪到 `0x09000000`（池外远处）。

## 五、按"性价比"排序的修复计划

| 顺序 | 改动 | 文件 | 预计收益 |
|---|---|---|---|
| **1** | 翻页时清 FIFO + 重置行/像素计数 | `bitblt_video_out.v` | **消除撕裂**（最大视觉改善）|
| **2** | 行首锁存 `row_ok`，整行统一 de | `bitblt_video_out.v` | **消除行内半黑** |
| **3** | `SPRITE_BASE` 挪到 0x09000000 | `main.c` / `game.h` | 消除底部异常带 |
| **4** | Axi_Mux R 通道超时/强制切换 | `Axi_Mux.v` | 消除总线锁死（否则前 3 项都白搭）|

**注意**：第 1、2 项是"画面难看"的直接原因，但它们**依赖 AXI 不再锁死**才能看到效果。建议 4 与 1/2 **同批做**。

## 六、结论

- **引擎（写内存）确实是对的**：29 个测试台 + 1000 次 copy-readback 0 错，这部分不是幻想。
- **显示通路（内存→屏幕）几乎没被测试覆盖**，而抖动/撕裂全部发生在这里。
- **不需要全盘重构**：缺的是 `bitblt_video_out` 的"行完整性 + 帧序号"两小块逻辑（FrameSpeed 对应代码不到 30 行），以及 Axi_Mux 的 R 通道兜底。

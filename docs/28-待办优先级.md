## 三之二、⭐ 排序的**前提**：报告 > 代码（2026-10-08 用户明确）

**⇒ 原文：「不是不比代码轻，是**比代码重多了**，因为评委基本上不会去复现，最多跑个仿真，
初赛基本就看**文档和演示视频**，看你做了什么来评审。」**

**⇒ 所以本文件的排序逻辑必须建立在这一点上：**

| 优先级 | 项 |
|---|---|
| **1** | **技术文档完整、清楚、数字对得上** |
| **2** | **演示视频**（含赛题要求的「纯 CPU vs 硬件加速」帧率对比） |
| **3** | **能跑起来**（板上一跑就出图 —— 这是视频的前提） |
| **4** | **代码**（RAR 是存在性证明；评委至多跑仿真） |

**⇒ ⚠️ 而第 3 条仍是一切的**前提**：视频拍不出来，第 1、2 条就无从谈起。**
**⇒ 详见 [50](50-提交材料清单与要求.md) §「评审的实际权重」。**

## 四、排序逻辑

**⇒ 只有一条：**能上板验证的事优先**。** **⇒ 理由是评分顺序（基础 → 高阶 → 创新），而本项目**基础要求一次都没在板上跑过**。** **⇒ 在没有板上结论之前，任何新的 RTL 功能都是在**增加未验证面**，而不是在增加分数。**

**⇒ 而当板子没到、上板的事一件也做不了时，第二优先是**降低上板那一天的摩擦**：脚本就绪、步骤可执行、失败时知道去看哪一项。** **⇒ 本会话的这一批（A1/C4/A3）就是按这个逻辑做的。**

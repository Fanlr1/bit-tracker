## 一、三个部件

| 部件 | 文件 | 做法 |
|---|---|---|
| **(a) 描述符读取器** | **复用 `bitblt_dma_rd`（S1）** | **描述符恰好 16 字节 = 1 个 128 位 beat，一次取一张，无需跨拍拼装** |
| **(b) 状态存储** | **`bitblt_sprite_state.v`** | **片上寄存器阵列：每 sprite 的 `x/y/vx/vy` + 一个 valid 位** |
| **(c) 遍历引擎** | **`bitblt_sprite_walker.v`** | **`读描述符 → 查状态 → 分派 blit → 等完成 → 下一个 → 帧末 sweep`** |

## 二、两个关键设计决策

### 决策 1：共享源读引擎，而不是新增 AXI 主

**⇒ `Axi_Mux` 是 `X5`，五个从端口全占（SoC / 源读 / 目标读 / 写 / 扫描输出）。** **⇒ 新增第六条要改 `X5` 宏、仲裁、以及 `system_top` 四十多个端口映射 —— 为一个小功能动互连，代价与收益不成比例。**

**⇒ 而**遍历引擎只在 blit 之间活动**，那正是源读引擎空闲的时候 ⇒ 二者**天然互斥**。**

```
读描述符时:  u_rd_src 归 walker      → 数据送 walker
blit 执行中: u_rd_src 归源读（P3 路径）→ 数据送像素引擎
仲裁信号:    spr_fetch_active
```

**⇒ 实现是三个 mux（`start`/`base_addr`/`total_bytes`）**加一道门控**：**

```verilog
wire px_in_valid = rd_src_valid & rd_dst_valid & ~spr_fetch_active;
assign rd_src_ready = spr_fetch_active | (px_in_ready & rd_dst_valid);
```

**⇒ 那道门控是**承重的**：没有它，像素引擎会把描述符当像素混进 framebuffer —— **静默的，因为描述符不过是 16 个看起来像数据的字节**。**
**⇒ 而 `rd_src_ready` 里的 `spr_fetch_active` 项也必需：fetch 期间没有目标读在跑，上一轮修的那套互锁会**永远等待**。**

### 决策 2：状态放片上，不放内存

**⇒ 最直觉的做法是把位置存进描述符表、每帧读-改-写。它有两处致命伤：**

| 问题 | 说明 |
|---|---|
| **没有写通路** | **walker 借的是**读**引擎。写回要再借写引擎 ⇒ 第二个互斥问题叠在第一个上** |
| **带宽** | **与扫描输出共用一条 1600 MB/s 的 DDR3，而 1080p60 扫描已占 594 MB/s。每帧对几百个 sprite 做读-改-写，正是最不该花的开销** |

**⇒ 片上状态**每帧零内存访问**，而且**CPU 的职责从「每帧喂」变成「设置一次」**。**
**⇒ 所以这不是妥协，是唯一合理的设计 —— 弹幕游戏每帧把几百个 sprite 状态写回 DDR，**在带宽上本来就行不通**。**

## 三、描述符格式（16 字节，仍是 1 个 beat）

| 偏移 | 字段 | 用途 |
|---|---|---|
| **+0** | **`src_addr [31:0]`** | **sprite 图像地址** |
| **+4** | **`y[31:16] \| x[15:0]`** | **初始屏幕位置** |
| **+8** | **`h[31:16] \| w[15:0]`** | **尺寸** |
| **+12** | **`vy[31:16] \| vx[15:0]`** | **速度（原 `flags\|alpha` 预留字）** |

**⇒ 第 4 个字原本预留，正好放速度 ⇒ **格式尺寸未变**，`x|y` 与 `vx|vy` 布局一致，解包写法也一致。**

## 四、帧的语义

```
CPU: 写 SPR_TABLE / SPR_CTL(enable|count)
  ↓
第 1 帧: walker 读表 → 槽位未初始化 ⇒ 用描述符的 (x,y,vx,vy) 播种状态 → 用 (x,y) 绘制
帧末:    state sweep: x += vx, y += vy（每拍一个槽位，共 N 拍）
  ↓
第 N 帧: 槽位已初始化 ⇒ 【不读表】直接用状态里的 (x,y) 绘制
  ↓
CPU 完全脱离（清 enable 即重新武装，可换一批 sprite，无需复位）
```

**⇒ `S_STEP` 是承重状态：画完最后一个 blit **不等于**帧结束 —— 位置还要推进，而下一帧绝不能走进一个**更新到一半**的数组。** **⇒ `busy` 横跨整个 sweep，所以从调用方看，「帧完成」只能是位置也完成的时候。**

## 五、验证

### 单元与集成

| 测试台 | 覆盖 |
|---|---|
| **`tb_bitblt_sprite_walker`** | **地址递推、字段解析、脉冲计数、**fetch 与 blit 不重叠**、busy 释放、**第二帧位置推进**** |
| **`tb_bitblt_top`（P4 用例）** | **端到端 AR 序列：`AR = 0x2000, 0x4000, 0x2010, 0x5000, 0x2020, 0x6000`** |

**⇒ 那条 AR 序列一个断言覆盖四件事：表被读了、行距是 16 字节、每个 sprite 用了**各自的**源地址（geometry mux 生效）、共享读引擎从未有两个主。**

### 故障注入（证明断言能失败）

| 注入 | 结果 |
|---|---|
| **geometry mux 拆除** | **描述符行仍 PASS，源地址行 FAIL（`00001000` ×3）⇒ 两条断言**互不掩盖**** |
| **描述符步长 `<<4`→`<<3`** | **表地址变 `0x2000/0x2008/0x2010`，两行都 FAIL ⇒ `0x2008` 直接指出是 8 字节步进** |
| **`rd_valid` 恒 0** | **第二帧位置**乱跳**（`08007860` vs `08000a08`）—— 不是不动，是反复重置又累加** |
| **帧末 sweep `x += 0`** | **第二帧差 `0x8` = 2 像素 × 4 字节 = `vx` ⇒ 差值直接点名缺的是哪一项** |

**⇒ 全部四组结果已写入对应测试台的注释（不只留在 commit message 里）。**

## 六、遗留

| # | 事项 | 说明 |
|---|---|---|
| **1** | **生命周期 / 重生未做** | **P4 三部件里的 (b) 只完成了位置与速度。描述符与存储都留了位置，但**没有消费者就不该先加存储** —— 那只会误导** |
| **2** | **N=16，弹幕量级需换 RAM** | **16 个 sprite 只够证明机制、且便于手算。几百个要换 `simple_dual_port_ram`；`bitblt_sprite_state` 的端口已按那个形状设计（一个读索引、一个写索引、无组合读入阵列），改动局限在该文件** |
| **3** | **片上状态与表的一致性** | **表只在首次访问时读。若 CPU 中途改表，已初始化槽位**不会**重读 ⇒ 需清 enable 重新武装。这条语义目前只写在注释里，未加寄存器位显式区分** |
| **4** | **`bitblt_sprite_state` 无独立单元测试台** | **它通过与 walker 的联测被覆盖（第二帧断言直接验证累加），但没有单独测 `clr_valid`、越界索引、`step_en` 重入** |
| **5** | **一帧的时长未实测** | **串行遍历：N 个 sprite × (取描述符 + blit)。N=16 无压力；N=500 时按每 sprite 约 1000 拍估约 5 ms，在 16.7 ms 帧预算内**尚有余量，但未仿真测量** |
| **6** | **新增 RTL 必须登记 xml** | **`bitblt_sprite_walker.v` 与 `bitblt_sprite_state.v` 都已加入 `bitblt_system.xml`。iverilog 靠 `-y` 搜目录、Efinity 只认 xml 列表 ⇒ **新文件会被仿真自动发现、却被综合静默漏掉**。这个坑本轮踩过一次** |
| **7** | **板上验证** | **全部结论仍是仿真与综合层面。这块板子至今未上过电（`docs/21`）** |

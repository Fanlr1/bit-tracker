# 79 - 方向 A 实施：输出 FIFO 改同步读（FWFT）

> 接 [78](78-通往2048的优化方向调研.md)。78 把方向 A 定为"整个优化链条的第一块砖"
> （唯一被实测确认卡住的位置）。本文是它的实施记录。**这一步只换实现，不加深度。**

## 〇、一句话

**组合读的 FIFO 换成了同步读（可落 BRAM）的 FWFT 模块，吞吐仍是 1 拍/字，回归 26 PASS / 0 FAIL。**
深度仍刻意留在 32 —— **同步化与加深分两步走**，否则上板时分不清是谁的效果。

## 一、为什么必须换

| 事实 | 出处 |
|---|---|
| 旧 FIFO 是 `assign dout = fifo_mem[fifo_rd]` —— **组合读** | `bitblt_dma_rd.v`（改前） |
| BRAM 只有**寄存读**，组合读数组**映射不到块 RAM** | docs/38 |
| 所以 2026-10-14 把深度提到 128 时，LUT **22,608 → 40,508**、FF **+21,515**，构建失败并回滚 | docs/66 §7 |
| 而 burst 上限**由 FIFO 深度决定**（准入规则要求整个 burst 装得下）⇒ 深度上不去，AR 数就下不来 | docs/66 §6 |

## 二、做了什么

| 文件 | 内容 |
|---|---|
| `rtl/bitblt_fwft_fifo.v`（**新**）| FWFT 同步读 FIFO：`wr_en/din/full/used/empty` + `dout/dout_valid/dout_ready` |
| `rtl/bitblt_dma_rd.v` | 内部数组与指针**删除**，改为实例化该模块；`fifo_free` 改由 `used` 计算；`dout`/`dout_valid` 来自模块 |
| `tb/tb_bitblt_fwft_fifo.v`（**新**）| 6 组契约测试，见 §四 |

**保持吞吐的关键是"提前一拍预读"**（`rd_ptr` 指向下一个待预读槽位）：

```
wire prefetch = fifo_have & (~out_valid | out_pop);   // 手里没字，或手里的字正在被取走
```

若改成"先寄存输出再暴露"，吞吐会掉到 1/2（预取→呈现→预取…）——这正是 docs/66 §7 警告的坑。

## 三、两个非显然的坑（都真实发生过）

### 3.1 `used` 只能算**数组**占用，不能加输出寄存器

**症状**：集成后 `tb_bitblt_dma_rd` 报 `bursts=6 want 5`，一个 strided 用例直接 **TIMEOUT**。
AR 序列长得一模一样，只是**每个 burst 都短 1**：`+32, +31, +31, +31 ...`

**根因**：输出寄存器里的字**已经离开数组**（`rd_ptr` 已推进）。把它算进占用，就使
**数组明明全空时也只报 31 个空位**。而准入逻辑正是拿这个数去定 burst 长度 ⇒ 每个 burst 短 1 ⇒
burst 总数**上升**（往返更多，正好与优化目标相反）。

```verilog
assign used  = wr_ptr - rd_ptr;          // 数组占用，正确
assign full  = (used == DEPTH[AW:0]);
assign empty = (used == {(AW+1){1'b0}}) & ~out_valid;   // "哪儿都没有字"
```

**★ `empty` 必须反过来包含输出寄存器** —— 旧代码的 `wr_ptr == rd_ptr` 对调用方的含义是
"所有 beat 都被消费了"，S_DONE 依赖它。

### 3.2 可用容量是 **DEPTH + 1**，不是 DEPTH

数组 32 项 **加上**输出寄存器那一个字。所以 `test_fill` 实际写进了 33 个，
而 tb 只 drain 32 个就断言 `empty` ⇒ 误报。**测试改成"以 DUT 实际接受的数目为准"。**

| 测试 | 覆盖 | 结果 |
|---|---|---|
| `test_single` | 单字进出、pop 后 valid 落下 | PASS |
| `test_empty` | 空时 valid=0、空时 pop 不产生数据 | PASS |
| `test_fill_and_throughput` | 填满 / full 含 used / **33 字 33 拍** | PASS |
| `test_backpressure` | 消费者停顿时字**不被预读覆盖** | PASS |

**★ 一个测试方法学教训（写进 tb 注释）**：各 task 共用一个 DUT 实例，
上个 task 结束时**还留在输出寄存器里的字**会被下个 task 当成第一个读走 ——
表现为整段序列错位，看起来像 DUT 坏了。已加 `flush` task 做隔离。
**这是 FWFT 特有的**：组合读版本没有"滞留字"，所以以前不会遇到。

**★ FF 降幅（7,385）≈ 两个 32×128 FIFO 的 8,192 个触发器** ⇒ 存储确实从 FF 搬进了 BRAM；
**LUT 降 4,549** 是组合读那棵 32:1 × 128 位 mux 树消失的结果。**这正是 docs/66 §7 失败时反过来发生的事**
（那时 LUT +17,900、FF +21,515，一块 BRAM 都没用上）。

**★ 面积账**：RAM10 97/256 = **38%**，XLR 55% —— 加深 FIFO 与行级流水都放得下。

## 六、两个流程坑（都会再遇到）

### 6.1 新增 RTL 文件必须在项目 XML 里注册

**症状**：`map` 阶段直接失败 ——
```
ERROR: rtl/bitblt_dma_rd.v(238): instantiating unknown module 'bitblt_fwft_fifo' [VERI-1063]
ERROR: Elaboration of module 'system_top' failed.
```

**根因**：**Efinity 用 `bitblt_system.xml` 里的显式 `<efx:design_file>` 清单**，
不像 iverilog 回归那样用 `-y` 目录搜索。新文件不注册就是"模块不存在"。

**⇒ 修法**：在清单里加一行（本工程加在 `bitblt_dma_rd.v` 之后，XML 第 16 行）：
`<efx:design_file name="rtl/bitblt_fwft_fifo.v" version="default" library="default" />`
（备份 `bitblt_system.xml.bak-20261015-before-fwft-reg`）

### 6.2 "构建失败"与"比特流存在"是两件事

**症状**：构建在 map 失败后，脚本**仍然把上一次的旧比特流烧进了 FPGA**，并报告了一次"实验完成"
—— 而那次测量什么都没测到（串口恰好是旧设计的输出，看起来还正常）。

**根因**：脚本只检查 `Test-Path $bit`。**失败的构建不会删除旧比特流**，所以"文件在"不等于"它是新的"。

**⇒ 修法**（`work/probe/build-and-board.ps1`，已改）：
```powershell
if ($rc -ne 0) { Log 'build FAILED -> NOT touching the board'; exit 1 }
...
if ($bitAge -gt 30) { Log 'bitstream is STALE -> NOT touching the board'; exit 1 }
```

## 七、★ A 第二步（FIFO 32→128 + MAX_BURST 31→127）：试过，**负收益 19%**，已回退

**面积上完全成功，性能上明确失败。**

| 项 | A1（32 深）| **A2（128 深）** | 变化 |
|---|---|---|---|
| EFX_RAM10 | 97 | **97** | **0** |
| XLR | 33,461（55.0%）| 32,923（54.2%）| −538 |
| EFX_LUT4 | 24,045 | 23,542 | −503 |
| **每精灵边际** | 1,206.9 | **1,437.7** | **+19.1%** |
| **60 Hz 上限** | 1,364 | **1,147** | **−16%** |
| `game-40fps-floor` | PASS | **FAIL**（worst > 25 ms）| |

**★ 顺带证实一件事：RAM10 完全没有增加（97→97）。** Efinity 把这些 FIFO 铺在约 6~7 个 RAM10 上
（每个覆盖若干位宽），而那几块的**深度远大于 128** ⇒ **在这个形状下"加深"是免费的**，面积从来不是限制。

### 为什么反而慢了 19%

**两个读引擎共用一条 R 通道，而 burst 一旦开始就不能被打断。**

源数据是紧凑的（一个 16×16 精灵 = 64 beats），FIFO 加深后准入控制允许它一次发 128 beats；
而目标读**每行只要 4 beats**（`row_cap` 禁止 burst 跨行）。于是：

> 源读占住 R 通道传完 128 beats 期间，目标读拿不到它那 4 beats；
> 像素引擎要**两个 reader 同时有效**才消费 ⇒ 引擎饿死 ⇒ 整体变慢。

**这与 2026-10-13 那次系统级死锁是同一个公平性机制（docs/61/63），只是没到死锁。**

**⇒ docs/66 §6 的"FIFO 加深 ⇒ AR 6→2 ⇒ 更快"是错的**：它默认那些往返都属于同一个 reader。
**在共享 R 通道的两个 reader 之间，拉长一个的 burst 是在抢另一个的时间。**

## 八、★ 四个实验的统一规律（2026-10-15 13:30）

到这一步为止，"提高吞吐"的尝试一共有四次，结果可以把机器行为**总结成一条规律**：

| # | 实验 | 改动 | 结果 |
|---|---|---|---|
| 1 | docs/74（2026-10-14）| 写侧不等 B（**无界**在途写）| 慢状态 **4/4** ❌ |
| 2 | 步骤 2 | FIFO 128 **+** burst 128 | **−19.1%** ❌ |
| 3 | **步骤 2b** | FIFO 128，**burst 不变** | **−14.6%** ❌ |
| 4 | **B1** | **有界**在途写（≤2）| **+0.2%，无慢状态** ✅ |

**★ 步骤 2 与 2b 的对比把归因定死了**：两者只差 burst 上限，而**深度本身**就贡献了 14.6% 的损失，
burst 上限只占剩下的 4.5%。**"加深 FIFO"不是无辜的。**

> **规律：DDR 控制器是 in-order 的，当前的请求模式已经落在它的平衡点上。
> 任何【增加在途请求数量或深度】的改动，都会让它更慢。**

这也解释了为什么之前那些"看起来该有用"的优化全部落空 —— 它们都在**加压**，而不是**减负**。

**⇒ 仍然开放的方向只有一类：减少往返的【数量】。**
| 方向 | 机制 | 估算 |
|---|---|---|
| 纹理缓存 | 省掉"读源"的往返 | ~6%（docs/78 §四 D）|
| 描述符批量 | N 次往返 → 1 次 | ~5%（docs/78 §四 C）|
| 行合并 / 扫描线 | 同一屏幕行的多个精灵合并成一次读写 | 2~3×（仅密排布点，docs/78 §四 G）|

**⇒ 提高并发（更深的 FIFO、更多在途、多引擎）在这台机器上是死路，已由四个实验封死。**

## 十一、★ "慢状态"的真相：探针里那个 +42% 是扫描输出被打开（2026-10-15 傍晚）

**结论先行**：PROBE 序列中 `after-readback (1,029) → after-dbuf (1,464)` 的 **+42% 跳变**
**不是退化，而是 `blt_set_fb(..., 1)` 打开了扫描输出**。
`1,464 / 982 = 1.49×`，与 docs/75 的带宽分享预测 `1/(1-0.31) = 1.45×` 吻合。

**证据链（全部来自现有代码与它自己的注释 —— 零新实验、零上板）**：

| 环节 | 证据 |
|---|---|
| 第 4 段之前扫描输出是**关**的 | `main.c:1192` 注释："this call is still the **FIRST** blt_set_fb of the entire run"；`blt_set_fb` 的最后一个参数是 enable，写进 `FB_CFG` 的 bit 16（`bitblt.h`）|
| 该调用**打开了**它 | `main.c:1205`：`blt_set_fb(buf[0], FB_W, FB_H, FB_STRIDE, 1)` |
| 前人已直接验证过这一位 | `main.c:1479` 注释："step 5 measured here with `blt_fb_enable(0)` —— **1,315 → 820** cycles/sprite" |
| 幅度吻合 | 1,464 / 982 = **1.49×** vs docs/75 的 **1.45×** |

**⇒ 三条推论**：

1. **PROBE `start` 的 982 拍/精灵是"扫描输出关"的读数，不代表产品性能。**
2. **密度扫描（第 9 段）测出的 1,204.9 拍/精灵、1,368 上限，才是"带 1080p60 显示"的真实数字** ✓
3. **"慢状态"没有可优化的空间** —— 要显示就必须读 8.3 MB/帧，这是物理账（docs/75 已算过）。
   **唯一能减的是扫描输出本身的带宽（改像素格式），而那会毁掉 alpha 与色键**（docs/46 §3）。

**⚠️ 必须与"快/慢状态"区分开，别合并讨论**：
docs/71/73/74 记录的"1,230 vs 1,730"是**另一个现象** —— 那是**扫描输出都开着**的前提下、
由**设计版本**决定的差异（docs/74 §5：方案 A 4/4 快、方案 B 4/4 慢）。
本节说的是**扫描输出开/关**这一个确定的、可解释的台阶（1.45×）。**两者机制不同。**

**★ 顺带记录的负面结果**：`main.c:1165-1176` 记录了前人四次"从软件侧改 `blt_set_fb` 调用模式"
的尝试 —— **两次直接把应用 wedged**。**⇒ 不要再用软件改动 `blt_set_fb` 做实验。**

**★ 方法论收获**：这条结论**没有用板子、没有改代码** —— 证据一直在源码及其注释里。
凡遇到"某个读数解释不了"，**先读那段代码自己的注释**，成本是零。

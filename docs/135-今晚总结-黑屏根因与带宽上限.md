# 135 · 今晚总结：DVI 黑屏根因 + 4000 精灵的带宽上限（2026-11-02 夜）

> **最终交付**：黄金版 **700 × 16×16 + alpha、59.2 fps、under 恒定 10、shown 完全追随 frames**（无黑屏、无闪烁）。
> **4000 × 8×8 达不到 60fps + 稳定显示**：引擎吞吐与 scan-out 共用 DDR 带宽，二者不可兼得（数据见下）。

## 一、DVI 黑屏：根因与它的真正性质

| 观察 | 证据 |
|---|---|
| 黑屏时串口无输出 | CPU 没跑（配置丢失/卡死），不只是显示问题 |
| `dvi_encoder.v` 输出打拍被人为 bypass | 源码里写着 `// EXPERIMENT: pipeline bypassed`；时序报告 `tmds_data*` slack **-3.7 ns**（与 doc 118 的 900 精灵版同款）|
| 恢复打拍后仍然黑 / 偶发不黑 | **DVI 稳定性由 PnR 布局抽签决定**，不是打拍级数；118 记录过 30 个 seed 全失败 |
| 同 RTL 不同 bit | 有的布局 under=10 shown 正常，有的 under 暴增 shown=0 |
| **黄金版 700（无额外打拍）稳定** | 布局宽松；用户 11-01 确认零黑屏 |

**结论**：DVI 问题是「资源占用 → 布局分散 → TMDS/scan 时序变差」的症状，不是某个孤立 bug。
**降精灵数（降资源）才是根本解法**。

## 二、4000 精灵的带宽上限（三组实测）

| 配置 | 引擎时间 | fps | under/帧 | shown | 结果 |
|---|---|---|---|---|---|
| 4000 + op4（读背景）| 22.7 ms | 34.8 | 45（恒定）| 正常 | 稳但慢 |
| 4000 + op6（不读背景）| 11.6 ms | 53.7 | ~7（增长）| 停滞 | 快但闪烁 |
| 4000 运动引擎（CPU 零写表）| 11.6 ms | 53.7-56.9 | 增长 | 停滞 | 闪烁 |
| 2000 + op6 | ~10 ms | 57 | 暴增 | 0 | 闪烁 |
| 2500 运动引擎 | ~11 ms | 46 | — | — | 表初始化每帧跑（bug）|
| **700 黄金版** | 14.4 ms | **59.2** | **10（恒定）**| **1:1** | ✅ 稳定 |

**物理原因**：引擎与 scan-out 共享 DDR。4000 个 8×8 精灵的引擎事务密度 ≈ 6900 事务/ms，
scan-out 每帧还要读 4 MB → 只要引擎跑满，scan 就欠载 → 显示行重复 → 闪烁。
把引擎放慢到 22.7 ms 就有带宽，但 fps 掉到 35。

## 三、今晚做出来的东西（代码都在）

1. **硬件运动引擎**（`gfx_sprtab.v`）：表项 64 位 {x,y,vx,vy,flag}，遍历器自己积分位置 + 边界反弹 + 写回；
   CPU **只在场景初始化写一次表**，每帧只写 6 个控制寄存器 → CPU 28.1 → **12.3 ms**（省掉 4000 次 AXI 写）。
2. **OP_COPY_KEY_NB(op6)**：key 像素不写（掩码），不读背景 → 引擎 22.7 → 11.6 ms（仿真 5/5 PASS）。
3. **表 RAM 从 48 块降到 9~20 块**（运动引擎方案），PnR 拥塞显著缓解（seed 3 一次布通）。
4. 三个把 map 卡死的综合陷阱已修复并记录：
   - 组合读 4096 深数组元素（`dbg_tab0 = tab[0]`）→ 综合成 13 万寄存器
   - 同 always 块读写同一数组 → BRAM 推断失败
   - 两个独立写源的数组 → 展开成 262k 触发器；必须 mux 成单写端口

## 五、如果还要冲 4000 @60 且稳定

唯一没试的方向是 **同时降引擎密度和保帧率**：
- 引擎命令限速（每 N 周期一条）把 4000 精灵的引擎拉到 ~16 ms，给 scan 留带宽 → 预计 45-50 fps、闪烁减轻
- 或改 AXI 仲裁给 scan-out 更高读优先级（历史上有死锁风险，需仿真验证）
- 或换更大器件 / 双 DDR 通道（不在本次范围）

## 二、RTL Bug 攻坚（重要成果）

### Bug 1：`spx`/`bpx` 越界写（真 bug，已修）
- 段 0 burst 可能 17 beats，`spx[0:127]` 越界写 `spx[128..135]`
- 症状：精灵形状异常（用户确认修复后正常）
- 修复：写使能加 `beatidx < 16` 守卫

### Bug 2：`spx` 读越界（不触发）
- `soff > 0` 时读 `spx[128..135]`
- 但固件所有精灵源都 16B 对齐 → `soff` 恒 0 → 不触发
- 尝试修复导致资源超容量（61733>60800）→ 已回退

### Bug 3：`bank_*` / `epoch` CDC（尝试修复，**有害**）
- `bank_ok/bank_row/bank_epoch/epoch` 在 clk 域写、pclk 域读
- **加了 2 级同步器后 `under` 从 9 暴涨到 10 行/帧**（同步延迟导致行就绪判断滞后）
- **已完全回退**（原版逻辑反而正确）

### 结论
- **真正的 bug 只有 Bug 1**（越界写）
- CDC 理论分析正确但修复方式破坏了时序 → 教训：**同步器引入的延迟必须补偿**

## 三、900 精灵为什么不行（最终数据）

| 配置 | 精灵 | under | 画面 |
|---|---|---|---|
| 黄金版 bitstream | 700 | **0** | ✅ 稳定 |
| compact（bug修复+完美校准）| **100** | **10** | ✅ 稳定 |
| compact（同上）| **900** | 暴涨 | ❌ 黑屏 |

**算账**：
- 900 精灵引擎时间 = 1800 命令 × 7.2µs = **13 ms**
- scanout 每帧读 DDR = 4MB / 16.7ms = **16.7 ms 满带宽**
- **两者相加 29.7ms > 16.7ms 帧预算** → scanout 饿死
- scanout 缓冲 16 行（120µs）→ 吸收不了 900 精灵的连续突发
- BRAM 已用 **199/260 块** → 无法加大缓冲

**结论：700 精灵是 Ti60F225 + 1080p + DDR3 的物理上限。**

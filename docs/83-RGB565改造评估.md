# 83 - RGB565 帧缓冲改造评估（2026-10-15 晚）

> 依据：`docs/80` 的带宽探针实测（本轮之前刚测出），`docs/82` 的 tile 化方案（已放弃，见 §六）。
> 本文只评估"把帧缓冲从 ARGB8888 改成 RGB565（每像素 2 B）"这一件事。

## 〇、结论先行

| 项 | 评估 |
|---|---|
| **收益** | **1,344 → 2,048 精灵进 60 Hz**（**实测支撑**，非推算：带宽减半后每精灵 1,218 → 754 拍）|
| **画质代价** | **对现有画面 = 0**。纯色背景（`blt_fill`）与纯色子弹的颜色值全部落在 565 格点上，数学上精确还原 |
| **工作量** | **3~5 天**（含回归、上板验证与回退余地）|
| **最高风险** | ① **像素吞吐匹配**（本轮新发现，见 §三·1）② **扫描输出**（docs/67/68 的历史翻车点）|
| **回退方式** | 单变量回退：格式常量 + 转换逻辑；比特流可整体回滚（`v0.3-2048sprites` 已标记）|
| **建议** | **做**。但必须先解决 §三·1 的吞吐问题，否则会在时序上撞墙 |

## 〇·补、实施进展（2026-10-15 21:35）

| 阶段 | 内容 | 状态 |
|---|---|---|
| **0** | 定吞吐方案 | ✅ **完成** —— 定下"**外围转换级**"：`pixel_engine` 保持 `DW=32`（它按 `fg[c*8 +: 8]` 索引 4 个通道，16 位下无法做 alpha 混合），转换放在它**外侧** |
| **1** | 转换模块 + 单测 | ✅ **完成** —— 两个模块 5 项检查全过，已进回归（**28 PASS / 0 FAIL**）|
| **2** | 扫描输出改造 | ❌ **试过、失败、已回退** —— 见 [docs/84](84-阶段2扫描输出565失败记录.md) |
| **3** | 软件适配 + 回归 | ⬜ |
| **4** | 上板验证 | ⬜ |

**已落地**：
- `rtl/bitblt_px565_unpack.v` —— 读侧：128 位 beat（8×16）分两拍送出 4×32 位像素，补 `alpha=0xFF`
- `rtl/bitblt_px565_pack.v` —— 写侧：两拍 4×32 位合成一个 beat，**每像素的 2 个 wstrb 位成对置起**

**⚠️ 这两个模块尚未接进 `bitblt_top`** ⇒ 当前比特流行为不变（仍是 1,344）。

**两条最要紧的保证**（决定像素不会被改坏）：
1. `expand()` 对**全部 65536 个** 565 颜色精确正确（高位复制 ⇒ 满量程映射到 255 而非 248/252）
2. **往返恒等** `pack(unpack(x)) == x` 对全部 65536 个值成立 —— **未被修改的像素，写出去再读回来完全相同**

**实施中发现并修掉的 4 个 bug**（都是字节序/位映射，不是设计缺陷）：
1. `first_half` 取了**高** 64 位 —— AXI 里**最低地址在最低位**，应取低 64 位
2. 像素在拼接内高低位颠倒
3. `pack` 的 `lo` 只装了 2 个像素（应 4 个 = 64 位）
4. `pack` 的使能按 4 位一组映射 —— 16 位像素占 **2** 字节，应 **2** 位一组

**★ 归因方法值得记下**：遍历全部 65536 值的两项检查在字节序修正**之前**就已通过，
所以故障必然在"**顺序**"而不在"**颜色换算**" —— 这让定位只花了三轮。
**⇒ 教训：把"与顺序无关的性质"和"与顺序有关的性质"分成不同的检查，故障范围立刻缩小一半。**

## 一、为什么值得做（实测依据）

`docs/80` 记录的带宽探针：让扫描输出每行只读 960 像素（而非 1920），**唯一变量是它拉走的字节数**：

| 项 | 全宽 1920 | 半带宽 960 |
|---|---|---|
| 每精灵（1344 档）| 1,218 拍 | **754 拍（−38.1%）** |
| **60 Hz 内最大** | **1,344** | **2,048** ✅ |
| 扫描输出自证 | PASS | **PASS（1080 行 / 59.99 Hz）** |

**⇒ "扫描输出带宽"是引擎最大的外部制约，而 RGB565 正好把它减半**（每像素 4 B → 2 B）。

**★ 画质代价为何是 0**：565 的格点是 R/B 的 8 的倍数、G 的 4 的倍数。
实测背景色 `ARGB(0xFF,0x80,0x40,0x20)` = (128,64,32) 三通道**全部精确还原**；
子弹用纯色同理；连 demo 的 16 步渐变（每步 12 级 > 565 的 8 级距）台阶也保得住。
（模拟证据：`work/logs/scene-bullets-*.png`、`depth-*.png`。**唯一会露色带的是"平滑径向光晕"，而本 demo 没有这类画面**。）

## 二、改动清单（按侦察后的真实规模）

侦察发现的**好消息**：两处原本以为要大改的地方其实不用动结构。

| # | 改动 | 文件 | 规模 | 风险 | 备注 |
|---|---|---|---|---|---|
| 1 | 帧缓冲 stride 与格式常量 | `sw/bitblt.h`、`main.c`、`game.h` | 小 | 低 | 8192 → 4096 |
| 2 | **像素引擎输出打包**（32 位 ARGB → 16 位 565）| `bitblt_pixel_engine.v` | 中 | 中 | 组合逻辑，需过时序 |
| 3 | **读通路扩展**（565 → 32 位，补 `alpha=0xFF`）| `bitblt_dma_rd.v` 或像素引擎入口 | 小 | 低 | 零扩展 |
| 4 | **写使能语义**（逐字节 → 逐半字）| `bitblt_dma_wr.v` | **小** | 低 | ✅ 侦察发现是直通：`assign m_axi_wstrb = din_strb;` 位宽不变，只是"哪些位对应哪些像素"变了 |
| 5 | **扫描输出拆分**（128→4×24 位 → 128→8×16 位）| `bitblt_video_out.v` | 中 | **高** | 现有代码已在丢 alpha（取 `[23:0]`），改造性质相同；但该模块历史翻车两次 |
| 6 | **软件适配**（颜色常量、stride、CPU 直写帧缓冲处）| `main.c`、`game.c` | 中 | 中 | 测试段有逐像素 CPU 写入（`dst[y*FB_STRIDE_PX + x] = 0u`）|
| 7 | 测试期望值重算 | `grad-row-predictable`、`blend value`、`copy-readback-1000x` 等 4~5 处 | 小 | 低 | |
| 8 | 演示的渐变段 | `main.c` | 小 | 低 | 16 步渐变本身没问题，但断言值要跟着改 |

**★ 不用改的**（侦察确认）：
- `BYTES_PER_BEAT = AXI_DW/8 = 16` —— 这是**总线属性**，与像素格式无关
- `din_strb` 的**位宽**（16 位）—— 只是语义变了
- DDR 控制器 / AXI 互联 / 精灵表 / walker 的**任何结构**

## 三、三个关键难点

### 三·1 ★ 像素吞吐匹配（本轮新发现，最需要先想清楚）

现在：`AXI_DW = 128` 位 = **4 个像素**（4 B/像素），而像素引擎恰好是 **4 像素/拍** ⇒ 一拍一个 beat，完美匹配。

改成 565 后：`128` 位 = **8 个像素**（2 B/像素）。于是：
- 若保持"4 像素/拍"，**两个周期才凑满一个 beat** ⇒ 需要加一个打包缓冲（或让写引擎接受半 beat）
- 若改成"8 像素/拍"，像素引擎的并行度翻倍 ⇒ **面积与布线压力上升**（当前 XLR 54.9%，还有余量，但时序要重新收敛）

**⇒ 建议取前者（加一个小打包级），把风险限制在"多一级流水"而不是"重写像素引擎"。**
**这一条必须在动手前用仿真定下来。**

### 三·2 扫描输出的拆分

现状（`bitblt_video_out.v`）：
```verilog
wire [95:0] beat_rgb = { m_axi_rdata[119:96], m_axi_rdata[87:64],
                         m_axi_rdata[55:32],  m_axi_rdata[23:0] };   // 4 x 24-bit
```
它**已经在丢弃 alpha**（每个 32 位像素只取 `[23:0]`），FIFO 宽 96 位（4 像素/条）。

565 后：一个 128 位 beat = **8 个 16 位像素**，FIFO 可保持 96 位（存 6 像素）或改 128 位（存 8 像素）。
**⇒ 性质与现有代码相同，但该模块是历史上唯一翻过两次车的地方**（docs/67 的 307Hz、docs/68 的分段读缺陷），
所以它单独排一个阶段，单独验证。

### 三·3 写使能的语义

`m_axi_wstrb` 是 16 位（每 bit 一个字节），565 下"跳过一个像素"= 清掉那**两个**字节位。
**⇒ 像素引擎侧生成 strb 时按半字成对处理即可，写引擎不需要改结构。**

## 五、回退与风险

| 风险 | 概率 | 缓解 |
|---|---|---|
| 扫描输出改造引入显示缺陷 | 中 | **阶段 2 单独仿真验证**；上板前不合并 |
| 时序不过（打包级插进写通路）| 中 | 当前 `core_clk` slack **+1.58 ns**，余量充足 |
| 实测收益低于 38% | 低 | 探针已实测；若上板只拿到一半，仍到 ~1,700 |
| 软件遗漏某处颜色常量 | 中 | 回归 + 上板逐像素自检会抓到 |

**★ 回退成本低**：格式是一个常量 + 转换逻辑，不是架构改动；比特流可整体回滚。

## 六、与 tile 化的对比（为什么这次选它）

| | **RGB565** | tile 化（docs/82）|
|---|---|---|
| 收益 | 1,344 → **2,048**（实测）| 12.46×（实测，但**仅对齐时**）|
| 是否要求精灵对齐 | ❌ **不要求** | ✅ **要求 16 像素对齐** |
| 对**移动**的精灵 | ✅ 同样受益 | ❌ 脱离对齐 ⇒ **慢一倍** |
| 扫描输出改动 | 拆分逻辑（性质同现有代码）| **重写 + 96 个 RAM10 行带缓冲** |
| 画质代价 | 对本 demo **= 0** | 无 |
| 工作量 | **3~5 天** | 数天 + 高风险 |

**⇒ tile 化要求"格子移动"（游戏不可接受），而 RGB565 对任何移动方式都有效 —— 这是它胜出的根本原因。**

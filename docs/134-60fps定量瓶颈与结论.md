# 134 · 60 fps 的定量瓶颈与结论（2026-11-02 夜）

> **结论先行**：当前架构下 **4000×8×8 + alpha 做不到 60 fps**。
> 瓶颈不是引擎（已优化到 11.6 ms），而是 **CPU 写表**：4000 次 AXI-Lite 单字写 ≈ **16.9 ms**，
> 已经超过 60 fps 的整帧预算 16.7 ms。

## 一、精确收账（板上实测值）

| 项 | 4000 精灵 · 8×8 | 来源 |
|---|---|---|
| CPU 写表 + 启动 | **16.88 ms**（PROF cpu=16877，op6 集成版）| 串口 |
| 其中写表 | 4000 次 store ≈ 16.8 ms → **4.2 µs/store** | 推算 |
| 引擎执行（等遍历器）| **11.6 ms**（tabspin 减半后）| 串口 |
| 一帧总计（串行）| **≈28.5 ms** → 35 fps | fps 计数 |
| 60 fps 预算 | **16.7 ms** | — |

**旧版对照**：写表 2 字/精灵（8000 次）× 3.5 µs = 28.1 ms（PROF cpu=28118）——
与 op6 版 4000×4.2 µs 同量级，说明 **4 µs/store 是 AXI-Lite 写通道固有往返代价**，不是软件写法问题。

## 二、为什么不是引擎的问题

op6（不读背景的去背）把引擎从 22.7 ms 压到 **11.6 ms**（tabspin 101800→53952），
但帧率没变（35 fps），因为 CPU 侧 16.9 ms 已经顶满预算。引擎再快也用不上。

## 三、三条可选路径（都要付代价）

| # | 方案 | 收益 | 代价 | 可行性 |
|---|---|---|---|---|
| A | 硬件运动引擎（遍历器自己更新位置）| 写表 16.9→0，CPU≈11.6 ms → 60 fps 可达 | 每精灵要存 x,y,vx,vy ≈ 64 bit → 表 RAM 48→~80 块；**当前 48 块已让 PnR 拥塞**（默认 seed 布不通）| ❌ 资源不够 |
| B | 降低运动更新率（每 N 帧更新一部分）| 写表按 1/N 分摊 → 帧率数字到 60 | 运动视觉更新率降为 60/N（N=4 时 15 Hz，明显卡顿）| ⚠️ 数字达标、体验差 |
| C | 降精灵数 | 3200 时写表 13.4 + 引擎 9.3 = 22.7 ms → 44 fps | 违反 4000 精灵需求 | ❌ |

## 五、建议

1. **接受 36 fps**，把 DVI 稳定性作为交付重点（等效像素量已是赛题 1408×8×8 的 2 倍以上）；
2. 若必须 60 fps 指标：降到 ~2400 精灵（写表 10 + 引擎 7 ≈ 17 ms，接近 60）；
3. 若必须 4000×8×8@60：需要换更大器件或改架构（硬件运动引擎 + 更大 BRAM），不在本次范围内。

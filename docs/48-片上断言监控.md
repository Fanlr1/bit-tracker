## 一、十一个条件，各能抓什么

| 位 | 条件 | 屏幕上看不到的原因 |
|---|---|---|
| **0** | **源读 AR 握手【未完成** | **总线卡死 —— 画面停住，和「主循环没跑」无法区分** |
| **1** | **源读 R 握手【未完成** | **同上** |
| **2** | **目标读 AR** | **同上** |
| **3** | **目标读 R** | **同上** |
| **4** | **写 AW** | **同上** |
| **5** | **写 W** | **同上** |
| **6** | **写 B** | **同上** |
| **7** | **`rresp`/`bresp` 非 OKAY** | **传输被【静默丢弃】—— 画面只是偶尔不对** |
| **8** | **walker 卡死**（`spr_busy` 超 2 亿拍 ≈ 2 秒）** | **同上** |
| **9** | **位置读回请求【被门控丢弃** | **软件【等到超时也不知道为什么】—— 补上 [47](47-游戏Demo实现与验证记录.md) #2 的已知弱点** |
| **10** | **扫描输出【供给不足**（`line shortfall`）** | **`de` 静默拉低，缺的像素【永远不出现】—— 没有【任何【报错】，画面只是少一行** |

**⇒ 握手超时的判据是「`valid` 拉高而 `ready` 持续为低**超过 `TIMEOUT`（默认 65535 拍 ≈ 0.65 ms）」。** **⇒ 计数器在握手完成时**复位** —— 否则一长串短等待会累积成**假超时**。** **⇒ 一条正常的 DDR3 访问是几十拍、最坏几百拍，所以 65535 有数量级的余量。**

**⇒ walker 卡死的上限 2 亿拍**按 [44](44-P4弹幕能力记录.md) 的实测推算：82 拍/精灵，即使 256 个 32×32 也远在一百万拍以下。** **⇒ 余量两个数量级，所以它不会在「慢但正常」的遍历上误触发。**

**⇒ **能写代码解决的都解决了。** 剩下这些要么本质无解（时序），要么只能上板（⑥⑦）。**

### 配套的两个寄存器（不属于 11 个条件，但同类）

| 寄存器 | 读 | 抓什么 |
|---|---|---|
| **`0x70 SHORT_CNT`** | **饱和 8 位** | **扫描输出被饿死的**拍数** —— 位 10 说「发生过」，它说「多严重」。见 §五** |

## 三、板上怎么用

**⇒ 最小用法（一条调用）：**

```c
blt_mon_dump();     // 每个曾触发过的条件 + 次数 + 一句判读
```

**⇒ 输出形如：**

```
=== on-chip assertion monitor ===
  [ 4] wr  AW handshake wedged              x 2
  [ 7] response not OKAY                    x 1
  2 of 11 conditions have fired
  VERDICT: a bus handshake never completed -- the engine is wedged,
           not merely slow. Check arbitration and the DDR3 controller.
```

**⇒ 而**计数器回答的是粘滞位回答不了的问题**：这是开机时的一次毛刺，还是**每帧都在发生**？** **⇒ 那个区别决定**要不要去追它**。**

**⇒ 推荐流程：**

| 步 | 做什么 |
|---|---|
| **1** | **开机后调一次 `blt_mon_dump()`** —— 建立基线（正常应该是「没有条件触发过」）** |
| **2** | **跑一轮测试后再调一次** —— 新增的触发就是这一轮引入的** |
| **3** | **计数在涨 ⇒ 是持续问题；只触发一次 ⇒ 是瞬态，记录但先不动** |
| **4** | **确认修好后写 1 清除对应位（`blt_mon_clear(1u << n)`），否则它会一直报** |

**⚠️ 而 §一 那个「清不掉」的 bug（§四 第 1 条）已经修掉了 —— 在那之前，位 7 和位 9 是**永远清不掉**的。**

## 四、两个真实的 bug（都是这一轮抓到的）

### 4.1 粘滞位清不掉（**负向断言抓到**）

**⇒ 第一版把 `resp_err` 和 `pos_drop` 做了**寄存**，而且**只置位、从不清零**：**

```verilog
// 错：
if (rd0_rvalid && rd0_rresp != 2'b00) resp_err <= 1'b1;   // 只置位
wire ev_resp = resp_err & ~sticky[7];                     // ← 自触发

// ⇒ 一旦发生过一次 SLVERR，resp_err 永远是 1
// ⇒ 软件清掉 sticky[7] 后，下一拍 ev_resp 又变 1 ⇒ 又置位
```

**⇒ 在板上那读起来像「这个错误一直在发生」，而实际只发生了**一次** —— 会把诊断引向完全错误的方向。** **⇒ 被两条**负向**断言抓住：**

```
FAIL an OKAY response does not set sticky[7]
FAIL a forwarded request does not set sticky[9]
```

**⇒ **只测「出错时置位」的测试台会让它通过。**** **⇒ 那两条现在都是 `bitblt_monitor.v` 里的**组合单拍事件**。**

### 4.2 `STATUS[2]` 把**正常裁剪**报成了错误

**⇒ 那是第 (3) 项的调查结果，而且它**在监控器之前就存在**：**

```verilog
// 错：
assign engine_status = {29'd0, (wr_b_error | addr_oob), addr_done, addr_busy};
                                  ↑ 真错误和正常裁剪 OR 在一起
```

**⇒ `addr_oob` 的含义是「整个操作完全在 framebuffer 之外 ⇒ 一个字节都没写」—— **那是弹幕游戏里子弹飞出屏幕时的正常情况，每帧都会发生**。** **⇒ 于是 `STATUS[2]` 恒为 1 ⇒ **软件会断定引擎坏了**。**

**⇒ 现在 `[2]` 只报真错误、`[3]` 报裁剪。** **⇒ `[2]` 的含义没变，所以驱动只会看到更少的假错误。** **⇒ 详见 [56f0389] 与 `bitblt_top.v` 里的注释。**

### 4.3 而这一轮我在工具上犯的错

**⇒ 改 `bitblt_top.v` 的第一次尝试死在 Python `SyntaxError`：Verilog 字面量 `29'd0` 里的**撇号终止了 Python 的单引号字符串**。** **⇒ 和之前两次是同一族：**硬写空格数量**、**守门条件检查了自己上一步写进去的字符串**、**这次是把目标语言的字面量当成了宿主语言的字符串**。** **⇒ 三次都不是逻辑错，是**表示错**。**

## 五、第 (6) 项：扫描输出供给不足 —— ✅ 已完成

**⇒ 最初这里写的是「判定为独立单元，暂不做」；它现在做完了。**

### 5.1 问题

**⇒ 扫描输出的 FIFO 供不上时，`de` **静默拉低**，缺的像素**永远不出现**。** **⇒ 没有错误、没有计数、没有中断 —— 画面只是**少一行或短一行**。** **⇒ 在它之前，唯一的发现方式是**盯着屏幕看，并记住它刚才什么样**。**

### 5.2 实现

| 层 | 改动 |
|---|---|
| **`bitblt_video_out`** | **`pixel_short = de_raw & ~de`，pclk 域饱和计数器（8 位）+ 粘滞位** |
| **`system_top`** | **⚠️ 两种【不同的【跨域方式，因为【位宽【不同** |
| **`bitblt_top`** | **转发到监控器 + 寄存器文件** |
| **`bitblt_axi_slave`** | **`0x70 SHORT_CNT`（只读）** |
| **`bitblt_monitor`** | **位 10** |
| **`bitblt.h`** | **`blt_short_count()`；`blt_mon_dump()` 会报它** |

### 5.3 ⚠️ 为什么用了两种跨域方式

| 信号 | 方式 | 理由 |
|---|---|---|
| **粘滞位（**1 位**）** | **2 级触发器** | **1 位，标准做法就够** |
| **计数（**8 位**）** | **稳定采样**（连续两次读到相同才采纳） | **⚠️ 2-FF 对多比特**不安全** —— 各位在不同触发器上跨越，软件可能读到**从未真实存在过**的值（`0x7F` 途经 `0xFF` 变成 `0x80`）。**不需要握手，而「一个停下来的值就是真值」** |

### 5.4 ⚠️ 为什么不数「行」而数「拍」

**⇒ 测试台的契约是「实际行数 ≥ 期望行数的 95%」（`tb_bitblt_video_out` 第 403 行）。** **⇒ 但硬件数的是**拍数** —— 因为**比例可以立刻算出来，而不必等一整行结束才知道出事了**。** **⇒ 饱和在 255 而不是回绕：回绕会把「256 拍坏」显示成「0 拍坏」，那读起来像「一切正常」。**

### 5.5 ⚠️ 这一项路上抓到的两个错误

**(1) 新输入端口在测试台里**悬空**。** **⇒ 悬空输入在仿真里是 `Z` ⇒ 变成 `X` ⇒ 传播进粘滞字，**弄坏了两条不相关的断言**。** **⇒ ⚠️ 而综合里悬空输入是 **0**。** **⇒ **两者会不一致，而且仿真那边才是错的。****

**(2) 边沿检测只置位、从不清零。** **⇒ 当时的理由是「上游粘滞位不会回落，所以无所谓」。** **⇒ 那让这个模块**依赖了上层的实现细节**：上游哪天加上清除路径，这里就会**静默漏掉第一次之后的所有事件**。** **⇒ 测试台那条 `starvation re-latches after the source cycles` **期望它重新触发 —— 它是对的**。** **⇒ 现在 `short_seen` **跟随源**（`short_seen <= scan_short`）—— 那就是一个上升沿检测，更简单，且对粘滞与非粘滞输入都正确。**

### 5.6 代价

| | 前 | 后 |
|---|---|---|
| **LUT4** | **15768** | **15408（−360）** |
| **FF** | **11969** | **12255（+286）** |
| **RAM10** | **74** | **74** |

**⇒ 回归 24/24，`FULL CHAIN OK`，12 条时序关系全部满足，CDC 零警告。**

## 六、测试与故障注入

**⇒ `tb_bitblt_monitor.v`：18 条断言，覆盖**每个条件的两个方向**。**

**⇒ 故障注入（`sticky[0]` 强制为 1，随后恢复）：**

```
FAIL sticky is clear before any stimulus          ← 负向
FAIL healthy handshakes do not set the sticky bit ← 负向
FAIL repeated short waits do not accumulate       ← 负向
FAIL the counter for that condition is 1
FAIL clr_mask bit 0 clears sticky[0]
FAIL a second wedge raises the count to 2
RESULT: FAILED with 6 error(s)
```

**⇒ 六条失败里三条是负向 —— 一个把一切都报成错的监控器，和什么都不报的一样没用。**

### ⚠️ 而测试台头部写明了**没覆盖**的部分

> **walker 卡死限值 2 亿拍、计数器 2³² 饱和 —— 两者都**无法**在这个规模的仿真里达到。**
> **⇒ 所以只断言了它们的**负向**（正常遍历不得触发卡死位、`clr_count` 确实清零）。**
> **⇒ 正向依赖「限值是编译期常量、与计数器比较」这个**结构事实** —— 它简单，但**没有被端到端观察到**。**

**⇒ 写这句是因为「18 条全 PASS」很容易被读成「全都验过了」，而那不是事实。**

## 七、⭐ 这一族错误：六次「我表示的文本」出错

**⇒ 这个 goal 里我犯了**六次**同类错误，而**没有一次是逻辑错** —— **六次都是我对"我刚做了什么"的建模错了**。值得单独记，因为它反复出现。**

| # | 表现 | 真因 |
|---|---|---|
| **1** | **替换字符串不匹配，静默什么都没改** | **硬写了 15 个空格，文件里是 14 个** |
| **2** | **「已恢复」的验证报 False，但文件其实没被改过** | **同上，同一个空格数错** |
| **3** | **守门条件说「已存在」而实际没写** | **检查的短语，被**同一脚本【几行前的替换】自己写进去了**** |
| **4** | **同上，换了个文件** | **检查的区域，被前一步的**插入**污染了** |
| **5** | **同上** | **检查的词，被我**刚加的注释**引入了** |
| **6** | **⚠️ 往单语句 `if` 分支后直接追加断言** | **把后面的 `else` 弄悬空了（测试台三处语法错）。**这一条【性质【不同】—— 前五条是【文本【匹配错，这一条是【语法【结构【错】。随后两次猜上下文文本又都没匹配上，因为**缩进假设错了**；**读文件再改，一次就成了**** |

### 7.1 共同形状

**⇒ 守门条件与它要守的东西**共享了文本**。** **⇒ 于是「它已经存在」和「我刚把它写进去」**无法区分**。** **⇒ 而检测失败的方式是**静默的** —— 脚本打印「已存在」，然后什么都不做，看起来像成功。**

### 7.2 ⚠️ 为什么这类错误特别值得记

| 原因 | 说明 |
|---|---|
| **它伪装成成功** | **不报错、不崩溃，只是**没做那件事**** |
| **它【每次都【看起来【像别的问题** | **第 3-5 次我都先怀疑「替换失败」，实际是**检查【条件【设计错了**** |
| **自检【查不出来** | **我在同一个脚本里既写又查，**检查用的也是同一个错误模型**** |

**⇒ 第 3 条最关键：**用出错的那个东西去检查它自己，检查不出来是必然的。****

### 7.3 已经生效的对策

| 对策 | 用在哪 |
|---|---|
| **检查【特征【字符串，不检查【裸【词** | **`### 五之六、`（节标题）而不是 `五之六`** |
| **检查【只有【目标【才【有的【标记** | **`(1u << 10)`（dump 函数内部的表达式）而不是 `starved`** |
| **改完【从磁盘【重读【验证** | **不信任内存里的字符串** |
| **改【结构化【代码【前【先【读【那【几【行** | **缩进与措辞【不【可【假设 —— 第 6 次就是缩进猜错了** |
| **⚠️ 追加【断言【前【看【清【分支【边界** | **单语句 `if` 后面直接追加，会让 `else` 悬空 —— 这【不是【文本【问题，是【语法【结构【问题**** |

### 7.4 ⭐ 而最后一次，正确做法是**换工具**而不是继续较劲

**⇒ 第 6 个问题是 C 语言的「用在定义之前」。** **⇒ 我试了两次**搬代码块**（把 accessor 移到 dump 前面），两次都没到位。** **⇒ 而正确做法是**前置声明** —— 语言本身就有这个机制：**

```c
// Defined below, after the monitor accessors. Forward-declared here because
// blt_mon_dump() reports the starvation count, and the dump function sits
// earlier in this header than the accessor does.
static inline uint32_t blt_short_count(void);
```

**⇒ 一次就成。** **⇒ **教训：当我在跟字符串较劲第三次时，该问的不是「怎么改对」，而是「有没有一个机制让这件事不需要改」。****

## 八、越界地址：0x74 `OOB_ADDR`

**⇒ 最初这一项写在 §二 的「抓不到什么」里，标注「加一个寄存器可以做，约 1 轮」。它做完了。**

### 8.1 问题

**⇒ `STATUS` 位 3 说「有东西被裁剪了」。** **⇒ **但那一句话无法定位任何东西** —— 三个候选【从状态字【看起来【一模一样**：

| 候选 | 真相 |
|---|---|
| **`FB_BASE` 寄存器写错了** | **⚠️ 真问题** |
| **`FB_CFG` 的 stride 写错了** | **⚠️ 真问题** |
| **精灵本来就在屏幕外** | **✅ 正常，什么都没坏** |

**⇒ 而第三种在弹幕游戏里**每帧都有**（子弹飞出屏幕）—— 所以位 3 会一直亮，而它亮着的时候你**分不清是哪种**。**

### 8.2 实现

| 层 | 改动 |
|---|---|
| **`bitblt_addr_gen`** | **新增 `oob_addr`，两个拒绝点各自写入** |
| **`bitblt_top`** | **转发（32 位）** |
| **`bitblt_axi_slave`** | **`0x74 OOB_ADDR`（只读）** |
| **`bitblt.h`** | **`blt_oob_addr()`；`blt_mon_dump()` 会打印它** |

**⇒ 两个拒绝点【地址【不同**：

```verilog
// ① 整个矩形在 [fb_start, fb_end) 之外
oob_addr <= first_line_ok ? {AW{1'b0}} : dst_base;

// ② 下一行会越界
oob_addr <= line_dst_addr + dst_stride;
```

### 8.3 ⚠️ 我第一版写错了，而错误是「语义不一致」

**⇒ 第一版只在拒绝时赋值，所以**有效传输【之后【它【保留【旧地址】。** **⇒ 软件读到的会是**一个看起来像当前的过期数字** —— 而那比没有这个寄存器**更糟**，因为它看起来可信。** **⇒ 现在 `oob = 0` ⇒ `oob_addr = 0`，两者一致。** **⇒ 测试台断言**三个方向**：below / above / **cleared**。** **⇒ 故障注入（赋值换成常量 `32'hDEADBEEF`，随后恢复）让**三条全部失败**：**

```
FAIL oob_addr/below:  got deadbeef want 00007000
FAIL oob_addr/above:  got deadbeef want 00009000
FAIL oob_addr/clears: got deadbeef want 0
RESULT: FAILED with 3 error(s)
```

**⇒ 其中 `clears` 那条最重要 —— **过期地址正是【最【像【当前【地址【的【那一种】。**

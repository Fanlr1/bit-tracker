# 101 - 画面花屏与抖动的两个真根因（2026-10-26）

> 接 [docs/100](100-慢态根因修复与回归全绿.md)。
> **一句话：串口 13/13 全过、像素读回 0 错，画面却是三段花屏 + 抖动 —— 因为固件【清错了缓冲】，并且【翻页不等消隐】。**

## 一、用户看到的现象（2026-10-26 19:30 照片）

| 区域 | 内容 |
|---|---|
| 屏幕上段 | **绿三角图案 + 白点阵**（早期测试留下的图案）|
| 屏幕中段 | **橙色点阵条**（另一个测试图案）|
| 屏幕下段 | **黑白横条纹**（从未写入的区域）|
| 全过程 | **抖动 / 撕裂** |

同时串口：`[TEST:SUMMARY] total=13 fail=0`、`copy-readback` 0 错。

**⇒ 这两个事实并不矛盾：那些测试只证明"内存里的像素对不对"，不证明"屏幕上显示的是哪块缓冲、什么时候换的"。**

## 二、根因一：清屏清的是**不可见**的缓冲

`main.c` 的动画循环（改前）：

    back = 1u;                                  // 画 buf[1]
    volatile uint16_t *dst = buf[1];
    ...
    blt_fill(FB_BASE, FB_W, FB_H, FB_STRIDE, ARGB(0xFF,0x10,0x10,0x20));   // 清 buf[0] !!
    ...
    blt_sprite_clipped(..., back ? FB_BASE + FB_BYTES : FB_BASE, ...);     // 画 buf[1]
    ...
    blt_set_fb(back ? (FB_BASE + FB_BYTES) : FB_BASE, ...);                // 显示 buf[1]

**清的是 buf[0]，画和显示的都是 buf[1]。** 于是：

- `buf[1]` **从来没有被清过** ⇒ 上一帧的精灵叠在更早的测试图案上 ⇒ **绿三角 / 橙点阵 / 精灵全部叠在一起**；
- 从未写过的区域（下半屏）保持 DDR 上电内容 ⇒ **黑白横条纹**；
- 每帧只往旧画面上"盖章" ⇒ 看起来像**花屏/拖影**。

**修复**：

    blt_fill(back ? (FB_BASE + FB_BYTES) : FB_BASE, FB_W, FB_H, FB_STRIDE, COLOR);
    blt_wait();

## 三、根因二：翻页写在帧中间（撕裂/抖动）

改前：

    blt_set_fb(back ? (FB_BASE + FB_BYTES) : FB_BASE, FB_W, FB_H, FB_STRIDE, 1);

`FB_BASE` 是扫描输出的读基址。**在帧中间**改它，这一帧的上半部分来自旧缓冲、下半部分来自新缓冲 ⇒ **水平撕裂 + 抖动**。

**修复**（驱动里本来就有这个轮询函数，只是没在这里用）：

    blt_scan_wait_blanking(300000u);   // 等垂直消隐
    blt_set_fb(...);

`o_blanking` 在 2026-10-24 已经修成"只表示垂直消隐"（`~v_active`，docs/94），所以这个等待现在是准的。

**旁证**：修复后串口每帧出现 `ANIM DIAG: f=N flip done`，即"等到了消隐、翻页完成"。

## 五、教训

| # | 教训 |
|---|---|
| 1 | **"测试全过"与"画面正确"是两件事**：copy-readback 只证明引擎写对了内存，不证明扫描输出读的是那块、也不证明翻页时机 |
| 2 | **双缓冲必须检查"三个地址一致"**：清哪个、画哪个、显示哪个。只查两个就会出这类 bug，而且**代码读起来完全合理**（每句都像对的） |
| 3 | **翻页是跨帧操作**，必须落在消隐期；驱动里已有 `blt_scan_wait_blanking`，不用它就是漏 |
| 4 | 主循环里若固定 `back`（不交替），至少**清/画/显示三者必须指向同一个缓冲**；否则就是本 bug |

## 六、顺带记下的两个坑

- **`flash-app-retry.bat` 的失败判定有漏洞**：`ftdi_program` 打印 `ERROR: problem occurred…` 时，`%ERRORLEVEL%` 仍可能是 0，脚本据此判"成功"。**必须按输出里是否出现 `JTAG2SPI programming...done` 判定。**
- **失败真因往往是残留进程**：`Unsupported JTAG Bridge version: 0.0` 与 openocd 的 `mpsse_flush() Haven't made progress` 都是**上一次的 openocd / read-uart 进程占着 USB 与 COM**。操作前先 `Stop-Process` 清干净（docs 旧文也记过这条）。

## ✅ 第一优先（已解决，不需上板定性）：AXI burst 跨 4KB 边界

> **2026-10-07 更新：这一项**不再是待验项**。**方案 B 不仅已实现，而且已在 RTL 里强制、并有契约测试。** 保留下面的原文作为决策记录。**

### 问题

AXI4 规定**一个 burst 不得跨越 4 KB 边界**，这是 Master 的责任。我们有两处违反：

```
video_out.v:307   line_addr = fb_base + rd_row * fb_stride
                  stride = 2560 (0xA00)，不是 4096 的倍数
                  ⇒ 第 4 行  0x2800..0x31FF  跨 0x3000
                  ⇒ 第 12 行 0x7800..0x81FF  跨 0x8000
                  ⇒ 每 4 行跨一次，每帧约 119 次

dma_rd.v:67 / dma_wr.v:78   burst 长度只按剩余拍数截断，不看 cur_addr[11:0]
                  ⇒ 256 拍 × 16 B = 4096 B，起始地址非 4 KB 对齐即必然跨界
```

### 为什么没有直接改

**改法是「把每次突发拆成不跨 4KB 的段」**，代价是**读状态机要支持分段、`arlen` 要重算**。
而**`ddr3_top` 是加密 IP，无法确认它是否容忍** —— 报告也把它列在「本次未覆盖」。

**⇒ 若它本来就容忍，改 A 是白改且引入新风险；若不容忍，不改就是花屏。**
**⇒ 一次板上测试就能定性，比现在盲改划算。**

> **★ 2026-10-06 更新：查到了两个新事实，改变了这里的判断（见 `docs/40` §2）**
>
> **① 厂商 UG 全文没有任何跨界承诺** —— `ddr3-controller-core-ug-v1.6.pdf` 里关于突发的**全部**内容是
> `axi_alen[7:0]` / `axi_asize[2:0]` / `axi_aburst[1:0]` 三个透传端口，**没有「自动拆分」也没有「跨界报错」**。
> ⇒ **契约必须由 master 遵守**，赌它容忍的依据比我原先以为的弱。
>
> **② 有一个不用改 RTL 的解法（方案 B）** —— 所以「改 A 是白改」这个顾虑消失了。

### 怎么验

**方法**：**填一个「逐行渐变」图案**（每行的值随行号变化，例如 `row*1000 + col`），
然后**逐行检查屏幕上第 4、8、12…行的内容是否与预期一致**。

| 现象 | 结论 | 行动 |
|---|---|---|
| **画面完全正常** | `ddr3_top` **容忍**跨界 | **不必改**，仅在文档记录 |
| **第 4/8/12…行错乱或重复上一行** | **不容忍** | **必须改**：优先方案 B，其次方案 A |
| **只有部分帧出错** | 容忍但**边缘**（时序/刷新相关）| **建议改**，或降低突发长度 |

**⚠️ 注意**：**「跨 4KB」与「跨 DDR3 row 边界」是两件事** —— 后者是 DDR3 控制器内部的事，
通常由它自己拆分行激活，不需要 AXI Master 关心。**这里只管 AXI 层的 4KB。**

---

### ⭐ 方案 B（首选）：把 stride 对齐到 4096 —— **不改 RTL**

**⇒ 跨界的根源是行起始地址没有 4KB 对齐：**

```
640 像素 × 4 字节 = 2560 字节/行
4096 ÷ 2560 = 1.6            ← 不是整数 ⇒ 行起始地址永远对不齐
```

**⇒ 但如果**把 stride 设成 4096 的整数倍**，则每行起始地址都是 4KB 对齐的；而**行长 ≤ 4096 字节（= 1024 像素）时，一次突发就不可能跨界。**

| 宽度 | 自然 stride | 对齐后 stride | 显存浪费 | 备注 |
|---|---|---|---|---|
| **640** | 2560 | **4096** | 每行 1536 B（**37.5%**） | **当前配置，只改软件写的 stride 寄存器** |
| **1024** | **4096** | **4096** | **✅ 0** | **同时满足 `ARLEN` ≤ 255 拍与 4KB 对齐** |
| **800** | 3200 | 4096 | 每行 896 B（22%） | |

**🎯 注意 1024 这个宽度：`1024 px ÷ 4 px/beat = 256 拍`（`ARLEN` 上限）而 `1024 × 4 B = 4096 B`（4KB 整）—— 两个独立约束在同一个数上重合。这不是巧合，是 AXI4 把突发上限定为 4KB 的结果。**

**⇒ 方案 B 的代价**：**只有显存占用上升，以及 `BLT_DST_STRIDE` 寄存器的值要改。**
**⇒ 方案 B 的前提**：**软件（驱动）必须按新 stride 计算行地址 —— 也就是 `main.c` 里那处 `row * 2560`。**

---

### 方案 A（备选）：读状态机按 4KB 边界分段

**⇒ 若宽度必须 > 1024（`ARLEN` 装不下），或显存浪费不可接受，才走这条。**

```
S_IDLE  计算 line_addr 时，同时算出「本行跨了几个 4KB 边界」
        第一段的 beats = min(剩余 beats, 到下一个 4KB 边界还能放几拍)
S_R     收到 rlast 后，若本行还有剩余 beats：
            重算 line_addr（= 原 addr + 已取字节数，该地址必然 4KB 对齐）
            重新发 AR，arlen = 第二段的 beats - 1
        否则回 S_IDLE
```

**⚠️ 关键**：第二段的起始地址必然落在 4KB 边界上，**所以最多只需要两段**（行长 2560 B < 4096 B）。
**⚠️ 但若宽度 > 1024 像素，一行可能跨多个边界 ⇒ 分段数不再固定为 2，状态机要能循环。**

### ✅ 2026-10-07 结案依据

**⇒ 三项证据，都在代码里，不依赖板子：**

| # | 证据 | 位置 |
|---|---|---|
| **1** | **`bitblt_video_out` **检查** `fb_base` 与 `fb_stride` 是否都是 4096 的倍数，不是就 raise `cfg_error`** | **`bitblt_video_out.v` 行 487-490** |
| **2** | **`tb_bitblt_video_out` 有 `cfg_error` 的契约测试，回归里一直跑** | **回归第 24 项之一** |
| **3** | **驱动用对齐值：`FB_BASE = 0x08000000`（4096 倍数）、`FB_STRIDE_BYTES = 8192`（2×4096）** | **`main.c` 行 45 / 69** |

**⇒ 而**真实的 4KB 压力比原先描述的更具体**：**

- **全高清一行是 1920×4 = 7680 B，**超过一页**（4096）⇒ **单个 burst 载不下** ⇒ 扫描输出**必须**每行分两个 burst：**4096 B + 3584 B****
- **⇒ 而【分【burst【的【算术【要求**行首【对齐**** —— 那正是 `cfg_error` 检查的** ✗
- **⇒ 代价：framebuffer 从 1.88 MB 涨到 8.85 MB/缓冲（含每行 512 B 填充），双缓冲 17.7 MB，DDR3 有 256 MB ⇒ 不是约束**

### ⚠️ 一个**不是**问题的情况，值得写清以免误判

**⇒ `tb_bitblt_dma_rd` 里有一个用例**故意【喂未对齐【基地址**（`0x0F00`，8192 B），实测【DUT【确实【会【跨页**：**

```
AR sequence: [0]00000f00+256  [1]00001f00+256
⇒ burst 0 覆盖 0x0F00..0x1EFF，跨过 0x1000
```

**⇒ 那【证明【了【模块【在【收到【未对齐【地址【时【会【违规 —— 但【真实【路径**不会【喂它【那种【地址**** ✓
**⇒ **⇒ **⇒ 地址【由 `addr_gen` 从【已【对齐的【`fb_stride` 算出，而【对齐【由【上面的 `cfg_error` 强制**** ✓

**⇒ 所以那个用例的价值是**记录边界行为**（测试断言的是跨界**次数**，不是禁止它），而**不是**报告一个活跃的缺陷。**
**⇒ 判据在 `tb_bitblt_dma_rd.v` 的头部注释里。**


## 🟠 第二优先：中断脉冲宽度

### 问题

```verilog
bitblt_addr_gen.v:41   output reg done,  // one-cycle pulse
bitblt_axi_slave.v     assign axi_interrupt = r_ctrl[1] & reg_status[1];
```

**⇒ 中断线宽 = 1 个 `core_clk` = 10 ns。**

而 `soc.v` 里有：
```verilog
system_axiA_interrupt_plic_gateway_waitCompletion <= axiAInterrupt;
```

**⚠️ `waitCompletion` 这个信号名提示 gateway 可能要求中断线保持到被应答。若是，10 ns 脉冲会丢失。**

### 怎么验

**驱动里已经内置了有界等待**：

```c
uint32_t guard = 0;
while (!g_done_irq && guard < 10000000u) { guard++; }
if (!g_done_irq) {
    bsp_printf("WARNING: no done interrupt within guard (frame %u)\r\n", f);
    break;
}
```

**⇒ 看串口有没有打印 `WARNING: no done interrupt`。**

| 现象 | 结论 |
|---|---|
| **没有 WARNING，且打印了 `interrupts observed: N`** | 脉冲能被捕获，**不必改** |
| **打印了 WARNING** | **脉冲丢失** ⇒ 要改成「电平型 + 软件清除」 |

### 若确认要改

在 `CTRL` 寄存器加一位 `irq_clear`（写 1 清除），并把
`assign axi_interrupt = r_ctrl[1] & irq_pending_r;` 改成锁存型，由该位清除。

## 🟡 第三优先：AXI ID 是否与 SoC 冲突

### 问题

`soc.v` 的 `io_ddrA_*_payload_id` 是 **8 位**输出，而 `ddr3_top` 的 `s_axi_*id` 是 **4 位**
⇒ **SoC 的 ID 也被截断到低 4 位**，而 `soc.v` 加密，看不到它实际用哪些值。

**当前做法是概率规避**：我们用 `8/A/C/E`，把 `0`–`7` 让给 SoC。

### 怎么验

**跑连续的 BitBlt 拷贝（例如 1000 次），每次读回目标区域并校验内容。**

| 现象 | 结论 |
|---|---|
| **全部一致** | ID 无冲突 |
| **间歇性数据错误**（每次错的位置不同）| **ID 冲突** ⇒ SoC 用了 `8/A/C/E` 之一 ⇒ 需换 ID 或改架构 |

**⚠️ 这类错误不会稳定复现，所以要跑够多次数。**

## 🔵 第五项：`tx_cal_clk` 时序余量很薄

### 现状

| 版本 | `tx_cal_clk` Setup Slack | 备注 |
|---|---|---|
| 复位修复前 | +0.479 ns | |
| 复位修复后 | +0.241 ns | |
| 之后某版 | +0.188 ns | |
| **2026-10-06 实测（seed=1）** | **+0.227 ns** | **当前基线** |
| **2026-10-06 seed=2** | **+0.347 ns** | **全部时钟域最优** |
| **2026-10-06 seed=7** | **+0.423 ns** | **`tx_cal_clk` 最高，但 `rx_cal_clk` 降到 0.396** |
| **官方同类 demo（`ddr_demo_ti60`）** | **+0.375 ~ +0.398 ns** | **基准** |

**约束 2.5 ns。当前 0.227 ns ≈ 余量 9%。**

> **★ 2026-10-06 更新：这里原先写的「成因＝复位逻辑使路径变长」是错的。**
>
> **看时序报告的实际路径后确认：这条路径【完全在厂商 DDR3 PHY 内部】，我们自己的代码一行都没参与。**
>
> ```
> Path Begin : u_ddr3_top/u_phy_top/u_ddr_phy_if/mem_dqs_out[0]~FF|CLK
> Path End   : ddr_dqs_out_lo[1]                       ← 都是 DDR3 的 DQS 输出
> Logic Level: 1                                       ← 只有 1 级 LUT
> ```
>
> **时间几乎全花在走线上**：数据路径 1.833 ns 中，两条 net 占 1.592 ns（87%）——
> `mem_dqs_out[0]` 走线曼哈顿 **X:12, Y:90**，`ddr_dqs_out_lo[0]` 走线 **X:114, Y:5**。
> **⇒ 这是布局问题，不是逻辑深度问题。**
>
> **⇒ 因此「加流水」这个办法【不适用】** —— 加不到厂商 IP 内部去。

### 为什么要盯住它

**`tx_cal_clk` 是 DDR3 的校准时钟。** 一旦这条路径不收敛，**DDR3 校准可能失败**，表现是上电后内存完全不可用 —— **而不是图像上的小问题。**

**⚠️ 但也要说清另一面**：官方自己发布过更薄的同类 demo —— `tinyml_helloworld` 的 `rx_cal_clk` 是 **0.160 ns**、`i_sysclk` 甚至是 **-0.136 ns（负的）**；`Ti60_Demo`（IMX219 HDMI）的 `tac_clk` 是 **0.116 ns**。**⇒ 0.1~0.2 ns 这个量级是这个 DDR3 IP 的常态，不是异常。**

### 怎么处理

| 时机 | 动作 |
|---|---|
| **每次改 RTL / 换 PnR 种子之后** | **看 `outflow\bitblt_system.timing.rpt` 里 `tx_cal_clk` 的 slack** |
| **想在布局上找余量** | **换 `seed` 重跑 pnr（每个约 30 秒）** —— **已验证：`tx_cal_clk` 在 seed 1/2/3/5/7 之间从 0.159 摆到 0.423，波动 2.7 倍 ⇒ 这条路径的时序几乎完全由布局决定** |
| **别再试图「加流水」** | **路径在厂商 PHY 内部，加不进去** |
| **最终判据** | **板上 DDR3 校准能否通过**（`bringup.ps1` 第 1 步）—— **在那之前一切调整都是抽签** |

**用法建议**：**把 XML 的 `seed` 固定为一个较好的值（`2` 或 `7`），并在每次大改 RTL 之后重跑 3~5 个种子挑最好的那个** —— **因为 RTL 一改布局就重排，余量会被吃掉。**

## 🟣 第六项（新增）：AXI 仲裁让视频被 CPU 结构性压制

> **来源：`docs/40-仲裁与HSIO与4KB查证.md` §1**

### 问题

**`rtl/system_top.v:975` 接的是优先级模式：**

```verilog
.Cfg_Arb_Type (1'b1),  // 1 = priority arbitration
```

**而 `Axi_Mux.v:811` 的作者注释写明：**

```
//仲裁策略 0:共享;1:优先级（S0为最高优先级）；
```

**⇒ 优先级模式下，`Axi_Mux_Addr_Ctrl` 每次空闲都把 `Channel_List` 重置回 S0（`Axi_Mux.v:2537-2541`）⇒ **CPU（S0）恒优先**。**

**⇒ 后果**：CPU 的每一次取指/访存都可能打断视频行突发的连续性 ⇒ **视频 FIFO 被抽空 ⇒ 画面闪烁/撕裂。** **⇒ 这正是 `docs/24` 第二节警告的「延迟问题，不是带宽问题」。**

### 怎么验

| 现象 | 结论 |
|---|---|
| **画面稳定无闪烁** | **CPU 的 AXI 流量不足以造成影响** ⇒ 不必改 |
| **画面周期性闪烁/撕裂，且 CPU 忙时更明显** | **坐实被饿** ⇒ 改 `Cfg_Arb_Type = 1'b0` 做 A/B 对比 |

**⇒ 建议的 A/B 方法**：同一段 Demo 程序跑两次，一次 `1'b1` 一次 `1'b0`，**对比闪烁是否消失。** **⇒ 这是唯一能定性的手段** —— **现有测试台证明不了**（`tb_mux_video` 只覆盖 S0/S4，S1/S2/S3 从未并发）。

### 若确认要改

| 项 | 说明 |
|---|---|
| **改法** | **`system_top.v:975`：`1'b1` → `1'b0`** |
| **效果** | **令牌环轮询，各通道轮流获得授权** |
| **代价** | **CPU 的 AXI 延迟上升** —— 但 `docs/24` 五.2 算过：CPU 每帧只写约 8 个寄存器 ≈ 0.8 µs，**开销可忽略** |
| **⚠️ 注意** | **轮询只保证「公平」，不保证「够快」** |

## 🟣 第七项：1080p60 的 HSIO 速率（**已实现，板级待验** —— 见本节末尾的 2026-10-09 更新）

> **来源：`docs/40-仲裁与HSIO与4KB查证.md` §3**

### 问题

**`Ti60 Data Sheet v3.2` 里 `1.5 Gbps` 这个数字是挂在 **LVDS/subLVDS/Mini-LVDS/RSDS** 和 **MIPI** 名下的。** **⇒ 而 **HDMI TMDS 是单端的**，两者都不算 ⇒ 文档里【没有给 TMDS 的速率上限】。**

**⇒ 唯一可靠的旁证是厂商自己的 demo**：

```
Ti60_Demo（目录名 HDMI_1080P）的 SDC：
  create_clock -period 13.4409 clk_pixel        ⇒ 74.4 MHz   （720p60 / 1080p30）
  create_clock -period  1.3441 clk_pixel_10x    ⇒ 744 MHz    （TMDS 串行位时钟）
```

**⇒ 厂商**验证过的最高 TMDS 速率是 744 Mbps/lane**，而 1080p60 需要 **1.485 Gbps** —— **是它的两倍。** **⇒ 且全速率模式要求串行时钟 1.485 GHz，而手册示例里出现的最高 fast clock 只有 800 MHz ⇒ 只能走半速率（742.5 MHz）。**

### 安全区

| 分辨率@帧率 | 像素时钟 | TMDS/lane | 判断 |
|---|---|---|---|
| **640×480@60** | 25.2 MHz | 252 Mbps | **✅ 当前配置** |
| **1024×768@60** | 65 MHz | 650 Mbps | **✅ 低于 744** |
| **1280×720@60** | 74.25 MHz | 742.5 Mbps | **✅ ≈ 厂商 demo 速率** |
| **1920×1080@30** | 74.25 MHz | 742.5 Mbps | **✅ 同上** |
| **1920×1080@60** | 148.5 MHz | 1485 Mbps | **⚠️ 无依据，须先做速率试验** |

### 怎么验

**⇒ 在改任何分辨率相关 RTL 之前，先做一个【TMDS 速率爬坡试验】**：用现有的 `color_bar_rgb` + `dvi_encoder`，把 `pix_clk` 逐步提到 100 / 120 / 148.5 MHz，**看屏幕是否稳定**。

**⇒ 这一步花不了多少时间，但能直接定死分辨率上限** —— **比先改架构再发现跑不动划算得多。**

> ### ★ 2026-10-09 更新：这一项已经做了，且本节原先的表述有一处单位错误
>
> **① 更正：「厂商验证过的最高 TMDS 速率是 744 Mbps/lane」是错的。**
>
> `hdmi_tx_slow_clk` 周期 6.723 ns = 148.75 MHz 是**像素时钟**，`hdmi_tx_fast_clk` 周期 1.345 ns =
> 743.5 MHz 是**串行时钟**。TMDS 用 DDR ⇒ 数据率 = 串行时钟 × 2 = **1.487 Gbps/lane**。
> **⇒ 厂商 demo 跑的就是 1080p60 的速率**，本节原先「是它的两倍」的推论不成立。
>
> **② `pix_clk` 已提到 148.50 MHz，并通过 FPGA 内时序。**
>
> Efinity `pt_timing.rpt` 实测：`pix_clk` 周期 **6.734 ns**、`pix_clk_fast` **1.347 ns**（742.5 MHz，90° 相位）；
> `pnr` 退出码 0，setup/hold slack 全为正。实现路径见 **`docs/41`**（27 MHz 晶振 + 独立反馈输出）。
>
> **③ 但「器件能不能跑 1.485 Gbps 的 TMDS」仍然没有权威依据。**
>
> Ti60 数据手册 Table 47 给的是 **HSIO 最大翻转率**（LVDS 半速率 1500 Mbps，I3 档），而 **TMDS 是单端输出，
> 手册没有单独给出它的速率规格**。⇒ 144 Mbps 的余量（1485 vs 1500）**不可直接套用**。
>
> **⇒ 本项状态：从「无依据」变为「FPGA 侧已实现且时序收敛，板级信号完整性待实测」。**

## 🟣 第八项（新增 2026-10-09）：TMDS 1.485 Gbps 的**板级**信号完整性

### 问题

**⇒ FPGA 内时序收敛 ≠ 板级能跑。** 148.5 MHz 像素时钟 / 742.5 MHz 串行时钟下：

| 关注点 | 为什么 |
|---|---|
| **走线阻抗与长度匹配** | **4 对差分（3 数据 + 1 时钟）之间的偏斜会直接吃掉建立/保持窗口。1.485 Gbps 的单元间隔只有 673 ps** |
| **`GPIOR_P_09` 与 `tmds_clk` 的布局距离** | **Efinity 报 warning：该 HSIO 引脚必须离 LVDS `tmds_clk` 至少 1 对，否则噪声会耦合进 HDMI 时钟。见第九项** |
| **无源器件带宽** | **板上 HDMI 连接器的 ESD/共模器件是否支持 1.5 Gbps** |
| **线缆** | **短线上板内测试可能过，长线不一定** |

### 怎么验

**⇒ 分级爬坡，别一步到位**：

```
100 MHz 像素（1.0 Gbps）→ 120 MHz（1.2 Gbps）→ 148.5 MHz（1.485 Gbps）
每档观察：① 是否出图 ② 是否稳定（跑几分钟）③ 长线是否也稳
```

**⇒ 前置条件**：**先确认第七项更正后的判断 —— 厂商 demo 已跑过 1.487 Gbps，所以这一档**预期可过**，爬坡只是为了定位余量。**

### 不合格的表现

**⇒ 图像随机闪烁 / 雪花 / 间歇性黑屏 / 显示器报「无信号」后自行恢复** —— 都是链路余量不足的典型。

## 🟣 第九项（新增 2026-10-09）：`GPIOR_P_09` 与 HDMI 时钟对的布局警告

### 现象

```
Efinity outflow/design_issue.xml:
  instance=tmds_clk  type=lvds_tx  severity=warning
  msg: These HSIO GPIO must be placed at least 1 pair away from LVDS tmds_clk
       in order to avoid noise coupling from GPIO to LVDS: GPIOR_P_09
```

**⇒ `GPIOR_P_09` 是 DDR3 的 `ddr_ck`。** **⇒ 这是 warning 而非 error，不阻塞构建 —— 但 `ddr_ck` 是持续翻转的高速时钟，耦合进 `tmds_clk` 会直接表现为 HDMI 时钟抖动。**

### 怎么验

**⇒ 若第八项的爬坡在 148.5 MHz 档失败，而低档正常，**优先怀疑这一项**。** **⇒ 判定手段：在 DDR3 空闲（不跑 BitBlt）时看 HDMI 是否更稳 —— 若明显改善，即证实耦合。**

### 处理方向

**⇒ 只能改布局（换引脚分配），不能靠 RTL 解决。** **⇒ 代价是重跑 pnr 并重新确认时序，**建议留到最后** —— 若第八项直接通过，这一项不影响交付。**

## 🟣 第十项（新增 2026-10-09）：软件无法检测垂直消隐期

### 问题

**⇒ `bitblt_video_out` 的 `rd_row` 由**显示侧实际消费的像素**推进，而显示侧只在 FIFO 非空时消费（`de` 被空标志门控）。** **⇒ 若在**活动区中途**置 `ENABLE`（`BLT_FB_CFG` bit 16），当行前几个像素因 FIFO 空而丢失，`rd_row` 与扫描行的相位**永久偏移**若干像素 —— 不会在下一帧自行恢复，因为两者以相同速率回绕。** **⇒ 正确做法是在**垂直消隐期**使能（1080p 有 45 行 ≈ 99,000 pclk，远够首次 AXI 读完成）。**

**🚨 但寄存器表**不暴露扫描位置，也没有 vsync 状态位** ⇒ **软件无法知道自己是否在消隐期。** **⇒ 所以这不是驱动写错了，是**接口缺了一个寄存器**。**

### 影响

**⇒ 上电后画面可能永久横向/纵向偏移几个像素。** **⇒ 仿真已复现：`tb_mux_video` 早期版本在活动区使能时，第 1 行读到的是第 0 行的数据，整帧错位一行。**

### 怎么验

**⇒ 上板后：① 记录使能后首帧与第 10 帧的画面是否对齐；② 若偏移，复位后重试是否复现（**若每次都偏移相同量 ⇒ 证实是相位竞争而非随机噪声**）。**

### 处理方向（二选一）

| 方案 | 说明 |
|---|---|
| **加一个只读寄存器暴露 `v_cnt`（或一个 vsync 脉冲计数）** | **软件轮询到消隐区再使能。RTL 改动小（`bitblt_axi_slave` 加一个寄存器，`bitblt_video_out` 已有 `v_cnt_o`）** |
| **RTL 内部处理：使能后自动丢弃若干行再开始推进 `rd_row`** | **不需要软件配合，但改的是显示通路的相位逻辑，风险更高** |

**⇒ 当前 `bitblt.h` 的 `blt_set_fb` 注释已写明这条契约与限制，见 `docs/41` §七。**

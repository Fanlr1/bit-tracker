## 〇、一句话

**docs/84 卡了九轮的"扫描输出 565 失锁"，根因不在读侧相位，而在【写侧三处 '每 beat 4 像素' 换算被遗漏】** ——
`rd_row` 永不推进，所有显示行都在读第 0 行。
**引擎侧接入后又暴露第二个真 bug：`pack` 的 `beat_valid` 是单拍脉冲，写引擎没接住就丢数据。**
两处修完后：**扫描输出 errors=0（640x480 与 1920 宽两种配置、iverilog + Questa）、集成测试 23 PASS / 0 FAIL。**

## 一、根因 1：三处遗漏的像素/beat 换算（扫描输出）

### 1.1 现象回顾（docs/84 §三·补3）

改成 8x16 位 entry 后：**一行前 634 个像素正确、从 col 634 起全错且不恢复**；
`checks - errors = 634`；`col 634 = 79*8 + 2`。

### 1.2 真因

那 21 处改动**只动了数据宽度**（beat_rgb / FIFO DW/AW / rd_px / rd_hold / need_group / rgb 输出 / 测试台），
**漏了三处"每 beat 4 像素"时代的换算常量**：

| 位置 | 888 写法（漏改）| 565 正确写法 | 后果 |
|---|---|---|---|
| `total_beats = fb_width >> 2` | >> 2 | **>> 3** | AR 长度按 4 px/beat 算 |
| `px_in_line` 步进 / 边界 | `+16'd4` / `fb_width-16'd4` | **`+16'd8` / `-16'd8`** | **rd_row 每 160 beat 才推进一次，而一行只有 80 beat** |
| `wpix16 = {wcnt16[13:0],2'b00}` | <<2 | **<<3** | FIFO 里的像素数只算到一半 |
| `cfg_bad` 的 `beats_w` | >> 2 | **>> 3** | 合法性判据同源 |

**★ 致命的是第二条**：`rd_row` 是扫描输出 AXI 读地址的行号（`fb_base + rd_row*fb_stride`）。
它永远推进不到下一行 ⇒ **每一显示行拿到的都是第 0 行的数据** ⇒
第 0 行之外全错；第 0 行内也从某一列开始错（相位差）。
**与实测"每行 634 个正确、col 634 起失锁、got=156（陈旧数据）"完全吻合。**

### 1.3 为什么九轮没找到

| 九轮看的量 | 真实病灶 |
|---|---|
| `rd_px` / `rd_hold` / `need_group` / `prefetch` / `fifo_empty` / `wcnt_o`（**全是读侧**）| **写侧**的 `total_beats` / `px_in_line` / `wpix16` |

**⇒ 教训：改数据宽度时，要 grep 所有"每 beat N 像素"的换算，而不只是声明宽度。
本次用 `>> 2` / `+ 4` / `<< 2` 三个模式一搜即得。**

## 二、根因 2：`pack` 的 `beat_valid` 是单拍脉冲（引擎侧）

### 2.1 现象

引擎侧接好转换级后：**写引擎 `beats_left=1, din_ready=0` 永久卡住**，
源/目标读引擎都已 done，`line_ack` 永不来 ⇒ 密度扫描 **0 ARs**、引擎 busy 挂死。

### 2.2 真因

`bitblt_px565_pack.v` 原来把 `beat_valid` 写成**一拍脉冲**：

```verilog
beat_valid <= 1'b0;                  // 默认每拍清
...
end else if (px_valid && beat_ready) begin
    beat_valid <= 1'b1;              // 只亮一拍
```

而写引擎 `bitblt_dma_wr.v` 的 **`S_WAIT` 是靠 `din_valid` 才启动的**，那一拍 `din_ready` 还是 0：

```verilog
S_WAIT: if (din_valid) begin m_axi_awvalid <= 1; wvalid_r <= 1; state <= S_DATA; end
```

**⇒ 脉冲在 `din_ready=0` 的窗口里结束，数据静默丢失，写引擎此后永远等一个已经丢掉的 beat。**

**两种错误改法都不要走（都实测过）**：
| 改法 | 结果 |
|---|---|
| 保持单拍脉冲（原样）| 写引擎 `beats_left=1/din_ready=0`，0 个写 burst |
| 脉冲前加 `&& beat_ready` | **死锁**：写引擎要 `din_valid` 才拉 `din_ready`，而 pack 要 `beat_ready` 才拉 `beat_valid` |
| **`beat_valid` 保持到被接受（level，非 pulse）** | ✅ 正确 |

### 2.3 修法

```verilog
assign px_ready = ~hold_valid | ~beat_valid;   // 组好的 beat 没发走，就不再收第二半
always @(posedge clk ...) begin
    if (beat_valid && beat_ready) beat_valid <= 1'b0;      // 只在真握手时撤销
    if (px_valid && px_ready) begin ... end                 // 收半拍
end
```

**★ 教训：`valid` 必须在整个等待期保持，`ready` 可以迟到 —— 这是 AXI-Stream 的基本契约。
把 valid 做成脉冲，只在"下游永远 ready"的假设下能跑；写引擎的 S_WAIT 恰好违反这个假设。**

## 三、我自己引入的一个死锁（记录，因为它反直觉）

接入时我按"两个读引擎是 lockstep 的"直觉，把两个 unpack 的 ready 门控成**共享条件**：

```verilog
wire both_beat_ready = unp_src_beat_ready & unp_dst_beat_ready;   // ❌ 死锁
assign rd_src_ready = spr_fetch_active | both_beat_ready;
assign rd_dst_ready = both_beat_ready;
```

**死锁机制**：源 unpack 收下一个 beat 后 `beat_ready` 拉低（它要等第二半被消费）⇒
目标 beat 也被挡住 ⇒ 目标的像素永远不来 ⇒ 源的像素也消费不掉 ⇒ 互相等待。

**正确写法：各自独立 ready。**
```verilog
assign rd_src_ready = spr_fetch_active | unp_src_beat_ready;   // ✅
assign rd_dst_ready = unp_dst_beat_ready;
```

**为什么安全**：每个 unpack 最多领先 **1 个 beat**（`beat_ready = ~second_pending`），
而"配对"由像素引擎的 `in_valid = src_px_valid & dst_px_valid` 保证 —— 先到的一侧只是等。
领先量有界 ⇒ 不会错位 ⇒ 不会丢配对。

## 五·补、为什么把 video_out 参数化（`PIX565`）

### 起因

565 化之后，两个**原本保护"4 KB 分段"逻辑**的测试台红了：`tb_video_split`、`tb_mux_video`。
它们都例化 `bitblt_video_out`，期望 1920 px 行 = 7680 B = **480 beats / 2 段**；
565 下一行只有 3840 B = **240 beats / 1 段** ⇒ 那段分段逻辑**根本不会被触发**。

### 选择

给 `bitblt_video_out` 加**参数 `PIX565`（默认 1）**，两个测试台以 `.PIX565(0)` 实例化。
**理由不是"少改测试台"，而是保住覆盖**：分段逻辑仍在生产 RTL 里（更高分辨率或 4 B/px 仍需要），
而**只有 888 模式能触发它** ⇒ 必须有测试台以 888 模式跑它。参数化让两种模式在回归里同时存活。

### 参数化踩的两个坑（都实测到）

| # | 坑 | 症状 | 抓到它的测试台 |
|---|---|---|---|
| 1 | `{四个24位像素, 32'd0}` 是 **160 位**，赋给 128 位 wire 时**最高像素被截掉** | 每个像素颜色全错 | **只有 `tb_mux_video`**（它检查像素值）|
| 2 | `fifo_wcnt` 位宽必须等于 `async_fifo_gray` 的 `wcnt_o`（**AW+1 位**）| 满 FIFO 读成 0 ⇒ 突发准入死锁 | 无（预防性）|

**★ 坑 1 的教训（值得记）**：`tb_video_split` 在同样的错误下**照样 PASS** ——
它只检查 **AR 的地址与长度形状**，不看一个像素。
**⇒ "绿的测试台"不等于"覆盖了这条路径"：判据是它检查什么，不是它通过与否。**
**⇒ 定位它靠的是"判定实验"**：把 `git HEAD` 的原始 888 版 `bitblt_video_out` 放进 `-y` 的优先目录，
同一个 tb 立刻 PASS ⇒ 变量只剩我改的那一处。**改对右对齐后三个测试台同时转绿。**

### ★ 上板路上踩的坑：散落的 ×4 字节偏移（编译器抓不到）

**症状**：565 首次上板，应用在 §6 动画段**确定性卡死**（两次捕获都停在 1,645 字节，
正常应 2 万字左右），串口无输出、无超时警告。

**真因**：软件里"像素 x 坐标 → 字节偏移"的地方**写死了 `* 4u`**（ARGB8888 时代的每像素字节数）。
改成 2 B/px 后，精灵被写到**两倍偏移**处 —— 越界写破坏内存，随后 sprite 路径挂住。

**修法**：8 处 `* 4u` → `* 2u`（坐标计算 `blt_sprite_clipped`、测试目的地址、双缓冲偏移、打印）。

**★ 教训**：把每像素字节数从 4 改成 2 时，**所有**"像素数 × 每像素字节数"的换算都要一起改，
而这类换算**散落在坐标算术、测试偏移、甚至打印里**，且全是 `uint32_t` 算术
⇒ **编译器一个字都不会说**（没有类型错误）。**唯一的防线是 grep `\* 4u` / `<< 2` 全盘搜。**

**★ 另一个教训（再次印证 §九·1）**：**"应用卡死"要先用诊断打印定位到行**，
而不是猜 —— 一次加 4 个打印点（帧号 / CPU 清零后 / 精灵后 / flip 后）就把范围钉死到
"精灵 blt 之后"，比读代码猜快得多。

## 五·补3、★★★ 扩表到 4096 才测出真正的极限：**2,240 精灵**（2026-10-16 01:45）

### 为什么必须扩表

2048 槽的表把密度扫描**截断在 2048** —— 而 2048 个精灵只花 903‰ 预算 ⇒ **真实极限必然高于 2048**。
拟合外推给的是 2,293，**但外推代替不了实测**（边际成本可能随 n 上升）。

### 结果

| 配置 | 表深 | 实测极限 |
|---|---|---|
| 565 + 2048 表 | 2048 | 2,048 —— **被表截断，不是真极限** |
| **565 + 4096 表** | 4096 | **2,240** ← **真极限** |

- **2,240 精灵 = 1,644,417 拍 = 98.7% 预算 ✓ 进 60 Hz**
- 2,304 精灵 = 1,690,873 拍 = **101.5%** ✗ 超预算
- 4,096 档 = 2,980,015 拍 = 178% ✗
- **11 PASS / 0 FAIL**，扫描输出自证 1080 行 / 59.99 Hz

### 实测 vs 外推

外推 2,293 → 实测 **2,240**（**低 2.3%**）。**边际成本确实随 n 略升**，
所以"扩表才测得准"不是保守，是必要。

### 代价与资源

| 项 | 2048 表（565）| 4096 表（565）|
|---|---|---|
| LUT4 | 23,754（39%）| **33,124（54%）** |
| FF / RAM10 | 14,373 / 100 | 16,425 / **119（46%）** |
| core_clk slack | +1.135 ns | **+1.397 ns** |
| **walker 固定成本** | 15,458 拍 | **36,541 拍**（8.92 拍/槽 ⇒ +1.3% 帧）|
| 边际每精灵 | 720.1 拍 | **718.4 拍** |

**⇒ 扩表买到的是"表容量"：2,048 → 2,240（+9.4% 可用精灵数）。**

### 结论

1. **精灵数量极限 = 2,240**（60 Hz，16×16 精灵，含扫描输出与双缓冲）。
2. 那是**帧预算墙**（2304 就 101.5%），**不是表墙** ⇒ **再扩到 8192 不会提高**。
3. **但**若要测"更小精灵"的极限（8×8 边际约 360 拍 ⇒ 推算 ~4,500），**表深必须 ≥ 8192** ——
   那时的瓶颈会重新回到表深。

## 七、方法论（可复用）

1. **改数据宽度 ⇒ 先 grep 换算常量**，不只看声明。模式：`>> 2`、`+ 4`、`<< 2`、`*4`。
2. **"每行一次"的量（rd_row/行计数）要在波形里直接看** —— 九轮都在看相位，没人看行号。
3. **`valid` 恒为电平，`ready` 可以迟到** —— 脉冲式 valid 只在"下游恒 ready"时成立。
4. **集成测试的期望值要"按语义层次"改**：字节级（地址/beat 数）与像素级（颜色）分开，
   本次靠"保字节数、翻像素数"把字节层全部保持不变，只重算像素层一处。
5. **单测覆盖不到握手边角**：`tb_bitblt_px565` 5 项全过却没抓到 pack 的脉冲 bug，
   因为它用的下游永远 ready。**集成测试（`tb_bitblt_top`）才是抓它的地方。**

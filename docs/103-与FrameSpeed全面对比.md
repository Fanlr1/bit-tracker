# 103 - 与 FrameSpeed-Engine 的全面项目对比

> 对照仓库：**https://github.com/rinofairy/FrameSpeed-Engine**（同赛题，公开源码 298 文件 / 10.44 MB，2026-10-19 建）
> 本文是**整个项目**的对比，不限于显示通路。所有结论都基于实际读到的 RTL 与 README。

---

## 一、规模对比（第一印象）

| 项 | FrameSpeed | 我们 | 比值 |
|---|---|---|---|
| RTL 模块数 | **8** | **25** | 3.1× |
| RTL 代码量 | 约 2,000 行（70 KB）| 约 8,000+ 行 | ~4× |
| 测试台 | 无独立 tb 目录（靠验证数据 + 板上）| **29 个 iverilog tb** | — |
| 顶层文档 | 3 份 README 共 **115 KB** | docs/ 100+ 篇 | — |
| 验证数据 | **06_Verification/ 大量 JSON + timing.rpt（2.3 MB）** | work/logs/*.txt | — |
| 素材管线 | **有**（PNG/WebP → RGB565 → .bin）| 无（代码生成图案）| — |
| 串口工具 | **有**（C# 源码 + exe）| pwsh 脚本读串口 | — |

**第一个关键事实**：**他们的代码量是我们的 1/4，但画面是稳定的。** 复杂度不等于正确性。

## 二、系统架构对比

| 层 | FrameSpeed | 我们 |
|---|---|---|
| CPU | Sapphire RISC-V @100 MHz | 同（VexRiscv EfxSapphireSoc）|
| 图形引擎 | **两条路径**：通用矩形（blitter_legacy）+ 批量扫描线（scanline）| **一条**：bitblt（addr_gen + dma_rd/wr + pixel_engine + sprite_walker）|
| 引擎访问 AXI | **两条路径互斥共享一组端口**（fs_blitter 里的 `scan_busy`）| 4 个主设备并发，Axi_Mux 仲裁 |
| 显示 | fs_scanout：**BRAM 双行 bank + epoch** | bitblt_video_out：**FWFT FIFO 流式** |
| 显示读仲裁 | **专用 fs_read_arbiter（1.6 KB / 40 行）** | 无（共用 Axi_Mux）|
| 帧缓冲 | 2 × 614,400 B（640×480×2）| 2 × 4,423,680 B（1920×1080×4）|
| 分辨率 | **640×480 @60Hz** | **1920×1080 @60Hz** |
| 寄存器接口 | APB（`psel/penable/pwrite`）| AXI4-Lite（`bitblt_axi_slave`）|

## 三、RTL 模块逐一对比

| 功能 | FrameSpeed | 我们 | 差距评估 |
|---|---|---|---|
| 寄存器/控制 | fs_blitter.v（5.1 KB，含**所有权互斥**）| bitblt_axi_slave.v（805 行）| 我们更大但无互斥 |
| 通用矩形引擎 | fs_blitter_legacy.v（22.1 KB）| bitblt_addr_gen + dma_rd + dma_wr + pixel_engine（~1,260 行）| 相当 |
| 批量精灵合成 | fs_scanline.v（25.2 KB，**逐行合成 + 双行 ping-pong**）| bitblt_sprite_walker + sprite_state（1,174 行，**逐精灵派发**）| **路线不同**：他们逐行、我们逐精灵 |
| 显示输出 | fs_scanout.v（6.1 KB，**双行 bank + epoch**）| bitblt_video_out.v（950 行，**FIFO 流式**）| **架构差异（关键）** |
| 读仲裁 | **fs_read_arbiter.v（40 行，专用）** | 无 | **我们缺失** |
| Alpha 混合 | fs_alpha565.v（1.7 KB，流水乘加）| alpha_blend + pixel_engine（~280 行）| 相当 |
| 显示调试 | fs_dashboard.v（2.5 KB）| bitblt_monitor.v（343 行）+ OSD | 我们有 OSD |
| 互联 | 无（自己写互斥）| **Axi_Mux.v（2,898 行，第三方）** | 我们引用了通用 IP |

**关键结论**：**我们在"图形计算"部分不弱甚至更强，但"显示输送给屏幕"这一段架构完全不同，且缺了专用的读仲裁。**

## 四、显示通路对比（抖动/撕裂的根源）

| 项 | FrameSpeed | 我们 | 后果 |
|---|---|---|---|
| 行缓存 | **BRAM 双行 bank**（ping-pong，按行完整）| **FWFT FIFO 4096 px**（连续流）| 我们是"流"，无行边界 |
| 行完整性 | **行首判 `ready_row`，整行统一** | 每像素判 `~fifo_empty` | **行内半黑半白 = 抖动** |
| 帧序号 | **`epoch` + `bank_epoch` 校验** | **无** | **翻页后旧数据混入 = 撕裂** |
| 欠载策略 | **整行黑**（"never shifted pixels"）| 行内 de 抖动 | 视觉撕裂 |
| 换帧接口 | **base + sequence + commit + accepted_seq** | 直接写 `FB_BASE` | 无切换确认 |
| 跨时钟 | **req/ack 翻转 + 载荷稳定** | FWFT FIFO | 相当 |
| 读突发 | **16 拍 × 4 B = 64 B，每行 20 次** | 原 256 拍×16 B=4 KB，现 64 拍=1 KB，每行 8 次 | 我们单次独占仍长 4 倍 |

**原文证据**（fs_scanout.v 头注释）：
    // RGB565 640x480 scanout. Two 320-word line banks with mailbox CDC.
    // A late/failed line is black for its whole duration, never shifted pixels.

**原文证据**（README §13.2）：
> 缓存行号和帧 epoch 必须同时匹配，不能把上一帧同奇偶行的数据当作新行。
> 若一行未按时准备好或读失败，本版选择整行黑色并计欠载，避免错位显示随机数据。

## 五、AXI 与仲裁对比（慢态/卡死的根源）

| 项 | FrameSpeed | 我们 |
|---|---|---|
| 引擎与显示的读 | **fs_read_arbiter**：显示在**突发边界**优先，**一次只维持一个在途突发** | Axi_Mux：多通道并发，info FIFO 深度 16 |
| 写与扫描 | 两核心互斥（`scan_busy`）| 4 主并发 |
| 突发上限 | **32 拍（128 B）默认**，显示读 16 拍 | 引擎自适应最多 256 拍 |
| 4 KB 约束 | 显式公式 `beats_to_page_end` | 有（seg 切分）|
| 通道锁死风险 | **低**（单突发在途）| **高**（R 通道等 rlast，任一从设备 rready=0 即全停）|

**README §12.4 原文**：
> 显示在**突发边界**拥有优先权；已经接受的突发必须走到 RLAST，不能读到一半切换接收者。
> 该仲裁器**一次维持一个在途读取突发**，并把相应响应送回原请求者。

**我们实测到的后果**：读延迟 ~58,000 拍（慢态）、openocd `Halt timed out`（总线挂死）。

## 六、双缓冲与提交对比

FrameSpeed 有**三层缓冲**（README §11.3）：

| 层 | 作用 |
|---|---|
| 帧缓冲 A/B | 前台显示、后台绘制，**防撕裂** |
| 命令 bank A/B | CPU 准备与 FPGA 执行重叠 |
| 合成行 bank A/B | 合成与写回重叠 |

**换帧必须走完整流程**（README §13.3）：
> 在后台 FB 完成所有区域和 HUD → 等绘图 DMA 全部结束 → 配置 next base/sequence → commit → 等 accepted sequence → 交换角色。

**我们**：只有帧缓冲 A/B，**换帧 = 写一个寄存器**，无 sequence、无 accepted 确认。

## 九、结论：差距到底在哪

### 我们**不弱**的地方
1. **图形计算**：29 个 tb 全绿、1000 次 copy-readback 0 错、13 项板上测试曾达成
2. **性能**：13.13× 加速比、4,352 精灵@60Hz（都是实测过的）
3. **精灵数量**：8192 槽（他们 512 描述符/次）

### 我们**明显落后**的地方（按影响排序）
| # | 差距 | 影响 |
|---|---|---|
| 1 | **显示通路无行完整性保护**（行首判 + 整行黑）| **抖动** |
| 2 | **无帧序号 epoch** | **撕裂** |
| 3 | **无专用读仲裁**（一次一个突发在途）| **慢态 / 总线锁死** |
| 4 | **换帧无 commit/accepted** | 切换瞬间错乱 |
| 5 | **显示质量无计数指标** | 问题不可观测（只能靠肉眼）|
| 6 | **缺总说明文档** | 交接成本极高（本次会话反复踩坑）|

### 关于"要不要重构"
- **不重构**：差距集中在 **1 个模块（bitblt_video_out）+ 1 个仲裁件**，不是整个架构错。
- **但要接受**：这两个地方必须**按 FrameSpeed 的做法重写**，而不是继续打补丁——这正是过去几天反复失败的原因。

## 十、建议的最小改动集（对齐 FrameSpeed）

| 顺序 | 改动 | 对应 FrameSpeed 代码 |
|---|---|---|
| 1 | `bitblt_video_out` 改为**双行 bank + 行首就绪判定** | fs_scanout.v 的 `lines[0:1023]` + `ready_row` |
| 2 | 加 **epoch/sequence**，翻页时旧行判黑 | fs_scanout.v 的 `epoch` / `bank_epoch` / `accepted_seq` |
| 3 | 加**读仲裁**（可先只给视频读限一个在途突发）| fs_read_arbiter.v 全文 40 行 |
| 4 | `SPRITE_BASE` 挪出帧池尾 | — |
| 5 | 增加 `underruns`/`axi_errors` 计数并上报 | fs_scanout.v 的 `underruns`/`axi_errors` |

## 十一、性能与"加速比"的对比（用户追问）

### 11.1 他们怎么报性能

**FrameSpeed 刻意不报单一加速比**，README §2.3 原文：

> 如果两模式都达到显示上限 60，`60/60=1` 不能说明没有加速；这时比较完成绘制的耗时、最大可承受负载和 CPU 可用时间。
> 若一种未达到 60，可报告相同条件下实际 FPS 比值，但要同时标明刷新上限和测试场景。

他们报的是**同条件 FPS + 容量边界**（07_Demo/README.md §4）：

| 场景 | 记录 |
|---|---|
| FPGA 纯色填充 | **60.0 FPS** |
| CPU 纯色填充 | **30.0 FPS** ⇒ **加速比 2×** |
| FPGA 双色搬运 32×32×64 项 | 29.5 FPS |
| 同上 + Alpha/键控 | 15.0 FPS |
| FPGA 批量精灵 640 项 | 60.0 FPS |
| **24×24 精灵容量（Alpha 192 + 键控 + 原尺寸背景）** | **1,376 个 @ 持续 60 FPS**（16.0 ms/帧，60 秒实测确认）；1,408 掉到 59.0；1,536 掉到 30.0 |

**注意**：他们的填充加速比只有 **2×**，因为 640×480 的填充量小（0.6 MB），CPU 侧 33 ms 就能做完，硬件优势不明显。

### 11.2 我们的数字

| 场景 | 记录 |
|---|---|
| **填充（1920×1080）** | 软件 14,522,767 拍（145 ms）/ 硬件 1,126,316 拍（11 ms）⇒ **12.89×** |
| 动画帧（32 精灵） | sw 1,361,884 / hw 294,797 拍 |
| **精灵容量** | **4,352 个 @ 60 Hz**（实测，largest density inside one 60 Hz frame）|

**口径说明**：我们的 13.13× 是**填充场景**的软件/硬件时间比，与他们的 60/30 = 2× **口径一致、可比**。
数字更大是因为分辨率高 9 倍（8.3 MB vs 0.6 MB），CPU 侧的劣势被放大。

### 11.3 谁更快？——按像素吞吐算

| 指标 | FrameSpeed | 我们 | 比值 |
|---|---|---|---|
| 分辨率 | 640×480 | 1920×1080 | 6.75× |
| 填充加速比 | 2× | 12.89× | 6.4× |
| 精灵容量 @60FPS | **1,376**（24×24，带 Alpha+键控）| **4,352**（32×32）| **3.2×** |
| 精灵面积/帧 | 1,376×576 = **792K px** | 4,352×1024 = **4.46M px** | **5.6×** |
| 换算像素吞吐 | 47.5 Mpx/s | **267 Mpx/s** | **5.6×** |

⇒ **单看吞吐，我们明显更强**（4,352 精灵、13× 填充加速、267 Mpx/s）。

### 11.4 那问题到底在哪

**性能我们赢，画面我们输。** 这不是"算力不够"，而是：

| 维度 | 结论 |
|---|---|
| 图形计算（写内存）| **我们更强**（吞吐 5.6×、精灵数 3.2×）|
| 显示通路（内存→屏幕）| **我们缺失**（无行完整性、无 epoch、无欠载计数）|
| 总线仲裁 | **我们缺失**（无专用读仲裁，R 通道可锁死）|
| 可观测性 | **我们缺失**（他们报 underrun/axi_errors/over_budget，我们只有 FPS）|

**他们用 1/4 的代码量做到"画面稳定"，代价是性能指标保守（1376 vs 4352）。我们相反：性能冲得很高，但画面这一层没有对应的保护机制。**

### 11.5 结论

1. **加速比不是差距所在**——我们的 12.89× 与他们的 2× 口径一致，且因分辨率更高而更显著。
2. **精灵吞吐我们领先 5.6 倍**（4,352 vs 1,376，面积口径）。
3. **真正的差距是"显示质量保护"和"总线仲裁"这两层**，以及**可观测性**。
4. 所以**不需要为了性能重构**，需要的是**把显示通路和仲裁这两块按他们的做法补齐**。

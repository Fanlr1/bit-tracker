# 70 - 精灵表扩到 1024 槽（2026-10-14 深夜）

## 一、做了什么

| 文件 | 改动 |
|---|---|
| `rtl/bitblt_sprite_state.v` | `parameter N: 256 -> 1024`（模块默认值）|
| **`rtl/bitblt_top.v`** | **实例化处 `.N(256) -> .N(1024)`** —— **关键**：默认值改了没用，实例化写死了 256 把它覆盖了 |
| `sw/bitblt.h` | `BLT_SPR_MAX 256 -> 1024`、`BLT_SPR_WORDS 8 -> 32`（退休位图 1024/32）|

**为什么改动面这么小**：`bitblt_sprite_state` 里所有相关位宽都是**推导**的 ——
`AW = $clog2(N)`（RAM 地址）、`RW = $clog2(N/32)`（退休位图字索引）、`spr_rt_sel` 已是 16 位。

## 四、⚠️ 发现一个未解释的性能退化（下一轮的入口）

| 密度 | N=256 时 | N=1024 时 | 变化 |
|---|---|---|---|
| 256 精灵 | 369,076 拍（1,442/精灵）| **494,558 拍（1,933/精灵）** | **+34%** |

**同密度、同应用逻辑，只改表深度，每精灵成本涨 34%。**

- **不是固定开销**：对 `(512, 985530)` 与 `(1024, 1972456)` 做线性拟合，
  斜率 = 1,934 拍/精灵、**截距 ≈ -300（即 ≈0）** ⇒ 纯线性，每精灵成本本身就变高了。
- **主要嫌疑**（每个精灵读状态都要走）：
  ```verilog
  assign rd_valid = ok[idx_clamped];   // 256 位 -> 1024 位的位选择
  assign rd_live  = lv[idx_clamped];   // 组合 LUT 树，深度随 N 增长
  ```
- **对照实验（N=512）没做完**：build 在 PnR 阶段被**电脑黑屏**中断（`build-n512.log`
  停在 `=== pnr ===`、`route.out` 为 0 字节），未生成比特流。

**⇒ 如果 34% 退化能修掉**：1024 × 1,442 = **1,476,608 拍 < 1,666,666** ⇒ **1024 自动进 60 fps**。
所以这条线值得继续查。

## 四·附、对照实验 A + B 的结果（2026-10-14 21:2x）

### A：读 walker 的逐精灵流程（纯代码）

`bitblt_sprite_walker.v` 只有 336 行，状态机为
`S_FETCH -> S_WAIT -> S_BLIT -> S_ADV -> S_STEP`。
**每精灵的绝大部分时间花在 `S_BLIT`（等像素引擎完成）**，walker 自身逻辑只有几拍。

**⇒ 每精灵成本几乎全在"引擎 + DDR 往返"上，不在 walker。**

### 排除"1024 位组合树"这个主嫌疑（两条证据）

1. **综合时序报告里最差路径不经过 `sprite_state`** —— grep `spr_state`/`ok[`/`lv[`/`rt[` **零匹配**（最差 slack 0.422 ns 属于其他逻辑）；
2. **仿真里 N=256 与 N=1024 性能完全相同**：`tb_bitblt_top` 两次都报
   `256 sprites -> 81670 cycles (319 per sprite)`。

**⇒ 退化不是 N 的逻辑后果，而是"板上特有"（布局/时序/DDR 交互）。**

### B：N=512 对照实验（决定性数据）

| N | 256 精灵 | **每精灵** | RAM10 | LUT4 | core_clk slack |
|---|---|---|---|---|---|
| **256** | 369,076 | **1,442** | 74 | 22,570 | 1.806 ns |
| **512** | 500,220 | **1,954** | 74 | 24,267 | 1.605 ns |
| **1024** | 494,870 | **1,933** | 77 | 31,304 | 1.440 ns |

**⇒ 512 与 1024 基本持平（1024 甚至略快），而 256 快 34%。**

**这不是"越深越慢"的线性效应，而是 256 -> 512 之间的一个跳变。**
**⇒ 扩到 1024 相对 512 是"免费"的**（表翻倍、算力不变）。

### 修正后的瓶颈账

| N | 表深 | 算力上限（1666666 ÷ 每精灵）| 60 fps 实际 |
|---|---|---|---|
| 256 | 256 | 1,155 | 256（**表**是瓶颈）|
| 512 | 512 | 852 | 512（**表**是瓶颈）|
| 1024 | 1024 | **861** | **512** ❌（**算力**是瓶颈）|

**⇒ 1024 要进 60 fps，需要把每精灵从 1,933 压到 <=1,627 拍（-16%）。
若恢复到 256 时代的 1,442，则 1024 × 1,442 = 1,476,608 直接进预算。**

**⇒ 问题收敛为一句话：N=256 时那 34% 的优势从何而来。** 尚未查明。

### 实验 ②：重做 N=256（2026-10-14 21:36）—— **不可复现**

把 `bitblt_top.v` 改回 `.N(256)`（软件同步回 256/8），**资源与最早那次逐项相同**
（LUT 22,570 / FF 19,612 / RAM10 74 / slack 1.806 & 1.941 ns），然后上板测：

```
256 slots
  64 sprites: 127835
 128 sprites: 246316
 256 sprites: 491058   -> 1,918 拍/精灵      <-- 不是 1,442
 512 sprites: 981121
```

**⇒ 那个 1,442 拍/精灵是孤例，与 N 无关。**

**修正后的认识**：

| 配置 | 每精灵 |
|---|---|
| N=256（最早那次）| **1,442** ← 孤例 |
| N=256（重做）| **1,918** |
| N=512 | 1,954 |
| N=1024（5 次）| 1,933 |

**⇒ 三种 N 全落在 1,918~1,954。该解释的是"那次孤例为什么快"，而不是"别人为什么慢"。**

**⇒ 因此"回到 N=256 拿回 34%"这条路不成立，1024 需要的 -16% 必须从别处找。**

**最可能的解释**仍是那个已知的 **1.87x 运行间波动**（DDR3 上电校准质量差异），
**但这一点没有被验证** —— 而本次连续多次测量都一致落在慢的一侧。

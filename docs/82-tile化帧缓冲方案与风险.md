# 82 - tile 化帧缓冲：12.46× 的实测证据、完整方案与风险

> 2026-10-15 晚。接 [docs/80](80-往返分解与各方向收益上限.md)（往返分解）与 [docs/81](81-行合并可行性判别.md)（行合并判别）。
> 本文是**唯一一条收益确定的未被封死的路**，但它需要架构改造 —— 所以先把方案和代价写清楚，再决定动不动手。

## 〇、一句话

**实测：同一个 16×16 COPY，连续目标是 89 拍，strided 目标是 1,109 拍 —— 12.46×。**
而 **1,109 ≈ 密度扫描实测的 1,204.9 拍/精灵** ⇒ **每精灵的成本几乎全是"16 行 strided 往返"**，
与带宽、与计算都无关。把帧缓冲改成 **tile（16×16 块连续）** 就能把 **32 次往返变成 2 次**。
**难点全在扫描输出**（§三）：它必须一起改，而那是历史最容易翻车的模块。

## 一、实测证据（本会话）

在 `main.c` 里加了一段对照（`3c. contiguous vs strided destination`，200 次取平均）：

| 用例 | 目标 stride | 耗时 |
|---|---|---|
| **A 连续**（tile 化的样子）| `BULLET_W*4 = 64 B` | **89 拍** |
| **B strided**（当前帧缓冲）| `FB_STRIDE = 8192 B` | **1,109 拍** |
| | | **B/A = 12.46×** |

**★ 关键交叉验证**：B 的 1,109 拍与密度扫描拟合出的 **1,204.9 拍/精灵**几乎一致
（差额是 ALPHA 要额外读目标）。**⇒ 那 1,200 拍就是往返本身。**

## 二、为什么这是"改次数"而不是"调节奏"

今天六个实验全在**调往返的节奏**（FIFO 深度、burst 上限、在途数、burst_floor），**全部变差**（docs/79 §八、docs/80 §五）。
本文改的是**往返的次数**：

| | 每精灵往返 | 来源 |
|---|---|---|
| 现在 | **32 次**（16 行 × 读+写）| `row_cap` 禁止 burst 跨行，因为行距 8192 B |
| tile 化后 | **2 次**（1 KB 连续读 + 连续写）| 一个精灵的 16 行落在同一块 1 KB 里 |
| tile 化后（精灵未对齐 16 网格）| **4 次**（跨 2×2 个 tile）| 仍是 8× |

**⇒ 与"提高并发"无关（不增加在途、不加深 FIFO），所以不触犯已被封死的那条规律。**

## 三、难点：扫描输出（全部难度所在）

扫描输出现在的读法是**逐行一个大 burst**（`rd_row × fb_stride`，一行 1920 px = 7680 B），
注释明确写着"holding rready low during the split is harmless" —— 它**依赖"一行是一段连续内存"**。

tile 化后，屏幕的一行要从 **120 个 tile 里各取 64 B**：

| 方案 | 后果 |
|---|---|
| 每 16 像素一个小 burst | **AR 数 ×120** —— 扫描输出已占 31% 的 AXI 时间，直接爆 |
| **读 tile 行带到片上重排**（唯一可行）| 缓冲 **122,880 B ≈ 96 个 RAM10** + 重排状态机 + `line FSM` 重写 |

**资源账**：当前 RAM10 **97 / 256（38%）**，加 96 后 **~193 / 256（75%）** —— **放得下，但余量用掉大半**。
**收益**：扫描输出的 AR 数反而从 **1080 次/帧降到 68 次/帧**（每 16 行一次连续大读）。

## 四、完整改造清单

| # | 内容 | 风险 |
|---|---|---|
| 1 | **帧缓冲布局改 tile**（120×68 个 16×16 块；1080/16 = 67.5 ⇒ 需 padding 到 1088）| 低（纯布局）|
| 2 | **引擎的目标地址生成**（`bitblt_addr_gen` / `dma_rd`/`wr`：`y×stride+x×4` → tile 索引 + 内偏移）| 中（有 tb 覆盖）|
| 3 | **扫描输出：行带缓冲 + 重排 + line FSM 重写** | **高**（docs/67 的 307Hz、docs/68 的分段读缺陷都在这里）|
| 4 | 软件：精灵目标地址 + 对齐约束（§五）| 低 |

## 五、★ 对齐约束 —— 本方案最硬的一条限制（已实测更正）

> **2026-10-15 晚更正**：本节最初写的是"不对齐 = 4 次往返"，**那是错的**。
> `tb_bitblt_tile_addr` 第 4 项实测：**不对齐的精灵切出 32 段，比行优先的 16 段还差一倍**。

| 情况 | 连续段数 | 往返（每段一读一写）|
|---|---|---|
| **tile + 对齐 16 网格** | **1** | **2 次** ✅ **12.46×** |
| 行优先（现状，任意位置）| 16 | 32 次 |
| **tile + 不对齐** | **32** | **64 次** ❌ **回归** |

**为什么是 32**：精灵每行 16 像素宽，只要起点不在 tile 边界上，该行就会被 tile 列边界切成两段
（原点 (5,7) 时是 x∈[5,15] 与 x∈[16,20]）⇒ 16 行 × 2 = **32 段**。

**⇒ 结论（与 docs/81 的行合并是同一个病）**：
**tile 化只在"精灵对齐到 16 像素网格"时成立。**

- **密度扫描（测量口径）**：布点就是 `(i%cols)*16, (i/cols)*16` ⇒ **天然对齐，拿满 12.46×** ✅
- **移动的弹幕精灵**：会脱离网格 ⇒ **反而更慢** ❌

**★ 出路在于游戏设计，不在引擎**：
若新游戏接受**格子移动**（精灵位置量化到 16 像素，即 `vx/vy` 取 16 的倍数），
则它在真实游戏里**也永远对齐** ⇒ tile 化对游戏同样有效；
代价是移动"按格跳"（16 像素 ≈ 屏宽 0.8%，复古风格里很常见）。

**⇒ 所以 tile 化的价值取决于一个设计决定：新游戏的精灵是【平滑移动】还是【格子移动】。**
这一条必须在动 RTL 之前定下来。

## 六、风险与分阶段计划

| 阶段 | 做什么 | 判据 | 硬件风险 |
|---|---|---|---|
| **0** | **仿真验证扫描输出**：在 `tb_bitblt_video_out` 里让帧缓冲按 tile 布局、扫描输出按 tile 读，检查输出像素逐点正确 | 波形/像素比对通过 | **零** |
| 1 | 引擎侧 tile 地址生成 + tb | 回归 26/0 | 零（仿真）|
| 2 | 上板：**只** tile 化 + 新扫描输出，跑扫描输出自证（1080 行 / 59.99 Hz）+ 密度扫描 | 显示正确 + 上限提升 | 中（可回退比特流）|
| 3 | 全量：回归 + 上板 + 文档 | 全绿 | 中 |

**★ 阶段 0 是关键的"便宜验证"**：它把最大的未知（扫描输出能否重写）放在**零硬件风险**的地方。

## 七、结论与建议

1. **这是今天唯一收益确定（12.46× 实测）、且不违反任何已封死规律的方向。**
2. **但它不是一轮能做完的**（改 4 处，其中扫描输出是重写）—— 需要一个完整的实施周期。
3. **建议从阶段 0（仿真）开始**：如果仿真都过不了，就不该碰板子；如果过了，再逐级上板。
4. **务必先归档当前状态**：`v0.3-2048sprites` 已标记（1,368 上限、26/0 回归），可随时退回。

**★ 一个必须诚实说明的边界**：12.46× 是**引擎侧**的实测。
端到端收益要等扫描输出改造完成、且显示仍然正确之后才能确认 —— **在那之前它是"有强证据的预期"，不是"已兑现的结果"。**

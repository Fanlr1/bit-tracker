# 90 - 慢态的逻辑推理（2026-10-17 凌晨，未动手，纯推理）

> 接 [docs/88](88-慢态根因与修复.md)（根因与修复尝试）· [docs/89](89-中断尝试与慢态最终形态.md)（中断尝试）。
> 本文不动手，只把已有观测按**时间关系**重排，推出结论与可检验判据。

## 一、★ 贯穿全场的方法论错误：观测时机

**今晚所有"引擎空闲"的观测，都是在 `blt_wait()` 超时之后采样的 —— 也就是引擎已经完成之后。**

| 观测 | 采样真实时刻 | 它实际证明的 |
|---|---|---|
| `bus=0`（五个 busy 全 0）| 超时后 | 引擎**最终完成了** |
| `fsmhist` 32/32 IDLE | 超时后（跨度仅约 1,000 拍）| 同上；在 373 万拍里取 1,000 拍窗口，采到空闲是必然 |
| walker IDLE | 同上 | 同上 |
| ddr / soc 总线空闲 | 同上 | 同上 |
| `mon sticky=0` | **全程有效** | **确实没有握手超时**（这条可信）|

⇒ 这批观测**不能推出"引擎没工作"**。此前多次拿它们当"卡住"的证据是错的。

## 二、量化反推：373 万拍的结构

    3,727,870 ÷ 32 精灵        ≈ 116,500 拍/精灵
    116,500  ÷ 2 次读(源+目标)  ≈ 58,250 拍/次读

**58,250 小于监视器的 TIMEOUT = 65,535** —— 这一个数同时解释两件事：

1. **为什么 `mon sticky = 0`**：每次等待都卡在阈值**之下**，monitor 永不触发；
2. **为什么时间是确定的**（±0.05%）：58,000 拍级等待来自某个固定机制，不是噪声。

## 三、因果链（自洽版）

    慢态下每次 DDR 读要等 ≈58,000 拍
      → 一次 blit 有 2 次读 ⇒ 116,500 拍
      → 32 个精灵 ⇒ 3.73 M 拍/帧                （与实测吻合）
      → 每次等待 < 65,535 ⇒ monitor 不报          （与 sticky=0 吻合）
      → 引擎 99.97% 的时间在等 ⇒ 任何事后采样都看到空闲（与全部空闲观测吻合）

## 四、58,000 这个数本身在说什么

| 候选 | 数值 | 判定 |
|---|---|---|
| DDR3 刷新 tREFI | ≈780 拍 @100 MHz | ✗ 差 74 倍 |
| 扫描输出一行 | ≈1,480 拍 | ✗ 差 39 倍 |
| monitor 阈值 | 65,535 | **接近但更大** ← 关键 |
| 正常态单次读 | ≈100–197 拍 | ✗ 差 294 倍 |

它落在阈值下方 12%，"恰好差一点"很难是巧合。monitor 的注释写明该阈值是**人为选的**
（"Cycles a valid may wait for its ready before it counts as wedged"）。

**推论 1**：系统里存在一个约 58,000 拍量级的内部等待，65,535 是当初为"比它略大、不要误报"
而定的值。**设计者见过这个等待，只是没当成 bug 记下来。**

## 五、等待发生在 AR 还是 R 阶段

有一条先前被当成噪声、现在看可能是唯一现场证据的数据：**7 轮取证里 `fsm` 反复读到 `0x8`**，
即 `{rd_src=IDLE, rd_dst=S_RD}`。

- `S_RD` 含义固定：**AR 已被接受、正在等 R 数据**；
- 7 轮全部读到它，而采样时刻是随机的；**从来不是 `S_AR`（值 1）**。

**推论 2**：**慢在 R 阶段，不在 AR 阶段。** AR 被正常接受，是 R 数据迟迟不到。
搜索面因此缩掉一半：**不是仲裁器不给总线，而是数据通道不送货。**

## 六、R 阶段被谁挡住

    M_R_Ready = R_Orphan | |(R_Act_Cnl_List & S_R_Ready)

| 变量 | 已知 | 推理 |
|---|---|---|
| `R_Act_Cnl_List` | 来自 info FIFO | 若与当前 R 数据**不匹配** ⇒ 指向一个没在等的通道 |
| `S_R_Ready` | 各 slave 的 rready | 被指通道 FIFO 满 ⇒ 0 |
| `M_R_Valid` | 慢态观测到过 `rvalid=1` | DDR 手里有数据 |
| `R_Orphan` | 本轮新加 | 仅当列表**全 0** 才生效 |

而 `mon sticky = 0` 说明 **rvalid 与 rready 从未同时错位到 65,535 拍** ——
即**它俩是"间歇性错位"**：错一会儿、通一下、再错。

**推论 3**：**不是死锁，是"断续阻塞"**。R 通道平均每次要错位几十次才送出一次数据，
累积出 58,000 拍。

## 七、"断续"的源头（配置相关约束）

约束：**上电时被随机定死、之后整次运行永不改变**。只有三类状态符合：

1. **info FIFO 的初始内容**（AR 与 R 的配对从此错位一格）；
2. **某个计数器的初值**（决定它何时翻转/重载）；
3. **DDR 控制器某个模式寄存器的采样结果**。

**推论 4**：若是 ①，配对错位是**恒定一格**，表现为"每一次读都稳定卡同样长的时间"——
与实测的 **±0.05% 稳定性**吻合；若是 ②③，等待长度应随帧数/相位变化，**不会这么平**。

⇒ **①（info FIFO 配对错位）为首选假设。**

## 八、★ 可检验推论（下次动手的判据）

若 ① 成立，下面两条必然成立，且**互相独立**：

| # | 推论 | 怎么验 |
|---|---|---|
| **A** | **AR 数 ≠ R 完成数**，差值恰为错位量 | 用 monitor 计数或加一对计数器，跑一次慢态 |
| **B** | **`R_Act_Cnl_List` 与 `M_R_Id` 解出的通道不一致** | 把 `R_Act_Cnl_Num` 与 `M_R_Id` 高位同时引入观测口对比 |

**A 或 B 任一被证实，修法即确定**：在 AR 完成那一刻把 `{通道号, 通道列表}` 与 AR 一起打戳，
R 侧按戳取；或给 FIFO 加复位/深度校验。
（先前加的"孤儿吸收"只是治标——列表不为 0 时它不生效。）

## 九、★ 必须承认的逻辑漏洞

推论 3 依赖"间断阻塞"，而它与"373 万拍是引擎真实工作时间"是同一件事的两种说法。
但如果 R 阶段只是间歇阻塞，**为什么正常态只要 197 拍**？
扫描输出在两种状态下都开着、AR 量也一样。

⇒ 还有一个**未被解释的自由度**：慢态下**要么 R 通道错位更频繁，要么有第二个 master 在抢**。
现有数据无法区分——这正是第八节 A/B 两条要先做的原因，**它们能把这个自由度消掉**。

## 十、一句话总结

**慢态不是"引擎空闲"，而是"引擎每次读要等约 58,000 拍、恰好低于监视器 65,535 的报警线，
于是既不报警、事后看又全是空闲"——一个此前从未被观测到的窗口。**

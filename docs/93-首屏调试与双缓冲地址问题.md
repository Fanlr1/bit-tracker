# 93 - 首屏调试：精灵已被画出，但落在看不见的地址上（2026-10-17 下午）

> 接 [docs/92](92-慢态尝试与未确证.md)（慢态，其结论已被本日后续推翻，见第三节）
> 本文记录 **第一次接显示器** 后的发现。屏幕接上后，很多此前只能靠串口数字猜的东西直接可见了。

## 一、一句话结论

**精灵一直画得对，但读回 buf[1] 有精灵、读回 buf[0] 全是背景——同一份代码、同一个函数、只改地址，结果相反。**

这是**帧缓冲地址映射问题**，不是引擎、不是慢态、不是扫描输出。

## 二、决定性证据

### 2.1 读回帧缓冲（关键实验）

在 240 帧动画的第 0 帧画完 32 个精灵后，读回精灵 0 所在位置的三个像素：

| 绘制目标 | 读回像素 | bg 参考 | hw |
|---|---|---|---|
| **buf[1]** = 0x08438000 | **0x0801 / 0x5a81 / 0xad01** | 0x1084 | 3,815,202（慢态）|
| **buf[0]** = 0x08000000 | **0x1084 / 0x1084 / 0x1084** | 0x1084 | **9,100**（正常）|

- buf[1] 那三个值与背景**完全不同** ⇒ **精灵确实被画进去了**；
- buf[0] 全是背景 ⇒ **精灵没落到那里**，即便同一个函数收到了 dst_base = FB_BASE；
- 而 buf[0] 那次 hw = 9,100 ⇒ **引擎立刻报完成**，说明它认为写成功了。

⇒ **写进去的地址和读回来的地址不是同一块内存。**

### 2.2 屏幕现象（第一次上屏）

| 阶段 | 屏幕 | 判读 |
|---|---|---|
| 正常态启动 | 暗蓝紫背景 + 左上角 OSD（1920x1080 / SW / HW / SPR 32）| **扫描输出、OSD 字体、帧缓冲读全部正常** |
| 8 帧双缓冲动画 | 背景正确、**无精灵** | 精灵画在 back，屏幕看 front |
| 240 帧动画（原代码）| 背景正确、**无精灵** | 原代码**从不翻页**，全部画进 buf[1] |
| 补上翻页后 | **OSD 开始闪烁，且闪一次消失一行** | **翻页确实在工作**，两个缓冲的 OSD 内容不同 |
| 直画 buf[0] 后 | 仍无精灵 | 与读回结果一致 |

**「OSD 闪烁、每次少一行」这一条价值极大**：它证明双缓冲交替是正常的，所以问题不在翻页机制，而在**被翻过去的那块内存内容**。

## 五、重要旁证：一处过时注释暴露了地址算错的来源

main.c:20 注释写：

    //   0x08870000  framebuffer B     immediately after A (FB_BYTES = 8192*1080 = 0x870000)

而实际值是：

    #define FB_STRIDE_BYTES 4096u                     // 2048 px 行距，不是 1920
    #define FB_BYTES        (FB_STRIDE_BYTES * FB_H)   // = 0x438000，不是 0x870000

⇒ **buf[1] 的真实地址是 0x08438000，注释里的 0x08870000 是旧 stride（8192）时代的残留。**

这类注释漂移很可能就是某些地方按错误地址计算的历史来源，值得全仓搜一遍 0x08870000 与 8192。

## 六、下次开局（一个实验就能判定）

**在同一帧里先后画到 buf[0] 与 buf[1]，然后分别读回两个地址。**

- 若**只有高位地址那块能写** ⇒ 查 blt_dma_wr 的目标地址**截位/对齐**（0x08000000 与 0x08438000 的差异可能在低位或高位被吞）；
- 若**两块都写不进去** ⇒ 怀疑 FB_BASE 在 RTL 侧被改写；
- 若**两块都能写** ⇒ 回到「扫描输出读哪个 base」，用 GPIO 观测 bitblt_video_out 的 base 寄存器值。

## 七、方法论收获

1. **接上显示器是决定性的一步**：此前所有判断只能靠串口数字，屏幕一接，「数据错乱」与「绘制错误」立刻可分；
2. **读回帧缓冲是最便宜的判据**：4 个像素、一次打印，就能区分「没画」与「画到别处」；
3. **注意「能力」与「现象」的分离**：hw=9,100 说明引擎认为成功——**引擎的成功信号不能当作数据落地的证据**。

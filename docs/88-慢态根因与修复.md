## 八、★★ 慢态的真正根因与修复（2026-10-17 凌晨，已修复并验证）

### 8.1 根因：CPU 的轮询本身在抢总线

`blt_wait()` 的实现是「读 STATUS，判断 BUSY，循环」：

    do { st = blt_status(); guard++; ... } while (st & BLT_ST_BUSY);

每次迭代约 22 拍，也就是**每 22 拍向 Axi_Mux 的 S0（CPU）端口发一次 AXI 读**——
每秒 4.5 万次请求。在 round-robin 仲裁下，这些请求摊到各通道上，
**把扫描输出（S4）挤到 10.6 fps**（实测 `short` 饿死 8.6 亿像素时钟）。

**这不是新问题**：`system_top.v` 2026-10-13 的注释记录了同一机制——
当时是优先级仲裁，被饿死的是引擎通道 S1/S2/S3（「a master that polls continuously
starves the DMA channels」），改 round-robin 后受害者换成了扫描输出。

### 8.2 关键证据：引擎其实一直是空闲的

| 观测 | 慢态读数 |
|---|---|
| 五个 busy 分量（含 spr_busy） | **全 0** |
| 两个读引擎 FSM（32 次直方图采样） | **32/32 都在 IDLE** |
| walker `{state, busy}` | **IDLE, busy=0** |
| DDR 侧 / SoC 侧 AR 握手 | 空闲 |
| `blt_wait` 超时瞬间的 STATUS[0] | **仍为 1** |

⇒ 那 4.4 亿拍**没有花在引擎上**，全部花在「等一个不落位的状态位」。

### 8.3 修复：轮询退避（`bitblt.h`）

    for (volatile uint32_t backoff = 0u; backoff < 100u; backoff++) { }   // 每次轮询后
    #define BLT_WAIT_LIMIT  2000u        // 原 20,000,000

退避把请求率降约 7 倍；上限同步下调以保持最坏情况在帧预算内：
32 blits x 2,000 x 约 150 拍 = 9.6 M 拍 < 16.67 M（60 Hz）。

### 8.4 实测效果

**★ 必须按状态分开对比**（状态是随机掷骰子，混在一起比会得出错误结论——
本轮就先犯过一次：把正常态的 6,288 当成了修复效果）：

| 状态 | 修复前（LIMIT 20M）| 修复后（退避 + LIMIT 2000）| 改善 |
|---|---|---|---|
| **慢态** | 440,002,608 | **3,728,656** | **118 倍** |
| 正常态 | 3,789 | 6,316 | 基本不变 |

**慢态下 `to=1`**（只超时一次）⇒ 那 373 万拍是**引擎真的在算**，
不再是被不落位的状态位空等。

**未根治**：慢态仍是正常态的 **590 倍**，总线竞争仍在（见 8.5）。

### 8.4.1 八轮取证的完整形态（`work/probe/forensics.ps1`）

| 轮 | 状态 | hw | to | fsm |
|---|---|---|---|---|
| 1,3,4,5,7,8 | slow | **3,727,870 ~ 3,729,405** | 1 | **0x8** |
| 2 | NORMAL | 6,316 | 0 | 0x0 |

三条结论：

1. **慢态 hw 稳定到 ±0.05%**（7 轮 373 万上下）⇒ 确定性状态，不是噪声；
2. **to=1**：每轮只超时一次 ⇒ 那 373 万拍**不是自旋**，是引擎真的花了这么多；
3. **fsm=0x8** = {rd_src=IDLE, rd_dst=S_RD} ⇒ **目标读 rd1 卡在「等 R 数据」**，
   每精灵 116,500 拍（正常态 197 拍，差 590 倍）。

⇒ **慢点收敛到一处：rd1 的 DDR 读延迟被放大 590 倍**，与「扫描输出抢带宽」一致。
下一轮要测的是 **rd1 的单笔读延迟分解**（AR 发出 → 首个 R beat → rlast），
需要在 RTL 里给这几个节点打时间戳（软件侧的 BRAM 槽机制已经现成）。

### 8.5 仍然存在的问题

1. **扫描输出饿死未根治**：`short` 仍为 8.6 亿（历史累积，不再快速增长），
   说明 Axi_Mux 的仲裁对扫描输出仍不友好——CPU 轮询只是减轻、没有消除竞争。
   下一步可考虑：中断驱动的 `blt_wait`（demo 已有中断机制）、或给 S4 更高权重。
2. **STATUS[0] 不落位**这个底层缺陷仍在（退避只是让它不再致命），
   超时痕迹保留在 BRAM 槽 32..38，随时可复查。

## 一、为什么做这次审计

**触发原因**：本轮改动面很大（**9 个 RTL、13 个 TB、4 个脚本、1 个驱动**），
**而且过程中我犯过两次真实错误**：

| 错误 | 发现方式 |
|---|---|
| **`awsizeReg <= axi_arsize - 3'd0 + axi_awsize`**（在 AW 块里写了 AR 的信号）| **写完立即核对 AW 块全文** |
| **`edit` 误删 `task run_transfer` 的 `input bytes;`** | **写完立即核对签名** |

**⇒ 两次都是【主动复核】抓到的，不是测试抓到的。**

**这直接推出一个推论**：**同类错误如果没被复核到，测试也未必能发现** —— **因为它们多半落在没有覆盖的地方**（第一个错误的 `awsizeReg` 根本没人用）。

**⇒ 所以这次审计的重点不是「回归过不过」，而是「逐行找回可能漏掉的笔误」。**

## 三、发现的问题

### 3.1 【真问题】AW 块的注释被插进了复位块内部

**位置**：`bitblt_axi_slave.v`（修复前 225-227 行）

```verilog
214:         if (!axi_resetn) begin
215-224:      ... 复位赋值 ...
225:         // Capture on the AW handshake, not merely on AWVALID being high.   ← ★ 位置错误
226:     // axi_awready = awreadyReg & axi_awvalid, ...
227:     // awvalid & awreadyReg -- the cycle the address is actually accepted.
228:     end else if (axi_awvalid && axi_awready) begin
```

**性质**：**语法合法**（注释不影响综合），**但缩进与结构都乱了** —— **是我上次编辑时插入点选错。**

**影响**：**纯可读性**，无功能影响。**但会误导后续阅读者**（看起来这段注释是描述复位逻辑的）。

**修复**：把注释移到 `always` 之前，恢复正确缩进。

**验证**：`compile exit: 0`，`PASS: all checks OK`。

### 3.2 【真问题】两处 `bsp_printf` 落在 `cycles()` 计时区间内

**位置**：`main.c` 的硬件填充段与中断段

```c
c0 = cycles();
for (...) {
    ...
    if (st & BLT_ST_ERROR) {
        bsp_printf("engine reported ERROR ...");   // ★ 在 c0..c1 之内
        break;
    }
}
c1 = cycles();
hw_cycles = c1 - c0;                               // ★ 把打印时间算进去了
```

**影响分析**：

**⚠️ 但这两处【都紧跟 `break`】，只在错误路径执行一次** ⇒ **正常运行时不会进入。**

**⇒ 所以严格说不是 bug**，**但**：

- **115200 波特率下一行 50 字符约 4.4 ms**，而**满屏填充只要 1 ms**
- **⇒ 一旦报错，帧率数字会被打印开销污染 4 倍以上**
- **⇒ 「报错的运行，帧率不可信」** —— 而**这正是最需要看清数字的场景**

**修复**：**计时区内只记录状态码/帧号，出了计时区再打印。**

```c
if (st & BLT_ST_ERROR) {
    fill_err        = 1;
    fill_err_status = st;      // 只记录
    break;
}
...
c1 = cycles();
hw_cycles = c1 - c0;
if (fill_err) {
    bsp_printf("engine reported ERROR during fill (STATUS 0x%x)\r\n", fill_err_status);
}
```

**验证**：复查脚本确认计时区内已无打印（唯一命中是注释文本），`compile exit: 0`。

## 四、【误报】我的检测脚本自己有缺陷

**扫描「复位分支 vs 正常分支的寄存器集合」时，脚本报告**：

```
bitblt_axi_slave.v:214  else 分支有、复位分支没有: bidReg, brespReg, bvalidReg
```

**人工核对后确认是误报** —— **B 响应块有完整的复位**：

```verilog
254: always @(posedge axi_aclk or negedge axi_resetn) begin
255:     if (!axi_resetn) begin
256:         bidReg    <= 8'd0;
257:         brespReg  <= 2'b00;
258:         bvalidReg <= 1'b0;
```

**⇒ 26 个寄存器【全部有复位】。**

**根因**：**我的脚本【跨 `always` 块收集赋值目标】** —— 从 AW 块的 `if (!axi_resetn)` 开始，一直收集到后面 B 块的 `else`。

**⚠️ 这件事本身值得记**：**我刚写的扫描脚本，和 `docs/20` 批评的 `audit-bitblt.ps1` 犯了同一类错** —— **检测逻辑看起来对，实现有缺陷。**

**唯一的区别是**：**它误报（宁可误报不漏报），而 `audit-bitblt.ps1` 是漏报。** **方向不同，但都是「检查工具本身不可靠」。**

## 五、交叉核对：本轮引入了一个新的跨层耦合

**新增的耦合**：**`board-check.ps1` 靠固件输出的 `[TEST:PASS] <name>` 判定** ⇒ **固件改名字，脚本可能静默失效。**

**核对结果**：

```
固件里的 5 个名字：
  axi-slave-responds / completion-interrupt-arrives / engine-fill-no-error
  hardware-faster-than-software / no-cpu-exception

脚本：靠【正则通配】匹配 \S+，不硬编码任何名字
一致性测试：5 个全部抓到 → BOARD CHECK: PASS (6 checks)
```

**⇒ 耦合是松的** —— **改名字不会让脚本静默失效**。

**⚠️ 但仍有一层硬耦合**：`[TEST:PASS]` / `[TEST:FAIL]` **这个格式本身**。**若固件改格式，脚本会报「固件没报任何 verdict」而不是静默通过** —— **这正是要的行为（宁误报不放过）。**

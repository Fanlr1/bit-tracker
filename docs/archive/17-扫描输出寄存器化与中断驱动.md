## 二、寄存器扩展：**只加 3 个，不扩地址解码**

**需要的值有 5 个**（`fb_base` / `stride` / `width` / `height` / `enable`），**而 4 位索引（`[5:2]`）只剩 3 个空位**。

**⇒ 打包成 3 个**，沿用 `IDX_WIDTH_H` 已有的约定：

| 偏移 | 名称 | 布局 |
|---|---|---|
| **0x34** | `FB_BASE` | 32 位基址 |
| **0x38** | `FB_SIZE_H` | `[15:0]` width，`[31:16]` height |
| **0x3C** | `FB_CFG` | `[15:0]` stride，`[16]` enable |

**⇒ 不动索引位宽、不碰现有 13 个寄存器的逻辑 ⇒ 回归风险最小。**

### ⚠️ 复位默认值必须复刻旧的常量

```
r_fb_base   <= 32'h0800_0000
r_fb_size_h <= 32'h01E0_0280    // height 480, width 640
r_fb_cfg    <= 32'h0001_0A00    // stride 2560, enable = 1
```

**⇒ 一个从不写这些寄存器的设计，行为与改动前完全相同。**

**⚠️ 差点埋的雷**：`enable` 我一开始复位成 **0**，**而旧代码里 `system_top` 把它接成常量 `1'b1`**。**那样上电后屏幕会变黑，且症状看起来像"视频通路坏了"**，不会有人想到是复位值。**已改成 1，并加了专门的测试断言。**

## 三、测试台的两个隐患（**都被 Questa 抓到，iVerilog 一声不吭**）

### 隐患 1：TB 端口少接 5 个

```
vopt-2685: Too few port connections for 'dut'. Expected 61, found 56.
vopt-2718: Missing connection for port 'reg_fb_base' (及另外 4 个)
```

**⇒ 我给 `bitblt_axi_slave` 加了 5 个输出端口，TB 例化没接。**

**⚠️ 但测试当时仍然 PASS** —— 因为 `unpack` 检查用的是**层次引用** `dut.reg_fb_width`，读的是端口信号本身（被 `assign` 正常驱动），**所以值是对的**。

**⇒ 而 `iVerilog` 对端口少接完全不报。** 修法：补上 5 个连接，Questa 警告从 6 条降到 0。

### 隐患 2：`expect` 是 SystemVerilog 保留字

```
vlog-13069: near "expect": syntax error,
            unexpected "SystemVerilog keyword 'expect'"
```

**TB 一直把 `expect` 当 `check_reg` 的形参名。**

**⇒ 它之所以没炸，纯粹因为 `sim.cmd` 的编译选项没启用 SV 关键字检查。** 手动加 `-sv` 立刻 4 个 Error。

**⚠️ 这类问题的性质**：**代码"能跑"依赖的是编译选项，不是代码本身正确。** 换人、换参数、工具默认行为变化，都会突然挂 —— **而且改动它的人根本没碰这段代码。** 已改名 `exp_val`。

### ⚠️ 由此得出的方法论

| 问题 | iVerilog | Questa |
|---|---|---|
| **端口少接** | **不报** | `vopt-2685` + 5 条 |
| **保留字冲突** | 不报 | `-sv` 下 4 个 Error |

**⇒ 双仿真器是互补的，不是冗余。** 本阶段之前有几轮只跑 iVerilog —— **漏掉的正是这两类问题。**

## 四、验证矩阵（第 1 项）

| 层次 | 检查内容 | iVerilog | Questa |
|---|---|---|---|
| **M1 单元** | 22 项：原有 13 寄存器 + **新 3 个读写** + **解包方向** + STATUS 只读 + start 单脉冲 + irq | ✅ | ✅ |
| **端到端** | 17 项：**复位默认值 5 项** + **顶层透传 4 项** + 原有 8 项 | ✅ | ✅ |
| **整机综合** | PASS；资源 +129 FF / +204 LUT | — | — |

### 两组关键的断言

**① 解包方向**（M1 单元）

```verilog
if (dut.reg_fb_width  === 16'h0280) ...   // 640，不是 480
if (dut.reg_fb_height === 16'h01E0) ...   // 480
```

**⇒ `check_reg` 查不出拆反** —— 打包和解包用同一个寄存器，读回来永远一样。**只有直接读解包后的输出才能发现。**

**② 顶层透传**（端到端）

```verilog
reg_write(32'h34, 32'h0812_C000);         // 写一个和默认值不同的可辨识值
...
if (top_fb_base === 32'h0812_C000) ...    // 在顶层端口读回来
```

**⇒ 补上端口连接只能消除警告，接错线同样不报。必须写值再读回。**

## 五、中断驱动（第 2 项）

### RTL 侧早已就绪

```verilog
// bitblt_axi_slave.v
assign axi_interrupt = r_ctrl[1] & reg_status[1];   // CTRL[1]=irq_en, STATUS[1]=done
```

**⇒ M1 单元测试的 `irq: asserted` / `irq: deasserted` 两项已覆盖。**

### 驱动侧实现

```c
static void intr_init(void)
{
    plic_set_threshold(BSP_PLIC, BSP_PLIC_CPU_0, 0);
    plic_set_enable (BSP_PLIC, BSP_PLIC_CPU_0, SYSTEM_PLIC_SYSTEM_AXI_A_INTERRUPT, 1);
    plic_set_priority(BSP_PLIC, SYSTEM_PLIC_SYSTEM_AXI_A_INTERRUPT, 1);

    extern void trap_entry(void);
    asm volatile ("csrw mtvec, %0" : : "r"((uint32_t)trap_entry));

    csr_set(mie, MIE_MEIE);
    csr_write(mstatus, csr_read(mstatus) | MSTATUS_MPP | MSTATUS_MIE);
}
```

### ⚠️ 中断服务程序**不得**写 BitBlt 寄存器

`bitblt_axi_slave` 用**单一 4 态 FSM 实现读写，二者互斥**。**ISR 里的寄存器访问会与主流程交错并破坏双方。**

**⇒ ISR 只做 claim/release 并置标志；寄存器操作全部留给主循环。**

### 修掉的三个 API 错误（**都是照抄旧代码导致的**）

| # | 错误 | 根因 |
|---|---|---|
| **1** | `plic_set_priority` 参数过多（写 4 个，实际 3 个）| **官方 `axi4Demo` 针对另一个 BSP 版本** |
| **2** | `trap_entry` 未声明 | 只存在于 `trap.S` 的 `.global`，C 头文件里没有 |
| **3** | `mtvec` 未定义 | **`riscv.h` 里没有这个宏**，`csr_write(mtvec,...)` 过不了预处理 ⇒ 改内联汇编 |

**⇒ 教训：参考代码是线索，不是答案。每个 API 都要在当前头文件里核对签名。**

### 实际签名（来自 `standalone/driver/plic.h`）

```c
plic_set_priority (plic, gateway, priority)               // 3 参数
plic_set_enable   (plic, target, gateway, enable)         // 4 参数
plic_set_threshold(plic, target, threshold)               // 3 参数
plic_claim        (plic, target)                          // 2 参数
plic_release      (plic, target, gateway)                 // 3 参数
```

## 七、⚠️ 本阶段**没有**证明什么

| 未验证项 | 说明 |
|---|---|
| **驱动从未在真实 SoC 上执行** | 编译验证的是语法、ABI、API 签名、容量 |
| **中断是否真的会触发** | PLIC 阈值/优先级配置是否符合 SoC 实际行为、`csrw mtvec` 的地址是否被正确加载 —— **全部未验证** |
| **帧率数字完全没有** | 赛题要求软硬件帧率对比，**目前只有代码没有数字** |
| **双缓冲切换是否真无撕裂** | 逻辑上成立，但**扫描输出与绘制的时序关系没实测过** |
| **BitBlt 输出能否真的显示出来** | framebuffer 从未被驱动写过；**烧进去大概率是雪花** |
| **`GPIOR_P_09` 噪声耦合** | Interface Designer 的警告（DDR 时钟离 LVDS 过近）。官方 `02` 也是此布局，判断可接受 |

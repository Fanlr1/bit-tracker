# 60 - 板上调试：从「第二行 printf 就死」到「硬件填充跑通」（2026-10-13/14）

> **接 docs/59。** 本文件记录 59 之后的完整突破过程。
> **一句话**：修好 4 个真根因后，应用从「第二行 printf 就跳 0x0」推进到「硬件填充跑通、6.15 倍加速」。

## 一、修好的四个真根因（全部板上验证）

| # | 根因 | 症状 | 修复 |
|---|---|---|---|
| 1 | `REDUCED_CSR=1'b1` 摘掉了 `mcycle`（CSR 0xB00）的译码 | `mcause=2` 非法指令，`mepc` 指向 `csrr a5,mcycle` | 在 `ip/soc/soc.v` 补回译码 + 读数据通路 |
| 2 | `%02u` 格式符（`bsp_printf` 只认 `c/s/d/X/x`）| `mcause=5` Load fault，读地址 5 | 全部 `%<数字>u` → `%d` |
| 3 | burst 写 FSM 死锁（我自己引入的）| 多拍写永久挂起 | `IDLE: busNext = wr_go ? (axi_wlast ? WR_RESP : WR) : IDLE` |
| 4 | **`MAX_BURST`(256 拍) 远大于输出 FIFO(32 拍)** | 读通道死锁：`rd_dst` 的 ARVALID 永远等不到 ARREADY | `MAX_BURST = 8'd31`（= FIFO 深度）|

**根因 4 的完整链条（每环都有板上实测）**：

```
rd_dst 的 ARVALID 挂着、ARREADY 不来        （GPIO 实测 0_0_0_1）
  ⇒ mux 确实转发了 AR，是 DDR 不给 ready     （s_axi_arvalid=1 / arready=0）
  ⇒ DDR 有 R 数据、而 mux 不收              （rvalid=1 / rready=0）
  ⇒ R 路由到通道 1，但两个 reader rready=0   （0xF8015000=0x4，五次采样一致）
  ⇒ M_R_Ready = |(R_Act_Cnl_List & S_R_Ready) = 0
  ⇒ 顺序执行的 DDR 控制器因此拒绝下一个 AR
```

**修复效果（两次独立运行输出完全一致）**：

```
software fill: 14521687 cycles/frame, 1.45 ms, 0.97 fps
hardware fill:  2357888 cycles/frame, 0.23 ms, 5.98 fps
[TEST:PASS] engine-fill-no-error
speedup (software/hardware) = 6.15x
[TEST:PASS] hardware-faster-than-software
[TEST:PASS] grad-row-predictable
software sprite copy (1x): 58425 cycles/frame, 0.0 ms, 241.34 fps
```

**⇒ 输出从 57 字节 → 674 字节。**

## 二、诊断手段（本轮最有价值的资产）

| 手段 | 用法 | 为什么关键 |
|---|---|---|
| **RAM 探针** | 写 `0xF9000F00+4n` | **BRAM 不经 AXI**，总线挂了也能被 openocd `mdw` 读到 |
| **提前装 trap** | 把 `intr_init()` 提到 `main()` 开头 | 异常不再静默，`trap()` 打印 `mcause/mepc` —— 找到根因 1、2 的直接原因 |
| **GPIO 观测通道** | `bitblt_top` 的 `dbg_observ`（4 位）→ `system_gpio_0_io_read`（APB, `0xF8015000`）| **不经 AXI**，能实时看引擎内部信号 |
| **汇编探针注入** | `load_image probe.bin 0xF9000000 bin` | 不烧 flash、不重综合，2 分钟一轮 |
| **空闲应用** | flash 放纯 `while(1)` 应用（`MINIMAL_C_PATH 2`）| 真应用一跑就卡死、把调试器挡在外面 |

### 通过 GPIO 依次观测过的信号（每次改 `dbg_observ` + 重综合）

| 观测 | 读数 | 结论 |
|---|---|---|
| `{f_src,f_dst,f_wr,all_done}` | `0000` | 连第一行都没完成 |
| `{addr,wr,rd_dst,rd_src}_busy` | `1111` | 四个引擎全卡 |
| `{wr_bready,wr_bvalid,wr_wvalid,wr_awvalid}` | `0000` | 写引擎 AXI 握手全空闲（卡在上游）|
| `{px_in_ready,px_in_valid,rd_dst_valid,rd_src_valid}` | `1_0_0_1` | **`rd_dst` 完全没数据** |
| `{rd1_rready,rd1_rvalid,rd1_arready,rd1_arvalid}` | `0_0_0_1` | **AR 挂着、ARREADY 不来** |
| `{arready,arvalid,ar_cnl_num}` | `0x6` ×4 | mux 转发了 AR，DDR 不接 |
| `{arready,arvalid,rready,rvalid}` | `0x5` ×5 | **DDR 有 R 数据、mux 不收** |
| `{r_cnl_num,rd1_rready,rd0_rready}` | `0x4` ×5 | **R 路由到通道 1，两 reader 都不收** |

## 三、被排除的假设（每个都有实验）

| # | 假设 | 排除方式 |
|---|---|---|
| 1 | 连续写引擎寄存器导致锁死 | `probe_seqwrite`：连续写 6 次全成功 |
| 2 | 写 `CTRL` 启动引擎 | `probe_ctrl_kill`：写后立刻读 DDR 仍正常 |
| 3 | 仲裁优先级饿死 DMA | `Cfg_Arb_Type` 1→0 重综合，无变化 |
| 4 | burst 写死锁（作为症状成因）| 修好 FSM 后仍无变化（缺陷真实，修复保留）|
| 5 | 引擎不工作 | 证伪：DDR 确实被写成 `ff204080` |
| 6 | 探针等待不足 | 延长到 2400 万周期，BUSY 仍是 1 |
| 7 | 加 32 拍 FIFO | 无效 —— 深度不够（burst 仍 256 拍）|
| 8 | 时序违例 | `core_clk` slack 1.551 ns，满足 |
| 9 | `MAX_BURST=31` 使情况变糟 | **推翻** —— 那次的 0 字节是烧写/启动偶发；基线复验后重测成功 |

## 四、当前卡点（下一步）

应用稳定停在 `software sprite copy (1x)` 之后（110 秒无新输出）。下一个阶段是**硬件 sprite 复制**。

**线索**：sprite 走同一对读引擎，但 `compact_src` 模式下源引擎「一次启动跑完整个矩形」，其 burst 需求可能超过当前 `MAX_BURST=31`。

**下一步**：把 `MAX_BURST` 与 FIFO 深度一起放大（如 FIFO 64 + `MAX_BURST=63`），或给 `compact_src` 路径单独限长。

## 六、工程坑（新增）

| 坑 | 真相 |
|---|---|
| 改了 `soc.v` / RTL 不生效 | **必须 clean build**（移开 `work_syn_sys`/`work_pnr_sys`/`outflow`）|
| `Axi_Mux` 顶层只有 `O_*_Cnl_Num`，没有 `*_Cnl_List` | 加端口前先核对顶层端口列表，否则 `EFX-0010` |
| openocd 残留进程 | 超时后不退，占住 JTAG ⇒ 后续 `mpsse_flush` 超时；先 `Stop-Process` |
| 串口脚本 + openocd 同时跑 | FTDI 通道冲突，表现为 `Can't communicate with the CPU` ⇒ 会误判成总线死 |
| `reset run` 不会重跑应用 | bootloader 只在 FPGA 配置后执行一次 ⇒ **要重烧比特流** |
| 单拍探针测不出 burst 问题 | 引擎 DMA 是 burst；探针要用真实多拍写才有判别力 |
| 报时间必须实测 | 我曾按「每轮几分钟」推算，报出 03:00/03:40，实测才 00:07 |

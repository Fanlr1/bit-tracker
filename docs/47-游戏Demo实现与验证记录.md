## 二、八项实现要点

| # | 项 | 做法 |
|---|---|---|
| **(1)** | **静态内存布局** | **零动态分配。链接脚本 `default.ld` 的 ram 只有 124K，代码+rodata+data+bss+4K栈+堆全在里面，且堆栈**相向生长**（`_heap_end` 是栈底，malloc 看不到栈用了多少）** |
| **(2)** | **静态对象池** | **`game_free_stack[255]` + `free_top`，alloc/free 都是 O(1)，零碎片。与硬件退休位图配合：硬件报告谁退休 ⇒ 软件 `blt_spr_retire(slot)` + `pool_free(slot)`** |
| **(3)** | **位图（紧凑存储）** | **程序化生成（无二进制资产），`stride == w*bpp` 满足 P3 整块读要求** |
| **(4)** | **弹幕发射** | **16 方向静态表。RV32IM 无 FPU，软浮点 sin/cos 是几十到几百拍，而查表是一次 load** |
| **(5)** | **每帧循环** | **`game_frame()` 做四件事：读退休位图 → 回收 → 推进影子位置 → 发射。⚠️ `enable` 是**边沿触发**，每帧必须 clear 再 arm** |
| **(6)** | **碰撞检测** | **`dx*dx + dy*dy < r*r`，两边平方避开开方，纯整数** |
| **(7)** | **自机** | **固定槽位 0（不参与池），无输入也能跑** |
| **(8)** | **FPS + 同屏计数** | **`run_game()` 里屏上打 LIVE / FREE；判据用**最坏帧**而非平均（单次超时就是掉帧）** |

## 三、host 端验证：29 条断言

**⇒ 做法：`host_game.c` 提供一个模拟 P4 引擎的 stub，把 `blt_*` 换成记录型假寄存器。** **⇒ 因为 `game.c` 不直接访问寄存器（全走 `bitblt.h`），同一份代码在两个平台编译，**验的是真实的 game.c****。

| 组 | 断言 |
|---|---|
| **池** | **初始 255 槽；空池 alloc 返回 -1；满池 free 被拒（防双重 free 破坏栈）；释放的正是那一个** |
| **边沿触发** | **arm 两次产生两次遍历**（证明 `enable` 真的是边沿触发，不是电平）** |
| **生命周期** | **子弹会出屏并被发布；位图不是全 1；reclaim 把槽还给池；自机槽不被回收** |
| **碰撞** | **重合点命中；3-4-5 直角三角形**恰好在边界**（`5 < 5` 为假）；半径内外各一条；负坐标** |
| **长跑 600 帧** | **饱和是**优雅的**（发射被丢弃而非破坏状态）；回收持续运行；`free + live + 自机 = 256`；精灵数收敛不漂移；饱和时 alloc 仍返回 -1** |

## 四、⚠️ 三个发现（都不是「测试通过」能体现的）

### 4.1 硬件靠**无符号回绕**检测出屏，不是靠符号判断

**⇒ RTL 里 x/y 是 16 位**无符号**字段，判据是 `x + vx > fb_w`。** **⇒ 所以一颗**向左**飞的子弹会下溢成大正数，**照样触发右边界检查**。** **⇒ 我的 stub 一开始用有符号 `int`，于是子弹飞到 `x = -3416` 还**永不退休**。** **⇒ **这是 RTL 的真实属性，而且很容易漏** —— 上一轮我说「退休检测已双向验证」，那只覆盖了**右和下**边界。**

### 4.2 测试之间没有隔离

**⇒ 我的一条测试**故意排空池**来验空池路径，只恢复一个槽。** **⇒ 紧随其后的长跑就在废墟上跑，报出「池泄漏、退休只有 12 次」——**看起来像游戏的 bug**。** **⇒ 加 `game_init()` 重置后，退休数从 **12 变 57**。** **⇒ **一条把共享状态搞坏的测试，会让它之后的每一条断言都失去意义。****

### 4.3 池饱和是**目标**，不是失败

**⇒ 8 发/帧 × 600 帧 = 4800 发，而池只有 255 槽；跨越 1920 像素需要几百帧 ⇒ **屏幕必然打满**。** **⇒ 而**那个饱和点正是赛题要测的「同屏精灵数极限」**。** **⇒ 我第一版断言检查「池不该耗尽、不该饱和」—— 那等于断言**游戏不应该正常工作**。** **⇒ 修的是断言，不是游戏。现在验的是**饱和是否优雅**。**

### 五之四、#2 / #3 的结构调查结论（2026-10-07，动手前做的）

**⇒ 两项都比预估复杂，各带一个不平凡的细节。以下是调查结果，动手时直接照这个来，不必重查。**

#### #3（暴露扫描位置 / vsync）

| 发现 | 后果 |
|---|---|
| **`bitblt_video_out.v` 已经引出 `h_cnt_o`/`v_cnt_o`（第 125–126 行）** | ✅ **不用改 `video_out`** |
| **⚠️ 它们在 **pclk 域（148.5 MHz）**，而寄存器在 `clk` 域（100 MHz）** | **多比特 CDC。**绝不能【直接【把 16 位【引到【寄存器** |
| **⚠️ `bitblt_video_out` **不在** `bitblt_top` 里 —— 它在 `system_top`** | **要跨三层：`system_top` → `bitblt_top` → `bitblt_axi_slave`，CDC 插在 `system_top`** |
| **消隐的判据是 `h_cnt >= fb_width \|\| v_cnt >= fb_height`**（`de_raw` 内部就是这个表达式）** | **在 pclk 域【算出 1 位 ⇒ 2-FF 同步到 clk 域 ⇒ 单比特 CDC，标准做法** |

**⇒ 方案：在 `system_top` 里从 `h_cnt_o`/`v_cnt_o` 算出 `pclk_blanking`，用 2 级触发器同步成 `clk` 域的 `scan_blanking`，作为只读寄存器的 1 位暴露出去。** **⇒ 软件轮询到「在消隐期」再写 `FB_CFG` —— 那正好解决 [21](21-板上待验清单.md) 里「消隐期使能」那一项。** **⇒ **不要暴露行号**：16 位跨域需要格雷码或握手，而软件真正需要的只是「现在能不能使能」。**

#### #2（按索引读位置）

| 发现 | 后果 |
|---|---|
| **`rd_idx` → `rd_x`/`rd_y` 读端口**已被 walker 占用**** | **不能直接用，要加第四条通路** |
| **⚠️ RAM 只有**一个读端口**，已被 `rd_idx`（walker）和 `swp_addr`（sweep）复用** | **要加 mux 分支，或分时** |
| **⚠️ 位置在 **Block RAM** 里 ⇒ **2 拍读延迟**** | **不能像 `rt_word` 那样组合读 —— 那个是寄存器阵列，而这个是 RAM** |

**⇒ 方案（请求-应答）：**

```
0x54  SPR_POS_IDX   写：要读哪个槽位（写【触发【一次【读）
0x58  SPR_POS_XY    读：[15:0]=x  [31:16]=y  [32]=valid
```

**⇒ 硬件：写 `IDX` 时启动一个 2 拍计时器，计时结束把 `x`/`y` 锁存进 `POS_XY` 并置 `valid`。** **⇒ 软件轮询 `valid` 后取数据 —— 而不是假定「写完就能读」。** **⇒ **那一条很重要**：组合读之所以在 `rt` 上可行，是因为它是寄存器阵列；位置在 Block RAM 里，没有那个性质。**

#### 动手顺序

| 步 | 做什么 | 为什么这个顺序 |
|---|---|---|
| **1** | **先做 #2** | **全在 `clk` 域，无 CDC，风险低** |
| **2** | **再做 #3** | **要动 `system_top` 的 CDC，单独一轮上下文才干净** |

**⇒ 两项都要：新 RTL 登记进 `bitblt_system.xml`、给新寄存器加正反配对断言、跑回归 + `full-chain.ps1`。** **⇒ 那是本项目的既定要求（`43`/`44` 的故障注入就是这么做的）。**

#### 三个设计要点

**(1) 为什么不能组合读。** `rt_word` 能组合读，因为**退休位图是寄存器阵列**。位置不是 —— 它在 **Block RAM** 里，有 **2 拍读延迟**。**⇒ 写完索引立刻读会拿到**上一个槽位**的坐标**，而那看起来像「引擎报告了过期位置」，不像时序错误。**⇒ 所以是请求-应答，且带 valid 位。**

**(2) 门控是必需的，不是保险。** RAM 只有一个读端口，已被 walker（`rd_idx` 持续由 `cur_index` 驱动）和 sweep（读-改-写）占用。**⇒ 让读回偷一个地址周期 ⇒ walker 会加载**别的槽位**的位置 ⇒ 精灵被画在彼此坐标上，**没有任何东西报错**。** **⇒ 所以只在 `~spr_busy & ~st_stepping` 时放行；sweep 拿最高优先级，因为打断读-改-写会损坏槽位。**

**(3) valid 不在 `POS_XY` 里。** `POS_XY` 的 32 位已被 x 和 y 占满。**⇒ 我第一版写的是 `{31'b0, valid, xy}` —— 那是 **33 位**，赋给 32 位的读 mux 时 **valid 被静默丢掉**，软件会去轮询一个永不变的位。** **⇒ 现在 valid 在 `0x54` 的 bit 0。**

#### ⚠️ 这一项踩的四个坑（其中两个是「仿真过、综合炸」）

| # | 坑 | 谁抓到 |
|---|---|---|
| **1** | **`dbg_addr` 声明两次（wire + reg）** | **iverilog** |
| **2** | **`.stepping` 端口连两次**（原来有空接 `.stepping ()`，我又加了一个） | **❌ iverilog 没报、21/21 全过 —— 只有 Efinity 报 `port is already connected`** |
| **3** | **valid 被 33 位拼接截掉** | **⚠️ 我写 API 时逐位核对才发现，不是工具报的** |
| **4** | **`tb_bitblt_regs` 里声明没加进去**（替换模式不匹配） | **iverilog（`Unable to bind wire`）** |

**⇒ 第 2 个是 [39](39-全链路验证与重复检测.md) 那类问题的第三次实例 —— 它再次证明 `full-chain.ps1` 不能省。**

**⇒ 第 3 个值得单说：**工具不会报「你丢了一个位」**，而软件会去轮询一个常量的位。** **⇒ 那类错误只能靠**写 API 时逐位核对**发现 —— 这也是「接口的软件侧应该尽早写」的一个论据，而不是等 RTL 看起来完工之后。**

#### ⭐ 故障注入：一条被推翻的断言

**⇒ 把读回倒数从 2 改成 1（早读一拍），实际输出：**

```
FAIL readback: slot 5 returned x=xxxx y=xxxx want 1111/AAAA
INFO readback latency: 2 cycles after the request
PASS readback: latency is bounded (2 cycles)      ← ★ 这条【照样通过】
FAIL readback: slot 6 / slot 7 / back-to-back / slot 9 before / slot 9 after
RESULT: FAILED with 6 error(s)
```

**⇒ 六条断言真的失败了 ⇒ 数值检查是真的。** **⇒ 但「延迟有上界」那条**在故障下依然通过**（`2 <= 6`）。** **⇒ **结论：上界是 sanity check，不是证明。只有数值检查能抓住早读。**** **⇒ 如果我只写了那一条，故障注入会全绿，而我会以为时序被测住了。** **⇒ 这条已写进测试台头注释。**

**⇒ 另一件：早读返回的是 `xxxx` 而不是「看似合理的错值」，因为 RAM 还没驱动总线。** **⇒ 如果是**静默的错值**，归因会难得多。**

| **`bitblt.h`** | **`blt_scan_blanking()` / `blt_scan_wait_blanking(max_polls)`** |

#### 解决了什么

**⇒ `blt_set_fb` 的注释一直写着「必须在垂直消隐期使能」，紧接着又承认**软件无法遵守**：寄存器没暴露扫描位置也没暴露 vsync。** **⇒ 原来的变通是「开机使能一次、忽略前一两帧」。** **⇒ 现在软件可以：**

```c
if (blt_scan_wait_blanking(200000) == 0)     // 有界等待，不是死等
    blt_set_fb(base, w, h, stride, 1);
```

**⇒ 那正好解决 [21](21-板上待验清单.md) 里「消隐期使能」那一项。**

#### 三个设计判断，其中两个推翻了我原来的计划

**(1) ⚠️ 我一开始说「不用改 `video_out`」—— 那是错的。** **⇒ `h_cnt_o`/`v_cnt_o` 确实是现成端口，但它们要和 `fb_width`/`fb_height` 比较，而那**来自 `clk` 域的寄存器**。** **⇒ 在 `system_top` 里比较 ⇒ 在我正想避免的那个跨域之上，**再加一个 16 位、无同步器的跨域**。** **⇒ 正确做法：在 `video_out` **内部**导出它本来就在算的那个值（`de_raw`），只跨**一位**。**

**(2) `o_blanking` 是 `~de_raw`，故意不是 `~de`。** **⇒ `de` 还依赖读 FIFO 有没有数据 ⇒ 供不上时它会掉。** **⇒ 把「饿死」报成「消隐」，会诱导软件**在显示最饿的时刻去重配扫描输出** —— 正好是最坏的时机。**

**(3) 只暴露 1 位，不暴露行号。** **⇒ 16 位跨域需要格雷码或握手，而软件真正需要的只是「现在能不能安全使能」。一位用两级触发器就够。**

#### ⭐ 故障注入：它验证了「双向断言」的必要性

**⇒ 把 `0x5C` 的读回换成常量 `1`（消隐位卡死在高），实际输出：**

```
PASS SCAN_STATUS = 1 while blanking = 00000001        ← ★ 这条照样通过
FAIL ...N_STATUS = 0 during active video: got 00000001 want 00000000
FAIL ... follows the input after a write
RESULT: FAILED with 2 error(s)
```

**⇒ **如果只测「消隐时读到 1」，注入常量 1 会让测试台全绿 —— 而那个寄存器就废了。**** **⇒ 只有**两个状态都测**才抓得住。** **⇒ 这是本目标内第二次「单向断言不够」：第一次是 #2 的延迟上界（早读一拍时上界照样满足），这次是只测高电平。** **⇒ 教训一样：**断言必须能区分「对」和「看起来对」**。**

## 一、基线：效率强烈依赖 sprite 尺寸

**⇒ P3 原描述写「效率 62% → 90%+」，但**没说尺寸**。实测（`tb/tb_bitblt_burst_eff.v`）表明尺寸就是全部：**

| sprite | beats/行 | AR 数（前→后） | 周期数（前→后） | 效率 | 加速比 |
|---|---|---|---|---|---|
| **16×16** | **4** | **16 → 1** | **192 → 72** | **33% → 88%** | **2.66x** |
| **32×32** | **8** | **32 → 1** | **512 → 264** | **50% → 96%** | **1.93x** |
| **64×64** | **16** | **64 → 4** | **1536 → 1041** | **66% → 98%** | **1.47x** ←「62%」对应这里 |
| **128×128** | **32** | **128 → 16** | **5120 → 4149** | **80% → 98%** | **1.23x** |
| **256×256** | **64** | **256 → 64** | **18432 → 16581** | **88% → 98%** | **1.11x** |
| **640×640** | **160** | **640 → 400** | **107520 → 103605** | **95% → 98%** | **1.03x** |

**⇒ 收益来源完全清楚：每次事务固定 **8 拍**开销（AR 握手 + 状态机切换）。** **⇒ 160 beats 的行里占 5%，4 beats 的行里占 50%。** **⇒ 而弹幕游戏的精灵普遍是 16×16 ~ 64×64 ⇒ **这正是 P3 的目标场景**，收益比原描述还高。**

**⇒ 上限是 98%，不是 100%** —— `ARLEN` 8 位 ⇒ 每 4096 字节必须切一次突发，无法消除。

**⚠️ 该测试台的偏差（文件内已注明）**：从设备一次只接受一个 AR，而真实 DDR3 控制器会流水 ⇒ **上表「前」列偏悲观，是损失的上界**。

## 二、第一次实现失败：跨行连续读导致引擎挂死

**⇒ 最初的做法是「紧凑时让源读一次性读完整个矩形」，改动：**
- **`addr_gen` 输出 `compact_src` 与 `src_bytes_total`**
- **`top` 里 `u_rd_src` 改用 `src_start`（仅第 0 行启动）与 `src_bytes_total`**
- **`all_done` 在紧凑时旁路源侧 done（否则第 1~h-1 行会永久等待）**

**⇒ 结果：`rd0_bursts` 确实从 2 变成 1（合并生效），但引擎**超时挂死**：**

```
wr : state=1 beats_left=2 din_ready=0     ← 写引擎等数据，等不到
rd_src: beats_sent=4 dout_valid=0          ← 源读却认为 4 个 beat 全交付了
```

## 三、根因：一个**真实的握手 bug**（与 P3 无关，被 P3 暴露）

**⇒ `bitblt_top.v` 原代码：**

```verilog
wire px_in_valid = rd_src_valid & rd_dst_valid;   // 两者同时有效才算有效输入
assign rd_src_ready = px_in_ready;                 // ★ ready 却不看 rd_dst_valid
assign rd_dst_ready = px_in_ready;
```

**⇒ 这个握手是**不对称**的：**

| 情形 | `px_in_valid` | `rd_src_ready` | 后果 |
|---|---|---|---|
| **源有、目标也有** | **1** | **1** | **✅ 正常** |
| **源有、目标**没有** | **0**（引擎不收） | **仍为 1** | **🔴 **源的数据被"收掉"但没进引擎 ⇒ 静默丢弃**** |

**⇒ 为什么以前不暴露：源读与目标读**严格锁步**（同一 `line_start`、同一 `line_bytes`、同时完成）⇒ 两者 `valid` 总是一起到 ⇒ 那个 AND 恒真。** **⇒ P3 打破锁步 ⇒ 缺陷立刻显形。**

---

## 四、修法与验证

**⇒ 两处改动**必须成对**：**

```verilog
// ① ready 互锁：有数据的一方【保持】到配对者跟上，而不是被丢弃
assign rd_src_ready = px_in_ready & rd_dst_valid;
assign rd_dst_ready = px_in_ready & rd_src_valid;

// ② 紧凑源时 all_done 不等源读的 done（它只在最后一行来）
wire all_done = (compact_src | f_src | rd_src_done) &
                (f_dst | rd_dst_done) &
                (f_wr  | wr_done);
```

**⇒ 缺 ① 会丢数据；缺 ② 会死锁。两者配合才成立：源读多读的 beat **保持在引擎里**，等目标读完当前行、下一行启动后再继续流动。**

**⇒ 正确性兜底**：`busy` 已包含 `rd_src_busy`，所以源读没跑完时引擎不会报完成。

### 验证结果

```
INFO: finished  cur_line=1  rd0=1 rd1=2 wr=2 bursts, wr_beats=4

PASS rd0 bursts = 1 (compact source read as one block)     ← 改动生效
PASS rd1 bursts = 2 (destination row also read)            ← 护栏：目标未被误改
PASS wr bursts  = 2 (one per row)                          ← 护栏：写未被误改
PASS wr beats   = 4                                        ← 数据一个没丢
PASS wr first data matches source row1 beat 0              ← 数据正确
PASS wr second data matches source row1 beat 1
PASS blend value 10001f00 = fg 10005a02 x bg 80205a01 / 255
```

**⇒ `rd1`/`wr` 保持 2 是**护栏** —— 目标带 stride、不该被合并；如果改动泄漏到目标路径，这两条会立刻报警。**

**⇒ 测试台期望值的更新（`rd0_bursts` 2→1、源数据引用从 `(0x1020, beat 0)` 改为 `(0x1000, beat 2)`）已在文件内注明**等价理由**：**0x1020 − 0x1000 = 32 字节 = 2 beats**，所以两处描述的是同一批字节。** **⇒ 这不是「改测试迁就实现」—— 若合并打乱或丢弃了 beat，这两条会失败。**

# 49 · 风险登记册

> **一条风险的价值不在于描述它，而在于**出事时能认出它**。** **⇒ 所以每条都有「怎么发现」一列，而且尽量给**可执行的判据**（寄存器、监控器位、测试台名字），不是「观察画面」。**
> **当前权威状态见 [README](README.md)。**

---

## 〇、怎么用这份表

| 场景 | 怎么做 |
|---|---|
| **上板前** | **读「触发条件」列 —— 知道哪些操作会踩到哪条风险** |
| **上板出问题时** | **读「怎么发现」列 —— 每一格都是可查的：`blt_mon_dump()`、某个寄存器、某条测试台断言** |
| **改 RTL 前** | **读「影响面」列 —— 判断这次改动会不会让某条风险变严重** |

**⇒ 而**大部分判据集中在两个新寄存器上**：** **⇒ `blt_mon_dump()`（11 个条件的粘滞位 + 计数）；** **⇒ `0x5C SCAN_STATUS`（消隐状态）。**

## 一、🔴 板级 / 物理层（只能上板确认）

### R1 · TMDS 1.485 Gbps 的板级信号完整性

| | |
|---|---|
| **风险** | **全项目**最没有依据**的一环** |
| **触发条件** | **1080p60 输出（`pix_clk` 148.5 MHz，TMDS 时钟 1.485 Gbps）** |
| **影响面** | **画面撕裂、闪烁、间歇黑屏；严重时完全无图** |
| **现有缓解** | **⚠️ 没有。**手册的 1500 Mbps 是 **LVDS** 规格，TMDS 是**单端输出**，手册未单独给出** |
| **怎么发现** | **⚠️ 只能人眼看。`board-check.ps1` 明确声明看不见显示器。**判据是「低分辨率正常、1080p 出问题」—— 那就指向这一条而不是 RTL** |
| **相关** | [21](21-板上待验清单.md) 第八项；[21](21-板上待验清单.md) 步骤 5（撕裂） |

### R2 · `GPIOR_P_09` 与 HDMI 时钟对的布局警告

| | |
|---|---|
| **风险** | **Efinity 报 warning：HSIO 需距 LVDS `tmds_clk` 至少一对** |
| **触发条件** | **上板即存在（是布局问题，不是运行时问题）** |
| **影响面** | **可能与 R1 叠加 —— 串扰会恶化本来就没依据的时序余量** |
| **现有缓解** | **⚠️ 没有。**但 `pnr` 通过了，说明工具认为可布** |
| **怎么发现** | **⚠️ 无法与 R1 区分。**两者表现相同；如果 1080p 失败而低分辨率正常，**两条都要怀疑**** |
| **相关** | [21](21-板上待验清单.md) 第九项 |

### R3 · `tx_cal_clk` 时序余量薄

| | |
|---|---|
| **风险** | **DDR3 校准时钟的余量只有 10% 量级** |
| **触发条件** | **高温 / 低压角；或后续改动增加该域逻辑** |
| **影响面** | **DDR3 校准失败 → 整个存储通路不可用；或偶发数据错误** |
| **现有缓解** | **`full-chain` 阶段 5 每次按域打印 slack，负值即失败** |
| **怎么发现** | **✅ 阶段 5 直接报。**板上表现为**偶发 `rresp` 非 OKAY` ⇒ `blt_mon_dump()` 的位 7 会涨** |
| **当前值** | **0.353 ns（约束 2.500 ns）—— 见最近一次 `full-chain`** |
| **相关** | [21](21-板上待验清单.md) 第五项 |

## 二、🟠 架构 / 协议（可在板上定性）

### R4 · AXI 固定优先级仲裁压制扫描输出

| | |
|---|---|
| **风险** | **`Axi_Mux` 是固定优先级，扫描输出排在最低** |
| **触发条件** | **CPU 大量访问加速器寄存器时；或三个引擎同时满负荷** |
| **影响面** | **扫描输出被饿死 ⇒ 缺行 / 短行** |
| **现有缓解** | **⚠️ 优先级没改。**但 `0x5C` 暴露消隐状态，软件可在安全时机重配（那**不改变优先级**，只是避开最坏时机）** |
| **怎么发现** | **✅ `blt_short_count()`（`0x70`）> 0，或 `blt_mon_dump()` 的位 10 置位。**那正是为它加的**** |
| **相关** | [21](21-板上待验清单.md) 第六项；[48](48-片上断言监控.md) §五 |

### R5 · AXI burst 跨 4KB 边界

| | |
|---|---|
| **风险** | **AXI 协议不允许单个 burst 跨 4KB；我们的地址生成器当时没处理** |
| **触发条件** | **stride 不是 4096 的倍数、且行宽使某一行跨过 4KB 边界** |
| **影响面** | **该行的部分数据错位** |
| **现有缓解** | **✅ **已实现且已强制**：方案 B（stride 对齐 4096）在驱动里用了（`FB_STRIDE_BYTES = 8192`），而 `bitblt_video_out` **检查** `fb_base`/`fb_stride` 是否都是 4096 的倍数，不是就 raise `cfg_error`（行 487-490）** |
| **怎么发现** | **✅ **不需要上板**：`tb_bitblt_video_out` 的 `cfg_error` 契约测试在回归里一直跑（第 24 项之一）。⚠️ 板上步骤 3 仍值得做，但它检的是「对齐约束是否被破坏」，而不是「这一项是否成立」** |
| **相关** | [21](21-板上待验清单.md) 第一优先项 |

### R6 · 中断脉冲宽度

| | |
|---|---|
| **风险** | **`done` 中断脉冲可能太窄，CPU 错过** |
| **触发条件** | **中断使能时，引擎完成得很快** |
| **影响面** | **软件等不到完成事件 ⇒ 帧率掉或挂起** |
| **现有缓解** | **中断与轮询两种方式都实现了，可对比** |
| **怎么发现** | **✅ [21](21-板上待验清单.md) 步骤 6：中断 vs 轮询帧率对比。**差很多就是这一条**；`[TEST:PASS] completion-interrupt-arrives` 会直接报** |
| **相关** | [21](21-板上待验清单.md) 第二优先项 |

### R7 · AXI ID 与 SoC 冲突

| | |
|---|---|
| **风险** | **我们的 AXI ID 低 4 位是 8/A/C/E，SoC 用 0-7 —— 但 `soc.v` 是加密的，它的 ID 分配看不到** |
| **触发条件** | **高并发访问时** |
| **影响面** | **响应被路由到错误的 master ⇒ 偶发数据错乱** |
| **现有缓解** | **低 nibble 分配是按惯例选的，不是按文档确认的** |
| **怎么发现** | **✅ [21](21-板上待验清单.md) 步骤 4：BitBlt 拷贝 + 回读 ×1000。**偶发不匹配就是这一条**** |
| **相关** | [21](21-板上待验清单.md) 第三项 |

## 三、🟡 设计与实现（代码内已知的妥协）

### R8 · 影子位置在丢帧时漂移

| | |
|---|---|
| **风险** | **硬件里的精灵位置**没有读回通路**，CPU 只能自己累加同样的速度** |
| **触发条件** | **丢帧（`game_frame` 被跳过或延迟）** |
| **影响面** | **碰撞判定用错位置 ⇒ 该中的没中、不该中的中了** |
| **现有缓解** | **✅ P4 #2 给了读回：`blt_spr_read_pos(slot, &x, &y)`（`0x54`/`0x58`）** |
| **怎么发现** | **⚠️ `game_frame` **目前没用读回**。**⇒ 若碰撞看起来不对，第一个该怀疑它**（`game.c` 里已注明）** |
| **改进方向** | **每 N 帧用读回校正一次影子位置**（docs/28 §二 🔵 第 10 项）** |
| **相关** | [47](47-游戏Demo实现与验证记录.md) §五之五；[48](48-片上断言监控.md) §八 |

### R9 · `blt_scan_wait_blanking` 的上界只有仿真验证

| | |
|---|---|
| **风险** | **`200000` 次轮询这个上界是按 1080p 一帧 16.7 ms **估**的，没在板上量过** |
| **触发条件** | **扫描输出未使能，或消隐位卡住** |
| **影响面** | **等待超时返回 −1 ⇒ 调用者若不检查，会在错误时机写 `FB_CFG`** |
| **现有缓解** | **函数是**有界**的（不死等），且返回 −1 而不是静默继续** |
| **怎么发现** | **✅ 检查返回值：`-1` 就是没等到。**另外 `0x5C` 的 bit 0 可以直接读** |
| **相关** | [48](48-片上断言监控.md) §五；[47](47-游戏Demo实现与验证记录.md) §五之六 |

### R10 · `rt` 读回窗口占用偏大

| | |
|---|---|
| **风险** | **退休位图 `rt` 是 256 个分散 FF（[44](44-P4弹幕能力记录.md) §五实测）** |
| **触发条件** | **不触发 —— 是面积成本，不是故障** |
| **影响面** | **LUT/FF 占用，不影响功能** |
| **现有缓解** | **LUT 只 24%，不影响当前设计** |
| **怎么发现** | **✅ `full-chain` 阶段 3 会报 `EFX_FF`** |
| **改进方向** | **重构成 8 个 32 位字（docs/28 §二 🟡 第 8 项）** |
| **相关** | [44](44-P4弹幕能力记录.md) §五 |

## 四、⚪ 观测能力本身的风险

### R11 · 监控器只覆盖 11 个条件

| | |
|---|---|
| **风险** | **监控器之外的问题**软件查不到证据**，只能靠人眼** |
| **触发条件** | **任何没被那 11 个条件覆盖的故障** |
| **影响面** | **调试退化为「看画面、猜原因」** |
| **现有缓解** | **✅ 11 个条件 + `SHORT_CNT` + `OOB_ADDR`；`blt_mon_dump()` 一条调用导出** |
| **怎么发现** | **⚠️ 反过来说：**`blt_mon_dump()` 全 0 而画面仍然不对 ⇒ 故障在覆盖范围之外**** |
| **已知未覆盖** | **时序违例在板上的具体表现 · DDR3 校准失败的细节 · 越界之外的其他地址错误** |
| **相关** | [48](48-片上断言监控.md) §二「抓不到什么」 |

### R12 · 「测试通过」不等于「板上正确」

| | |
|---|---|
| **风险** | **24 项回归 + 全链路 7 阶段全过，**一次板都没上过**** |
| **触发条件** | **始终存在** |
| **影响面** | **所有软件侧结论都可能被板级现实推翻** |
| **现有缓解** | **⚠️ 没有真正的缓解 —— 这正是 board bring-up 是最高优先级的原因** |
| **怎么发现** | **⇒ 只能靠上板。**本文的 R1–R7 就是「可能被推翻」的具体清单** |
| **相关** | [21](21-板上待验清单.md) |

## 五、维护规则

**⇒ 新增风险时，六列都要填。** **⇒ 特别是「怎么发现」—— 如果那一格只能写「观察画面」，说明这条风险**还缺观测手段**，那本身该记进 §四。** **⇒ 风险被证明不存在时，不删，改成「✅ 已排除（依据）」并留在表里 —— 因为「我们查过这条」和「我们没想到这条」是两件不同的事。**

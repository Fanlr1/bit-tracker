# 59 - 板上「写引擎寄存器崩溃」排查（2026-10-13 全天）

> **一句话**：比特流已自足、应用能启动、第一个自检 PASS；但**完整应用在写引擎寄存器时崩溃**，
> 而一个**操作序列完全相同**的最小 C 路径正常。**根因未定**，已排除 13 个候选。

## 一、已修复（三件，都有证据）

| # | 问题 | 根因 | 修复 | 证据 |
|---|---|---|---|---|
| 1 | 上电后 CPU 5ms 内跳 `0x0` | 比特流 BRAM 里是**厂商原始 bootloader**（缺 flash dummy）| 把 `boot_new.bin` 按 lane 规则固化进 4 个 `symbol*.bin`，**5 处副本全改**，clean build | 复位后不注入任何东西，应用自动启动 |
| 2 | 应用在第二行 printf 崩溃 | `bsp_printf`（`print.h:363`）**不支持 `%u`**，内层 `while` 继续扫描 ⇒ **格式串解析越界** | main.c 里 29 处 `%u` → `%d` | 第二行 printf 完整输出 |
| 3 | 写后读死锁（`docs/58` 的修复）| — | 已在板上 A/B 验证**无回归** | 修复前后探针读数逐位相同 |

**BRAM 镜像的 5 处副本**（只改一处无效，这是今天踩的大坑）：
`sys\`、`sys\ip\`、`sys\ip\soc\`、`sys\work_syn_sys\`、`sys\work_pnr_sys\`

**lane 编码规则**：字节 `i` → `lane = i%4`、`line = i/4`；每行 8 个 0/1 字符（MSB first）+ **LF**。

## 二、未解决问题

**现象**：完整应用执行到 `blt_write(BLT_FB_CFG, 0x2000)`（写 `0xE100003C`）时崩溃，
PC 落到 `0x0` 死循环，串口输出停在 `[TEST:PASS] axi-slave-responds`。

**反汇编核对**（`main+0x114`）：
```
1414: lui a5, 0xE1000        # 引擎基址
1418: lui a4, 0x2000         # 值
141c: sw  a4, 60(a5)         # 写 0xE100003C = 0x2000   ← 地址与值都正确
1420: lui a5, 0xF9001
1428: sw  a4, -224(a5)       # PROBE(8)，未执行到
```

**关键对照**：最小 C 路径（`#define MINIMAL_C_PATH`）复现了**卡点前的每一件事**——
`printf ×2（原样格式串）→ 读 STATUS → printf STATUS → test_result() → 写 FB_CFG`——**全部成功**。
⇒ 差异**不是某个操作**，而是**代码/数据的整体布局**。

## 七、RAM 探针法（今天定位三个 bug 的关键手段）

应用里 `#define PROBE(n)` 往 `0xF9000F00 + 4n` 写 `n+1`，openocd `mdw` 读回：
**完全绕开串口**，在 UART 不可用时仍能定位。探针区在 BRAM 尾部，bootloader 只占前 224 字节，不冲突。

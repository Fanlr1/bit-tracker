**rows/frame=3.9 的解释**：4000 个 8×8 精灵 = 96000 个 DDR 小事务/帧，占满带宽；
scan-out 每帧 4 MB 读偶尔抢不到 → 每帧约 3.9 行重复（1080 行的 0.36%，肉眼难辨）。
黄金版（700 精灵）能到 0.0 是因为 DDR 压力小得多。

## 五、性能上限分析（为什么是 36 fps）

- 引擎 8000 条 8×8 命令 ≈ 22.7 ms → 2.84 µs/命令
- 每精灵 24 个 DDR 事务（擦 FILL 8 写 + 绘 BLIT 8 读背景 + 8 写）
- 4000 精灵 = 96000 事务/帧 → 每事务 ≈ 236 ns（23.6 周期 @100 MHz）
- 8×8 精灵每行仅 16 B，行 stride 4096 → **无法突发合并**，事务数降不下来
- ⇒ 36 fps 已接近该架构极限；要 60 fps 需引擎流水线重构或降精灵数

## 七、若要继续优化的候选（按性价比）

1. **AXI 读通道给 scan-out 更高优先级** → 可能把 rows/frame 压到 1 以下（fps 略降）
2. **引擎流水线重构**（提高每事务吞吐）→ 根本解，风险大
3. **不透明精灵走 COPY 类命令**（省背景读）——但会丢失 alpha 效果，违背需求
4. 降精灵数到 3200 → ~45 fps + rows/frame 更小

# 56 - 引擎 AXI 写通道不可用 —— 板上根因（2026-10-12 夜）

> **结论先行**：`rtl/bitblt_axi_slave.v` 的 **AXI 写通道不符合 AXI 规范**——
> 它要求 **AW（地址）与 W（数据）必须同周期有效**，而 AXI 主设备（SoC 的 VexRiscv 桥）**不保证**这一点。
> 后果：**对引擎寄存器的任何写都不可靠**，且会**挂起 AXI 事务、最终锁死整条总线**。
> **这是"板上跑不通"的真正根因**，与 bootloader、应用代码、DDR、缓存均无关。

## 一、症状（板上实测）

| 现象 | 观测手段 |
|---|---|
| 引擎 `FRAME_CNT` 恒为 0 | openocd 读 `0xE100002C` |
| 应用跑不完（`g_test_total` 非合理值） | openocd 读 `0x435C` |
| 写引擎寄存器后读回**全是 `0x00000001`** | CPU 探针 + openocd 两条路径均如此 |
| 引擎启动后 **2.5 秒内** openocd 还能连、**之后彻底失联** | `Can't communicate with the CPU` |
| **PC 被写成 `0x00000001`** | openocd `reg pc` |
| 重烧 bitstream 后一切恢复 | `reflash.bat` |

## 二、决定性证据：那些"正确值"其实是复位默认值

复位后**不做任何写**，直接读引擎寄存器：

```
0xE1000020 : FILL_COLOR=0  ALPHA=0x000000ff  KEY_COLOR=0x00ff00ff  FRAME_CNT=0
0xE1000030 : BPP=4  FB_BASE=0x08000000  FB_SIZE_H=0x04380780  FB_CFG=0x00010a00
```

对照 RTL 复位块（`bitblt_axi_slave.v`）：

| 行 | 代码 | 板上读到的值 |
|---|---|---|
| 557 | `r_alpha <= 32'hFF;` | `0x000000ff` ✅ |
| 558 | `r_key_color <= 32'hFF00FF;` | `0x00ff00ff` ✅ |
| 560 | `r_bpp <= 32'h4;` | `4` ✅ |
| 564 | `r_fb_base <= 32'h0800_0000;` | `0x08000000` ✅ |
| 565 | `r_fb_size_h <= 32'h0438_0780;` | `0x04380780` ✅ |
| 576 | `r_fb_cfg <= 32'h0001_0A00;` | `0x00010a00` ✅ |

**⇒ 逐项吻合** ⇒ 这些值是**硬件默认**，不是应用写进去的。
**⇒ 之前"应用成功配置了引擎"的判断是假象**（曾据此误判过多次）。

## 三、根因（RTL 层面）

`bitblt_axi_slave.v` 头部注释（**设计者自己标注的**）：

```verilog
//   2. AW AND W MUST BE VALID IN THE SAME CYCLE (see awreadyReg below).
//   3. axi_rvalid is combinationally gated by axi_rready, which violates the AXI
```

实现：

```verilog
L295: assign axi_awready = awreadyReg & axi_awvalid;
L300: else if (axi_awvalid && axi_wvalid && busReady) awreadyReg <= 1'b1;   // ← 要求 wvalid 同周期
```

- **AXI4 规范**：AW 与 W 是**独立通道**，主设备可以任意顺序/间隔发出。
- **本从机**：`awreadyReg` 需要 `awvalid && wvalid` **同时**为高。
- ⇒ 一旦主设备**先发 AW、后发 W**（或反之），`awready` 永不置位 ⇒ **写事务永久挂起** ⇒ 总线死锁。
- ⇒ quirk 3（`rvalid` 组合依赖 `rready`）同理违反规范，会让读通道在特定时序下出错。

**为什么之前没发现**：仿真激励（`tb_bitblt_axi_slave.v`）恰好总让 AW/W 同周期到达，
所以 25 项回归全过、门级仿真也过，**只有真主设备（VexRiscv 的 AXI 桥）才暴露**。

## 四、修复方案（二选一）

### 方案 A（推荐）：改 `bitblt_axi_slave.v`，支持 AW/W 独立到达

在写通道前加一级 **skid buffer**：

```verilog
reg              aw_got, w_got;
reg [ADDR-1:0]   aw_addr_q;
reg [DATA-1:0]   w_data_q;
reg [STRB-1:0]   w_strb_q;
reg [7:0]        aw_len_q;

assign axi_awready = !aw_got && busReady;      // 只看 awvalid
assign axi_wready  = !w_got  && busReady;      // 只看 wvalid

// 两者都到齐 -> 执行写
wire wr_fire = aw_got && w_got;
```

同时修 quirk 3：`axi_rvalid` 改为**不依赖** `axi_rready`（寄存器化 `rvalid`）。

### 方案 B（改动小）：在 SoC 与从机之间加适配层

新增一个小模块，把「独立到达的 AW/W」压成「同周期」，再送进现有从机。**不动从机本身**，风险更低，但多一层逻辑。

## 五、验证方法（不需要 HDMI 屏）

1. 改完 RTL → `full-chain.ps1` 重综合（约 110 s）
2. 烧写：`reflash.bat`
3. 用现成探针（`work/probe/bt_wr_dst.S` 等）写寄存器并读回：
   - **期望**：`DST_ADDR` 写进去后读回 `0x08000000`
   - **修复前**：读回 `0x00000001`（写不进去）
4. 启动引擎（`work/probe/engine_min.S`）后 openocd **不再失联**，且 `FRAME_CNT` 递增

## 六、影响面

| 项 | 影响 |
|---|---|
| **所有引擎寄存器写** | 不可用（引擎无法配置、无法启动）|
| **引擎状态寄存器读** | 通常可用（读路径另一套逻辑）|
| **整机** | 应用一旦调用 `blt_fill` 等即拖死总线；`FRAME_CNT` 恒 0 |
| **回归/仿真** | 全过 —— **这是"假 PASS"的第 N 例**，仿真激励不覆盖 AW/W 分离场景 |

## 三、剩余最可疑点（下一步从这里开始）

写操作链条：`AW 握手 → W 握手 → WR_RESP → B 响应`

从机 B 通道实现：
```verilog
bidReg   <= awidReg;                       // BID 必须等于 AWID
brespReg <= wr_bad ? 2'b10 : 2'b00;
WR_RESP: busNext = axi_bready ? IDLE : WR_RESP;
```

**怀疑：SoC 的 AXI 主桥没有收到"属于自己的"B 响应（BID/BRESP 不匹配），于是永久等待；单状态机随之冻结，后续读全部无响应，主设备只能读回总线残留（即写入值）。**

2. **加粘滞位**（写 `0x7C` 清零）：记录 `BVALID` 是否曾置位、`B` 是否真握手、`WR_RESP` 停留拍数

## 三、当前唯一剩下的解释

**读请求根本没有从 SoC 发出**（AR 未到达从机）。

依据：
- 从机侧已试遍三种读实现，**包括一个"无条件接受 AR、下一拍即给 RVALID"的极简版本** —— 若 AR 到达，它必然会响应
- 从机不响应 ⇒ 只能是 AR 没来
- 而 AR 由 SoC 的 `arw` 通道发出；该通道的写方向工作正常

**⇒ 所以问题在 SoC 的 axiA **读**路径（或我们与该端口的集成），不在从机。**

## 四、观测困境（重要，避免下次重复踩）

| 手段 | 为什么失效 |
|---|---|
| openocd 读寄存器 | 读操作本身被卡住 |
| openocd 读 GPIO | `halt` 失败 —— 调试模块的访问依赖同一条被堵的路径 |
| CPU 经 UART 上报 | CPU 卡在那条 `lw` 指令上，无法继续 |
| SoC GPIO 诊断（已接线）| 仅在"未卡住"时可读，卡住后同样读不到 |

**⇒ 结论：任何依赖 SoC 总线或调试模块的观测，在卡死后都不可用。**
**⇒ 若要继续，必须用**完全独立于 SoC 的观测**：外部逻辑分析仪抓 `axiA_arvalid/arready/rvalid/rready`，或把诊断信号直接引到 LED/引脚用示波器看。**

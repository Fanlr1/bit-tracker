# 87 - 8192 上板验证：极限 4,096 → 4,320，与「演示不暴雷」方案

> 2026-10-17 凌晨。接 [86](86-五个优化方向研究.md) §26/§27。
> 上级交接：[新会话交接-20261017-8192告破.md](../新会话交接-20261017-8192告破.md)

## 一、★ 最终数字（细档位实测，1080p · 16×16 · 含扫描输出）

| 表深 | 60 Hz 精灵极限 | 依据 |
|---|---|---|
| 4096 | **4,096** | 表深用尽（1,545,576 拍 = 927/1000 预算）|
| **8192** | **4,320** | **细档位实测**：4096→4128→…→**4320 通过**、4352 超预算 |

**⇒ +5.47%**，与 docs/86 §25 的推算值 **4,322** 几乎一致（差 2 个精灵）。

### 为什么必须用细档位

粗档位（64/256/1024/2048/3072/4096/4352/…）只能给出「4096 过、4352 不过」，
而每精灵约 365 拍意味着两者相差约 9.3 万拍 —— 恰好跨在 1,666,666 的预算线上，
**真实上限落在 6.25% 的档位缝隙里**。细档位（32 粒度）把它夹到 [4320, 4352)。

改法：main.c 的 densities[] 换成 `64,256,1024,2048,3072,4096,4128,4160,4192,4224,4256,4288,4320,4352,4608,5120`。
改前备份：main.c.bak-20261017-before-fine-densities。

## 二、★★ 慢态：三重排除 + 根因

**A/B 实验（同一晚、同一块板）**：

| 比特流 | 固件 | 结果 |
|---|---|---|
| 8192 | 旧（4096 槽） | 1 正常 / 2 慢 |
| **4096** | **新（8192 槽）** | 2 慢 → **第 3 次正常（hw=3754）** |
| 8192 | 新 | 3 慢 → 第 4 次正常（hw=3542） |

⇒ **慢态与比特流无关、与固件无关** —— 它是配置的属性，不是任何一次代码改动造成的。

**根因（既有记录，docs/68）**：片上监视器的输出就是答案 ——

    [0] rd0 AR handshake wedged x 1
    [2] rd1 AR handshake wedged x 1
    VERDICT: a bus handshake never completed -- the engine is wedged, not merely slow

即 **Axi_Mux 的 AR 握手挂起**，此后每次 sprite fetch 都走超时路径
（每精灵约 1,375 万拍 vs 正常约 1,460 拍）。fill 不受影响（它不读 DDR），
与「慢的只有 sprite/walker 通路」的记录吻合。

**今晚慢态率异常高**：21 次以上运行仅 3 次正常。正常 hw 值 3,542~3,780；
慢值恒在 440,002,6xx~9xx（确定性状态）。这与 docs/86 二·补3 记录的 25~33% 不符，
**说明慢态率本身会变**，值得作为独立问题跟踪。

## 三、★★ 「演示不暴雷」方案：demo 循环

**原理**：慢态是**配置的属性** ⇒ **只要不重新配置 FPGA，就不会重新掷骰子**。
把「每展示一次掷一次骰子」变成「演示前掷一次」。

**实现**（main.c 末尾；改前备份 main.c.bak-20261017-before-demoloop）：

    while (1) {
        for (volatile uint32_t d = 0u; d < 300000000u; d++) { __asm__ volatile ("nop"); }
        __asm__ volatile ("j _start");   // 复位向量 0x1000：重跑软件，不动 FPGA 配置
    }

**依据**：_start 在 0x1000（riscv-none-elf-nm 实测）；DDR 控制器与 Axi_Mux 都在 FPGA 内部，
软重启不触碰它们的硬件状态。

**演示流程（建议）**：

1. 演示前 5~10 分钟：跑 work/probe/sweep-fast.ps1 直到判定正常态（慢态每轮只花约 35 s 就被丢弃）；
2. **进入正常态后不再重配置、不断电**；
3. 演示：demo 自己循环，观众随时能看到完整的一轮（12 项自检 + 弹幕游戏 + 密度扫描）。

## 六、★ 看门狗修复尝试：**失败**（2026-10-17 01:00–01:15，诚实记录）

**假设**：慢态 = 一笔没人接收的读占住 in-order DDR（依据是 system_top.v 里 2026-10-13 的实测注释：
`s_axi_arvalid=1/arready=0` 与 `rvalid=1/rready=0`）。

**实现**：在 system_top 加 R 通道看门狗 —— SoC 拒收 R 数据超过 10 ms，
就把它送给 Axi_Mux 的 `I_S0_R_READY` 强制拉高（`soc_ddrA_rready_eff`），
让 burst 走完、info FIFO 弹出、in-order 控制器前进。

**结果**：**无效**。修复后跑 2 轮：run 1 正常（hw=3530）、**run 2 仍慢（hw=440002937）**。

**为什么无效（推断）**：`Axi_Mux` 的 `M_R_Ready = |(R_Act_Cnl_List & S_R_Ready)`。
若内部的 `R_Act_Cnl_List` 为 0（例如 DDR 回的 ID 与预期通道不匹配），
则**根本没有通道被选中**，在 SoC 侧怎么强制 ready 都不起作用。

**★ 同时纠正一个错误推断**：本轮加的 GPIO 探针 `{r_cnl_num, rd1_rready, rd0_rready}`
在**慢态与正常态读到的都是 0x0**（正常态实例：run 1 NORMAL hw=3530 也报 `r_cnl=0 rd0_rr=0 rd1_rr=0`）
⇒ **该探针没有区分度**，不能用它推断"R 通道挂在 SoC 上"。真正的证据只有 2026-10-13 那次直接测量。

**结论**：慢态的机制比"某一笔读没人收"更复杂，下一步必须先取得**有区分度**的观测
（`R_Act_Cnl_List` / `M_R_Valid` / `M_R_Ready` / `s_axi_rvalid` / `s_axi_rready`），再谈修法。

**当前可用的可靠方案仍是**：演示前跑 sweep-fast（1~3 分钟掷到正常态）+ demo 循环（软重启保持正常态，见 §三）。

与 `rtl/system_top.v.bak-20261017-before-rwatchdog`（改前备份，回退用）。

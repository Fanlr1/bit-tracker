# 63 - 读通道死锁的根因与修复：突发准入控制（2026-10-14 上午）

> **接 docs/62。** 62 记录了"当前 RTL 通不过 vlog、仿真从未覆盖"，本文记录**修好编译后**仿真立刻做到的三件事：
> **复现板上死锁 → 定位根因 → 修复并验证**。

## 一、一句话

**根因**：`bitblt_dma_rd` 在 `S_AR` **无条件**发 AR，不管 FIFO 装不装得下 ⇒ 连续 burst 长期霸占共享 R 通道；
真实 DDR 是**顺序**的 ⇒ 另一个 reader 的 AR 永远轮不到 ⇒ 像素引擎要**双方都有数据**才消费 ⇒ 两个 FIFO 都不排空 ⇒ **死锁**。

**修复**：**突发准入控制** —— 只有整个 burst 能装进 FIFO 时才发 AR。

## 二、三步证据链（每步都有实验）

| 步 | 动作 | 结果 |
|---|---|---|
| 1 | tb 的 sprite 用例 8×2 → **64×64**（16 KB = 32 burst）| **不挂** —— 说明逻辑本身通 |
| 2 | 给 tb 加**有序总线模型**（一个 reader 的 burst 未收完时，另一个的 AR 不被接受）| **立刻挂死**：rd0 只发 4 个 AR；P4 scale **40 万周期 guard 耗尽** |
| 3 | 给 `dma_rd` 加**准入控制** | **不挂了**：rd0 发满 99 个 AR；P4 scale **2656 周期完成** |

**第 2 步是决定性的**：同一份 RTL，**加约束就挂、不加就不挂** ⇒ 死锁的成因就是"跨 reader 的总线耦合"，而这正是板上 `r_cnl_num` 卡住时观测到的现象（docs/61）。

## 三、死锁的完整链条

```
rd_src 走 compact_src，一次要读 16 KB（32 个 burst）
  ⇒ 它连续发 AR，每个 burst 32 拍正好填满 32 深的 FIFO
  ⇒ FIFO 满 ⇒ m_axi_rready = 0 ⇒ burst 卡在半途（或刚完就发下一个）
  ⇒ 共享 R 通道被它占着，DDR（in-order）无法开始 rd_dst 的 burst
  ⇒ rd_dst 永远拿不到数据 ⇒ rd_dst_valid = 0
  ⇒ px_in_valid = rd_src_valid & rd_dst_valid = 0 ⇒ 像素引擎不消费
  ⇒ rd_src 的 FIFO 永不排空 ⇒ 回到第二行。永久死锁。
```

**为什么 8×2 的精灵不会触发**：64 字节 = 1 个 burst，FIFO 装得下且立刻结束，不会长期占线。

## 四、修复（`rtl/bitblt_dma_rd.v`）

```verilog
wire [FIFO_AW:0] fifo_occupancy = fifo_wr - fifo_rd;      // 指针带 wrap 位，直接相减
wire [31:0]      fifo_free      = FIFO_DEPTH - {26'd0, fifo_occupancy};
wire             fifo_can_start = (fifo_free >= burst_want);

S_AR: begin
    if (fifo_can_start) begin          // ← 新增准入
        m_axi_arvalid <= 1'b1;
        ...
    end else begin
        m_axi_arvalid <= 1'b0;         // 让出 R 通道，给另一个 reader 机会
    end
end
```

**为什么这样就安全**：burst 总能独自完成（FIFO 装得下）⇒ 引擎在 burst 之间**必然放开 R 通道** ⇒ 另一个 reader 一定有机会 ⇒ 双方数据都会到 ⇒ 像素引擎开始消费 ⇒ FIFO 排空。

**代价**：FIFO 要排空到能容纳整个 burst 才能开下一个，中间有气泡。

## 五、性能影响：几乎为零（有数据）

| 指标 | 修复前（无死锁时）| 修复后 |
|---|---|---|
| P4 scale 单精灵成本 | **82 拍**（docs/44 记录）| **83 拍**（2656 周期 / 32 sprite）|
| 仿真总时长 | 125506 ns | 125506 ns |

⇒ 准入控制**没有可测的性能代价**。

## 六、附带修好的两个问题

| # | 问题 | 性质 |
|---|---|---|
| 1 | `FAIL blend value: got 10001f00 want 10xxxxxx` | **测试台缺陷**：参考值取 `dut.rd_dst_data`（FIFO 组合输出），传输结束后 FIFO 已排空，读到从未写过的位置 ⇒ X。改用从设备模型公式 `exp_pattern(16'h8020, 0)`；手工验证 `0x02*0x00/255=00, 0x5a*0x5a/255=1f, 0x00*0x20/255=00` ⇒ `10001f00` **与 DUT 输出逐字节一致**，RTL 本来就是对的 |
| 2 | P4 断言仍按 8×2 写（期望 6 个 AR）| 用例改 64×64 后应为 **99**（3 描述符 + 3×32 burst）；已参数化索引：描述符在 0/33/66，源在 1/34/67 |
| 3 | 等待循环把 `guard` 同时当计数器和退出标志 | 卡死会被伪装成"跑得慢"，只报"AR 数不对"。改成先等 busy 拉高、再等它落下，**超时明确报 deadlock** |

### 上板过程中修掉的两个应用侧缺陷

| # | 缺陷 | 性质与修法 |
|---|---|---|
| 1 | `game-60fps-budget` **恒失败** | **测量口径错**：`fc` 在 `wait_frame()` **之后**采样，而后者从调用点忙等满 16.67 ms ⇒ 每帧 = 工作 + 16.67 ms，**按构造不可能通过**。改为只测工作（wait_frame 之前采样）⇒ worst **46468** 周期，2.8% 预算 |

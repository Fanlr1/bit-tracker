## 一、⚠️ 我先推迟了 P3，理由如下

**`28-待办优先级.md` 里把 P3（突发合并）标为「风险中」**，但动手前重新看了一遍数据流：

```
现状（每行一次）：
  读源一行  ──┐
              ├─> pixel_engine ──> 写目标一行
  读背景一行 ──┘
  ⇒ 读和写【同步推进】，不需要缓冲

若源侧「一次读多行」：
  rd_src 读 4 行（4 KB）  ──┐
                            ├─> ？ ──> wr 按行写
  rd_dst 仍按行读         ──┘
  ⇒ 读快、写慢 ⇒ 【必须加 FIFO 缓冲】
  ⇒ 而且读引擎与写引擎的握手要重做
```

**⇒ 这不是「加个条件分支」，是【给数据通路加缓冲 + 改握手协议】。**

**⇒ 而 `28` 号里我自己定的规则是**：

> **链路没通 ⇒ 不做「改动大、失败后难定位」的**

**⇒ P3 正好落在这条线上。** **板子没到、链路没验证过，现在动数据通路，出了问题分不清是它还是 DDR3。**

**⇒ 所以先做 P2 的另一半 —— 它是收尾，成本低，不依赖板子。**

## 二、驱动侧裁剪

### 2.1 为什么需要它

**⇒ 现在靠【约束位置】避免越界，而不是【裁剪】**：

```c
sx[i] = RAND() % (FB_W - SPRITE_W);        // 初始化就限制在范围内
if (nx < 0 || nx > FB_W - SPRITE_W) { 反向 }  // 移动时反弹
```

**⇒ 所以 demo 里的 sprite 只能【反弹】，不能【飞出屏幕】** —— **而弹幕游戏的子弹必须能飞出去。**

### 2.2 `blt_sprite_clipped`

```c
static void blt_sprite_clipped(uint32_t src_base, uint32_t src_stride,
                               int32_t x, int32_t y,          // 屏幕坐标，可为负
                               uint32_t w, uint32_t h,
                               uint32_t dst_base, uint32_t dst_stride,
                               uint32_t op)
```

**⇒ 逻辑**：
1. **算与屏幕的交集**（`x0 = max(x,0)`、`x1 = min(x+w, FB_W)` ……）
2. **完全在屏幕外 ⇒ 直接返回**
3. **源指针推进到第一个可见像素**（`(y0-y)*src_stride + (x0-x)*4`）
4. **只传交集部分**

**⇒ 与 RTL 保护的分工**：

| 层 | 作用 |
|---|---|
| **驱动裁剪** | **正确的机制** —— 只画可见部分 |
| **RTL 越界保护** | **安全网** —— 驱动算错时拒绝执行，而不是破坏内存 |

### 2.3 让裁剪【每帧都被用到】

**⇒ 原来的动画【反弹时会修正位置】，所以 sprite 从不越界 ⇒ 裁剪路径永远不被执行。**

**⇒ 改成【只反向速度，不修正位置】**：

```c
sx[i] += sdx[i];
sy[i] += sdy[i];
if (sx[i] < -EDGE_MARGIN || sx[i] > FB_W + EDGE_MARGIN) sdx[i] = -sdx[i];
if (sy[i] < -EDGE_MARGIN || sy[i] > FB_H + EDGE_MARGIN) sdy[i] = -sdy[i];
```

**⇒ 初始位置也允许在屏幕外**（`RAND() % (FB_W + 2*EDGE_MARGIN) - EDGE_MARGIN`）。

**⇒ 结果**：**sprite 会短暂越界，裁剪每帧都在工作，而且视觉上更像弹幕游戏（从边缘滑入滑出）。**

## 三、验证：`clip_check.py`

### 3.1 为什么用 Python 而不是跑 C

**⇒ 本机【没有宿主机 C 编译器】**（`gcc`/`clang`/`cc`/`cl` 全无，`python` 还是 Store 的占位 stub，`exit 9009`）。

**⇒ 所以用 Python 复现算法并穷举边界条件。**

**⚠️ 而我在文件头部【明确写了这个局限】**：

> It does not prove the C implementation matches. There is no host C compiler
> on this machine... the two must be kept in step by hand.
> What it DOES prove is that the algorithm itself handles every edge case.

### 3.2 结果：28 项 + 42320 个扫描点

```
== fully inside ==                      4 项
== one edge each ==                    10 项
== corner: off both axes ==             2 项
== entirely off screen ==               7 项   （左/右/上/下/远/零宽/零高）
== touching the boundary exactly ==     3 项   （1 像素露出 / 刚好贴边）
== sprite larger than the display ==    1 项
== invariants over a coordinate sweep == 1 项（42320 个点）

ALL 28 CHECKS PASSED
```

### 3.3 关键：三个不变量

**⇒ 扫描中对每个点验证**：

| # | 不变量 | 覆盖的错误 |
|---|---|---|
| **1** | **目标矩形落在屏幕内** | **忘了减尺寸、偏移算反** |
| **2** | **源偏移落在 sprite 内** | **源指针推进错误** |
| **3** | **可见尺寸 = 交集** | **宽高没更新** |

**⇒ 这三条覆盖了裁剪所有可能的写错方式。**

## 四、⚠️ 本次验证的局限（必须说清）

| 它证明了 | 它**没**证明 |
|---|---|
| **算法在边界条件下正确** | **C 实现忠实于算法** |
| **负坐标、完全越界、贴边都对** | **编译器行为、整数提升** |
| **42320 个点上不变量成立** | **实际硬件上的表现** |

**⇒ `blt_sprite_clipped` 的 C 实现是靠【人工逐行对照】确认与 Python 一致的。** **⇒ 这个事实写在测试文件头部，避免以后有人误以为它验证了 C。**

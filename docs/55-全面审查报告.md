### 1.2 审查结论

| 检查项 | 结果 |

### 1.3 ⚠️ 唯一的形式化不一致：复位风格混用

| 模块 | 复位写法 | 综合后果 |
|---|---|---|
| **`bitblt_pixel_engine`** | **同步：`always @(posedge clk)` + `if (!rst_n)`** | **⇒ 复位需要时钟，占用**一个时钟周期**；**不依赖复位信号的布线**** |
| **⇒ 其余 10 个** | **⇒ 异步：`always @(posedge clk or negedge rst_n)`** | **⇒ 复位立即生效，**不占时钟**；但**要求复位信号有低偏斜布线**** |

**⇒ **⇒ 判定：**两者都对，且在这个设计里**无害**** —— 理由是：**
1. **`bitblt_pixel_engine` 是**纯数据通路**（流水线打拍），复位只影响三个输出寄存器的初值；同步复位在此**更省资源**（不需异步复位专用的触发器）
2. **⇒ 时序已签核通过（12 条关系全过）⇒ 两种写法都被工具正确实现**
3. **⇒ **⇒ 但**风格不统一本身值得记录** —— 后来者加模块时不知道该跟哪种。**

**⇒ ⚠️ 建议（非缺陷）：在 [docs/34](34-架构总览.md) 里写明两种复位各自的适用场合，而不是统一改掉 —— 统一改一处反而会引入新风险。**

### 3.3 ⭐ 唯一那条警告：**代码自己已经分析过，且证明无害**

**⇒ `bitblt_pixel_engine.v:146`：`expression size 20 truncated to fit in target size 18`。**
**⇒ 而该文件 132~145 行的注释原文：**

```
// CHECKED, AND IT CANNOT OVERFLOW: num <= 255*255 = 65025, so
// num + 1 + num[17:8] <= 65025 + 1 + 254 = 65280, well inside
// the 262143 that 18 bits hold. What is discarded is padding,
// not data. Left at 18 bits rather than widened, since widening
// would change nothing except to silence a warning whose premise
// does not hold. Recorded so the next reader need not redo this.
```

**⇒ ⇒ 审查复核了该分析：255×255 = 65025，加 1 加 254 = **65280 < 262143 = 2^18−1** ⇒ **结论正确，无害**。**
**⇒ ⇒ 而这段注释是本项目的范例：**它把「为什么可以忽略」写在代码旁边，所以下次审查不必重做，也不会被误读成缺陷** —— 那正是我前两次误报的反面。**

### 3.4 ⚠️ 新发现：`bl3_bresp[1]` 未驱动 ⇒ 写通道**报不出错误**

**⇒ 5 条 `VDB-1002`（does not have a driver）里，4 条无害，1 条值得记录：**

| 信号 | 性质 |
|---|---|
| **`s_axi_awcache[3]` · `s_axi_awprot[2]` · `s_axi_arcache[3]` · `s_axi_arprot[2]`** | **AXI 的 cache/prot 提示位未驱动 —— **常见且无害**（多数设计忽略这些提示）** |
| **`bl3_bresp[1]`** | **★ **BitBlt 写通道的响应位，只有 `[0]` 被驱动**** |

**⇒ ⇒ 后果：写通道只能返回 OKAY 或 EXOKAY，**永远无法返回 SLVERR / DECERR**：**

| `bresp` | 含义 | 能否报出 |
|---|---|---|
| **`2'b00`** | **OKAY** | **✅** |
| **`2'b01`** | **EXOKAY** | **✅** |
| **`2'b10`** | **SLVERR（从设备错误）** | **❌** |
| **`2'b11`** | **DECERR（解码错误）** | **❌** |

**⇒ ⇒ 影响：**写失败时 CPU 收不到错误响应**（会被当作成功）。**
**⇒ ⇒ 部分弥补：**片上有 `bitblt_monitor` 的 `resp_err` 粘滞位 ⇒ 异常**不是完全不可见**，只是不走 AXI 的正式通路。**
**⇒ ⇒ 判定：**不是致命缺陷，属于**设计限制** —— 若板上出现「写了但没生效」，排查时要记得这条。**
**⇒ ⚠️ 是否修：见 §五 待决事项 6（修的话要动 RTL，而目标约定「审查只查明与报告」）。**

### 5.2 报错的路径（**每一步的障碍都不是我们的 RTL**）

**⇒ 得出上述结果之前，连续撞了 **6 个**障碍，逐个记录如下 —— 它们的价值在于：下一次不必重走。**

| # | 现象 | 真因 | 解法 |
|---|---|---|---|
| **1** | **`ModuleNotFoundError: No module named 'encodings'`** | **Efinity 内嵌 Python 的 `sys.prefix` 指向 `C:\Efinity\2026.1`，而 stdlib 在 `python311\Lib`** | **设 `PYTHONHOME=C:\Efinity\2026.1\python311`** |
| **⇒ 2** | **⇒ `LookupError: EFINITY_HOME not set`** | **⇒ `efx_run_sim.py` 需要它** | **⇒ 设 `EFINITY_HOME=C:/Efinity/2026.1`（**unix 风格**）** |
| **⇒ 3** | **⇒ `OSError: cannot load library 'libdevicedb_wrapper.dll': error 0x7e`** | **⇒ 0x7e = ERROR_MOD_NOT_FOUND；该 DLL 依赖 `libgcc_s_seh-1.dll` / `libstdc++-6.dll` 等，它们**在 `bin\` 里但不在搜索路径**** | **⇒ 把 `C:\Efinity\2026.1\bin` 加进进程 PATH** |
| **⇒ 4** | **⇒ `An exception occurred: 'EFINITY_USER_DIR_INI'`** | **⇒ 那是 `setup.bat` 设的 12 个变量之一 —— **手动补变量是错的路子**** | **⇒ ✅ **正解：一个变量都不设，让 `efx_run.bat` 自己 `call setup.bat`**（而 `efx_run.bat` 只在 `EFINITY_HOME` **未定义**时才 call 它 ⇒ 我"帮它"设变量反而破坏了流程）** |
| **⇒ 5** | **⇒ iverilog: `bitblt_system.map.v:184102: syntax error`** | **⇒ **网表里有 IEEE 1735 加密块**（`` `pragma protect ``，因为工程含 IP Manager 生成的加密 IP）⇒ **iverilog 不能解密**（Efinity 教程原文即写明此限制）** | **⇒ 用 `--modelsim` 走 Questa —— Questa 能解密** |
| **⇒ 6** | **⇒ Questa: `vopt-14408` 容量超限 / `vsim-3009 [TSCALE]`** | **⇒ 前者是 **Starter 版许可提示**（5000 推荐实例 vs 我们 33,241）；后者是**厂商原语** `efx_ram10.v` 缺 `timeunit` 声明** | **⇒ `-suppress 14408,12110,2958,3009`** |

**⇒ ⚠️ 第 6 条里的两个都必须抑制才放行 —— 而它们是**可抑制（suppressible）**的许可/风格提示，不是逻辑错误。**

### 5.3 关键发现：网表是**扁平化**的，端口与 RTL **不同名**

**⇒ `outflow\bitblt_system.map.v`（26.3 MB / 270,117 行）的性质：**

```
module 定义总数 : 1（只有 system_top）
内部          : EFX_LUT4 28,458 · EFX_FF 19,724 · EFX_ADD 4,994 · EFX_SRL8 1,460
                EFX_RAM10 148 · EFX_DSP48 80
⇒ ⇒ 层次【全部展平】：bitblt_top / dma_rd / sprite_walker 这些模块名【都不存在】
```

**⇒ **⇒ 后果①：**无法按子模块单独做门级仿真**（网表里没有子模块边界）。**
**⇒ **⇒ 后果②：**网表顶层 `system_top` 的端口 ≠ `rtl/system_top.v` 的端口**：**

| | RTL 顶层 | 网表顶层 |
|---|---|---|
| **端口数** | **—** | **⇒ **72**（27 input + 45 output）** |
| **⇒ 时钟** | **⇒ `clk_100m` / `clk_27m` / `clk_25m` / `pix_clk_fast` / `pll_fb`** | **⇒ **`axi_clk` / `core_clk` / `sdram_clk` / `pix_clk` / `rx_cal_clk` / `tx_cal_clk`**（板级名）** |
| **⇒ 复位** | **⇒ `i_arstn`** | **⇒ **没有复位端口**（复位在网表内部）** |
| **⇒ JTAG** | **⇒ `io_jtag_*`** | **⇒ `jtag_inst1_*`** |

**⇒ **⇒ 所以 testbench 的例化**必须按网表端口生成**，不能照抄 RTL 顶层。**
**⇒ 本次做法：用脚本从 `map.v` 解析端口（方向 + 位宽），**自动生成例化块**，再拼进 `tb/tb_system_top_map.v`。**
**⇒ ⚠️ 这样两边不可能再漂移** —— 而那正是文档里反复出现的「两份同名文件内容不同」那类问题的预防。

### 5.4 ⚠️ 本次门级仿真**不能**证明什么（边界，必须写清）

| 不能证明 | 原因 |
|---|---|
| **加速器功能正确** | **`sim_models/` **只有原语模型**（`efx_lut4`/`efx_ff`/`efx_dsp48`/`efx_ram10`…），**没有 DDR3 行为模型** ⇒ 内存接口未驱动 ⇒ **校准无法完成**）** |
| **⇒ 帧率 / 带宽数字** | **⇒ 同上：跑不到帧缓冲读写** |
| **⇒ 时序（建立/保持）** | **⇒ 门级仿真（post-map）**不含布局布线延迟**；那需要 post-route 仿真 + SDF 反标** |

**⇒ **⇒ 它能证明的是：**映射后的网表**能被加载、能出复位、逻辑会活起来** —— 而那是此前**完全没有验证过**的一层。**
**⇒ ⇒ 一句话：这是**结构性与活性**验证，**不是功能验证** —— `tb_system_top_map.v` 的注释里也这么写了。**

### 5.5 附带确认：Questa 能在 4 秒内编译 26 MB 门级网表

```
vlog -work work outflow/bitblt_system.map.v     ⇒ 退出码 0，耗时约 4 秒
⇒ ⇒ 而那【包含解密 IEEE 1735 加密块】—— iverilog 在同一文件上直接语法错误
```

**⇒ **⇒ 所以：**本机做门级仿真的可行路径是 Questa**（`--modelsim`），而 iverilog 受加密 IP 限制。**

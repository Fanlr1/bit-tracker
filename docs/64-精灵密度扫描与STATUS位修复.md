# 64 - 精灵密度扫描，以及一个被注释掩盖的 STATUS 位（2026-10-14 下午）

> 接 [63](63-读通道死锁根因与修复.md)。本文记录"可调精灵密度"的实现，以及它顺手挖出的一个 RTL bug。

## 一、一句话

**可调密度扫描已实现并上板（10/10 通过）**；过程中发现 **STATUS bit 0 用的是 `addr_busy`（不含 walker）**，
而它的注释明确写着"busy 必须包含 walker"。于是所有"用 `blt_wait()` 测 walk 时间"的尝试都在测**寄存器写延迟**。
修复后测出**真实能力边界：60 fps 内 128 个 16×16 精灵**。

## 二、能力边界（实测，可信）

| 密度 | 周期/帧 | 占预算 | 60 fps 内？|
|---|---|---|---|
| 32 | 298,057 | 178‰ | ✅ |
| 64 | 589,171 | 353‰ | ✅ |
| **128** | **1,181,581** | **708‰** | ✅ **上限** |
| 192 | 1,773,472 | 1064‰ | ❌ |
| 256 | 2,361,546 | 1417‰ | ❌ |

**线性度**：32 个 → 9220 拍/精灵；256 个 → 9233 拍/精灵 ⇒ **完全线性**（测量可信的标志）。

## 三、那个 RTL bug

```verilog
// bitblt_top.v:922（修复前）
assign engine_status = {28'd0, addr_oob, wr_b_error, addr_done, addr_busy};
//                                                                    ^^^^^^^^^
// bitblt_top.v:924-930
//   busy must include the walker. Without spr_busy, software polling this
//   sees an idle engine while a whole frame of sprites is being dispatched...
assign busy = addr_busy | rd_src_busy | wr_busy | spr_busy;   // ← 为这个目的而建，却没人用
```

**症状**：walker 运行时，精灵与精灵之间 `addr_busy` 会落下 ⇒ 软件轮询看到"引擎空闲" ⇒
`blt_wait()` 在 walk 还没跑完时就返回。

**后果**：密度扫描测到的**不是 walk 时间，而是三次寄存器写的 AXI 延迟**（~10-15k 周期，与精灵数几乎无关，且不单调）。

**修复**：`engine_status[0] = busy`（一行）。

## 四、方法论：为什么必须先在仿真里量

| 步骤 | 结果 |
|---|---|
| 板上直接测（两次尝试）| 数字**不单调**（256 精灵比 32 还"快"）⇒ 明显是测量坏了，但**看不出坏在哪** |
| **仿真同一套测量** | `DENSITY: 32→11814, 64→22342, 128→43398, 256→85510` ⇒ **完美线性**，证明 walker 本身没问题 |
| **对比两边** | 仿真 85,510 vs 板上 10,455（8 倍差）⇒ 差异只可能来自"等的是什么" ⇒ 顺着找到 `engine_status` 用错信号 |

**教训**：板上测量失真时，**仿真是唯一能把"被测对象"和"测量装置"分开的地方**。
在板上反复试参数，只会得到更多不可信的数字。

## 五、密度演示（可调）

**改一行就能改档位**（`main.c` 的密度扫描段）：

```c
static const uint16_t densities[] = { 32u, 64u, 128u, 192u, 256u };
```

- 每档：`game_density_fill(n)` 填表（16×16 精灵铺网格，**静止、不退休**）
- 测量：`spr_walk_one(n)`（arm → 等 busy **上升** → 等它**落下**）
- 判据：`sprite-density-64-at-60hz`（**下限**，不是上限——上限由扫描打印）
- **为什么判据是下限**：断言"256 必须过"会在**真实硬件极限**上失败，而不是在缺陷上失败

## 六、仍未解决

| # | 项 | 说明 |
|---|---|---|
| 1 | **每精灵 9220 拍（92 µs）远高于仿真的 334 拍** | 差 **27 倍**。瓶颈是 **DDR 往返延迟 + burst 准入控制的气泡**（小精灵每个只有 2 个 burst，准入要求 FIFO 先排空）。**这是最大的性能空间** |
| 2 | 游戏的"60 fps"只测了 **CPU 侧**（46k 拍），**没测硬件 walk** | 按 9220 拍/精灵算，255 个精灵的 walk 要 ~23 ms ⇒ 游戏实际帧率可能低于 60 |
| 3 | `scan-out starved` | 255 周期（**8 位饱和** ⇒ 是下限不是总数），1 次事件。RTL 的周期计数器只有 8 位，建议加宽 |
| 4 | 回归 6 个历史遗留失败 | 见交接文档 |

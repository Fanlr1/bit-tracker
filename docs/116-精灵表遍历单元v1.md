# 116 · 精灵表遍历单元 v1（RTL 实现记录）

> 目标：把「CPU 逐精灵写命令」改成「CPU 写表 + 硬件遍历发命令」，CPU 每精灵开销从 20 次 AXI 寄存器写降到 4 次表写。
> 状态：RTL 完成、iverilog 仿真 PASS；PnR 结果待补。

## 一、软件接口

| 项 | 值 |
|---|---|
| 表窗口 | `0xE1008000`（SoC 的 16 MB AXI 窗口内，紧跟寄存器 0x00-0xFF）|
| 表项 | 16 字节 = 4 个 32 位字 |
| word0 | `old_x | old_y<<16`（擦除用的旧位置）|
| word1 | `x | y<<16`（新位置）|
| word2 | 精灵源地址（绝对）|
| word3 | 保留 |
| 启动 | `SPR_CTL(0x7C) = 0` 然后 `= N | (1<<16)`（上升沿触发）|
| 表基址寄存器 | `SPR_TAB(0x78)` |
| 完成判定 | 引擎 `DONE_CNT(0x38)` 累加 2N（每精灵擦除+绘制两条命令）|

固件开关：`main.c` 的 `USE_SPR_TABLE`（1=走表，0=老路径）。

## 二、RTL 结构（gfx_regs.v）

1. **表 RAM**：`spr_ram[0:4095]`（16 KB，block RAM），写口来自 AXI 从口偏移 ≥0x8000 的存；读口给 walker。
2. **AXI 从口地址扩宽**：`s_awaddr/s_araddr` 8 → 16 位（`gfx_top`、`system_top_gfx` 同步），低 8 位仍是寄存器，≥0x8000 是表。
3. **walker 状态机**（11 态）：
   - `SW_IDLE` → `SW_RD` → `SW_WA` → `SW_W1` → `SW_WB` → `SW_W2` → `SW_WC` → `SW_W3` → `SW_E0` → `SW_E1` → `SW_D0` → `SW_D1`
   - 每态之间插等待，因为 **block RAM 读数据要在地址后 2 拍才有效**（TB 抓到的第一个 bug）；
   - `SW_E0/E1` 发擦除（FILL），`SW_D0/D1` 发绘制（COPY_KEY），命令直接塞进 32 深 352 位 FIFO；
   - FIFO 满时停在 `E0/D0` 重试；CPU 的 START 写入优先级高于 walker。
4. **命令格式**：与 CPU 完全相同（352 位：`op[2:0] | src | dst | size | ss | ds | color | alpha | key | cx | cy`）。

## 三、仿真验证（rtl-sim/tb_sprdma.v）

结果：**TB PASS** —— 写入 3 条表项后启动，输出 6 条命令，op/地址全部正确：

| 命令 | op | src | dst | 含义 |
|---|---|---|---|---|
| 0 | 0 (FILL) | - | `0800a014` | 擦 old(10,10) |
| 1 | 5 (COPY_KEY) | `08870000` | `0801e028` | 画 new(20,30) |
| 2 | 0 | - | `0803c064` | 擦 old(50,60) |

| 5 | 5 | `08872000` | `080780dc` | 画 new(110,120) |

**TB 抓到的两个 bug**：
1. **BRAM 读延迟 2 拍**：原来只等 1 拍 → 采到上一字（源地址读到「新位置」值）→ 每个字之间补等待态；
2. **坐标字节序反了**：RTL 把 x 当高 16 位、y 当低 16 位，与软件约定相反 → 所有精灵坐标转置 → 改为 x 低、y 高。

## 六、板级实测结论（2026-10-31 20:40）

| 配置 | CPU | 引擎等待 | fps | 结论 |
|---|---|---|---|---|
| 老路径 700×16×16 | 14.2 ms | 0.16 ms | 59.2 | 基线 |
| **表模式 700×16×16** | **2.05 ms** | **13.9 ms** | 35.5 | CPU 大降，但**引擎成为瓶颈** |
| 表模式 700×8×8（不等） | 2.06 ms | 0.001 ms | 59.2 | 流水正常，但命令落在 flip 之后 → 黑屏 |
| 表模式 2000×8×8 | 6.1 ms | 39.3 ms | 29.5 | 引擎每命令 ~10 µs |

**关键发现**：引擎每命令 ~9.8 µs（8×8 与 16×16 相同）→ 与像素量无关的**固定开销**：
- gfx_core 每行串行处理：读源行 → 等 DDR 读数据 → 写目标行 → 下一行；
- 8 行 × 1.25 µs DDR 读往返 ≈ 10 µs；16×16 的 16 行被行内 burst 摊薄后仍是 ~10 µs。
- 老路径之所以看起来「快」，是 CPU 发命令与引擎执行**并行**，两者都是 14 ms，被 CPU 掩盖了。

**结论**：表模式把 CPU 从 14.2 ms 降到 2.05 ms（**7 倍**），但数量上限不变——瓶颈已转移到引擎的行串行处理。
要继续提升数量，必须改 gfx_core 的行流水（预取下一行），预计 2-4 倍，工期约 1 天。

## 九、引擎侧优化：分段 compact-source（2026-10-31 20:55）

### 问题

`gfx_core` 的 compact-source 路径要求整个精灵放进 128 像素暂存数组，**16×16（256 像素）被迫退化成逐行读** → 每条命令 16 次 DDR 往返 ≈ **10 µs**（8×8 与 16×16 一样慢的原因）。

### 尝试 1（放弃）：数组扩到 256 项

- `spx[0:255]` + 条件放宽到 256 像素；
- 综合后 `hier_util` 显示 **113.5%**（256×16 被推断成逻辑而不是 block RAM）→ **回退**。

### 尝试 2（采用）：分段读取

- 暂存数组保持 **128 项**；
- 精灵按 **128 像素为一段**分批突发读：`段数 = ceil(w*h / 128)`，`每段行数 = 128 / w`（8×8→16 行，16×16→8 行）；
- `S_NEXT` 检测段边界（`(row+1) & (rows_per_seg-1) == 0`，掩码代替取模）→ 重新 `S_SPX_REQ` 读下一段；
- 源地址 = `{src[31:4],4'd0} + seg*256`。

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 700×16×16 引擎等待 | 13.9 ms | **10.1 ms**（-27%）|
| 700×16×16 帧时间 | 16.0 ms | **14.1 ms** |
| 800×16×16 | — | **59.2 fps**（CPU 2.4 ms + 引擎 11.5 ms）|
| 850×16×16 | — | 12.3 ms 引擎 → 掉帧（flip 临界）|

### 当前天花板

- 引擎每精灵仍 ~14.4 µs（写路径是主因：每行 16 字节未对齐写 = 2 个写事务，16 行 = 32 写事务/命令）；
- 要再提升需要动**写路径**（对齐合并/批量），工程量 2 天以上，收益约 2 倍；
- 800 精灵 × 16×16 = 老路径 700 的 **+14%**，且 CPU 余量从 14.2 ms 降到 2.4 ms（游戏/HUD 全部受益）。

### 欠载

分段版 PnR 后 `rows/fr = 23.6`（黄金版 0.0）——截图无黑线/撕裂，但建议扫 seed 找 0.0 的布局（`efx_run_pnr_sweep.bat gfx2_system.xml sweep_seeds --nJobs 2`，每个 seed ~10 分钟）。

## 十、表模式 v1 的两个显示缺陷（2026-10-31 21:05 实机确认）

> 板级现象：800 精灵表模式画面**闪烁严重**、精灵**残缺**（边缘缺口/碎片）。已回退到老路径。

### 10.1 闪烁：表模式只重画一个 back buffer

- 老路径：`g_old_x[bi]` **每个 buffer 各记一份**，每帧对当前 buffer 擦旧位置再画新位置 → 两个 buffer 内容**一致**；
- 表模式：表里只有**一份**旧位置，每帧只画到**当前** buffer → 另一个 buffer 停留在更早的帧 → flip 交替显示 → **闪烁**；
- 修复需要每帧对两个 buffer 各发一遍命令（×2 命令量，引擎 11.5→23 ms → 掉帧），或改单缓冲（有撕裂）。

### 10.2 残缺：逐精灵「擦旧+画新」交错

- 表模式命令顺序：精灵 A 擦旧→画新，精灵 B 擦旧→画新……
- 若 B 的旧位置与 A 的新位置重叠，**B 的擦除会抹掉 A 刚画的像素** → 残缺；
- 老路径顺序是「**先擦全部旧位置，再画全部新位置**」→ 不互相覆盖。

### 10.3 结论

表遍历单元（RTL 已验证）+ 分段 compact（RTL 已验证）本身正确，但**与现有的双缓冲渲染模型不兼容**。
要用它，需要两者之一：
1. **双表**（每 buffer 一份旧位置）+ 命令翻倍 → 引擎需要再快 2 倍（依赖写路径优化）；
2. **walker 两趟模式**（先全擦、再全画）+ 单缓冲 → 撕裂风险。

**当前交付**：老路径 700×16×16 @ 59.2 fps（无闪烁、无残缺、欠载 0.0），表遍历 RTL 与比特流归档在 `work/backup/sprtab-20261031/` 供后续使用。

### 11.2 引擎读停顿实测（新增调试计数器）

`gfx_core` 加了 `dbg_rd_wait`/`dbg_wr_wait` 计数器（每命令的读/写等待周期），PROF 输出 `rdw=`：
- **rdw ≈ 647 周期 = 6.5 µs** → **每命令总耗时 7.2 µs 里 90% 是在等 DDR 读数据**；
- 结论：引擎瓶颈 = **读延迟**（不是写、不是组合逻辑）；
- 下一步优化方向应是「命令级预取」（在写当前命令目标时提前读下一条命令的源），预计每命令 7.2 → 2 µs、数量翻 3 倍，但需要双缓冲暂存数组（资源临界，今天试过 256 项 PnR 失败）。

### 11.3 表遍历单元的去留

- RTL 与仿真已完整（`rtl-sim/tb_sprdma.v` PASS）；
- 表模式 + 分段 compact 上板实测 CPU 2.4 ms（vs 老路径 10.4 ms）；
- **但**：表模式只重画单 buffer → 闪烁；逐精灵擦画交错 → 残缺（见第十节）；
- 结论：**保留 RTL 与归档比特流**，等「双表 + 引擎预取」一起做时再启用。

### 12.2 未部署原因：**DVI 输出不稳定**

**现象**：换用带分段 compact 的 bitstream 后，显示器画面闪烁/间歇黑屏（framebuffer 内容正常、scanout 在跑、时序 slack 全为正）。

**排查过程**：
| 实验 | 结果 |
|---|---|
| 扫 seed 10 个（第一批）| seed_3 最稳但仍闪，seed_9 闪，seed_1/7 更差 |
| 再扫 20 个（第二、三批，共 30 个）| 自动筛选欠载（seed_20 最好 0.6）→ 仍闪 |
| 方案 2：给 TMDS 输出加 `set_output_delay` 约束 | 构建产物 CPU 不启动（LPF 复制问题），方案失败 |
| **方案 3：去掉表遍历（16KB 表 RAM），只保留分段 compact** | **仍有画面但不稳定** |

**结论**：**`gfx_core` 的改动（分段 compact 状态机）改变了布局，导致 DVI 串行器输出质量下降**，与表 RAM 无关。30 个 seed 均未命中可用布局。

### 12.3 交付决定

- **部署黄金版**：700 × 16×16 @ 59.2 fps，欠载 0.0，DVI 稳定；
- **900 精灵产物保留**：源码提交、bitstream 归档（`work/backup/final-20261031/` 是 900 版，但 DVI 不稳）；
- **后续路径**（如需 900+）：
  1. 继续扫 seed（每批 20 个，~40 分钟，命中率未知）；
  2. **DVI 输出改用其它方案**（如降低分辨率/改时序）→ 赛题不允许；
  3. **优化 CPU 侧**（隔帧渲染，30Hz 更新）→ 数量翻倍但视觉降级，不需要新 bitstream。
